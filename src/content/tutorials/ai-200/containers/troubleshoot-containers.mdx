## Start with a question

<Story question="The app says it's deployed. So why does every request time out?">

Maybe the container keeps crashing. Maybe it never started because the image name has a typo. Maybe it's running fine but listening on the wrong port, so nothing reaches it. Each of those looks the same from the outside: no answer.

The trick is to look in the right place. **Logs** tell you what the app said, **events** tell you what the platform did, and **connectivity** checks tell you whether traffic can get there.

</Story>

## Explain it like I'm 10

<Eli10>

Your friend didn't turn up to football. Three questions find out why. Did they say anything (their **logs**)? Did their parents report anything, like "the car broke down" (the **events**)? Or did they turn up at the wrong field (**connectivity**)?

You ask in that order, and you usually find the answer by the second question.

</Eli10>

## The technical explanation

### Read the status first

| What you see | It usually means | Look at |
| --- | --- | --- |
| `ImagePullBackOff` / `ErrImagePull` | Wrong image name or tag, or no pull permission | `kubectl describe pod`, `az aks check-acr` |
| `CrashLoopBackOff` | The app starts and exits (missing env var, bad config, exception) | `kubectl logs <pod> --previous` |
| `Pending` | No node has room for the pod's requests, or a volume can't attach | Events: `FailedScheduling` |
| `OOMKilled` | The container went over its memory limit | `kubectl describe pod` (Last State), raise the limit |
| Running but `0/1 READY` | The readiness probe fails | Events: `Unhealthy`, check probe path and port |

### AKS: logs and events

```bash
kubectl get pods                                  # status column first
kubectl describe pod ragapi-7d9f8c6b5-x2k4q       # Events at the bottom
kubectl get events --sort-by=.metadata.creationTimestamp
kubectl logs ragapi-7d9f8c6b5-x2k4q               # current container
kubectl logs ragapi-7d9f8c6b5-x2k4q --previous    # the one that crashed
kubectl logs deployment/ragapi -f                 # follow one pod of the Deployment
az aks check-acr -g rg-ai -n aks-rag --acr myreg.azurecr.io   # can nodes pull?
```

### AKS: connectivity

```bash
kubectl get endpoints ragapi                      # empty = selector matches no ready pods
kubectl port-forward deployment/ragapi 8000:8000  # bypass the Service, test the pod
kubectl run tmp --rm -it --image=busybox -- wget -qO- http://ragapi/healthz   # DNS + Service from inside
kubectl exec -it deployment/ragapi -- sh          # check env vars and outbound access
```

With **Container insights** turned on, logs and events also go to Log Analytics (`ContainerLogV2`, `KubeEvents`, `KubePodInventory`), so you can query history after the pod is gone.

### Container Apps: system and console logs

```bash
az containerapp logs show -g rg-ai -n ragapi --type system --follow   # platform: pulls, probes, revision state
az containerapp logs show -g rg-ai -n ragapi --type console --follow  # your app's stdout and stderr
az containerapp revision list -g rg-ai -n ragapi -o table              # health and running state per revision
az containerapp exec -g rg-ai -n ragapi --command sh                   # shell inside a replica
```

The same logs are in the environment's Log Analytics workspace:

```kusto
ContainerAppConsoleLogs_CL
| where ContainerAppName_s == "ragapi"
| where Log_s contains "Error"
| project TimeGenerated, RevisionName_s, Log_s
| order by TimeGenerated desc

ContainerAppSystemLogs_CL
| where ContainerAppName_s == "ragapi" and Reason_s != ""
| project TimeGenerated, RevisionName_s, Reason_s, Log_s
```

Common Container Apps causes: **target port** doesn't match what the container listens on, ingress is **internal** when callers are outside, the registry identity has no **AcrPull**, a **secret** was changed but the revision wasn't restarted, or a **health probe** points at the wrong path. The portal's **Diagnose and solve problems** page checks many of these for you.

<Callout type="exam">
Match the symptom to the tool. **Container never started** (image pull, scheduling) = **events**: `kubectl describe pod`, `kubectl get events`, or Container Apps **system** logs. **Container started then crashed** = **logs**, with `kubectl logs --previous`. **Running but unreachable** = **connectivity**: Service endpoints, `targetPort`, ingress settings. For Container Apps history in Log Analytics, use **ContainerAppConsoleLogs_CL** (app output) and **ContainerAppSystemLogs_CL** (platform).
</Callout>

<DeepDive title="Make the app easy to troubleshoot">

Log to stdout and stderr, not to files inside the container, so both platforms collect it. Add a `/healthz` endpoint that checks only what the app needs to serve (not every downstream dependency, or one slow database fails every probe and the platform restarts healthy pods). Fail fast with a clear message when a required environment variable is missing, so `--previous` shows "SEARCH_KEY is not set" instead of a stack trace three calls deep. And send traces to Application Insights with OpenTelemetry so a timeout can be followed across services.

</DeepDive>
