## Start with a question

<Story question="Who rebuilds your app when Python gets a security patch?">

Your image is built on `python:3.12-slim`. Next Tuesday a security fix lands in that base image. Your code didn't change, so nobody rebuilds, and production keeps running the old, vulnerable layers for months.

**ACR Tasks** can watch for that. They build images inside Azure Container Registry when you push code, when the base image changes or on a timer, so patched images appear without anyone remembering to do it.

</Story>

## Explain it like I'm 10

<Eli10>

Instead of baking a cake at home and carrying it to the shop, you send the recipe to the shop's kitchen. They bake it there and put it straight on the shelf. That's `az acr build`.

Better still, you can tell the kitchen: "Whenever I change the recipe, or whenever the flour supplier sends better flour, bake a fresh one." That's a task with **triggers**.

## The technical explanation

### Quick task: build in the cloud

Run it from the folder that holds your `Dockerfile`. The final `.` is the **build context** the CLI uploads.

```bash
az acr build --registry myreg --image ragapi:1.4.0 .

# Unique tag per run, and a Dockerfile that isn't at the root
az acr build --registry myreg --image 'ragapi:{{.Run.ID}}' --file docker/Dockerfile .
```

The logs stream to your terminal and the image lands in the registry. There's also `az acr run --registry myreg --cmd 'myreg.azurecr.io/ragapi:1.4.0' /dev/null` to run a container in the task environment, which is handy for a smoke test.

### Automated task: build on a trigger

```bash
az acr task create \
  --registry myreg \
  --name build-ragapi \
  --image 'ragapi:{{.Run.ID}}' \
  --context https://github.com/contoso/ragapi.git#main \
  --file Dockerfile \
  --git-access-token $GITHUB_PAT
```

That one task now has three ways to start:

| Trigger | What starts it | Flag |
| --- | --- | --- |
| Source code commit | A push to the branch in `--context` | `--commit-trigger-enabled` (on by default) |
| Base image update | The `FROM` image is updated in its registry (ACR, Docker Hub, MCR) | `--base-image-trigger-enabled` (on by default) |
| Schedule | A cron expression, in UTC | `--schedule "0 2 * * *"` or `az acr task timer add` |

Pull request builds can be turned on with `--pull-request-trigger-enabled true`. Run a task by hand with `az acr task run --registry myreg --name build-ragapi`, and see history with `az acr task list-runs` and `az acr task logs`.

### Multi-step task: build, test, push

```yaml
# acr-task.yaml
version: v1.1.0
steps:
  - build: -t $Registry/ragapi:{{.Run.ID}} .
  - cmd: $Registry/ragapi:{{.Run.ID}} python -m pytest -q
  - push:
      - $Registry/ragapi:{{.Run.ID}}
```

Run it once with `az acr run --registry myreg -f acr-task.yaml .`, or save it as a task: `az acr task create --registry myreg --name ci-ragapi --context https://github.com/contoso/ragapi.git#main --file acr-task.yaml --git-access-token $GITHUB_PAT`. If the `cmd` step fails, the push never happens.

<Callout type="exam">
Map the words: **"without Docker"** or **"in Cloud Shell"** = `az acr build`. **"Rebuild when the base image is patched"** = base image update trigger. **"Every push to main"** = commit trigger with `--context` pointing at the repo branch. **"Nightly build"** = `--schedule` with a UTC cron. **"Build, test, then push"** or **"several images in one run"** = a multi-step YAML task. `--context` is *where the source is*; `--file` is *which Dockerfile or YAML to use*.
</Callout>

<DeepDive title="Keeping base image triggers under your control">

Pointing `FROM` straight at Docker Hub means any upstream change rebuilds your app, and rate limits can fail builds. A common pattern is two tasks: one imports or builds your own base (`myreg.azurecr.io/base/python:3.12-slim`) and runs its tests, and the app task's `FROM` points at that internal base. The app's base image trigger then fires only after your base passed its checks. Task runs authenticate to the registry automatically; to reach another registry or Key Vault from a task, give the task a managed identity with `--assign-identity`.

</DeepDive>
