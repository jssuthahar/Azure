## Start with a question

<Story question="Why pay for ten servers at 3 a.m. when nobody's uploading documents?">

Your summarisation worker reads jobs from a Service Bus queue. In the morning, 500 PDFs arrive in ten minutes. At night, nothing. If you size for the morning, you pay for idle servers all night. If you size for the night, the morning queue backs up for an hour.

**KEDA** scale rules in Azure Container Apps watch the queue itself. More messages, more replicas. Empty queue, back to zero.

</Story>

## Explain it like I'm 10

<Eli10>

A bakery opens one counter. When the line gets long, the manager opens another counter for every five people waiting. When everyone's served and the shop's been quiet for a few minutes, the counters close, even the last one.

The manager counting people in the line is **KEDA**. Five people per counter is **messageCount**. The most counters the shop has is **max replicas**.

## The technical explanation

### Scale rule types

| Type | Scales on | Scale to zero? |
| --- | --- | --- |
| HTTP | Concurrent HTTP requests per replica | Yes |
| TCP | Concurrent TCP connections | Yes |
| Custom (KEDA scaler) | An event source: `azure-servicebus`, `azure-queue`, `kafka`, `redis`, `cron` and more | Yes |
| CPU / memory | Resource use of running replicas | No |

If an app has ingress and no rule, Container Apps adds a default HTTP rule. The replica count always stays between **min** and **max** (defaults 0 and 10).

### A Service Bus rule with the CLI

```bash
az containerapp create --resource-group rg-ai --name summariser \
  --environment env-rag \
  --image myreg.azurecr.io/summariser:2.1.0 \
  --secrets sb-conn="<service-bus-connection-string>" \
  --min-replicas 0 --max-replicas 20 \
  --scale-rule-name summarise-queue \
  --scale-rule-type azure-servicebus \
  --scale-rule-metadata queueName=summarise namespace=sb-rag messageCount=5 \
  --scale-rule-auth connection=sb-conn
```

`--scale-rule-auth connection=sb-conn` maps the scaler's `connection` parameter to the app secret `sb-conn`. To avoid a connection string, give the app a managed identity with the **Azure Service Bus Data Owner** role and pass `--scale-rule-identity system` instead of the auth line. For a topic, use `topicName` and `subscriptionName` instead of `queueName`.

Change rules on an existing app with `az containerapp update ... --scale-rule-name ... --min-replicas ... --max-replicas ...`. Scale rules are part of the template, so this creates a new **revision**.

### How the numbers work

KEDA checks the queue every **30 seconds**. It aims for roughly `queue length ÷ messageCount` replicas, never above max:

| Messages waiting | messageCount | max | Replicas |
| --- | --- | --- | --- |
| 0 (for 5 minutes) | 5 | 20 | 0 |
| 12 | 5 | 20 | 3 |
| 500 | 5 | 20 | 20 |

After the queue is empty, the **cooldown period** (300 seconds) passes before the last replica goes away. Your code should complete messages only after the work is done, so a replica being removed mid-job doesn't lose anything.

<Callout type="exam">
"Scale on queue length" or "scale on events" in Container Apps is a **custom KEDA rule** (`azure-servicebus`, `azure-queue`). "Scale to zero" needs **min replicas 0** and a rule that isn't CPU or memory. "Never more than N replicas" is **max replicas**. Credentials for the scaler come from a **secret** with `--scale-rule-auth` or from a **managed identity**. Know that the rule's metadata names the queue and the per-replica target (`messageCount`).
</Callout>

<DeepDive title="Container Apps jobs for run-to-completion work">

A worker app keeps replicas running and pulls messages in a loop. If each message is a self-contained job (summarise one PDF and exit), a **Container Apps job** with `--trigger-type Event` can fit better: the same KEDA scaler starts one job execution per batch of messages, each runs to completion, and you get execution history per job. Use `--replica-completion-count`, `--parallelism` and `--polling-interval` to tune it.

</DeepDive>
