## Start with a question

<Story question="Production broke at 2 a.m. Which version of the app was it actually running?">

The deployment said `ragapi:latest`. But `latest` was pushed three times yesterday, by two different people. Nobody can say for sure which build the servers pulled, so nobody knows what to roll back to.

That's the problem a registry with good **tags** and **digests** solves. **Azure Container Registry** keeps every image version, and if you tag them properly you always know exactly what's running.

</Story>

## Explain it like I'm 10

<Eli10>

Imagine a library for lunchboxes. Each shelf holds one kind of lunch (a **repository**). Every box gets a sticky label like "Tuesday" (a **tag**). Someone can peel that label off and stick it on a different box.

But every box also has a serial number stamped into the plastic (a **digest**). Nobody can change that. If you want to be sure you get the same box, ask for the serial number.

## The technical explanation

A registry has a **login server** (`myreg.azurecr.io`). Inside it are **repositories** (`ragapi`), and each image in a repository has one or more **tags** and exactly one **digest**.

```bash
# Create a registry (name: 5-50 letters and numbers, globally unique)
az acr create --resource-group rg-ai --name myreg --sku Standard

# Sign Docker in with your Microsoft Entra ID account
az acr login --name myreg

# Tag a local image with the full registry name and push it
docker tag ragapi:dev myreg.azurecr.io/ragapi:1.4.0
docker push myreg.azurecr.io/ragapi:1.4.0
```

### Seeing what's there

```bash
az acr repository list --name myreg --output table
az acr repository show-tags --name myreg --repository ragapi --orderby time_desc --output table
az acr manifest list-metadata --registry myreg --name ragapi   # digests, tags, dates
```

To run an exact image regardless of tags, reference the digest: `myreg.azurecr.io/ragapi@sha256:…`.

### Bringing images in

`az acr import` copies an image server side, so you don't need Docker on your machine and you stop depending on Docker Hub rate limits:

```bash
az acr import --name myreg \
  --source docker.io/library/python:3.12-slim \
  --image base/python:3.12-slim
```

It works from another ACR too (`--source otherreg.azurecr.io/ragapi:1.4.0`), including across subscriptions when you have access.

### Tagging so you can trust it

| Tag style | Example | Use it for |
| --- | --- | --- |
| Stable tag | `ragapi:1`, `ragapi:latest` | Base images that should pick up patches |
| Unique tag | `ragapi:1.4.0`, `ragapi:build-482`, `ragapi:3f9c2e1` | Anything you deploy |

Lock a release so nobody overwrites or deletes it:

```bash
az acr repository update --name myreg --image ragapi:1.4.0 \
  --write-enabled false --delete-enabled false
```

Old builds pile up, so clean them: `az acr repository delete --name myreg --image ragapi:1.2.0`, or run `acr purge` on a schedule to remove tags older than a set age and untagged manifests.

### Who can pull and push

| Method | When |
| --- | --- |
| Your Entra ID account (`az acr login`) | Developers at the command line |
| Managed identity + **AcrPull** | App Service, Container Apps, AKS pulling at run time |
| Service principal or workload identity + **AcrPush** | CI/CD pipelines |
| Admin account | Off by default; single-user testing only |

**SKUs:** Basic, Standard and Premium share the same features for storing and pulling. Premium adds the most storage and throughput, **geo-replication** to other regions and **private endpoints**.

<Callout type="exam">
Watch for these: copying an image from Docker Hub or another registry without Docker is **az acr import**. Listing versions is **az acr repository show-tags**. Preventing an overwrite is **--write-enabled false**. Pulling without passwords is a **managed identity** with **AcrPull**. Multi-region replication needs **Premium**. If a question says "the same tag now runs different code", the fix is **unique tags** or deploying by **digest**.
</Callout>

<DeepDive title="Why digests matter for rollbacks">

When you push, ACR stores the layers and a manifest that lists them. The digest is the hash of that manifest. Kubernetes and Container Apps can resolve a tag to a digest when they start a replica, but if the tag moves between two replica starts, you end up with mixed versions. Deploying by a unique tag, or pinning the digest in the manifest, makes every replica run the same bytes and makes "roll back to the last good build" a one-line change.

</DeepDive>
