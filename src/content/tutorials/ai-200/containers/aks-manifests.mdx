## Start with a question

<Story question="How do you tell 30 servers to run three copies of your API, and keep it that way?">

You could log in to each machine, start containers and restart them when they die. That's fine for one server and miserable for thirty.

On **AKS**, you write down what you want in a **manifest**: "three copies of `ragapi:1.4.0`, 0.5 CPU each, reachable on port 80". You hand it to Kubernetes with `kubectl apply`, and Kubernetes keeps making it true.

</Story>

## Explain it like I'm 10

<Eli10>

You give the teacher a note: "Our team always has three players on the field." If a player gets tired and leaves, the teacher sends a new one on without being asked. That note is a **Deployment**.

The team also has one phone number that always rings whoever is on the field. That number is a **Service**.

</Eli10>

## The technical explanation

### Cluster and access

```bash
az aks create --resource-group rg-ai --name aks-rag \
  --node-count 2 --attach-acr myreg --generate-ssh-keys

az aks get-credentials --resource-group rg-ai --name aks-rag
kubectl get nodes
```

`--attach-acr` assigns **AcrPull** to the cluster's kubelet identity, so pods pull from `myreg.azurecr.io` without secrets. For an existing cluster: `az aks update -n aks-rag -g rg-ai --attach-acr myreg`.

### The manifest

```yaml
# ragapi.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: ragapi
spec:
  replicas: 3
  selector:
    matchLabels:
      app: ragapi
  template:
    metadata:
      labels:
        app: ragapi            # must match the selector above
    spec:
      containers:
        - name: ragapi
          image: myreg.azurecr.io/ragapi:1.4.0
          ports:
            - containerPort: 8000
          env:
            - name: MODEL_DEPLOYMENT
              value: gpt-4.1-mini
            - name: SEARCH_KEY
              valueFrom:
                secretKeyRef:
                  name: rag-secrets
                  key: search-key
          resources:
            requests: { cpu: 250m, memory: 512Mi }
            limits: { cpu: 500m, memory: 1Gi }
          readinessProbe:
            httpGet: { path: /healthz, port: 8000 }
          livenessProbe:
            httpGet: { path: /healthz, port: 8000 }
            initialDelaySeconds: 15
---
apiVersion: v1
kind: Service
metadata:
  name: ragapi
spec:
  type: LoadBalancer
  selector:
    app: ragapi
  ports:
    - port: 80
      targetPort: 8000
```

The Service's **selector** finds pods labelled `app: ragapi`. `port` is what callers use, `targetPort` is the container's port. **ClusterIP** (the default) is reachable only inside the cluster; **LoadBalancer** asks Azure for a public IP on the cluster's load balancer.

### Apply and check

```bash
kubectl create secret generic rag-secrets --from-literal=search-key="$SEARCH_KEY"
kubectl apply -f ragapi.yaml
kubectl get deployments,pods,services
kubectl get service ragapi --watch     # wait for EXTERNAL-IP
```

### Roll out a new version

```bash
kubectl set image deployment/ragapi ragapi=myreg.azurecr.io/ragapi:1.5.0
kubectl rollout status deployment/ragapi
kubectl rollout undo deployment/ragapi     # if 1.5.0 misbehaves
kubectl scale deployment/ragapi --replicas=5
```

In a real pipeline you'd change the tag in the YAML and `kubectl apply` again, so the file in git always matches the cluster.

<Callout type="exam">
Expect to read YAML. Check that **selector.matchLabels** matches **template.metadata.labels**, that the Service **selector** matches those labels, and that **targetPort** matches **containerPort**. **LoadBalancer** = public IP, **ClusterIP** = internal only. **kubectl apply -f** creates or updates; **rollout undo** rolls back. Pulling from ACR without secrets is **--attach-acr**. Secrets go in a **Secret** (secretKeyRef) or the **Key Vault CSI driver**, never as plain values.
</Callout>

<DeepDive title="Keeping secrets in Key Vault on AKS">

A Kubernetes Secret is only base64-encoded and sits in the cluster's store. The **Azure Key Vault provider for Secrets Store CSI Driver** (`az aks enable-addons --addons azure-keyvault-secrets-provider`) mounts Key Vault secrets as files, and can sync them to a Kubernetes Secret if you need env vars. With **Microsoft Entra Workload ID**, the pod's service account is federated with a managed identity that has access to the vault, so there's no credential in the cluster at all. The same identity can call Azure OpenAI or Cosmos DB with `DefaultAzureCredential`.

</DeepDive>
