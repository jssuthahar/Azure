  keyPoints:
    - A container image bundles code, runtime and dependencies; a registry such as ACR stores and versions it.
    - App Service runs one container as a web app; app settings become environment variables.

## Start with a question

<Story question="Your RAG API works on your laptop. Why does it break on the server?">

The server has Python 3.10, you used 3.12. It's missing a system library that one of your packages needs. Someone installed a different version of the OpenAI SDK last month. Every machine is a little different, and AI apps pull in a lot of packages.

A **container image** fixes that. You pack the code, the Python runtime and every package into one image, push it to a registry, and every host runs exactly the same thing. The question then becomes where to run it on Azure.

</Story>

## The technical explanation

You build an image from a `Dockerfile`. For a small FastAPI back end it looks like this:

```dockerfile
FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
EXPOSE 8000
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]
```

The image goes into **Azure Container Registry (ACR)** with a version tag such as `ragapi:1.4.0`. From there, any of the three hosts can pull it. Secrets like your model key don't go in the image. They're supplied at run time as environment variables or, better, fetched with a **managed identity**.

### Picking a host

| | App Service | Azure Container Apps | AKS |
| --- | --- | --- | --- |
| What you manage | The app and its settings | The app, revisions and scale rules | Node pools, upgrades, manifests, add-ons |
| Best for | One web API or site | Microservices, APIs, queue workers | Large platforms, GPU nodes, custom Kubernetes |
| Scale | Autoscale rules on the plan, no scale to zero | KEDA rules (HTTP, queues, custom), can scale to zero | Horizontal Pod Autoscaler, cluster autoscaler, KEDA add-on |
| Releases | Deployment slots and swap | Revisions with traffic splitting | Rolling updates in the Deployment |
| Config | App settings, Key Vault references | Env vars, secrets, Key Vault references | ConfigMaps, Secrets, Secrets Store CSI driver |
| Kubernetes API | No | No | Yes |

A quick way to decide: start from App Service if it's one web app, move to Container Apps when you need several services, event-driven workers or scale to zero, and go to AKS only when you need something Kubernetes itself gives you.

<Callout type="exam">
Read the requirement words. **"Scale to zero"**, **"scale on Service Bus messages"**, **"split traffic between versions"** point to **Container Apps**. **"Kubernetes API"**, **"manifest files"**, **"custom controllers"** point to **AKS**. **"Single web app"**, **"deployment slots"**, **"least management"** point to **App Service**. Every option pulls from **ACR**, and the pull is best done with a **managed identity** with **AcrPull**.
</Callout>

<DeepDive title="Why images and secrets stay apart">

An image is shared: it's in the registry, it's cached on nodes, and anyone with pull rights can unpack it. A key baked into a layer stays there even if a later layer deletes the file. So images carry code, and each host injects configuration when the container starts: App Service app settings, Container Apps secrets referenced with `secretref:`, or Kubernetes Secrets. Pointing those at **Azure Key Vault** means rotating a secret doesn't mean rebuilding an image.

</DeepDive>
