## Start with a question

<Story question="You've got a new model prompt. How do you test it on 10% of users first?">

If you swap the image for everyone and the new prompt gives worse answers, every user sees it before you notice. You'd rather send a small slice of traffic to the new version, watch it, then move everyone across, or back.

**Azure Container Apps** does this with **revisions**. Every deploy creates a new snapshot of the app, and you choose how much traffic each one gets.

</Story>

## Explain it like I'm 10

<Eli10>

Think of a school play with two casts. Cast A has done the show for weeks. Cast B is new. On Friday, most of the audience watches cast A and a few watch cast B.

If people love cast B, everyone watches them next week. If not, cast A carries on. Each cast is a **revision**, and the usher deciding who goes where is **traffic splitting**.

</Eli10>

## The technical explanation

### Environment first, then the app

```bash
az containerapp env create --resource-group rg-ai --name env-rag --location eastus

az containerapp create --resource-group rg-ai --name ragapi \
  --environment env-rag \
  --image myreg.azurecr.io/ragapi:1.4.0 \
  --registry-server myreg.azurecr.io --registry-identity system \
  --ingress external --target-port 8000 \
  --secrets search-key=keyvaultref:https://kv-rag.vault.azure.net/secrets/search-key,identityref:system \
  --env-vars MODEL_DEPLOYMENT=gpt-4.1-mini SEARCH_KEY=secretref:search-key \
  --min-replicas 1 --max-replicas 5
```

A few things to notice. `--registry-identity system` pulls from ACR with the app's managed identity. Secrets are stored on the app (or referenced from Key Vault with `keyvaultref:`), and env vars point at them with `secretref:`. `--target-port` is the port your container listens on.

`az containerapp up --name ragapi --source .` is the shortcut: it builds the image (with ACR), creates the resource group, environment and registry if needed, and deploys, all in one command.

The **environment** is the shared boundary: apps in it share a virtual network and send logs to the same **Log Analytics** workspace. **Ingress** is either **external** (internet) or **internal** (only apps in the same environment, which call each other by app name).

### Revisions

| Change | Scope | New revision? |
| --- | --- | --- |
| Image, env vars, CPU/memory, probes, scale rules | Revision (`properties.template`) | Yes |
| Ingress, traffic weights, secrets, registries, revision mode, Dapr | Application (`properties.configuration`) | No |

```bash
# Deploy 1.5.0 as a new revision with a readable name: ragapi--v15
az containerapp update -g rg-ai -n ragapi \
  --image myreg.azurecr.io/ragapi:1.5.0 --revision-suffix v15

az containerapp revision list -g rg-ai -n ragapi -o table
```

In **single revision mode** (the default), the new revision takes all traffic once it's healthy and the old one is deactivated. To keep both running and split traffic, switch to **multiple**:

```bash
az containerapp revision set-mode -g rg-ai -n ragapi --mode multiple

az containerapp ingress traffic set -g rg-ai -n ragapi \
  --revision-weight ragapi--v14=80 ragapi--v15=20
```

Roll forward by moving weights to 100 on `ragapi--v15`; roll back by moving them to the old revision. You can also add a **label** (`az containerapp revision label add --label blue --revision ragapi--v15`) to get a stable URL for testing a revision directly.

<Callout type="exam">
Know which changes are **revision-scope** (template: image, env vars, scale rules) and which are **application-scope** (ingress, secrets, revision mode). Traffic splitting needs **multiple revision mode**. **Internal ingress** keeps an app private to the environment. Env vars read secrets with **secretref:**, and Key Vault secrets use **keyvaultref:** plus a managed identity. If a question says "deploy and build from source in one command", that's **az containerapp up**.
</Callout>

<DeepDive title="Workload profiles and what you pay for">

New environments use the **workload profiles** model. The **Consumption** profile bills per vCPU-second and GiB-second while replicas run, with a monthly free grant, and scales to zero. **Dedicated** profiles give you reserved node types (including GPU options) for steady or heavy workloads, billed per node. Apps in the same environment can mix profiles. An environment can be created in your own virtual network so apps reach private endpoints for Cosmos DB, Key Vault or Azure OpenAI.

</DeepDive>
