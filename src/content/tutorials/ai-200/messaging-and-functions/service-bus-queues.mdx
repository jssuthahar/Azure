Your AI app has the same problem. Summarising a 40-page PDF takes a minute. If the web API does it inline, requests pile up and time out. An **Azure Service Bus queue** is the token system: the API drops a job on the queue, replies straight away, and a worker at the back does the slow part.

## The technical explanation

Service Bus is a message broker. You create a **namespace** (`contoso-ai.servicebus.windows.net`) and inside it one or more **queues**. A queue keeps messages in the order they arrived and hands each message to **one** receiver. If you run five workers on the same queue, they compete and share the load.

### Pick a tier

| Tier | What you get | Use it for |
| --- | --- | --- |
| **Basic** | Queues only. No topics, sessions, transactions or duplicate detection. | Simple dev/test or one-way job queues |
| **Standard** | Queues and topics, sessions, duplicate detection, transactions. Shared capacity, messages up to 256 KB. | Most apps |
| **Premium** | Dedicated messaging units, predictable latency, larger messages, network isolation. | Production with steady high volume |

### Send a message

Install `azure-servicebus` and `azure-identity`. Give the sender the **Azure Service Bus Data Sender** role, then sign in with Microsoft Entra ID instead of a connection string:

```python
import json
from azure.identity import DefaultAzureCredential
from azure.servicebus import ServiceBusClient, ServiceBusMessage

NAMESPACE = "contoso-ai.servicebus.windows.net"
credential = DefaultAzureCredential()

with ServiceBusClient(fully_qualified_namespace=NAMESPACE, credential=credential) as client:
    with client.get_queue_sender(queue_name="summarise-jobs") as sender:
        msg = ServiceBusMessage(
            json.dumps({"docId": "invoice-42", "blob": "uploads/invoice-42.pdf"}),
            content_type="application/json",
            subject="summarise",
            message_id="invoice-42",              # used by duplicate detection
            application_properties={"tier": "premium"},
        )
        sender.send_messages(msg)
```

You can pass a list of messages, or build a batch with `sender.create_message_batch()` so you don't go over the size limit.

### Receive and settle

The worker gets the **Azure Service Bus Data Receiver** role. In the default **peek-lock** mode, each message you receive is locked for you and stays in the queue until you **settle** it:

```python
with ServiceBusClient(fully_qualified_namespace=NAMESPACE, credential=credential) as client:
    with client.get_queue_receiver(queue_name="summarise-jobs", max_wait_time=5) as receiver:
        for msg in receiver.receive_messages(max_message_count=10, max_wait_time=5):
            job = json.loads(str(msg))
            try:
                summarise(job["blob"])
                receiver.complete_message(msg)        # done, remove it
            except TemporaryError:
                receiver.abandon_message(msg)         # unlock, try again later
            except BadInputError as e:
                receiver.dead_letter_message(msg, reason="BadInput", error_description=str(e))
```

| Settlement | What happens |
| --- | --- |
| `complete_message` | The message is removed from the queue. |
| `abandon_message` | The lock is released and the message is available again. Delivery count goes up by one. |
| `dead_letter_message` | The message moves to the queue's dead-letter sub-queue with your reason. |
| `defer_message` | The message stays in the queue but is set aside. You fetch it later with `receive_deferred_messages(sequence_numbers=[...])`. |

If you don't settle in time, the **lock duration** runs out (1 minute by default, 5 minutes at most) and the message becomes visible to other receivers. Long jobs should renew the lock, for example with `AutoLockRenewer`, rather than relying on a huge lock. Every time a message is delivered its delivery count goes up. When it passes the **max delivery count** (10 by default), Service Bus moves it to the **dead-letter queue**.

**Receive-and-delete** (`receive_mode=ServiceBusReceiveMode.RECEIVE_AND_DELETE`) skips the lock and removes the message on delivery. It's faster but a crash loses the message. Use it only for data you can afford to drop, such as live telemetry samples.

### Queue settings worth knowing

- **Message time to live (TTL)**: a message that isn't processed in time expires. Set it per message (`time_to_live`) or as a queue default. Turn on **dead-lettering on message expiration** if you want expired messages kept instead of dropped.
- **Sessions**: turn on **requires session** when you create the queue, then set `session_id` on each message. One receiver locks a whole session at a time, so all messages for `customer-17` are handled in order. Receive with `client.get_queue_receiver(queue_name=..., session_id="customer-17")`.
- **Duplicate detection**: turn it on when you create the queue and choose a window (10 minutes by default). A second message with the same `message_id` inside the window is quietly dropped, which protects you when a sender retries after a timeout.
- **Scheduled messages**: set `scheduled_enqueue_time_utc` or call `sender.schedule_messages()` to deliver later.
- **Peek**: `receiver.peek_messages()` reads messages without locking them. Handy for debugging.

<Callout type="exam">
Watch the verbs. "Must not lose the message if processing fails" points to **peek-lock** with **complete** at the end. "Make it available to another receiver now" is **abandon**. "Set it aside and get it later by sequence number" is **defer**. "Process each customer's messages in order" is **sessions**. "Ignore a resend with the same ID" is **duplicate detection**. If a question uses the **Basic** tier and needs a topic or sessions, the fix is to move to Standard or Premium.
</Callout>

<DeepDive title="At-least-once means your handler must be idempotent">

Peek-lock gives you at-least-once delivery. A worker can finish the summary, then crash before `complete_message` reaches Service Bus. The lock expires and another worker processes the same job again. So design for repeats: write the summary with an upsert keyed on `docId`, or check a "processed" marker before doing paid model calls. Duplicate detection only stops duplicate *sends*; it doesn't stop a message being *delivered* twice.

For high throughput, use the async client in `azure.servicebus.aio`, receive in batches, and set `prefetch_count` so the next messages are already on their way while you work. Keep prefetch modest with long jobs, because prefetched messages are locked too and their locks keep ticking.

</DeepDive>
