Think of the motion-sensor light in a corridor. It doesn't burn all night. Someone walks in, it switches on, does its job, and switches off. You pay for the minutes it was on.

## The technical explanation

A **function app** is the unit you deploy and scale. Inside it you write one or more **functions**. Each function has:

- exactly **one trigger**, which starts it and usually passes in the data (the request, the message, the event);
- zero or more **input bindings**, which read extra data (a blob, a Cosmos DB item);
- zero or more **output bindings**, which write results (a queue message, a blob, a Cosmos DB document).

### The Python v2 programming model

In the v2 model there's no `function.json`. You create one `FunctionApp` object in `function_app.py` and decorate plain Python functions:

```python
import json, logging
import azure.functions as func

app = func.FunctionApp(http_auth_level=func.AuthLevel.FUNCTION)

# 1. HTTP API that queues work through an output binding
@app.route(route="summarise", methods=["POST"])
@app.service_bus_queue_output(arg_name="job", queue_name="summarise-jobs",
                              connection="ServiceBusConnection")
def summarise(req: func.HttpRequest, job: func.Out[str]) -> func.HttpResponse:
    body = req.get_json()
    job.set(json.dumps({"docId": body["docId"], "blob": body["blob"]}))
    return func.HttpResponse(json.dumps({"status": "accepted"}), status_code=202,
                             mimetype="application/json")

# 2. Worker triggered by each queue message
@app.service_bus_queue_trigger(arg_name="msg", queue_name="summarise-jobs",
                               connection="ServiceBusConnection")
def worker(msg: func.ServiceBusMessage):
    job = json.loads(msg.get_body().decode("utf-8"))
    logging.info("Summarising %s (delivery %s)", job["docId"], msg.delivery_count)
    summarise_document(job["blob"])      # raise to retry, return to complete
```

`connection="ServiceBusConnection"` is the **name of an app setting**, not the secret itself. In Azure that setting can be a connection string, or you can use identity-based connections (covered in the deploy lesson).

### Common triggers and bindings

| Decorator | Fires when / does | Notes |
| --- | --- | --- |
| `@app.route` | An HTTP request arrives at `/api/<route>` | Returns `func.HttpResponse`. Auth levels below. |
| `@app.service_bus_queue_trigger` / `@app.service_bus_topic_trigger` | A message arrives on a queue or subscription | Peek-lock: completed on success, abandoned on exception. |
| `@app.event_grid_trigger` | Event Grid pushes an event | Receives `func.EventGridEvent`. The validation handshake is handled for you. |
| `@app.timer_trigger` | A schedule is due | Six-field NCRONTAB, seconds first: `0 */15 * * * *`. |
| `@app.cosmos_db_trigger` | Items are inserted or updated in a container | Reads the change feed and needs a lease container. |
| `@app.blob_trigger` | A blob is added or updated | For high volume, Event Grid-based blob triggers are faster. |
| `@app.service_bus_queue_output` / `@app.queue_output` | Writes a message to Service Bus / Storage queue | Parameter type `func.Out[str]`, then `.set()`. |
| `@app.blob_input`, `@app.cosmos_db_input` | Reads a blob or item before the function runs | Value arrives as a parameter. |

Two more you'll see often:

```python
@app.event_grid_trigger(arg_name="event")
def on_blob(event: func.EventGridEvent):
    data = event.get_json()
    logging.info("%s on %s", event.event_type, event.subject)

@app.timer_trigger(schedule="0 0 2 * * *", arg_name="timer", run_on_startup=False)
def nightly_reindex(timer: func.TimerRequest):
    if timer.past_due:
        logging.warning("Running late")
    rebuild_index()
```

You can split a big app into files with `func.Blueprint()` and register it with `app.register_functions(bp)`.

### HTTP authorization levels

| Level | Caller needs |
| --- | --- |
| `ANONYMOUS` | Nothing. Anyone with the URL can call it. |
| `FUNCTION` | A function key or host key, in the `x-functions-key` header or `?code=` query string. This is the default. |
| `ADMIN` | The master key. Keep it for admin tools only. |

Keys aren't checked when you run locally with Core Tools. Keys prove "this caller has the key", not who the user is. For user identity, add built-in authentication with Microsoft Entra ID or put Azure API Management in front.

<Callout type="exam">
"Run code when X happens" maps straight to a **trigger** (HTTP, Service Bus, Event Grid, timer, Cosmos DB, blob). "Send the result somewhere without client code" is an **output binding**. Remember that a function has **one trigger only**. In Python v2 questions, look for `function_app.py`, `func.FunctionApp()` and decorators; `func.Out[...]` with `.set()` means an output binding. A `connection` value is an **app setting name**. For timers, count the fields: NCRONTAB has six, starting with seconds.
</Callout>

<DeepDive title="Retries, timeouts and long AI work">

A Service Bus-triggered function gets Service Bus's own retry: abandon on failure, dead-letter after max delivery count. Event Grid has its own retry policy too. For other triggers you can add a function-level **retry policy** (fixed delay or exponential backoff) in some cases, but don't stack retries on top of the broker's retries without thinking about the total.

HTTP functions behind the Azure load balancer must respond within about 230 seconds, whatever the function timeout. That's why the pattern above returns 202 straight away and lets a queue-triggered function do the slow model call. For multi-step workflows with waits and fan-out, **Durable Functions** (orchestrator and activity functions) keeps state for you.

</DeepDive>
