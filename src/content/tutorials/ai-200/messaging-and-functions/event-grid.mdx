## The technical explanation

Event Grid has three moving parts:

- **Sources** publish events to a **topic**. Azure services publish to **system topics** (Blob Storage, Key Vault, Resource groups and more). Your apps publish to **custom topics**.
- **Event subscriptions** connect a topic to a **handler** and hold the filters, retry policy and dead-letter settings.
- **Handlers** receive the push: Azure Functions, webhooks (any HTTPS endpoint), Service Bus queues and topics, Storage queues, Event Hubs and Relay hybrid connections.

Delivery is **push** and **at-least-once**, so a handler might see the same event twice. Use the event `id` to ignore repeats. Event Grid also has **namespace topics** that support pull delivery and MQTT, but the classic push model below is what most event-driven Azure apps use.

### Two schemas

| | CloudEvents 1.0 | Event Grid schema |
| --- | --- | --- |
| Who defines it | CNCF open standard | Microsoft |
| Key fields | `id`, `source`, `type`, `subject`, `time`, `data`, `specversion` | `id`, `topic`, `subject`, `eventType`, `eventTime`, `data`, `dataVersion` |
| Good for | New apps, portable across clouds and tools | Older integrations that already expect it |

You choose the **input schema** when you create a custom topic, and you publish in that schema. Microsoft recommends CloudEvents for new work.

### Publish a custom event in Python

Install `azure-eventgrid` and `azure-identity`. Give your app the **EventGrid Data Sender** role on the topic, or use the topic's access key with `AzureKeyCredential` if you must.

```python
import os
from azure.identity import DefaultAzureCredential
from azure.core.messaging import CloudEvent
from azure.eventgrid import EventGridPublisherClient

client = EventGridPublisherClient(
    os.environ["EVENTGRID_TOPIC_ENDPOINT"],   # https://<topic>.<region>-1.eventgrid.azure.net/api/events
    DefaultAzureCredential(),
)

client.send([
    CloudEvent(
        source="/contoso/summariser",
        type="Contoso.Docs.SummaryReady",
        subject="contracts/contract-88.pdf",
        data={"docId": "contract-88", "summaryUrl": "summaries/contract-88.json"},
    )
])
```

For a topic that uses the Event Grid schema, send `EventGridEvent(subject=..., event_type=..., data=..., data_version="1.0")` from `azure.eventgrid` instead.

### Filters on the event subscription

| Filter | Example | Use it to |
| --- | --- | --- |
| **Event types** | `Microsoft.Storage.BlobCreated` only | Ignore deletes and other events |
| **Subject begins with** | `/blobServices/default/containers/contracts/` | Limit to one container or folder |
| **Subject ends with** | `.pdf` | Limit to one file type |
| **Advanced filters** | `data.pages` NumberGreaterThan `20`, `data.tier` StringIn `premium` | Match on fields inside the event data |

Subject matching is case-insensitive unless you turn on case-sensitive subject matching. Advanced filters have operators for numbers, strings, booleans and null checks, and an event must pass every filter on the subscription.

```bash
az eventgrid event-subscription create \
  --name contracts-to-func \
  --source-resource-id $STORAGE_ID \
  --endpoint-type azurefunction --endpoint $FUNCTION_ID \
  --included-event-types Microsoft.Storage.BlobCreated \
  --subject-begins-with /blobServices/default/containers/contracts/ \
  --subject-ends-with .pdf \
  --max-delivery-attempts 10 --event-ttl 120 \
  --deadletter-endpoint $STORAGE_ID/blobServices/default/containers/eg-deadletter
```

### Retries and dead-lettering

If the handler doesn't return success, Event Grid waits and tries again with **exponential backoff**. The **retry policy** on each subscription has two limits, and whichever is hit first ends the retries:

- **Max delivery attempts**: 1 to 30, default **30**.
- **Event time to live**: 1 to 1,440 minutes, default **1,440** (24 hours).

Some failures aren't retried at all, such as 400 Bad Request and 413 Request Entity Too Large, because trying again won't help. When retries end, the event is **dropped** unless you set a **dead-letter destination**: a blob container in a storage account, where Event Grid writes the undelivered event as JSON with the reason.

### Webhook validation

Event Grid won't send events to a random URL until the endpoint proves it wants them. With the Event Grid schema, it first posts a `Microsoft.EventGrid.SubscriptionValidationEvent` containing a `validationCode`; your endpoint returns `{"validationResponse": "<code>"}`, or someone opens the `validationUrl` in the event within a few minutes. With CloudEvents, Event Grid sends an HTTP **OPTIONS** request with `WebHook-Request-Origin`, and your endpoint replies with `WebHook-Allowed-Origin`. Azure Functions with the Event Grid trigger, Logic Apps and Service Bus handlers don't need you to code any of this.

<Callout type="exam">
Look for these clues. "Only react to new .png files in one container" is **event type + subject begins/ends with**. "Filter on a value inside the payload" is an **advanced filter**. "Keep events the handler couldn't take" is **dead-lettering to a storage blob container**, not a Service Bus DLQ. Retry defaults are **30 attempts** and **1,440 minutes**. "Interoperable, open event format" is **CloudEvents 1.0**. And a webhook that never receives events probably failed the **validation handshake**.
</Callout>

<DeepDive title="Event Grid or Service Bus?">

Use Event Grid when the publisher just announces facts and doesn't care who listens: it's cheap, push-based and fans out to many handlers with filters. Use Service Bus when the payload is work that must be processed, when the receiver needs to control the pace (pull, peek-lock), or when you need ordering, sessions or transactions.

They combine well. A common pattern is Event Grid delivering `BlobCreated` events into a **Service Bus queue**: Event Grid handles the filtering and the push, and the queue gives your workers peek-lock, a dead-letter queue and a buffer for bursts.

</DeepDive>
