## Start with a question

<Story question="It ran fine on my laptop. Why does it break the moment I deploy it?">

Moving into a new flat, you bring your furniture, but the electricity, water and Wi-Fi password come with the building. If you assume your old Wi-Fi password still works, nothing connects.

A function app is the same. Your code moves, but the settings live in Azure. **local.settings.json** stays on your laptop, so in Azure you set **app settings**. You also pick the building: the **hosting plan** decides how the app scales, how fast it wakes up and whether it can reach a private network.

</Story>

## The technical explanation

### Three files, three jobs

| File | Where it lives | What goes in it |
| --- | --- | --- |
| `function_app.py` | Deployed | Your functions, triggers and bindings |
| `host.json` | Deployed | Runtime settings for **every** function in the app: `version`, `extensionBundle`, logging, `functionTimeout`, trigger tuning |
| `local.settings.json` | **Your machine only** | `Values` that become environment variables when you run `func start`. Never published, kept out of git. |

A small `host.json` for a Service Bus worker:

```json
{
  "version": "2.0",
  "extensionBundle": { "id": "Microsoft.Azure.Functions.ExtensionBundle", "version": "[4.*, 5.0.0)" },
  "logging": { "applicationInsights": { "samplingSettings": { "isEnabled": true } } },
  "extensions": {
    "serviceBus": { "maxConcurrentCalls": 8, "autoCompleteMessages": true }
  }
}
```

And the matching `local.settings.json`, using identity locally too:

```json
{
  "IsEncrypted": false,
  "Values": {
    "FUNCTIONS_WORKER_RUNTIME": "python",
    "AzureWebJobsStorage": "UseDevelopmentStorage=true",
    "ServiceBusConnection__fullyQualifiedNamespace": "contoso-ai.servicebus.windows.net"
  }
}
```

### App settings and identity-based connections

In Azure, every value from `Values` becomes an **app setting**, read by your code with `os.environ["NAME"]`. Changing an app setting restarts the app. Secrets belong in Key Vault, referenced from an app setting like `@Microsoft.KeyVault(SecretUri=...)`.

Better still, skip the secret. When a binding has `connection="ServiceBusConnection"`, the runtime looks for settings that **start with** that name:

| Setting | Meaning |
| --- | --- |
| `ServiceBusConnection` | A connection string (has a key in it) |
| `ServiceBusConnection__fullyQualifiedNamespace` = `contoso-ai.servicebus.windows.net` | Use the app's **managed identity** |
| `AzureWebJobsStorage__accountName` = `stcontosoai` | Host storage over identity instead of a key |

Give the function app's managed identity the right data role: **Azure Service Bus Data Receiver** for a trigger, **Data Sender** for an output binding (or **Data Owner** for both). If you use a user-assigned identity, also add `ServiceBusConnection__credential` = `managedidentity` and `ServiceBusConnection__clientId`.

```bash
az functionapp config appsettings set -g rg-ai -n func-summarise \
  --settings ServiceBusConnection__fullyQualifiedNamespace=contoso-ai.servicebus.windows.net
```

### Hosting plans

| Plan | Scaling | Cold start | Network | Notes |
| --- | --- | --- | --- | --- |
| **Flex Consumption** | Event-driven, per function, to zero | Optional **always-ready** instances | VNet integration | Recommended serverless plan. Linux. Pay per execution plus any always-ready instances. Choose instance memory. |
| **Premium** (Elastic Premium) | Event-driven, never below 1 | Pre-warmed, none | VNet integration | Linux or Windows, deployment slots, longer runs. Billed per core-second while instances run. |
| **Dedicated** | Manual or autoscale | None (always on) | VNet integration | Runs on an App Service plan you already pay for. |
| **Consumption** (legacy) | Event-driven, to zero | Yes | No VNet | Older serverless plan. Prefer Flex Consumption for new apps. |

Functions can also run in **Azure Container Apps** if you ship them as a container image.

### Create and deploy

Create a Flex Consumption app (the storage account holds the deployment package and host state):

```bash
az functionapp create -g rg-ai -n func-summarise \
  --storage-account stcontosoai \
  --flexconsumption-location eastus \
  --runtime python --runtime-version 3.12 \
  --assign-identity '[system]'
```

Then deploy from the project folder. Core Tools packages the code and, for Python on Linux, runs a **remote build** that installs `requirements.txt` in Azure:

```bash
func azure functionapp publish func-summarise
```

Other options: **zip deploy** (`az functionapp deployment source config-zip -g rg-ai -n func-summarise --src app.zip`), the Azure Functions extension in VS Code, or a GitHub Actions / Azure Pipelines workflow. Whatever you pick, `local.settings.json` isn't sent.

Keep a warm instance for the HTTP functions so the first morning request isn't slow:

```bash
az functionapp scale config always-ready set -g rg-ai -n func-summarise --settings http=1
```

<Callout type="exam">
Sort the clues. "Applies to every function in the app" is **host.json**. "Works locally, missing in Azure" is a value left in **local.settings.json** that needs to be an **app setting**. "No connection string or key" is a **managed identity** plus a `__fullyQualifiedNamespace` (or `__accountName`) setting. "Serverless, scale to zero, private network, no cold start" is **Flex Consumption** with **always-ready instances**. "Always warm, deployment slots" points to **Premium**. "Reuse an existing App Service plan" is **Dedicated**.
</Callout>

<DeepDive title="Timeouts, concurrency and what Flex doesn't do">

`functionTimeout` in host.json caps how long a run can take. On Flex Consumption and Premium the default is 30 minutes and you can raise it; the legacy Consumption plan stops at 10 minutes. HTTP responses still have the roughly 230-second load balancer limit, so long AI calls go through a queue.

Flex Consumption scales HTTP functions on concurrency (how many requests one instance handles at once) and queue triggers on backlog. You can tune `maxConcurrentCalls` in host.json to stop one instance from opening too many model calls and hitting rate limits. Flex Consumption doesn't support deployment slots, so if you need swap-based releases, use Premium or Dedicated, or deploy a second app and switch traffic in front of it.

</DeepDive>
