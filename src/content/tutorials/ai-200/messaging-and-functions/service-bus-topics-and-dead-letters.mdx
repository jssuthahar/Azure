## Start with a question

<Story question="One upload, three teams. How does each one hear about it?">

Think about a newspaper. The printer prints one edition, but every subscriber gets their own copy. The sports fan reads the cricket page, the investor reads business. Nobody has to fight over the single paper on the table.

When a document lands in your AI app, the search indexer, the billing team and the audit log all want to know. A **Service Bus topic** works like that newspaper: one message in, a copy for every **subscription**. And when a message is broken beyond repair, it goes to a **dead-letter queue** where you can look at it instead of losing it.

</Story>

## The technical explanation

A **topic** accepts messages from senders exactly like a queue. The difference is on the receiving side: a topic has **subscriptions**, and each subscription behaves like its own queue with its own receivers, lock settings, max delivery count and dead-letter queue. Topics need the **Standard** or **Premium** tier; Basic has queues only.

### Send to a topic, read from a subscription

```python
from azure.identity import DefaultAzureCredential
from azure.servicebus import ServiceBusClient, ServiceBusMessage

NAMESPACE = "contoso-ai.servicebus.windows.net"

with ServiceBusClient(NAMESPACE, DefaultAzureCredential()) as client:
    with client.get_topic_sender(topic_name="documents") as sender:
        sender.send_messages(ServiceBusMessage(
            '{"docId": "contract-88", "pages": 64}',
            subject="uploaded",
            application_properties={"tier": "premium", "pages": 64},
        ))

    with client.get_subscription_receiver(topic_name="documents",
                                          subscription_name="indexer") as receiver:
        for msg in receiver.receive_messages(max_message_count=20, max_wait_time=5):
            index_document(str(msg))
            receiver.complete_message(msg)
```

Senders don't know or care how many subscriptions exist. You can add a new reader next month without touching the sender.

### Filters decide what each subscription keeps

Every new subscription starts with a rule called **$Default**: a true filter (`1=1`) that lets everything through. To be picky, add your own rule and remove `$Default`.

| Filter | Example | Notes |
| --- | --- | --- |
| **SQL filter** | `tier = 'premium' AND pages > 20` or `sys.Label LIKE 'invoice%'` | Conditions, comparisons, LIKE, IN. Application properties by name, system properties with `sys.`. Most flexible, most work for the broker. |
| **Correlation filter** | subject = `uploaded`, tier = `premium` | Exact-match on system properties (correlation ID, message ID, subject, content type, to, reply-to, session ID) and application properties. Cheaper and faster. |
| **True / False filter** | `1=1` / `1=0` | Accept everything, or nothing. |

A SQL rule can also have an **action** that changes the copy for that subscription, such as `SET priority = 'high'`. If a message matches no rule on a subscription, that subscription simply doesn't get it.

```bash
az servicebus topic subscription rule create \
  --resource-group rg-ai --namespace-name contoso-ai \
  --topic-name documents --subscription-name billing \
  --name PremiumOnly --filter-sql-expression "tier = 'premium'"

az servicebus topic subscription rule delete \
  --resource-group rg-ai --namespace-name contoso-ai \
  --topic-name documents --subscription-name billing --name '$Default'
```

### The dead-letter queue

Every queue and every subscription has a **dead-letter queue (DLQ)**, a sub-queue at `<entity>/$deadletterqueue`. Messages go there when:

| Reason | When |
| --- | --- |
| `MaxDeliveryCountExceeded` | The message was delivered more times than the max delivery count (10 by default). This is the classic poison message. |
| `TTLExpiredException` | The message expired and **dead-lettering on message expiration** is turned on. |
| Filter evaluation error | A subscription rule threw an error for this message (on by default for subscriptions). |
| Your own reason | Your code called `dead_letter_message(msg, reason=..., error_description=...)`. |

Dead-lettered messages don't expire and aren't retried. They wait until you receive and complete them. You read a DLQ like any other queue:

```python
from azure.servicebus import ServiceBusSubQueue

with ServiceBusClient(NAMESPACE, DefaultAzureCredential()) as client:
    dlq = client.get_subscription_receiver(
        topic_name="documents", subscription_name="indexer",
        sub_queue=ServiceBusSubQueue.DEAD_LETTER)
    sender = client.get_topic_sender(topic_name="documents")
    with dlq, sender:
        for msg in dlq.receive_messages(max_message_count=50, max_wait_time=5):
            print(msg.dead_letter_reason, msg.dead_letter_error_description)
            if can_fix(msg):
                sender.send_messages(ServiceBusMessage(fix(msg),
                                     application_properties=msg.application_properties))
                dlq.complete_message(msg)   # resubmitted, remove it from the DLQ
            else:
                dlq.abandon_message(msg)    # leave it there for a person to check
```

For a queue, it's `client.get_queue_receiver(queue_name="summarise-jobs", sub_queue=ServiceBusSubQueue.DEAD_LETTER)`.

<Callout type="exam">
"Several services each need every message" means **topic and subscriptions**, never a single queue with competing receivers. "Only premium messages for billing" means a **filter** on that subscription. If the question stresses **exact property matches** and **performance**, pick a **correlation filter**. If it needs **greater than**, **LIKE** or **OR**, pick a **SQL filter**. For "find messages that failed repeatedly", open the **dead-letter sub-queue**. Basic tier plus topic is always wrong.
</Callout>

<DeepDive title="Auto-forwarding and alerting on the DLQ">

You can set **forward to** on a subscription so its messages land in another queue or topic, which helps when one team owns a queue and another owns the topic. You can also set **forward dead-lettered messages to** so every DLQ in a system feeds one central queue that your support tooling reads.

Don't let a DLQ grow unnoticed. Azure Monitor exposes a dead-lettered message count metric for each entity; put a metric alert on it so the team hears about poison messages the same day. When you resubmit, send a *new* message; there's no single "move back" call in the SDK. For a handful of messages, Service Bus Explorer in the portal can peek the DLQ and resend selected messages.

</DeepDive>
