## Start with a question

<Story question="Your model API key was in a config file. Someone pushed it to a public GitHub repo. What now?">

By morning there's a bill for thousands of model calls you never made. Bots scan public repos for keys within minutes, so "we'll fix it later" doesn't work.

The fix isn't just "delete the commit". The key shouldn't have been in the code at all. **Azure Key Vault** holds it instead, and your app asks for it at run time using an identity Azure gives it. There's no password in the repo, nothing to leak, and when the key changes, the app gets the new one on its own.

</Story>

## The technical explanation

Key Vault stores three kinds of things: **secrets** (any string up to 25 KB, like a connection string or an API key), **keys** (cryptographic keys for encryption and signing) and **certificates**. For AI-200 you'll mostly read and rotate **secrets** from code.

### Who's allowed in: identities and roles

Your app needs two things to read a secret: an identity, and permission for that identity.

| Identity type | What it is | When to pick it |
| --- | --- | --- |
| **System-assigned managed identity** | Created with the resource and deleted with it. One per resource. | One app, its own access. The simplest choice. |
| **User-assigned managed identity** | A standalone Azure resource you attach to one or more resources. | Several apps share the same access, or the role must exist before the app does. |

Permission comes from **Azure RBAC**, the recommended permission model for Key Vault. The older **vault access policies** still work, but they can't be scoped to a single secret and they're managed outside the normal role system.

| Role | Can do | Give it to |
| --- | --- | --- |
| **Key Vault Secrets User** | Read secret values | The running app |
| **Key Vault Secrets Officer** | Create, update, delete, recover secrets (not change permissions) | A rotation function, a release pipeline |
| **Key Vault Reader** | See metadata, not values | Auditors, dashboards |
| **Key Vault Administrator** | Everything on data in the vault | Admins only |

```bash
# Give the web app's system-assigned identity read access to secrets in one vault
az role assignment create \
  --role "Key Vault Secrets User" \
  --assignee <principal-id-of-the-app> \
  --scope $(az keyvault show -n kv-tailspin-prod --query id -o tsv)
```

### Read, write and list versions in Python

```bash
pip install azure-keyvault-secrets azure-identity
```

```python
import os
from azure.identity import DefaultAzureCredential
from azure.keyvault.secrets import SecretClient

# In Azure this uses the managed identity; on your laptop it uses az login
credential = DefaultAzureCredential()
client = SecretClient(vault_url=os.environ["KEY_VAULT_URL"], credential=credential)

# Read the latest version
secret = client.get_secret("openai-api-key")
print(secret.name, secret.properties.version)   # never print secret.value in real code

# Write a new value: this creates a NEW version, the old one stays
client.set_secret("openai-api-key", "sk-new-value", content_type="text/plain")

# See every version of one secret
for props in client.list_properties_of_secret_versions("openai-api-key"):
    print(props.version, props.created_on, props.enabled, props.expires_on)
```

`KEY_VAULT_URL` looks like `https://kv-tailspin-prod.vault.azure.net/`. For a **user-assigned** identity, tell the credential which one to use with `DefaultAzureCredential(managed_identity_client_id="<client-id>")` or the `AZURE_CLIENT_ID` environment variable.

### Versions, expiry and deleting safely

- **Versions.** Each `set_secret` makes a new version with its own ID. `get_secret(name)` returns the latest; `get_secret(name, version)` returns a specific one. If your config pins a version, rotation never reaches you, so don't pin unless you mean it.
- **Activation and expiry.** You can set `not_before` and `expires_on` when you write a secret. They're metadata: Key Vault still returns the value, but the dates drive events and tell your tooling what's stale.
- **Soft delete.** Always on. A deleted secret stays recoverable for the retention period (7 to 90 days, 90 by default) with `begin_recover_deleted_secret`.
- **Purge protection.** Optional. While it's on, nobody can purge a deleted secret or vault before retention ends, not even an admin. You can't turn it off once enabled.

### Rotation

**Keys** have a built-in **rotation policy**: you set "rotate 30 days before expiry" or "every 90 days" and Key Vault creates the new key version itself. **Secrets** don't, because only you know how to make a new database password or API key. So secret rotation is event-driven:

Key Vault also publishes `SecretNewVersionCreated` and `SecretExpired`, which are handy for telling apps to refresh their cache or for alerting.

### Cache what you read

Key Vault throttles a vault that gets too many requests. Don't call `get_secret` on every HTTP request. Read the secret at startup, keep it in memory, and refresh on a timer (say every few hours) or when the downstream service rejects the old value. If you run on App Service, Functions or Container Apps, **Key Vault references** in app settings do this for you.

<Callout type="exam">
Watch the role names. A question that says the app "must only read secrets" wants **Key Vault Secrets User**, not Reader (no values) and not Officer (too much). "No credentials in code or config" points to a **managed identity** with **DefaultAzureCredential**. "Run code before a secret expires" is **Event Grid** with the **SecretNearExpiry** event. If the question is about **keys** rotating on a schedule, it's a **rotation policy**.
</Callout>

<DeepDive title="Two-credential rotation for zero downtime">

If a database has only one password, there's a gap between "changed in the database" and "every app has the new one". Services such as Azure Storage and Cosmos DB give you **two keys** for exactly this reason. The rotation function regenerates the key that *isn't* in use, stores it as the new secret version, and on the next rotation flips to the other one. Apps that still hold the previous version keep working until their cache refreshes. Microsoft's rotation tutorials ship this dual-credential pattern as a function you can deploy.

</DeepDive>
