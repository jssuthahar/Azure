## Start with a question

<Story question="You want to switch the chatbot to a newer model. Why does that need six redeploys?">

Because the deployment name is typed into six services' config files. Change it, rebuild six images, roll out six releases, and hope nobody missed one. Then, if the new model misbehaves, do it all again backwards.

Settings that many services share shouldn't live inside each service. **Azure App Configuration** keeps them in one store. Change a value once, flip a **feature flag** for the new model, and every app reloads it in the next minute or so, without a restart.

</Story>

## Explain it like I'm 10

<Eli10>

The board never shows the safe's combination. It just says "ask the office" (that's a **Key Vault reference**).

## The technical explanation

### What's in a store

Each entry is a **key-value**:

| Part | Example | Notes |
| --- | --- | --- |
| **Key** | `ChatApp:Model:Deployment` | Any string. `:` or `/` are common separators for a hierarchy. |
| **Label** | `prod` | Optional. Same key, different value per label. No label is the "null label". |
| **Value** | `gpt-4.1` | A string, up to the store's size limit. |
| **Content type** | `application/json` | Optional. Tells the provider how to read the value. |

Two special kinds of key-value:

- **Feature flags** use keys under `.appconfig.featureflag/` (for example `.appconfig.featureflag/use-gpt-5`) with the content type `application/vnd.microsoft.appconfig.ff+json;charset=utf-8`. The value is JSON with `enabled` and optional **filters** (targeting a group, a percentage of users, a time window).
- **Key Vault references** have the content type `application/vnd.microsoft.appconfig.keyvaultref+json;charset=utf-8` and a value like `{"uri":"https://kv-tailspin.vault.azure.net/secrets/cosmos-key"}`. App Configuration stores only the URI.

```bash
az appconfig kv set -n appcs-tailspin --key ChatApp:Model:Deployment --value gpt-4.1 --label prod
az appconfig kv set-keyvault -n appcs-tailspin --key ChatApp:Cosmos:Key \
  --secret-identifier https://kv-tailspin.vault.azure.net/secrets/cosmos-key --label prod
az appconfig feature set -n appcs-tailspin --feature use-gpt-5 --label prod
```

### Access

Use Microsoft Entra ID, not access keys. The app's managed identity gets **App Configuration Data Reader** on the store (**Data Owner** can also write). If the store has Key Vault references, the same identity needs **Key Vault Secrets User** on the vault, because the provider in your app fetches the secret, not App Configuration.

### Load settings in Python

```bash
pip install azure-appconfiguration-provider azure-identity featuremanagement
```

```python
import os
from azure.identity import DefaultAzureCredential
from azure.appconfiguration.provider import load, SettingSelector, WatchKey
from featuremanagement import FeatureManager

credential = DefaultAzureCredential()

config = load(
    endpoint=os.environ["APP_CONFIG_ENDPOINT"],          # https://appcs-tailspin.azconfig.io
    credential=credential,
    selects=[
        SettingSelector(key_filter="ChatApp:*"),                     # no-label defaults first
        SettingSelector(key_filter="ChatApp:*", label_filter="prod") # prod values win
    ],
    trim_prefixes=["ChatApp:"],                         # "ChatApp:Model:Deployment" -> "Model:Deployment"
    keyvault_credential=credential,                     # resolves Key Vault references
    refresh_on=[WatchKey("ChatApp:Sentinel", label="prod")],
    refresh_interval=60,                                # seconds between sentinel checks
    feature_flag_enabled=True,
)

deployment = config["Model:Deployment"]   # behaves like a read-only dict
cosmos_key = config["Cosmos:Key"]         # already the secret value from Key Vault

features = FeatureManager(config)

def handle_request(question: str):
    config.refresh()                      # cheap: checks the sentinel only when the interval has passed
    model = "gpt-5" if features.is_enabled("use-gpt-5") else config["Model:Deployment"]
    ...
```

A few details that catch people:

- **Order of selectors matters.** Later selectors override earlier ones for the same key, so put the null-label defaults first and the environment label after.
- **`refresh()` is yours to call.** `refresh_on` and `refresh_interval` only say *what* to watch and *how often* to check. If you never call `config.refresh()`, nothing reloads.
- **The sentinel goes last.** Change the five settings you need, then update `ChatApp:Sentinel`. The app sees the sentinel change and reloads all of them together, so it never runs with half old, half new values.

### Snapshots

A **snapshot** is a named, read-only set of key-values captured from filters at one moment, for example `release-2026-11`. Load it with `SettingSelector(snapshot_name="release-2026-11")`. Because it can't change, production runs exactly what you tested, and rollback means loading the previous snapshot.

<Callout type="exam">
Map the requirement to the feature. "Different values for dev and prod with the same key" is **labels**. "Enable a feature for some users without a deployment" is a **feature flag** (with a targeting filter). "Settings must include a secret but the secret must stay in Key Vault" is a **Key Vault reference**, and the app needs **Key Vault Secrets User** too. "Reload only after several values change" is a **sentinel key** in `refresh_on`.
</Callout>

<DeepDive title="App Configuration or Key Vault?">

They do different jobs and usually work together. Key Vault is for values that would hurt if leaked; it has hardware-backed keys, rotation events and tight per-secret access. App Configuration is for everything else your app reads: deployment names, timeouts, prompt templates, feature flags. It has labels, snapshots, change history and fast refresh. Putting plain settings in Key Vault makes them awkward to change and costs more operations; putting secrets in App Configuration means anyone with Data Reader can read them. The Key Vault reference joins the two: one config source in code, secrets still guarded by Key Vault.

</DeepDive>
