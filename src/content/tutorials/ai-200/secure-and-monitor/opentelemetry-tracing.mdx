## Start with a question

<Story question="The chatbot takes nine seconds to answer. Five services are involved. Which one is slow?">

The web team says the API is fine. The data team says Cosmos DB is fine. The AI team says the model replies in two seconds. Everyone shows you their own logs, and none of them line up.

What you need is one view of **one request**: when it hit the API, when it went on the queue, how long the worker spent in Cosmos DB, how long the model took. That's **distributed tracing**, and **OpenTelemetry** is the standard way to collect it. In Azure, the data lands in **Application Insights**, where you can see the whole journey on one screen.

</Story>

<Eli10>

Without the tracking number, every depot just says "we were quick".

## The technical explanation

### The words you need

| Term | Meaning | Example |
| --- | --- | --- |
| **Trace** | One request end to end | A user's question, from browser to answer |
| **Span** | One timed step, with a **span ID** and a **parent** | `POST /ask`, `cosmos query`, `chat completion` |
| **Trace ID** | 32 hex characters shared by every span in the trace | `4bf92f3577b34da6a3ce929d0e0e4736` |
| **Span kind** | Server, client, producer, consumer or internal | Incoming HTTP is server; outgoing call is client |
| **Attributes** | Key-value detail on a span | `tenant.id = "contoso"`, `http.route = "/ask"` |
| **Resource** | Who produced the telemetry | `service.name = "chat-api"` |

**Context propagation** is what links services. When `chat-api` calls `retriever` over HTTP, OpenTelemetry adds a W3C **traceparent** header:

```text
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
             ver  trace ID (32 hex)                parent span (16)  flags (01 = sampled)
```

The receiving service reads it and starts its span as a child of `00f067aa0ba902b7`, in the same trace. Azure SDK instrumentation does the same for Service Bus and Event Hubs messages, so a trace survives a queue.

### Turn it on with the Azure Monitor OpenTelemetry Distro

```bash
pip install azure-monitor-opentelemetry
export APPLICATIONINSIGHTS_CONNECTION_STRING="InstrumentationKey=...;IngestionEndpoint=https://...;ApplicationId=..."
export OTEL_SERVICE_NAME="chat-api"      # becomes the cloud role name on the application map
```

```python
# app.py: configure BEFORE importing and creating the web app
from azure.monitor.opentelemetry import configure_azure_monitor

configure_azure_monitor(
    # connection_string=... is optional when the environment variable is set
    logger_name="chat",        # send logs from this logger to Application Insights too
    sampling_ratio=1.0,        # keep every trace in dev; lower it in production
)

from flask import Flask
import requests
app = Flask(__name__)
```

<Callout type="note">
Microsoft Learn now also offers a newer **Microsoft OpenTelemetry Distro** (`pip install microsoft-opentelemetry`) for brand-new Python apps. Apps already on `azure-monitor-opentelemetry` need no change, and the ideas here (spans, trace IDs, sampling, cloud role name) are the same in both. Don't initialise both distros in one app.
</Callout>

That one call sets up traces, metrics and logs and switches on the bundled **automatic instrumentation**:

| Library | What you get for free |
| --- | --- |
| Flask, FastAPI, Django | A server span per incoming request |
| requests, urllib, urllib3 | A client span per outgoing HTTP call, plus the traceparent header |
| psycopg2 | A span per PostgreSQL query |
| Azure SDK (azure-core) | Spans for Cosmos DB, Service Bus, Storage, Key Vault and other Azure client calls |

### Add your own spans

Automatic spans show *where* time went. Custom spans and attributes say *what* the app was doing.

```python
from opentelemetry import trace
from opentelemetry.trace import Status, StatusCode

tracer = trace.get_tracer(__name__)

@app.post("/ask")
def ask():
    with tracer.start_as_current_span("retrieve-context") as span:
        span.set_attribute("tenant.id", tenant_id)
        span.set_attribute("retrieval.top_k", 5)
        chunks = search(question)                 # Cosmos DB call: an automatic child span

    with tracer.start_as_current_span("generate-answer") as span:
        span.set_attribute("gen_ai.request.model", deployment)
        try:
            answer = call_model(chunks, question)
        except Exception as ex:
            span.record_exception(ex)
            span.set_status(Status(StatusCode.ERROR))
            raise
    return {"answer": answer}
```

`start_as_current_span` makes the new span the **current** one, so anything called inside it (including automatic spans) becomes its child. Keep prompts, personal data and secrets out of attributes: they're stored and searchable.

### Where you read it in Application Insights

- **Application map**: one node per cloud role name, with call counts, failure rates and average durations on the arrows.
- **Transaction search** and the **end-to-end transaction details** view: every span of one trace as a timeline, so the 2.4-second Cosmos DB query stands out.
- **Failures** and **Performance**: grouped by operation, with drill-down into sample traces.

Server spans become rows in the `requests` table, client and internal spans in `dependencies`, recorded exceptions in `exceptions`, and logs in `traces`. They're joined by `operation_Id`, which is the trace ID.

### Sampling and naming

- **Sampling** keeps a share of traces. `sampling_ratio=0.1` keeps about 10%. The decision travels in the trace flags, so a kept trace is kept by every service and stays complete. If you don't set anything, current versions of the distro use a **rate-limited sampler** of about 5 traces per second, and the `OTEL_TRACES_SAMPLER` / `OTEL_TRACES_SAMPLER_ARG` environment variables win over code options.
- **Resource attributes** identify the service. Set `OTEL_SERVICE_NAME`, or `OTEL_RESOURCE_ATTRIBUTES="service.name=chat-api,service.namespace=tailspin,service.instance.id=pod-7"`. Application Insights uses them for the **cloud role name** and **role instance**.

<Callout type="exam">
Expect the setup order: install **azure-monitor-opentelemetry**, call **configure_azure_monitor()** with the **connection string** (or set **APPLICATIONINSIGHTS_CONNECTION_STRING**) at startup, then add custom spans with **start_as_current_span**. Questions about "correlating calls across services" are about the **trace ID** and **traceparent**. "Each service shows separately on the application map" is the **service.name** (cloud role name).
</Callout>

<DeepDive title="Why the distro and not the raw OpenTelemetry SDK?">

You could install the OpenTelemetry SDK, the Azure Monitor exporter and each instrumentation library yourself, then wire up tracer, meter and logger providers. The distro does that in one call with sensible defaults, adds live metrics and Microsoft Entra ID authentication for ingestion, and stays on supported versions. Because it's still OpenTelemetry underneath, your custom spans use the standard `opentelemetry` API, so moving to another backend later means changing the exporter, not your code. If you need an instrumentation the distro doesn't bundle (say, Redis), install the community package and it plugs into the same pipeline.

</DeepDive>
