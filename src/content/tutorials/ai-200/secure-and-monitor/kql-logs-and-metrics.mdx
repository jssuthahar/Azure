## Start with a question

<Story question="The logs have everything. So why does finding one error take an hour?">

Because you're scrolling. Two million log lines a day, and you're paging through them looking for the one that says "timeout". By the time you find it, users have already told you the app is broken.

The logs aren't the problem. Reading them by hand is. **KQL** lets you ask the logs a question, like "how many requests failed in each 5-minute window today?", and get a chart back in a second. Then you save that question as an **alert**, so next time you hear about it before your users do.

</Story>

## Explain it like I'm 10

<Eli10>

Imagine a huge box of every receipt from a shop.

You could read them one by one. Or you could say: "Only the ones from today. Only the refunds. Put them in piles by hour. Count each pile."

That's a KQL query. Each step is a sieve, and what falls through goes to the next sieve. At the end you've got a small answer instead of a huge box.

</Eli10>

## The technical explanation

### Where the data lives

Telemetry from Application Insights and other Azure resources lands in **tables**. The same data has two sets of names, depending on where you query it:

| Data | Application Insights (classic names) | Log Analytics workspace |
| --- | --- | --- |
| Incoming requests | `requests` (`timestamp`, `name`, `success`, `duration`, `resultCode`) | `AppRequests` (`TimeGenerated`, `Name`, `Success`, `DurationMs`, `ResultCode`) |
| Outgoing calls | `dependencies` | `AppDependencies` |
| Exceptions | `exceptions` | `AppExceptions` |
| Log messages | `traces` | `AppTraces` |
| Custom metrics | `customMetrics` | `AppMetrics` |
| Container Apps stdout/stderr | — | `ContainerAppConsoleLogs_CL` (`ContainerAppName_s`, `Log_s`) |
| AKS container logs | — | `ContainerLogV2` (`PodName`, `ContainerName`, `LogMessage`) |

Every Application Insights row carries `operation_Id` (the OpenTelemetry trace ID) and `cloud_RoleName` (the service name). In the workspace those are `OperationId` and `AppRoleName`.

### The operators you'll use every day

A query reads top to bottom. Each `|` hands the rows to the next step.

| Operator | Does | Example |
| --- | --- | --- |
| `where` | Keeps matching rows | `where timestamp > ago(1h) and success == false` |
| `project` | Picks (and renames) columns | `project timestamp, name, duration` |
| `extend` | Adds a calculated column | `extend seconds = duration / 1000` |
| `summarize` | Groups and aggregates | `summarize count(), avg(duration) by name` |
| `bin()` | Buckets numbers or time | `by bin(timestamp, 5m)` |
| `top` / `sort by` / `take` | Orders and limits | `top 10 by duration desc` |
| `join` | Combines two tables | `join kind=inner (exceptions) on operation_Id` |
| `render` | Draws a chart | `render timechart` |

Useful aggregates: `count()`, `countif()`, `dcount()` (distinct count), `avg()`, `sum()`, `max()`, `percentile(duration, 95)` and `percentiles(duration, 50, 95, 99)`.

### Queries worth knowing

**Failed requests over time:**

```kusto
requests
| where timestamp > ago(24h)
| summarize failed = countif(success == false), total = count() by bin(timestamp, 5m)
| extend failRate = round(100.0 * failed / total, 1)
| render timechart
```

**Slowest operations by 95th percentile:**

```kusto
requests
| where timestamp > ago(1h)
| summarize p95 = percentile(duration, 95), calls = count() by name
| top 10 by p95 desc
```

**Which dependency is slow for the /ask endpoint:**

```kusto
dependencies
| where timestamp > ago(1h) and operation_Name == "POST /ask"
| summarize avgMs = avg(duration), p95 = percentile(duration, 95) by target, type
| sort by p95 desc
```

**Failed requests with their exception message (a join on the trace ID):**

```kusto
requests
| where timestamp > ago(1h) and success == false
| project operation_Id, name, resultCode, timestamp
| join kind=inner (
    exceptions | project operation_Id, type, outerMessage
  ) on operation_Id
| take 50
```

**Errors from one container app:**

```kusto
ContainerAppConsoleLogs_CL
| where TimeGenerated > ago(30m)
| where ContainerAppName_s == "summary-worker" and Log_s has "error"
| project TimeGenerated, RevisionName_s, Log_s
| sort by TimeGenerated desc
```

**A custom metric your code sends (for example tokens used):**

```kusto
customMetrics
| where timestamp > ago(1d) and name == "gen_ai.tokens"
| summarize tokens = sum(valueSum) by bin(timestamp, 1h), cloud_RoleName
| render timechart
```

### Logs vs metrics, and the two alert types

**Metrics** are numbers sampled at regular intervals (CPU, request count, queue length), stored in a time-series database and fast to chart in Metrics explorer. **Logs** are rows with lots of detail, queried with KQL.

| | Metric alert | Log search alert |
| --- | --- | --- |
| Watches | A platform or custom metric | The result of a KQL query |
| Evaluated | About every minute | On a schedule you set (for example every 5 minutes over the last 15) |
| Good for | CPU over 80%, queue length over 1,000 | Failure rate per endpoint, a specific exception text, a pattern across tables |
| Cost | Lower | Higher, and grows with how often it runs |

Both send notifications through an **action group** (email, SMS, webhook, Logic App, Azure Function). In the portal you can go straight from a query in **Logs** to **New alert rule**, and the query is carried over.

<Callout type="exam">
Exam items often give you a nearly complete query and ask for the missing operator. "Count per time interval" is **summarize ... by bin()**. "Add a column" is **extend**, "keep only some columns" is **project**, "line chart over time" is **render timechart**, and "combine requests with exceptions" is **join on operation_Id**. If the scenario says the query runs against the **workspace**, expect `AppRequests` and `TimeGenerated`.
</Callout>

<DeepDive title="Writing queries that stay fast and cheap">

Filter on time first, then on other columns, because tables are partitioned by time and the engine can skip whole chunks. Prefer `has` over `contains` for whole words: `has` uses the term index, `contains` scans every string. Project away big columns (like `customDimensions`) before a `join`, and put the smaller table on the left. For dashboards over long periods, summarise into bins instead of returning raw rows. And for alerts, keep the look-back window short: a log search alert that scans 24 hours every 5 minutes is slow and costs more than one that scans 15 minutes.

</DeepDive>
