## The technical explanation

### Request Units

An **RU** bundles CPU, memory and IO into one number. Rough costs to keep in your head:

| Operation | Typical cost |
| --- | --- |
| Point read, 1 KB item | about 1 RU |
| Write (create, replace, upsert), 1 KB item, default indexing | about 5 RUs or more, and more with every indexed property |
| Query | depends on items scanned, index use, result size and partitions touched |

You buy throughput in one of three ways: **provisioned manual** (fixed RU/s), **provisioned autoscale** (you set a maximum and it scales between 10% and that maximum), or **serverless** (pay per RU used, for spiky or small workloads). Go over the RU/s you have and the service returns **429 Too Many Requests**. The SDK retries for you, but steady 429s mean you need more throughput or cheaper operations.

Always measure. The response header `x-ms-request-charge` tells you the exact charge:

```python
container.query_items(query="SELECT * FROM c WHERE c.category = @c",
                      parameters=[{"name": "@c", "value": "kettles"}],
                      partition_key="kettles")
print(container.client_connection.last_response_headers["x-ms-request-charge"])
```

### Indexing policy

The default policy indexes everything with **range indexes**, uses `consistent` indexing mode (the index updates with every write), and excludes only the system `_etag` path. That's great for ad hoc filters and expensive for writes when items are big.

Here's a lean policy for a product container that stores embeddings:

```json
{
  "indexingMode": "consistent",
  "automatic": true,
  "includedPaths": [
    { "path": "/*" }
  ],
  "excludedPaths": [
    { "path": "/\"_etag\"/?" },
    { "path": "/embedding/*" },
    { "path": "/description/?" }
  ],
  "compositeIndexes": [
    [
      { "path": "/category", "order": "ascending" },
      { "path": "/price", "order": "ascending" }
    ]
  ]
}
```

How to read the paths:

- `/*` means every path under the root.
- `/description/?` means the scalar value at `description`.
- `/embedding/*` means everything under `embedding`, including every element of the array.
- You can flip it round: include only the paths you filter on (`/category/?`, `/price/?`) and exclude `/*`. That's the leanest option for write-heavy containers.

**Composite indexes** are needed for `ORDER BY` on more than one property, and they help queries that filter on one property and sort on another. The order (ascending or descending) has to match the query, or be its exact reverse.

Changing the policy on an existing container is allowed. Cosmos DB rebuilds the index in the background using spare RUs, and queries keep working while it does.

<Callout type="tip">
Don't exclude a path that a query filters on. The query still runs, but it has to scan, and the RU charge jumps. Check `x-ms-request-charge` before and after.
</Callout>

### Consistency levels

Consistency is set as the **account default** and applies to reads. A client or a single request can choose a **weaker** level than the default, never a stronger one.

| Level | What a reader is promised | Read cost |
| --- | --- | --- |
| **Strong** | Always the latest committed write, in every region. | About 2x |
| **Bounded staleness** | At most K versions or T time behind, in order. | About 2x |
| **Session** (default) | Within one session: read your own writes, in order. Others may lag. | 1x |
| **Consistent prefix** | Never out of order, but may be behind. | 1x |
| **Eventual** | Will catch up eventually; order isn't guaranteed. | 1x |

Strong and Bounded staleness read from two replicas to keep their promise, which is why their reads cost about twice as much. Strong in a multi-region account also adds write latency, because a write waits for every region.

Weakening the level for one client in Python:

```python
client = CosmosClient(
    url=os.environ["COSMOS_ENDPOINT"],
    credential=DefaultAzureCredential(),
    consistency_level="Eventual",  # weaker than the account's Session default
)
```

**Session** is the right answer for most apps, AI chat history included: the user sees their own messages straight away, and you don't pay for global agreement.

<Callout type="exam">
Expect cost questions. "Reduce the RU charge of inserts" points to **excluding paths** from the indexing policy. "ORDER BY on two properties fails" points to a **composite index**. For consistency, learn the order (Strong, Bounded staleness, Session, Consistent prefix, Eventual), that **Session** is the default, that clients can only **weaken** it, and that **Strong** and **Bounded staleness** reads cost about **twice** the RUs.
</Callout>

<DeepDive title="Indexing mode none, and the vector index">

`indexingMode: "none"` turns indexing off. It suits a container used only as a key-value store with point reads, or a bulk load where you'll turn indexing back on afterwards. Queries without an index scan everything, so don't use it for anything you search.

If you search embeddings, the vector path goes in `excludedPaths` (so the range index skips it) **and** in `vectorIndexes` (so the vector index covers it). Those are two different indexes. Excluding the path from the range index is what Microsoft recommends to keep insert RUs and latency down.

</DeepDive>
