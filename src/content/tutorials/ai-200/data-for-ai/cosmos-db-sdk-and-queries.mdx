## Start with a question

<Story question="Your AI shopping assistant needs a product's price and stock in under 10 milliseconds, thousands of times a minute. Where does that data live, and how does your code ask for it?">

Think of a huge warehouse with labelled aisles. If you know the aisle and the shelf number, a picker walks straight there and grabs the box. If all you've got is "something blue, about this big", they have to walk every aisle.

**Azure Cosmos DB for NoSQL** works the same way. The **partition key** is the aisle and the **id** is the shelf. Give both and you get a cheap, fast **point read**. Give a vague query and it walks the whole warehouse, and you pay for every step in **Request Units**.

</Story>

## The technical explanation

The hierarchy is simple: an **account** holds **databases**, a database holds **containers**, and a container holds JSON **items**. Each container has a **partition key** path, for example `/category`. Items with the same `category` value share a **logical partition** (up to 20 GB), and Cosmos DB spreads logical partitions across physical ones as you grow. An item's `id` must be unique within its logical partition, and an item can be up to 2 MB.

### Connect with Microsoft Entra ID

```bash
pip install azure-cosmos azure-identity
export COSMOS_ENDPOINT="https://<account-name>.documents.azure.com:443/"
az login
```

```python
import os
from azure.cosmos import CosmosClient, PartitionKey
from azure.identity import DefaultAzureCredential

client = CosmosClient(
    url=os.environ["COSMOS_ENDPOINT"],
    credential=DefaultAzureCredential(),  # no account key in code
)

# Usually created by Bicep, the CLI or the portal (see the note below)
database = client.create_database_if_not_exists(id="shop")
container = database.create_container_if_not_exists(
    id="products",
    partition_key=PartitionKey(path="/category"),
)
```

Create the `CosmosClient` **once** and reuse it for the life of the app. It holds connections and caches routing information, so making a new client per request is slow and wastes resources.

### Write, read and query

```python
# Insert, or replace if this id + partition key already exists
container.upsert_item({
    "id": "p-1001",
    "category": "kettles",
    "name": "Steel Kettle 1.7 L",
    "price": 2499,
    "stock": 42,
})

# Point read: id + partition key value. About 1 RU for a 1 KB item.
item = container.read_item(item="p-1001", partition_key="kettles")
print(item["name"])

charge = container.client_connection.last_response_headers["x-ms-request-charge"]
print("RU charge:", charge)

# Parameterised query inside ONE logical partition
cheap = container.query_items(
    query="SELECT c.id, c.name, c.price FROM c WHERE c.category = @cat AND c.price < @max",
    parameters=[
        {"name": "@cat", "value": "kettles"},
        {"name": "@max", "value": 3000},
    ],
    partition_key="kettles",
)
for row in cheap:
    print(row)

# A query that must look across partitions
low_stock = container.query_items(
    query="SELECT TOP 20 c.id, c.category, c.stock FROM c WHERE c.stock < @n",
    parameters=[{"name": "@n", "value": 5}],
    enable_cross_partition_query=True,
)
```

A few things to notice:

- **upsert_item** inserts or replaces. Use `create_item` if you want an error when the id already exists, and `replace_item` or `patch_item` for updates.
- **read_item** isn't a query, it's a direct lookup, and it's always cheaper than `SELECT * FROM c WHERE c.id = @id`.
- **query_items** returns a lazy iterator. Results come back in pages as you loop, and each page has its own RU charge. For paging in an API, use `max_item_count` and `by_page()` and hand the continuation token back to the caller.

### The query language in one table

| You want | Write |
| --- | --- |
| Pick fields | `SELECT c.id, c.name FROM c` |
| Filter | `WHERE c.category = @cat AND c.price < @max` |
| Limit results | `SELECT TOP 10 ...` or `OFFSET 0 LIMIT 10` |
| Sort | `ORDER BY c.price DESC` (multi-property sorts need a composite index) |
| Search inside an array | `WHERE ARRAY_CONTAINS(c.tags, @tag)` |
| Flatten an array in the item | `SELECT t FROM c JOIN t IN c.tags` |
| Count | `SELECT VALUE COUNT(1) FROM c WHERE c.category = @cat` |

`JOIN` in Cosmos DB works **inside one item** (across its arrays), never between items or containers. Model your data so a request needs one item or one partition.

<Callout type="exam">
Three things the exam likes to test. A **point read** needs the **id** and the **partition key** value, and it's the cheapest way to fetch one item. Queries should use **parameters** (`@name`), not string concatenation. A query that doesn't filter on the partition key is a **cross-partition** query and costs more RUs. When you see "Microsoft Entra ID" plus "403 Forbidden" on data calls, the fix is a **Cosmos DB data plane role** (Cosmos DB Built-in Data Contributor or Reader), not an Azure IAM role.
</Callout>

<DeepDive title="Entra ID data access, and why create_* can fail">

Cosmos DB has two kinds of access. **Control plane** (Azure Resource Manager) is for creating accounts, databases and containers, and uses normal Azure roles. **Data plane** is for reading and writing items, and with Entra ID it uses Cosmos DB's own role definitions, assigned with `az cosmosdb sql role assignment create`. The built-in ones are **Cosmos DB Built-in Data Reader** and **Cosmos DB Built-in Data Contributor**.

Data plane roles don't include management operations, so `create_database_if_not_exists` and `create_container_if_not_exists` can fail when you sign in with Entra ID. In production, create the database and container with Bicep, the CLI or the portal, then use `client.get_database_client("shop")` and `database.get_container_client("products")` in the app. Many teams also set `disableLocalAuth` on the account so account keys stop working altogether.

</DeepDive>
