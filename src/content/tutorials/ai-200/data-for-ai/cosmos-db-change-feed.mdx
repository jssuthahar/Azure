If the cook goes on a break, the next cook looks at the clip and carries on from there. Nothing is cooked twice by accident and nothing is missed.

Cosmos DB has that rail: the **change feed**. The cook is the **change feed processor**, the clip is a **lease**, and cooking is your code, the **delegate**. A new product lands, the processor sees it, and your code embeds it straight away.

## The technical explanation

The change feed is on by default for every Cosmos DB for NoSQL container. It's ordered per **partition key range**, and it's persistent, so a reader can start now, at a point in time, or from the beginning (in latest version mode).

### The four parts of the processor

| Part | What it is |
| --- | --- |
| **Monitored container** | The container with your data, such as `products`. Its changes are what you read. |
| **Lease container** | Stores one **lease** per partition key range: the checkpoint and which instance owns it. Its partition key must be `/id`. |
| **Compute instance** | Wherever the processor runs: an App Service, a container app, a VM. Each has a unique **instance name**. |
| **Delegate** | Your handler. It receives a batch of changed items and does the work. |

The life cycle loops: read the feed, sleep if there's nothing new (the poll interval), otherwise call the delegate, and **only after the delegate finishes successfully** update the lease. If the delegate throws, the same batch comes back again. That's why delivery is **at least once**, and why your delegate should be **idempotent** (safe to run twice on the same item).

### The processor in C#

The processor library ships in the **.NET** and **Java** SDKs:

```csharp
Container monitored = client.GetContainer("shop", "products");
Container leases    = client.GetContainer("shop", "leases");

ChangeFeedProcessor processor = monitored
    .GetChangeFeedProcessorBuilder<Product>(
        processorName: "embedProducts",
        onChangesDelegate: HandleChangesAsync)
    .WithInstanceName(Environment.MachineName)   // unique per instance
    .WithLeaseContainer(leases)
    .WithStartTime(DateTime.UtcNow.AddHours(-1)) // optional; default is "from now"
    .Build();

await processor.StartAsync();

static async Task HandleChangesAsync(
    ChangeFeedProcessorContext context,
    IReadOnlyCollection<Product> changes,
    CancellationToken token)
{
    foreach (Product p in changes)
    {
        // embed p.Description and save the vector (idempotently)
    }
}
```

- To **scale out**, run more instances with the same `processorName` and lease container and different instance names. Leases are shared out between them, and one lease is owned by one instance at a time, so more instances than leases won't help.
- A new processor starts **from now** by default. `WithStartTime` sets a point in time; `DateTime.MinValue.ToUniversalTime()` reads from the beginning. These only matter the first time; once leases exist, the processor resumes from them.
- Register `WithErrorNotification` so you hear about failures, and send items that keep failing to an error store so the processor doesn't get stuck retrying them.

### In Python: an Azure Functions trigger

The Python SDK doesn't include the processor. The usual Python answer is the **Azure Functions Cosmos DB trigger**, which runs the processor for you, leases and all:

```python
import azure.functions as func

app = func.FunctionApp()

@app.cosmos_db_trigger(
    arg_name="items",
    connection="CosmosDbConnection",          # app setting (or identity-based settings)
    database_name="shop",
    container_name="products",                # the monitored container
    lease_container_name="leases",
    create_lease_container_if_not_exists="true",
)
def embed_new_products(items: func.DocumentList):
    for doc in items:
        if doc.get("textHash") == hash_of(doc["description"]):
            continue                          # vector is already current: skip
        vector = embed(doc["description"])
        save_vector(doc["id"], doc["category"], vector)
```

That `textHash` check matters. If your function writes the embedding back into the **same** item, that write is an update, which appears in the change feed and fires the function again. Without a guard you get an endless loop and a big RU bill. Either compare a hash of the source text, or write vectors to a separate container.

If you'd rather run your own loop in Python, the **change feed pull model** (`container.query_items_change_feed(...)`) reads changes directly, but you store and resume the continuation token yourself.

### Change feed modes

| | Latest version (default) | All versions and deletes |
| --- | --- | --- |
| Creates and updates | Yes, latest version of each item only | Yes, every intermediate version |
| **Deletes** | **No** | Yes, including TTL expiries |
| Start from the beginning or a time | Yes | No: from now or a saved checkpoint within the retention period |
| Requirements | None | **Continuous backup** on the account, NoSQL API only |

In latest version mode, if an item is created and then updated before you read the feed, you only see the updated version. To react to deletes without switching modes, use a **soft delete**: set `"deleted": true` (which is an update the feed records) and a TTL so the item is removed later.

<Callout type="exam">
Know the vocabulary: **monitored container**, **lease container**, **delegate**, **instance name**, **processor name**. Several instances share work when they use the **same processor name and lease container** with **different instance names**. The processor starts **from now** unless you set a **start time**. **Latest version** mode doesn't capture **deletes**; **all versions and deletes** does and needs **continuous backup**. If the scenario says "serverless" or "without managing the processor host", choose the **Azure Functions Cosmos DB trigger**.
</Callout>

<DeepDive title="Watching lag and cost">

The change feed processor costs RUs on both containers: reading the monitored container's feed and reading and writing leases. Give the lease container enough throughput, especially with many partition key ranges.

To see whether the processor keeps up, use the **change feed estimator** in .NET, which reports how many changes are still waiting per lease. With Functions, watch the trigger's execution count and duration in Application Insights. If lag grows, add instances (up to the number of leases) or make the delegate faster, for example by embedding a batch of items in one call instead of one call per item.

Use the account's **global endpoint** when you create the client for the processor. Leases are scoped to the endpoint you use, so switching to a regional endpoint later creates a fresh set of leases.

</DeepDive>
