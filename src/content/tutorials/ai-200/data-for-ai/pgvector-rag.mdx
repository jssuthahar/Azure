## Start with a question

<Story question="How does a chatbot answer from your company's own documents instead of making things up?">

Imagine a new support agent on their first day. They don't know your refund policy, so before answering a customer they open the policy binder, find the right page and read it out. They don't guess.

**Retrieval-augmented generation (RAG)** makes a language model do the same. Your app finds the most relevant passages in your own data, hands them to the model, and asks it to answer only from those. With **pgvector**, the "find the right page" part is a SQL query in the PostgreSQL database you already run.

</Story>

## Explain it like I'm 10

<Eli10>

Every paragraph in your binder gets a secret number code that describes what it's about. Paragraphs about refunds get codes that are close to each other.

When someone asks "can I get my money back?", you make a code for the question too, then grab the paragraphs with the closest codes.

But you only look in your own binder, not your neighbour's. That's the filter.

Then the robot reads those few paragraphs and answers.

</Eli10>

## The technical explanation

RAG has two halves. **Ingestion** happens ahead of time. **Retrieval and generation** happen on every question.

### Ingestion: store chunks with embeddings

This uses the `doc_chunks` table from the schema lesson (`tenant_id`, `content`, `metadata jsonb`, `embedding vector(1536)`) and the `pgvector` Python package, which teaches psycopg how to send and receive vectors.

```python
# pip install pgvector numpy openai
import numpy as np
from pgvector.psycopg import register_vector

register_vector(conn)            # lets psycopg pass numpy arrays as vector values

def embed(text: str) -> np.ndarray:
    resp = openai_client.embeddings.create(model="text-embedding-3-small", input=text)
    return np.array(resp.data[0].embedding, dtype=np.float32)

with conn.cursor() as cur:
    for i, chunk in enumerate(chunks):
        cur.execute(
            """INSERT INTO doc_chunks (tenant_id, doc_id, chunk_no, content, metadata, embedding)
               VALUES (%s, %s, %s, %s, %s, %s)""",
            ("contoso", doc_id, i, chunk, Jsonb({"lang": "en", "product": "router"}), embed(chunk)),
        )
conn.commit()
```

`Jsonb` comes from `psycopg.types.json`. In a real loader you'd embed in batches (the embeddings API takes a list) and bulk-load with `COPY`.

### Retrieval: similarity search plus metadata filter

```sql
SELECT id, content, embedding <=> %(q)s AS distance
FROM doc_chunks
WHERE tenant_id = %(tenant)s
  AND metadata @> '{"lang": "en"}'
ORDER BY embedding <=> %(q)s
LIMIT 5;
```

Three details matter here:

- `<=>` is **cosine distance**, which is 1 minus cosine similarity. Smaller is closer, so you sort **ascending**. If you want a similarity score for display, use `1 - (embedding <=> q)`.
- The filters live in the **same query**. That's how a customer only ever sees their own documents, and it means all 5 rows are useful.
- The HNSW index must be built with `vector_cosine_ops` to match `<=>`. OpenAI embeddings are normalised to length 1, so inner product (`<#>`, `vector_ip_ops`) gives the same order and is slightly cheaper.

### Generation: ground the answer

```python
q = embed(question)
with conn.cursor() as cur:
    cur.execute(RETRIEVE_SQL, {"q": q, "tenant": tenant_id})
    rows = cur.fetchall()

context = "\n\n".join(f"[{r[0]}] {r[1]}" for r in rows)
response = openai_client.responses.create(
    model="gpt-4.1-mini",   # your deployment name
    instructions=(
        "Answer only from the sources below. Cite source ids in square brackets. "
        "If the sources don't contain the answer, say you don't know."
    ),
    input=f"Sources:\n{context}\n\nQuestion: {question}",
)
print(response.output_text)
```

The instruction "say you don't know" is what stops the model from filling gaps with guesses.

### Tuning recall at query time

HNSW is approximate. It examines a candidate list of size **hnsw.ef_search** (default **40**) and returns the best of those. Raise it for better recall, lower it for speed:

```sql
BEGIN;
SET LOCAL hnsw.ef_search = 100;   -- only for this transaction
SELECT ... ORDER BY embedding <=> %s LIMIT 5;
COMMIT;
```

With IVFFlat, the matching knob is **ivfflat.probes** (default 1): how many clusters to search.

<Callout type="exam">
Expect a query to complete or fix. **Smallest distance first** (`ORDER BY ... <=> ... LIMIT k`, ascending) returns the most similar rows. "Only this customer's documents" is a **WHERE filter in the same query**, not post-filtering. "Better recall" is a higher **hnsw.ef_search** (or **ivfflat.probes**). And the question must be embedded with the **same model** as the documents.
</Callout>

<DeepDive title="When filters and HNSW don't get along">

HNSW walks its graph to find `ef_search` candidates, and only then applies your `WHERE`. If the filter matches 1% of rows, most of those 40 candidates get thrown away and you might get 2 rows back instead of 5. Fixes, roughly from simplest: raise `hnsw.ef_search`; add a B-tree index on the filter column so the planner can choose an exact search over the few matching rows when the filter is very selective; build a **partial index** per big tenant or **partition** by tenant; or, on pgvector 0.8.0 and later, `SET hnsw.iterative_scan = relaxed_order` so the index keeps scanning until enough rows pass the filter (`hnsw.max_scan_tuples` caps the work). Check your version with `SELECT extversion FROM pg_extension WHERE extname = 'vector';`.

</DeepDive>
