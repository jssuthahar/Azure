## Start with a question

<Story question="Why does the same query take 3 milliseconds in one database and 3 seconds in another?">

Picture two libraries with the same books. One has a catalogue sorted by author and a shelf map. The other has books piled in the order they arrived. Finding one book in the second library means checking every pile.

Databases work the same way. The **schema** decides what each column holds, and **indexes** are the catalogue. Get them right and your AI app pulls the right 5 chunks out of 2 million rows before the user notices. Get them wrong and every question walks the whole table.

</Story>

## The technical explanation

### Step 1: allow the extension, then create it

On flexible server, extensions are off until you allow them. The **pgvector** project's extension name is **vector**:

1. In the portal, open **Server parameters**, find **azure.extensions** and tick **VECTOR**. Save. (The CLI equivalent is `az postgres flexible-server parameter set --name azure.extensions --value vector`.)
2. Connect to your database and run:

```sql
SHOW azure.extensions;        -- check it's allowed
CREATE EXTENSION IF NOT EXISTS vector;
```

`CREATE EXTENSION` works per database, so repeat it in each database that needs vectors. If you skip step 1, you get an error saying the extension isn't allow-listed.

### Step 2: pick the right types

Here's a table for document chunks in a multi-tenant support assistant:

```sql
CREATE TABLE doc_chunks (
    id          uuid        PRIMARY KEY DEFAULT gen_random_uuid(),
    tenant_id   text        NOT NULL,
    doc_id      uuid        NOT NULL,
    chunk_no    int         NOT NULL,
    content     text        NOT NULL,
    metadata    jsonb       NOT NULL DEFAULT '{}'::jsonb,   -- {"lang":"en","product":"router"}
    created_at  timestamptz NOT NULL DEFAULT now(),
    embedding   vector(1536)                                -- text-embedding-3-small
);
```

| Type | Use it for | Why |
| --- | --- | --- |
| `uuid` / `bigint` | Keys | uuid is safe to generate anywhere; bigint is smaller and sorts well |
| `text` | Chunks, titles | No length limit worries; use `varchar(n)` only when a limit is a real rule |
| `jsonb` | Flexible metadata | Indexed with GIN, queried with `@>` and `->>` |
| `timestamptz` | Times | Stores an exact moment, so time zones don't bite you later |
| `vector(1536)` | Embeddings | Fixed dimensions are required for indexing |
| `halfvec(1536)` | Embeddings, smaller | Half precision, about half the storage and index size |

Two limits are worth knowing. A `vector` column without dimensions can't be indexed. And HNSW and IVFFlat indexes on `vector` support up to **2,000 dimensions**. If your model returns 3,072, either ask the model for fewer (the `dimensions` parameter on text-embedding-3 models) or store `halfvec`, which pgvector can index at higher dimensions.

### Step 3: index for the way you query

```sql
-- B-tree: equality, ranges and sorting
CREATE INDEX ix_chunks_tenant_created ON doc_chunks (tenant_id, created_at DESC);

-- GIN: jsonb containment, such as metadata @> '{"lang":"en"}'
CREATE INDEX ix_chunks_metadata ON doc_chunks USING gin (metadata);

-- HNSW: approximate nearest neighbour search with cosine distance
CREATE INDEX ix_chunks_embedding ON doc_chunks USING hnsw (embedding vector_cosine_ops);
```

| Index | Good for | Not good for |
| --- | --- | --- |
| **B-tree** (default) | `=`, `<`, `BETWEEN`, `ORDER BY` on normal columns | jsonb contents, vectors |
| **GIN** | jsonb `@>`, arrays, full-text `tsvector` | Range queries |
| **HNSW** | Vector search, best speed versus recall; can be built on an empty table | Very large builds on small memory |
| **IVFFlat** | Vector search with faster builds and less memory | Building before data is loaded (it learns clusters from the rows) |

The vector index has to match the operator your query uses. pgvector has three main ones:

| Operator | Distance | Operator class |
| --- | --- | --- |
| `<->` | Euclidean (L2) | `vector_l2_ops` |
| `<=>` | Cosine distance | `vector_cosine_ops` |
| `<#>` | Negative inner product | `vector_ip_ops` |

An index built with `vector_cosine_ops` speeds up `ORDER BY embedding <=> $1`, and is ignored by `ORDER BY embedding <-> $1`.

### Step 4: prove it with EXPLAIN ANALYZE

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, content
FROM doc_chunks
ORDER BY embedding <=> '[0.012, -0.031, ...]'
LIMIT 5;
```

Before the HNSW index, the plan shows `Seq Scan on doc_chunks` under a `Sort`, and the real time grows with every row. After it, you should see `Index Scan using ix_chunks_embedding`. If you still see a Seq Scan, check the operator class, check that `LIMIT` is there (the index is used for "top K" queries), and run `ANALYZE doc_chunks` so the planner has fresh statistics. On a huge table where `ANALYZE` itself would take too long, run `EXPLAIN` without `ANALYZE` to see the plan instantly.

<Callout type="exam">
The exam likes the order of operations: **azure.extensions** allow-list first, then **CREATE EXTENSION vector**. It also tests matching: **GIN** for jsonb, **B-tree** for equality and ranges, **HNSW/IVFFlat** for vectors, and the operator class that matches the operator (**vector_cosine_ops** with `<=>`). "How do you confirm the index is used?" is **EXPLAIN ANALYZE**.
</Callout>

<DeepDive title="Cutting pgvector compute and storage">

Every 1536-dimension `vector` is about 6 KB. Two million chunks is 12 GB before indexes, and an HNSW index adds more. A few levers help. Ask the embedding model for fewer dimensions if your tests show recall holds up. Switch to `halfvec`, which halves the bytes, and you can even keep `vector` in the table and index an expression cast to `halfvec`. Use a **partial index** (`WHERE tenant_id = 'bigcustomer'`) when one slice gets most of the searches, remembering that the query's `WHERE` must match the index's `WHERE` exactly for the planner to use it. And partition very large tables by tenant or date so searches touch fewer rows.

</DeepDive>
