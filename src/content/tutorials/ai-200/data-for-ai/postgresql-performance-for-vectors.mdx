## Start with a question

<Story question="The vector search was fast in testing. Why is it slow now that real users have arrived?">

Think of a busy railway ticket counter. In testing there was one clerk and three customers. On launch day there are 500 people in the queue, every one of them wants a new form printed from scratch, and the clerk's desk is too small to keep the timetable open.

That's what happens to an untuned database. Too little **memory** to keep the vector index handy, a **compute tier** that runs out of CPU credits, and an app that opens a brand-new **connection** for every request. Each of these has a specific fix.

</Story>

## Explain it like I'm 10

<Eli10>

Your database is a librarian. The vector index is a big map of where every book is.

If the map fits on the librarian's desk (memory), finding books is quick. If it's in the basement (disk), every search means a trip downstairs.

Building the map takes a big table too, so you give the librarian extra table space while building it.

And instead of every visitor ringing the bell and waiting for the door to open, a doorman (the pool) keeps a few doors open all the time.

## The technical explanation

### 1. Pick the compute tier

| Tier | What it's for | Vector workloads |
| --- | --- | --- |
| **Burstable** | Dev, test, low steady use; runs on CPU credits | Fine for trying pgvector. Long index builds and steady search burn credits. No built-in PgBouncer, no Premium SSD v2 |
| **General Purpose** | Most production apps, balanced CPU and memory | A good default for moderate vector search |
| **Memory Optimized** | More RAM per vCore | Large HNSW indexes that must stay in memory |

The rule of thumb: HNSW is fast when the index lives in memory (`shared_buffers` plus the OS cache). Check its size with `SELECT pg_size_pretty(pg_relation_size('ix_chunks_embedding'));`. If it's bigger than the RAM you can spare, searches hit disk and latency jumps. Moving to Memory Optimized or a larger size is often the real fix, and you can scale compute up or down after creation (with a short restart).

### 2. Size storage and IOPS

Loading millions of embeddings and building indexes is heavy on disk. **Premium SSD v2** lets you set capacity, IOPS and throughput separately. A disk under 400 GiB gets a baseline of 3,000 IOPS and 125 MB/s at no extra cost, and you can raise IOPS (up to 80,000 on large enough disks) for a busy load day, then lower it again. The VM size also caps IOPS, so a 2-vCore server can't use all of an 80,000 IOPS disk. Premium SSD v2 works with General Purpose and Memory Optimized, not Burstable.

### 3. Build indexes the smart way

The Microsoft docs put it simply: load your data first, then build the index. It's faster and the result is better laid out.

```sql
-- in the session that builds the index
SET maintenance_work_mem = '4GB';            -- let the HNSW graph fit in memory
SET max_parallel_maintenance_workers = 7;    -- parallel build

CREATE INDEX CONCURRENTLY ix_chunks_embedding
  ON doc_chunks USING hnsw (embedding vector_cosine_ops)
  WITH (m = 16, ef_construction = 64);

-- watch progress from another session
SELECT phase, round(100.0 * blocks_done / nullif(blocks_total, 0), 1) AS pct
FROM pg_stat_progress_create_index;
```

`CONCURRENTLY` lets reads and writes continue during the build, at the cost of a slower build. Keep `maintenance_work_mem` within what the server can spare: setting it higher than free memory causes trouble.

| | **HNSW** | **IVFFlat** |
| --- | --- | --- |
| How it works | Layered graph of neighbours | k-means clusters ("lists") |
| Build options | `m` (default 16), `ef_construction` (default 64) | `lists`: start with rows/1000 up to 1M rows, sqrt(rows) above |
| Query knob | `hnsw.ef_search` (default 40) | `ivfflat.probes` (default 1): start near lists/10 |
| Build on empty table | Yes | No. Load data first, or clusters are meaningless |
| Speed vs recall | Better | Lower, but faster to build and smaller |
| Memory | More | Less |

Higher `m` and `ef_construction` give better recall and a bigger, slower-to-build index. Most apps keep the defaults and tune `hnsw.ef_search` per query instead. If you set `ivfflat.probes` equal to `lists`, you're searching everything and the planner skips the index. Flexible server also offers a **DiskANN** index through the `pg_diskann` extension for very large datasets.

### 4. Cut connection overhead

Every new PostgreSQL connection means a TLS handshake, sign-in and a new server process. Two layers of pooling fix it.

**In the app: psycopg_pool.** Each app instance keeps a few connections open and lends them out:

```python
from psycopg_pool import ConnectionPool

pool = ConnectionPool(
    conninfo="host=contoso-pg.postgres.database.azure.com port=6432 dbname=support user=rag-api sslmode=require",
    connection_class=EntraConnection,   # fetches a fresh Entra token per new connection
    min_size=2, max_size=10,
    max_lifetime=3000,                  # recycle connections before tokens and servers get stale
)

def search(q, tenant):
    with pool.connection() as conn:
        return conn.execute(RETRIEVE_SQL, {"q": q, "tenant": tenant}).fetchall()
```

**On the server: built-in PgBouncer.** When 30 container replicas each hold 10 connections, that's 300 PostgreSQL processes. PgBouncer sits on the server, accepts up to thousands of client connections on **port 6432** and shares a small pool of real connections. Turn it on with the **pgbouncer.enabled** server parameter (no restart needed); then `pgbouncer.pool_mode` (default `transaction`), `pgbouncer.default_pool_size` and `pgbouncer.max_client_conn` appear. Your app only changes its port from 5432 to 6432. In transaction mode, session state such as `SET` (without `LOCAL`) doesn't stick between transactions, so use `SET LOCAL hnsw.ef_search` inside a transaction. If you hit prepared statement errors, set psycopg's `prepare_threshold=None` or keep PgBouncer's `max_prepared_statements` tracking on.

<Callout type="exam">
Map the symptom to the fix. **CPU credits run out** = leave **Burstable**. **Index doesn't fit in memory** = **Memory Optimized** or more RAM. **Slow index build** = load first, raise **maintenance_work_mem**. **IOPS bottleneck** = **Premium SSD v2** with higher IOPS. **Too many connections or slow connects** = **psycopg_pool** plus **PgBouncer on 6432**. Recall versus speed at query time = **hnsw.ef_search** or **ivfflat.probes**.
</Callout>

<DeepDive title="Exact search can be fine, and parallel workers help">

Without an index pgvector does an exact search, with perfect recall. For a table of 50,000 chunks per tenant that might be quick enough, especially if `max_parallel_workers_per_gather` lets PostgreSQL scan in parallel (look for `Workers Launched` in `EXPLAIN ANALYZE`). Approximate indexes earn their cost once tables reach hundreds of thousands of rows or latency targets get tight. Start with `EXPLAIN (ANALYZE, BUFFERS)`: `shared hit` means pages came from memory, `read` means disk. A plan full of reads is your hint that memory, not CPU, is the problem.

</DeepDive>
