## The technical explanation

### What Azure Managed Redis is

Azure Managed Redis is built on **Redis Enterprise** and runs your data in memory. Four tiers:

| Tier | Memory to vCPU | Good for |
| --- | --- | --- |
| **Memory Optimized** | 8:1 | Lots of data, lower throughput, dev and test |
| **Balanced** | 4:1 | Most workloads |
| **Compute Optimized** | 2:1 | The highest throughput |
| **Flash Optimized** | RAM plus NVMe | Very large datasets where cold keys can live on disk |

Clients connect on **port 10000** over **TLS** (the older Azure Cache for Redis used 6380). New caches have **access keys disabled** by default, and Microsoft recommends **Microsoft Entra ID** with a managed identity.

### Connecting from Python

```python
# pip install redis redis-entraid azure-identity
import redis
from redis_entraid.cred_provider import create_from_default_azure_credential

credential_provider = create_from_default_azure_credential(
    ("https://redis.azure.com/.default",),
)

r = redis.Redis(
    host="contoso-cache.westeurope.redis.azure.net",
    port=10000,
    ssl=True,
    decode_responses=True,
    credential_provider=credential_provider,   # refreshes the Entra token for you
)
r.ping()
```

Before this works, add your user or the app's managed identity as a Redis user on the cache (the **Authentication** page in the portal). With Entra ID, the Redis user name is the identity's object ID and the token is the password; redis-entraid handles both and re-authenticates before the token expires. If you've enabled access keys instead, pass `password=<key>` and keep that key in Key Vault.

### The core commands

```text
SET product:42 "{...json...}" EX 300    # store for 300 seconds
GET product:42                          # read it (nil after it expires)
TTL product:42                          # seconds left; -1 = no expiry, -2 = key doesn't exist
EXPIRE product:42 60                    # change the TTL on an existing key
DEL product:42                          # remove it now (invalidation)
```

### Cache-aside in code

```python
import json

def get_product(product_id: int) -> dict:
    key = f"product:{product_id}"
    cached = r.get(key)
    if cached:                                   # hit
        return json.loads(cached)
    row = db_get_product(product_id)             # miss: go to PostgreSQL or Cosmos DB
    r.set(key, json.dumps(row), ex=300)          # cache it for 5 minutes
    return row

def update_price(product_id: int, price: float) -> None:
    db_update_price(product_id, price)           # 1. write the source of truth
    r.delete(f"product:{product_id}")            # 2. invalidate, so the next read is fresh
```

The same pattern works for AI calls: cache an embedding by a hash of its input text, or a model answer by a hash of the exact prompt. That saves tokens and latency on repeats. When "repeat" should mean "same meaning" rather than "same text", you need a semantic cache, covered in the Redis vector search lesson.

### Choosing TTLs and handling invalidation

- Delete the key **after** the database commit. Deleting first leaves a gap where another request can reload the old value.
- Prefer **delete** over writing the new value into the cache on update. The next read rebuilds it, and you avoid two writers racing.
- Add a little random jitter to TTLs (300 ± 30 seconds) so thousands of keys don't expire in the same second and hit the database together.
- Short TTLs for prices and stock, longer ones for product descriptions and embeddings, which rarely change.

### When memory fills up: eviction policies

| Policy | What Redis removes when memory is full |
| --- | --- |
| `volatile-lru` | Least recently used keys **that have a TTL** |
| `allkeys-lru` | Least recently used keys, TTL or not |
| `volatile-lfu` / `allkeys-lfu` | Least frequently used keys |
| `volatile-ttl` | Keys with the shortest time left |
| `noeviction` | Nothing. Writes fail with an out-of-memory error |

For a pure cache, `allkeys-lru` or `volatile-lru` (with TTLs on everything) are the usual choices. `noeviction` suits data you can't afford to lose silently. Watch the **used memory** and **evicted keys** metrics in Azure Monitor.

<DeepDive title="Clustering policy and multi-key commands">

Every Azure Managed Redis instance is sharded internally. The **clustering policy** decides how clients see that. **OSS** exposes the Redis Cluster API for the best throughput, and your client must support cluster mode. **Enterprise** gives one endpoint that proxies to the right shard, so any client works. **Non-clustered** is for caches up to 25 GB. You pick the policy when you create the cache, and OSS or Enterprise can't be changed afterwards. Multi-key commands across shards can raise `CROSSSLOT` errors; with Enterprise, `DEL`, `MGET`, `MSET`, `EXISTS`, `UNLINK` and `TOUCH` work across slots, and with OSS all keys must share a hash slot (use hash tags like `{product:42}:price`).

</DeepDive>
