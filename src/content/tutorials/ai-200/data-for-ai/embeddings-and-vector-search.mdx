A keyword search looks for the words "money" and "back". Your refund policy doesn't contain either, so it comes back empty, and the customer opens a support ticket.

A good shop assistant wouldn't miss this. ## The technical explanation

An **embedding model** reads text and returns a fixed-length array of floating-point numbers. With **text-embedding-3-small** you get **1,536** numbers by default; **text-embedding-3-large** gives **3,072**. Both let you ask for fewer dimensions with the `dimensions` parameter, which saves storage at a small cost in quality. Whatever you choose, every vector in one index must have the same length.

### Create an embedding in Python

You call the embedding deployment in your Foundry project the same way you'd call a chat model, just with `embeddings.create`:

```python
import os
from azure.identity import DefaultAzureCredential
from azure.ai.projects import AIProjectClient

project = AIProjectClient(
    endpoint=os.environ["FOUNDRY_PROJECT_ENDPOINT"],
    credential=DefaultAzureCredential(),
)
openai = project.get_openai_client()

def embed(text: str) -> list[float]:
    result = openai.embeddings.create(
        model="text-embedding-3-small",  # your DEPLOYMENT name
        input=text,
    )
    return result.data[0].embedding     # a list of 1,536 floats

vector = embed("How do I get my money back?")
print(len(vector))  # 1536
```

`input` can also be a list of strings, which embeds a batch in one call. That's much cheaper on round trips when you're loading thousands of documents.

### How "close" is measured

The database compares the query vector with stored vectors using a **distance function**:

| Function | Range | Closest means | Notes |
| --- | --- | --- | --- |
| **Cosine** | -1 to 1 | Highest value | The usual default for text. Looks at direction, not length. |
| **Dot product** | -inf to +inf | Highest value | Same ranking as cosine when vectors are normalised (OpenAI embeddings are). |
| **Euclidean** | 0 to +inf | Lowest value | Straight-line distance. |

Pick the function your embedding model was trained for. For OpenAI text embeddings, cosine is the safe choice.

### Exact versus approximate search

With no index, the database compares the question with **every** stored vector. That's exact **k-nearest neighbours (kNN)**: 100% recall, but the cost grows with every row you add. With a million vectors of 1,536 dimensions, that's a lot of maths per question.

An **approximate nearest neighbour (ANN)** index builds a structure, usually a graph, that lets the search jump towards the right neighbourhood and check only a small slice of the data. You lose a little **recall** (you might miss one of the true top 10) and gain a big drop in latency and cost.

| Store on Azure | Exact option | ANN index options |
| --- | --- | --- |
| Cosmos DB for NoSQL | `flat` (up to 505 dimensions), `quantizedFlat` (compressed) | `diskANN` |
| PostgreSQL + pgvector | No index (sequential scan) | `hnsw`, `ivfflat`, and DiskANN through the `pg_diskann` extension |
| Azure Managed Redis | `FLAT` | `HNSW` |

### Chunking matters more than people expect

If you embed a 40-page manual as one vector, the numbers become an average of everything in it, and nothing matches well. Split it into passages of a few hundred tokens, often with a small overlap so sentences aren't cut in half, and store each chunk with metadata such as `docId`, `page` and `tenantId`. Then a search returns the exact paragraph, and filters keep one customer's data away from another's.

<Callout type="exam">
Watch for these traps. **Same model, same dimensions** for documents and questions, every time. The vector length in the database's policy or column type (`dimensions: 1536`, `vector(1536)`) must match the model. **Cosine** is the normal choice for text. If a question says "millions of vectors, low latency, a small loss of accuracy is acceptable", the answer is an **ANN index** (DiskANN, HNSW). If it says "must always return the exact closest items", it's a **flat / exact** search.
</Callout>

<DeepDive title="Where RAG fits">

Retrieval-augmented generation is vector search plus a chat model. You embed the user's question, fetch the top few chunks (with filters such as tenant or language), and put those chunks in the prompt as context. The model answers from your data instead of guessing. The quality of a RAG app depends mostly on the retrieval step: good chunks, the right filters and a sensible `k`. A bigger chat model won't fix chunks that are wrong.

Many apps also add **hybrid search**, which combines a vector score with a keyword (full-text) score. That helps with exact terms the embedding model may blur, like product codes or error numbers.

</DeepDive>
