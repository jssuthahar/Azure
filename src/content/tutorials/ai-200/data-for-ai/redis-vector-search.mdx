## Start with a question

<Story question="Two customers ask 'How do I reset my password?' and 'I forgot my password, what now?'. Should your app pay the model twice?">

A normal cache only helps if the question is typed exactly the same way. People don't do that. A good receptionist hears both questions and knows they mean the same thing, so she hands over the same printed sheet.

**Vector search in Azure Managed Redis** gives your app that skill. Each question becomes an **embedding**, Redis finds the stored question with the closest meaning in about a millisecond, and if it's close enough you reuse the saved answer. That's a **semantic cache**, and the same index can power fast retrieval for RAG too.

</Story>

## Explain it like I'm 10

<Eli10>

Every question gets turned into a dot on a giant map. Questions that mean the same thing land near each other.

When a new question comes in, you put its dot on the map and look for the nearest dot you've already answered.

If it's really close, you give the same answer. If it's far away, you ask the teacher and save the new answer for next time.

</Eli10>

## The technical explanation

### Step 1: create the cache with RediSearch

Vector search lives in the **RediSearch** module. On the **Advanced** tab when you create the cache:

- With **Redis 7.4** (the default version), tick **RediSearch** under modules. You can't add or change modules after creation. With Redis 8.2 (preview) on the in-memory tiers, all modules are already included.
- Choose the **Enterprise** or **Non-clustered** clustering policy. RediSearch doesn't support the **OSS** clustering policy, and you can't switch from OSS or Enterprise later.

Get this wrong and the only fix is a new cache, so it's a favourite exam trap.

### Step 2: store embeddings as bytes

Each document or cached prompt is a **hash** with normal fields plus the embedding as raw **FLOAT32** bytes:

```python
import numpy as np

def to_bytes(vec) -> bytes:
    return np.asarray(vec, dtype=np.float32).tobytes()   # 1536 x 4 bytes

r.hset("doc:1001", mapping={
    "content": "To reset your password, open Settings > Security...",
    "tenant": "contoso",
    "embedding": to_bytes(embed("To reset your password, open Settings > Security...")),
})
```

For this, create the Redis client with `decode_responses=False`, because the embedding is binary.

### Step 3: create the vector index

```text
FT.CREATE idx:docs ON HASH PREFIX 1 doc:
  SCHEMA
    content   TEXT
    tenant    TAG
    embedding VECTOR HNSW 6 TYPE FLOAT32 DIM 1536 DISTANCE_METRIC COSINE
```

- `ON HASH PREFIX 1 doc:` indexes every hash whose key starts with `doc:`, including ones you add later.
- `HNSW 6` means six attribute arguments follow (three name-value pairs).
- `DIM` must match your embedding model exactly. `DISTANCE_METRIC` can be `COSINE`, `L2` or `IP`.
- `TAG` fields such as `tenant` give you exact-match filters.

| Algorithm | How it searches | Use it when |
| --- | --- | --- |
| **FLAT** | Compares against every vector (exact) | Small sets, up to tens of thousands, or when you need perfect recall |
| **HNSW** | Walks a graph (approximate), tuned with `M`, `EF_CONSTRUCTION`, `EF_RUNTIME` | Larger sets where speed matters more than the last bit of recall |

### Step 4: query with KNN

```text
FT.SEARCH idx:docs "(@tenant:{contoso})=>[KNN 3 @embedding $vec AS score]"
  PARAMS 2 vec <1536 float32 bytes>
  SORTBY score
  RETURN 2 content score
  DIALECT 2
```

In Python:

```python
from redis.commands.search.query import Query

q = (
    Query("(@tenant:{contoso})=>[KNN 3 @embedding $vec AS score]")
    .sort_by("score")
    .return_fields("content", "score")
    .dialect(2)
)
results = r.ft("idx:docs").search(q, query_params={"vec": to_bytes(embed(question))})
for doc in results.docs:
    print(doc.score, doc.content)
```

The part before `=>` is a **pre-filter** (here, only this tenant's docs; `*` means all). `score` is the **cosine distance**, so lower means closer. **DIALECT 2** is required for this KNN-with-parameters syntax.

### A semantic cache in a few lines

```python
THRESHOLD = 0.10   # cosine distance; tune it on real questions

def answer(question: str, tenant: str) -> str:
    vec = to_bytes(embed(question))
    q = (Query(f"(@tenant:{{{tenant}}})=>[KNN 1 @embedding $vec AS score]")
         .return_fields("response", "score").dialect(2))
    hits = r.ft("idx:cache").search(q, query_params={"vec": vec}).docs
    if hits and float(hits[0].score) < THRESHOLD:
        return hits[0].response                          # semantic hit
    text = call_model(question)                          # miss
    key = f"cache:{tenant}:{uuid4()}"
    r.hset(key, mapping={"prompt": question, "response": text, "tenant": tenant, "embedding": vec})
    r.expire(key, 86400)                                 # cached answers age out after a day
    return text
```

Microsoft's tutorial shows the same idea with **RedisVL**'s `SemanticCache` class, and Azure API Management can do it at the gateway with the `llm-semantic-cache-lookup` and `llm-semantic-cache-store` policies backed by Azure Managed Redis. Semantic caching is a pattern you build, not a switch on the cache.

<Callout type="exam">
Look for these clues. "Add vector search to Azure Managed Redis" means **RediSearch**, selected **when the cache is created**, with **Enterprise** (or Non-clustered) clustering, never **OSS**. The index definition is **FT.CREATE ... VECTOR HNSW|FLAT ... TYPE FLOAT32 DIM n DISTANCE_METRIC COSINE**. The query is **FT.SEARCH** with **KNN k** and **DIALECT 2**. "Reuse answers for questions with the same meaning" is a **semantic cache**.
</Callout>

<DeepDive title="Tuning a semantic cache so it doesn't hand out wrong answers">

The threshold is the hard part. Too loose, and "cancel my order" gets the cached answer for "cancel my subscription". Too strict, and you never hit. Start strict, log every hit with its distance, and loosen slowly. Partition the cache with TAG filters by tenant, user (for personal data), model deployment and prompt version, so a new system prompt doesn't serve answers written under the old one. Give entries a TTL so facts like prices don't live forever, and skip caching for prompts that include personal details or time-sensitive data.

</DeepDive>
