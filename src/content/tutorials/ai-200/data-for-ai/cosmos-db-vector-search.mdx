## Start with a question

<Story question="Your product catalogue already lives in Cosmos DB. Do you need a separate vector database for semantic search?">

Imagine a shop that keeps its stock in one storeroom and its "items customers liked together" list in a different building across town. Every time stock changes, someone has to drive over and update the list. Sooner or later they get out of sync.

**Azure Cosmos DB for NoSQL** lets you keep the vector in the same item as the product. You tell the container where the vector is with a **vector embedding policy**, give it a **vector index**, and ask for the closest items with **VectorDistance**. No second database, no sync job.

</Story>

## The technical explanation

You don't need to enable a feature on the account. You define two things **when you create the container**: a vector embedding policy and the vector indexes.

### 1. The vector embedding policy

```python
vector_embedding_policy = {
    "vectorEmbeddings": [
        {
            "path": "/embedding",
            "dataType": "float32",
            "dimensions": 1536,          # text-embedding-3-small
            "distanceFunction": "cosine",
        }
    ]
}
```

| Setting | Allowed values |
| --- | --- |
| `path` | The property that holds the vector. No wildcards, and not nested inside an array. |
| `dataType` | `float32` (default), `float16`, `int8`, `uint8`. `float16` halves storage with a small accuracy cost. |
| `dimensions` | Length of every vector at that path. Default 1536. |
| `distanceFunction` | `cosine` (default, -1 to 1, higher is closer), `dotproduct`, `euclidean` (lower is closer). |

You can have several vector paths, for example one for text and one for images, each with its own entry.

### 2. The vector index

```python
indexing_policy = {
    "indexingMode": "consistent",
    "includedPaths": [{"path": "/*"}],
    "excludedPaths": [
        {"path": "/\"_etag\"/?"},
        {"path": "/embedding/*"},      # keep the range index off the vector
    ],
    "vectorIndexes": [
        {"path": "/embedding", "type": "diskANN"}
    ],
}
```

| Index type | How it searches | Max dimensions | Good for |
| --- | --- | --- | --- |
| `flat` | Exact, brute force, 100% recall | 505 | Small vectors where exact results matter |
| `quantizedFlat` | Brute force over compressed vectors | 4,096 | Up to about 50,000 vectors in scope, or searches narrowed by filters |
| `diskANN` | Approximate nearest neighbour graph | 4,096 | Large sets, lowest latency and RU cost |

`quantizedFlat` and `diskANN` need at least **1,000 vectors** before they're used. With fewer, Cosmos DB does a full scan, which works but costs more RUs.

### 3. Create the container and store items

```python
from azure.cosmos import PartitionKey

container = database.create_container_if_not_exists(
    id="faq",
    partition_key=PartitionKey(path="/tenantId"),
    indexing_policy=indexing_policy,
    vector_embedding_policy=vector_embedding_policy,
)

question = "How do I get my money back?"
container.upsert_item({
    "id": "faq-17",
    "tenantId": "contoso",
    "question": question,
    "answer": "Refunds go back to the original card within 5 to 7 working days.",
    "embedding": embed(question),    # 1,536 floats from text-embedding-3-small
})
```

`embed()` is the helper that calls your embedding deployment (see the embeddings lesson). Use the same model and dimensions for stored items and for questions.

### 4. Search with VectorDistance

```python
query_vector = embed("I want a refund")

results = container.query_items(
    query="""
      SELECT TOP 3 c.id, c.question, c.answer,
             VectorDistance(c.embedding, @q) AS score
      FROM c
      WHERE c.tenantId = @tenant
      ORDER BY VectorDistance(c.embedding, @q)
    """,
    parameters=[
        {"name": "@q", "value": query_vector},
        {"name": "@tenant", "value": "contoso"},
    ],
    partition_key="contoso",
)
for r in results:
    print(round(r["score"], 3), r["question"])
```

`ORDER BY VectorDistance(...)` already sorts the most similar items first, whatever the distance function, so you don't add `DESC`. Always include **TOP N**: without it the query tries to return far more results than you need and costs more RUs.

`VectorDistance` also takes optional arguments: a third, boolean argument forces a brute-force search, and a fourth, JSON options argument can override the `distanceFunction` or `dataType` and set `searchListSizeMultiplier`, which raises diskANN's recall for more RUs.

<Callout type="exam">
Learn the three index types and their limits: **flat** is exact and stops at **505** dimensions, **quantizedFlat** and **diskANN** go to **4,096**, and diskANN is the approximate one for big data sets. The vector policy fields are **path, dataType, dimensions, distanceFunction**. The query shape is `SELECT TOP n ... ORDER BY VectorDistance(c.path, @vector)`. If a question puts the vector path in `excludedPaths` as well as `vectorIndexes`, that's correct, not a mistake.
</Callout>

<DeepDive title="Limits and design choices worth knowing">

- **Plan the policy up front.** You can add or remove vector paths, but you can't change an existing path's dimensions or distance function in place. You'd drop the vector index and policy and add them back. Changing embedding models usually means re-embedding into a new path or container.
- **No turning back.** Once vector indexing and search are on for a container, you can't disable them.
- **Shared throughput databases** don't support vector indexing and search; give the container its own throughput.
- **Approximate means approximate.** diskANN results can vary slightly between runs, because each replica builds its own index. Use `flat` (where dimensions allow) when you need exact results.
- **Hybrid search.** With a full-text policy and index you can rank by both meaning and keywords: `ORDER BY RANK RRF(VectorDistance(c.embedding, @q), FullTextScore(c.answer, "refund"))`. Reciprocal rank fusion merges the two rankings.
- **Keep vectors fresh.** When an item's text changes, its vector is stale. A change feed consumer can re-embed changed items automatically (next lesson).

</DeepDive>
