    q: How would you configure elasticity for a web app on Azure App Service?
    a: >-
      Enable autoscale on the App Service plan with a minimum and maximum instance count, a scale-out rule (for example CPU above 70% for 10 minutes, add 2 instances), a matching scale-in rule (CPU below 30%, remove 1), and cool-down periods. Optionally add schedule-based profiles for known peaks, or use automatic scaling, which scales on HTTP traffic.

  - level: experienced
    q: What can go wrong with autoscale in production?
    a: >-
      Flapping, where rules that are too sensitive or have no cool-down scale out and in repeatedly. Slow start-up, where new instances take minutes to warm up, so the peak passes first (use pre-warming, minimum instances or scheduled scale-out). Missing scale-in rules, so costs never come down. Scaling on the wrong metric, such as CPU when the real bottleneck is a queue length or database. And downstream overload, where scaling out the front end overwhelms a database that cannot scale as fast. You also need quota headroom in the region.

## Start with a question

<Story question="Results are published at 10:00. At 9:59 there are 300 visitors. At 10:01 there are 300,000. Who adds the servers?">

No human can react that fast. If someone has to notice the slowdown, log in and add servers, the site will already be down when they finish.

The cloud's answer is **elasticity**: the system watches demand and stretches itself automatically, then shrinks back when the crowd leaves.

</Story>

## Explain it like I'm 10

<Eli10>

Think of a **rubber band** around a stack of cards. Add more cards and the band **stretches** to hold them. Take cards away and it **shrinks back** on its own. You never have to adjust it.

Elastic cloud systems are like that rubber band. **More users? They stretch. Fewer users? They shrink.** Nobody has to push a button.

</Eli10>

## The technical explanation

**Elasticity** is the ability to **automatically** and **rapidly** provision and release resources so that capacity matches demand at any moment. It builds on scalability. Scalability says *you can* add resources; elasticity says *the system does it for you*, in real time.

<DemandChart initial="elastic" caption="Compare all three strategies. Elastic capacity follows demand closely: little waste and almost no users turned away." />

### Scalability vs elasticity

| | Scalability | Elasticity |
| --- | --- | --- |
| What it is | Ability to change resources to meet demand | Automatic, real-time adjustment of resources |
| Trigger | Manual or planned (often) | Metrics or events (CPU, queue length, HTTP requests) |
| Speed | Minutes to days | Seconds to minutes |
| Typical tool | Resize a VM, add instances | Autoscale rules, serverless platforms |

Services with built-in elasticity include **Virtual Machine Scale Sets**, **App Service** autoscale, **Azure Functions** and **Azure Container Apps** (event-driven, including scale to zero), and **AKS** (horizontal pod autoscaler and cluster autoscaler).

<Callout type="exam">
"Scalability vs elasticity" is one of the most frequently confused pairs in AZ-900. Remember: **elasticity = automatic scalability based on demand.**
</Callout>

<DeepDive title="Writing autoscale rules that behave">

- Always pair **scale-out** and **scale-in** rules, with a gap between thresholds (70% out, 30% in) to avoid oscillation.
- Set realistic **minimums** (for availability, at least 2) and **maximums** (to cap cost and protect downstream systems).
- Scale on the metric that reflects user pain. For workers, **queue length** usually beats CPU.
- Use **scheduled profiles** for known events and let metric rules handle surprises.
- Keep start-up time short. Elasticity is only as fast as your instances become healthy.

</DeepDive>

## When to use it and when not to
