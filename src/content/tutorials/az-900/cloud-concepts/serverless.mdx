## Start with a question

<Story question="Why pay for a security guard to stand at the door all night if visitors only arrive twice a day?">

A web server on a VM is like a guard on a 24-hour shift. It is paid every hour, whether ten people arrive or none.

Now imagine a **doorbell**: nothing happens until someone presses it, then help appears instantly. **Serverless computing works like a doorbell.** Your code sleeps until an event happens, wakes up, does its job, and you pay for that moment.

</Story>

## Explain it like I'm 10

<Eli10>

Think about the **automatic lights** in a school corridor. They switch on only when someone walks past and switch off when the corridor is empty. Nobody has to remember to flip a switch, and the school does not pay for lights in an empty hallway.

Serverless is automatic lights for computer programs. **The program runs only when something happens**, and nobody has to look after the computer it runs on.

</Eli10>

## The technical explanation

**Serverless computing** is a cloud execution model in which the provider **dynamically allocates resources on demand**, so developers do not provision, scale or maintain servers. It has three defining traits:

1. **No infrastructure management**: no VMs, no OS patching, no capacity planning.
2. **Event-driven scaling**: instances are created automatically as events arrive, from zero to many, and removed when idle.
3. **Consumption-based billing**: on consumption-style plans you pay per execution and for resources used while code runs, not for idle time.

### Serverless on Azure

| Service | Best for |
| --- | --- |
| **Azure Functions** | Small units of code triggered by events (HTTP, timers, queues, blobs, databases) |
| **Azure Logic Apps** | Low-code workflows that connect services with hundreds of built-in connectors |
| **Azure Container Apps** | Containers that scale on events, including to zero, without managing Kubernetes |

<Callout type="exam">
Serverless is **not** a fourth service type that replaces IaaS, PaaS and SaaS. It is an execution model, and Azure Functions is generally described as both **PaaS** and **serverless**. On AZ-900, link serverless with **event-driven**, **no infrastructure management** and **pay only when code runs**.
</Callout>

<DeepDive title="Serverless in production: hosting plans and patterns">

Azure Functions can be hosted on several plans with different trade-offs:

- **Flex Consumption**: event-driven scale-out, scale to zero, optional always-ready instances, and virtual network integration. This is Microsoft's recommended serverless plan for new apps.
- **Consumption** (legacy): pure pay-per-execution with cold starts and a shorter maximum run time.
- **Premium**: pre-warmed instances (no cold starts), VNet support, longer run times.
- **Dedicated (App Service plan)**: runs on always-on instances you already pay for.

Patterns that work well include fan-out/fan-in and long-running orchestrations with **Durable Functions**, queue-based load levelling to protect databases, and scheduled jobs replacing VM cron tasks. Watch out for unbounded scale-out hammering downstream systems (set maximum instance counts), and invest early in distributed tracing with Application Insights.

</DeepDive>

## When to use it and when not to

<UseWhen
  use={[
    'Event-driven tasks such as file processing, notifications, webhooks and IoT messages.',
    'Spiky or unpredictable workloads with idle periods.',
    'Scheduled jobs (timer triggers) and glue code between services.',
    'Rapid prototyping, where you pay almost nothing until there is traffic.',
  ]}
  avoid={[
    'Long-running, CPU-heavy jobs that exceed plan time limits.',
    'Steady, high-volume traffic. An always-on service may be cheaper and more predictable.',
    'Latency-critical endpoints that cannot tolerate cold starts on consumption plans.',

    '**Azure App Service** for always-on web apps and APIs.',
