  - level: beginner
    q: What is a hybrid cloud?
    a: >-
      It's a mix of public cloud and private or on-premises infrastructure that work together. For example, a company keeps its customer database in its own datacenter but runs its website in Azure, and the two are securely connected.
    followUps:
      - q: How are they connected?
        a: >-
          Usually with a site-to-site VPN over the internet (Azure VPN Gateway) or a private dedicated connection (Azure ExpressRoute). Identity is often unified too, with Microsoft Entra ID synchronised from on-premises Active Directory.
  - level: intermediate
    q: What is the difference between hybrid cloud and multi-cloud?
    a: >-
      Hybrid is about combining on-premises or private infrastructure with public cloud. Multi-cloud is about using more than one public cloud provider. An organisation can be both, with on-premises servers plus Azure and AWS.
    followUps: []
  - level: experienced
    q: What is the biggest operational challenge of hybrid and multi-cloud, and how do you address it?
    a: >-
      Fragmentation. Different consoles, policies, identity systems, monitoring and skill sets for each environment, which leads to inconsistent security. I would standardise identity on one provider, use a single control plane where possible (Azure Arc to project on-premises and other-cloud servers and Kubernetes into Azure, then apply Azure Policy, Defender for Cloud and Azure Monitor consistently), and use infrastructure as code with tools such as Terraform for multi-cloud deployments. Also be deliberate. Multi-cloud for its own sake doubles complexity.
    followUps:
      - q: Is multi-cloud a good way to avoid vendor lock-in?
        a: >-
          Sometimes, but it has a price. To be truly portable you limit yourself to the lowest common denominator and give up many managed services. A pragmatic approach is to pick a primary cloud, use its managed services, and design for portability only where the business risk justifies it.
  - level: scenario
    q: A retailer's on-premises order system copes fine except during Black Friday. What hybrid pattern could help?
    a: >-
      Cloud bursting. The order system keeps running on-premises normally, and during the peak extra application instances run in Azure, connected back to on-premises over VPN or ExpressRoute. They pay for the cloud capacity only during the peak.

## Start with a question

<Story question="What if a hospital must keep patient records in its own building, but wants to use cloud AI to analyse scans?">

It doesn't have to pick one world. It can keep the records system at home and still use the cloud for the parts that benefit from it, connected safely.

That "best of both worlds" approach is **hybrid cloud**, and it's how most large organisations actually run today.

</Story>

## Explain it like I'm 10

<Eli10>

Imagine you have a bookshelf at home with your favourite books, the ones you never want to lend to anyone. But when you need a book you don't own, you go to the **public library**.

You use **both**: your home shelf for the special books, the library for everything else. A **library card** connects them, because you can borrow and bring books home.

A hybrid cloud is your home shelf (on-premises) plus the library (public cloud), with a secure connection in between.

## The technical explanation

**Hybrid cloud** is a computing environment that combines a **public cloud** with a **private cloud or on-premises infrastructure**, allowing data and applications to be shared between them. The organisation decides, workload by workload, where each piece runs.

**Multi-cloud** means using **two or more public cloud providers**, for example Azure for applications and another provider for a specific analytics tool. It often happens through acquisitions or team preferences.

### Azure Arc: managing everything from one place

**Azure Arc** projects resources running outside Azure (on-premises Windows and Linux servers, Kubernetes clusters, SQL Server instances, even VMs in other clouds) into Azure Resource Manager. Once connected, you can tag them, apply **Azure Policy**, protect them with **Microsoft Defender for Cloud**, monitor them with **Azure Monitor** and control access with **Azure RBAC**, exactly like native Azure resources.

<Callout type="exam">
Azure Arc appears in Domain 3 ("Describe the purpose of Azure Arc"). The one-line answer is that it **extends Azure management and governance to resources outside Azure**: on-premises, at the edge and in other clouds.
</Callout>

<DeepDive title="Hybrid design patterns architects actually use">

- **Tiered hybrid**: front ends in the cloud, back-end systems of record on-premises. Watch the chatty calls across the link, because latency adds up.
- **Partitioned multi-cloud**: different workloads on different clouds, each fully self-contained. This is simpler than spreading one app across clouds.
- **Cloud bursting**: needs the app to be stateless or to have data close at hand, plus pre-tested capacity in the cloud. Often harder in practice than on slides.
- **Backup and DR to cloud**: Azure Backup and Azure Site Recovery replicate on-premises workloads to Azure. This is often the first and lowest-risk hybrid step.
- **Edge**: run workloads on-premises with Azure Local or Arc-enabled Kubernetes for latency or disconnected scenarios, managed centrally.

Key cross-cutting decisions are identity (Entra ID with hybrid sync), DNS resolution across environments, IP address planning with no overlaps, and egress cost on data that crosses boundaries.

</DeepDive>
