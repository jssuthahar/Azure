interview:
  - level: beginner
    q: What is scalability, and what are the two types?
    a: >-
      Scalability is being able to add or remove resources as demand changes. Vertical scaling makes one machine bigger or smaller, for example more CPU or memory. Horizontal scaling adds or removes machines, for example going from two web servers to six.
    followUps:
      - q: Which one is better?
        a: >-
          Horizontal scaling is usually preferred in the cloud because there's no upper limit set by the biggest machine, it adds redundancy, and it can happen without downtime. Vertical scaling is simple and useful for things like databases that are hard to split, but it has a ceiling and often needs a restart.
  - level: intermediate
    q: What is the difference between scalability and elasticity?
    a: >-
      Scalability is the ability to grow or shrink resources to handle load, which can be done manually or on a schedule. Elasticity is scalability that happens automatically and rapidly in response to real-time demand, for example autoscale adding instances when CPU goes above 70%.
    followUps: []
  - level: experienced
    q: You need to scale out a web application. What design changes might be needed first?
    a: >-
      Make the tier stateless. Move session state to a distributed cache like Redis, store uploads in Blob Storage instead of local disk, externalise configuration, and make background jobs idempotent so they can run on any instance. Then check downstream bottlenecks. Scaling the web tier often just moves the bottleneck to the database, so consider read replicas, caching, partitioning or queue-based load levelling.
    followUps:
      - q: How do you scale a relational database?
        a: >-
          First vertically (more vCores), then with read replicas for read-heavy loads, caching, and finally partitioning or sharding, or a horizontally scalable service such as Azure SQL Hyperscale or Azure Cosmos DB, depending on the data model.
  - level: scenario

## Start with a question

<Story question="A restaurant suddenly gets a queue out of the door. Does it buy a bigger kitchen, or open more counters?">

Both are ways of handling more customers. A bigger stove and a faster chef is **scaling up**. Opening three more counters with more staff is **scaling out**. When the rush is over, a smart restaurant sends the extra staff home so it isn't paying for them.

That is **scalability**: matching capacity to demand, in both directions.

</Story>

## Explain it like I'm 10

<Eli10>

Imagine carrying books for your class.

- **Scale up**: you swap your small school bag for a **giant backpack**. One person, more space.
- **Scale out**: you ask **four friends** to help, each with their own bag.

If there are fewer books tomorrow, you go back to the small bag, or your friends go and play. In the cloud, you only pay for the bags you're actually using.

</Eli10>

## The technical explanation

**Scalability** is the ability of a system to handle more (or less) work by adjusting resources. Because cloud resources are on demand and billed by consumption, you can scale to the load you have now **and pay only for that**.

### How you scale in Azure

| Service | Scale up | Scale out |
| --- | --- | --- |
| Virtual Machines | Resize the VM | Virtual Machine Scale Sets |
| App Service | Change the App Service plan tier | Increase instance count (manual or autoscale) |
| Azure SQL Database | More vCores or higher tier | Read replicas, Hyperscale, elastic pools |
| Azure Functions | Larger instance memory (Flex) | Automatic, event-driven |
| AKS | Bigger node sizes | More pods and nodes (cluster autoscaler) |

<DeepDive title="Scaling the whole system, not one tier">

Scaling one tier often just moves the bottleneck. Senior engineers look at the full path:

1. **Edge**: CDN and Front Door absorb static content and spread load globally.
2. **Web/API**: stateless instances behind a load balancer, with autoscale.
3. **Async work**: queues (Service Bus, Storage Queues) decouple spikes from slower back ends. This is queue-based load levelling.
4. **Data**: caching (Redis), read replicas, partitioning. Choose a data store whose scaling model fits the access pattern.
5. **Limits**: every service has quotas (vCPU per region, connections per database). Request increases before a big event, not during it.

Load-test before the big day. Real behaviour under load rarely matches the diagram.

</DeepDive>
