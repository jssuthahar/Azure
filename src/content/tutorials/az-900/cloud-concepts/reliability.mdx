interview:
  - level: beginner
    q: What does reliability mean in the cloud?
    a: >-
      Reliability means a system can recover from failures and keep working. Azure helps because it has regions and availability zones all over the world, so I can run copies of my app and data in more than one place and fail over if one has a problem.
    followUps:
      - q: Is reliability the same as high availability?
        a: >-
          They're related but not the same. High availability is about maximising uptime. Reliability is broader. It's about the system recovering from failures and working correctly over time, including recovering data and restoring service after a disaster.
  - level: intermediate
    q: What are RTO and RPO, and why do they matter?
    a: >-
      RTO is how quickly service must be restored after a failure; RPO is how much data loss is acceptable, measured in time. They drive design and cost. An RPO of zero needs synchronous replication; an RTO of minutes needs a warm or active standby. Backups alone give longer RTO and RPO but cost far less.
    followUps: []
  - level: experienced
    q: How would you validate that a system is actually reliable rather than just designed to be?
    a: >-
      Test failure on purpose. Run regular failover drills, restore backups into a clean environment, and use fault injection with Azure Chaos Studio to kill instances, add latency or simulate a zone outage. Observe with health models and alerts. Document runbooks and automate failover where possible. A DR plan that has never been tested is a hope, not a plan.
    followUps: []
  - level: scenario
    q: A hospital appointments system must recover within one hour after a regional outage with at most five minutes of data loss. What would you suggest?
    a: >-
      RTO of one hour and RPO of five minutes. Replicate the database to a second region with asynchronous geo-replication (for example Azure SQL failover groups), keep the app deployable in the secondary region via infrastructure as code (or a warm standby), use Azure Site Recovery for any VMs, put Azure Front Door in front for traffic switching, and test the failover regularly.

## Start with a question

<Story question="A flood knocks out an entire city's power for two days. Does your hospital booking system still work?">

If it runs in one server room in that city, no. Patients can't book, and doctors can't see schedules.

If it's designed to **recover**, with copies of the data and the app ready in another city, it switches over and keeps running. That ability to bounce back is **reliability**.

</Story>

## Explain it like I'm 10

<Eli10>

Imagine you're writing a big school project. A **reliable** student saves the work on the laptop, **and** on a USB stick, **and** emails a copy to themselves. If the laptop dies the night before it's due, no panic: they open the copy and keep going.

The cloud lets companies keep copies of their programs and data in **many different places around the world**, so if one place has trouble, they carry on from another.

</Eli10>

## The technical explanation

**Reliability** is the ability of a workload to **recover from failures and continue to function as expected**. The cloud's **decentralised design**, with dozens of regions worldwide, most with multiple availability zones, gives you building blocks to survive failures at every scale:

  caption="Reliability at every scale"

    { title: 'Component', text: 'Instance crashes → load balancer routes to healthy instances.' },
    { title: 'Datacenter', text: 'Zone failure → zone-redundant services continue in other zones.' },
    { title: 'Region', text: 'Regional outage → fail over to a second region (geo-replication, Site Recovery).' },

  ]}

### Azure features that support reliability

| Feature | Protects against |
| --- | --- |
| Availability zones and zone-redundant services | Datacenter failure |
| Region pairs and geo-redundant storage (GRS/GZRS) | Regional disaster |
| Azure Backup | Data loss, corruption, ransomware |
| Azure Site Recovery | VM and server outages (replicate and fail over to another region) |
| Azure SQL Database failover groups | Database regional outage |
| Azure Front Door / Traffic Manager | Route users away from an unhealthy region |

<DeepDive title="Reliability engineering in practice">

The **Reliability pillar** of the Azure Well-Architected Framework recommends:

- **Define targets** with the business for each flow: availability, RTO and RPO. Not every flow needs the same.
- **Failure mode analysis**: list what can fail and how each failure is detected and mitigated.
- **Self-healing**: retries with exponential back-off, circuit breakers, health probes, automatic instance replacement.
- **Test**: chaos experiments with **Azure Chaos Studio**, DR drills, backup restore tests.
- **Observe**: health models in Azure Monitor that reflect user experience, not just CPU.

A useful mental model: you *design* for high availability, but you *prove* reliability by recovering under realistic failure.

</DeepDive>
