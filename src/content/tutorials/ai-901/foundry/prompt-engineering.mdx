keyTerms:
  - term: System prompt
    definition: The instruction, usually hidden from end users, that sets the model's role, rules, tone and format for every turn.
  - term: User prompt
    definition: The message from the user that asks the question or describes the task.
  - term: Few-shot prompting
    definition: Including a few example inputs and ideal outputs in the prompt so the model copies the pattern.
  - term: Zero-shot prompting
    definition: Asking the model to do a task with instructions only and no examples.
  - term: Grounding data
    definition: Facts you paste into the prompt (or retrieve automatically) so the model answers from your content instead of memory.
  - term: Delimiter
    definition: Markers such as triple quotes, ### or XML-style tags that separate instructions from the content the model should work on.
  - term: Safety system message
    definition: Lines in the system prompt that set safety rules, such as refusing harmful requests and staying on topic.

## Start with a question

<Story question="Why does the same AI give a great answer to one person and a useless one to another?">

Two people ask a model about trains. One types "trains?". The other types "I'm travelling from Bengaluru to Mysuru on Saturday morning with a toddler. List three train options in a table with departure time and duration."

The second person gets a far better answer, and it's not luck. They told the model who they are, what they want and how to lay it out. That's **prompt engineering**, and in an app you do most of it once, in the **system prompt**, so every user gets the good version.

</Story>

## Explain it like I'm 10

<Eli10>

Imagine a new helper at a sweet shop. On day one the owner says, "You sell sweets only. Be polite. Always tell people the price." Those are the **system** rules.

Then customers walk in and ask things: "Do you have laddoos?" Those are **user** messages.

If the owner also shows the helper two examples of a perfect reply, the helper copies that style. That's **few-shot**.

## The technical explanation

Every chat request to a model is a list of messages, each with a **role**:

| Role | Who writes it | What goes in it |
| --- | --- | --- |
| `system` | You, the developer | Persona, scope, rules, tone, output format, safety rules |
| `user` | The person using your app | The question or task for this turn |
| `assistant` | The model | Its earlier replies, sent back so it remembers the conversation |

### Techniques that make prompts work

1. **Be clear and specific.** Say the task, the audience and the length. "Summarise this for a busy store manager in two sentences" beats "summarise this".
2. **Give it a role.** "You're a customer support agent for Contoso Electronics" sets vocabulary and tone.
3. **Ask for a format.** A table, a numbered list, or JSON with named keys your code can read.
4. **Show examples (few-shot).** Two or three input and output pairs teach a pattern faster than a paragraph of rules. With no examples it's **zero-shot**.
5. **Ground it.** Paste the facts the answer must come from, and say "If the answer isn't in the text, say you don't know."
6. **Use delimiters.** Wrap pasted content in `"""`, `###` or tags like `<policy>…</policy>` so the model can tell instructions from data.
7. **Ask for steps on hard problems.** "Work through it step by step, then give the final answer" helps with maths and logic.
8. **Iterate.** Test in the playground, look at bad answers, change one thing, test again.

Here's a system message that uses most of them:

```text
You are a support assistant for Contoso Electronics.
Answer only questions about Contoso products, using the policy text between <policy> tags.
If the answer is not in the policy, say "I'm not sure, please contact support."
Reply in at most 3 sentences, in plain English.
Never give medical, legal or financial advice. Politely decline off-topic requests.

<policy>
Returns are accepted within 30 days with a receipt. Laptops carry a 1-year warranty.
</policy>
```

The last two lines of rules are a small **safety system message**. Microsoft recommends adding one to every app: it sets what the model should refuse and how. It works alongside Foundry's **guardrails** (content filters and Prompt Shields), not instead of them.

<Callout type="exam">
Questions often describe a symptom and ask for the fix. **Wrong tone or persona** → change the system prompt. **Inconsistent format** → add few-shot examples or specify the format. **Made-up facts** → add grounding data. **Model mixes up instructions and pasted text** → use delimiters. **Harmful or off-topic requests** → safety system message plus guardrails.
</Callout>

<DeepDive title="Prompting reasoning models and agents">

Reasoning models (such as the o-series and GPT-5 reasoning modes) already think step by step, so "think step by step" adds little. Give them a clear goal and constraints instead, and use the reasoning effort setting. For agents, the system prompt is called **instructions** and also tells the agent when to use each tool. Keep instructions short and testable; long, contradictory instructions are a common reason agents misbehave.

</DeepDive>
