## Start with a question

<Story question="What if your chatbot could look things up and do sums before it replied?">

Ask a plain chat model "How many leave days do I have left if I've taken 7 out of our policy's allowance?" and it'll guess the policy. It's never seen your HR handbook.

Now picture a new hire on the HR desk. They open the handbook, find the allowance, work out the subtraction and then reply. That's an **agent**: a model that's allowed to open files and use tools before it answers.

</Story>

## Explain it like I'm 10

<Eli10>

Think of a robot helper with a backpack.

The robot's brain is the **model**. The note taped to its arm saying "Be polite, only talk about school rules" is the **instructions**. The backpack holds a rule book, a calculator and a phone. Those are the **tools**.

When you ask it something, the robot decides which thing in the backpack to pull out, uses it, and then tells you the answer.

</Eli10>

## The technical explanation

In Microsoft Foundry an agent is defined by three parts: the **model** it runs on, the **instructions** that shape its behaviour, and the **tools** it may call. Foundry Agent Service runs the loop for you: read the user's message, decide whether a tool is needed, call it, look at the result, and either call another tool or answer. The conversation keeps the history, so the next question can say "and what about next year?" and the agent knows what "next year" refers to.

### Building one in the portal

You need a Foundry project with a chat model already deployed (for example `gpt-4.1-mini`). Then, in the Foundry portal at ai.azure.com:

1. Open your project and go to **Build → Agents → Create agent**.
2. Give it a **name** (letters, numbers and hyphens, like `hr-helper`). Your code will use this name later.
3. Pick the **model** deployment it should run on.
4. Write the **instructions**. This is the agent's system prompt: who it is, what it may answer, the tone, and what to do when it doesn't know.
5. Add **knowledge** and **tools** (below).
6. **Save**, then type a question in the **agent playground** on the right and watch the reply, including which tools it called.

| Tool | What it gives the agent | Typical use |
| --- | --- | --- |
| File search | Searches files you upload (PDF, Word, text) | Answer from a policy handbook or product manual |
| Azure AI Search | Searches an existing search index | Large or shared company knowledge bases |
| Web search (grounding) | Fresh public web results with citations | News, prices, anything newer than the model |
| Code interpreter | Writes and runs Python in a sandbox | Maths, charts, cleaning an uploaded CSV |
| Function calling | Asks your app to run a function you described with a JSON schema | Look up an order in your own database |
| OpenAPI / MCP | Calls an external API or MCP server | Booking systems, ticketing tools |

Good instructions make or break an agent. Say which tool to prefer ("Use the attached handbook for any policy question"), what's off-topic, and what to say when the answer isn't in the files. Then test the awkward cases in the playground: an off-topic question, a question the handbook doesn't cover, and a follow-up that depends on the last turn.

### Versions

Every time you save, Foundry creates a new **version** of the agent. A version is immutable: the model, instructions and tools inside it never change. You can compare versions, and apps can keep using a known good one while you try changes. If version 5 starts answering worse, you go back to version 4.

<Callout type="exam">
Watch for the tool hidden in the scenario. "Answer questions from the company's uploaded documents" points to **file search**. "Calculate", "analyse a spreadsheet" or "create a chart" points to **code interpreter**. "Current events" points to **web search**. "Check stock in our inventory system" points to **function calling** or an **OpenAPI** tool. And the place to try it all without code is the **agent playground**.
</Callout>

<DeepDive title="Function calling doesn't run your code">

With function calling you describe a function (name, description, parameters as JSON schema). When the model decides it needs it, the response contains a function call with arguments, not a result. Your client app runs the real function, sends the output back, and the agent carries on. That keeps your database credentials in your app, never in the model. In the playground you can type the function's output by hand to test the flow.

</DeepDive>
