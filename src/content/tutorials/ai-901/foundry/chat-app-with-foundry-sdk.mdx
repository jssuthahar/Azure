## Start with a question

<Story question="The model works in the playground. How do you put it inside your own app?">

The playground is great for testing, but your customers won't log in to ai.azure.com. They'll use your website, your WhatsApp bot or your internal tool. Somewhere in that app, a few lines of code have to send the question to your model and show the answer.

That's what the **Foundry SDK** is for. With about fifteen lines of Python you get a working chat client that remembers the conversation.

</Story>

## Explain it like I'm 10

<Eli10>

Think of calling a friend on the phone. First you need their number (the **endpoint**). Then you have to prove who you are so they pick up (the **credential**). Then you talk, and they answer.

If you hang up and call again, a good friend still remembers what you said earlier. In code, a **conversation** is how the model remembers.

</Eli10>

## The technical explanation

You need four things in place before the code runs:

1. A Foundry project with a deployed model (for example a deployment named `gpt-4.1-mini`).
2. The **project endpoint**, from the project's overview page, saved in an environment variable.
3. The packages: `pip install "azure-ai-projects>=2.3.0" azure-identity`
4. A signed-in identity with the **Foundry User** role. Locally that's `az login`; in Azure it's a managed identity.

```bash
export FOUNDRY_PROJECT_ENDPOINT="https://<resource-name>.services.ai.azure.com/api/projects/<project-name>"
az login
```

### A one-shot question

```python
import os
from azure.identity import DefaultAzureCredential
from azure.ai.projects import AIProjectClient

# Connect to the project with Microsoft Entra ID (no API key)
project = AIProjectClient(
    endpoint=os.environ["FOUNDRY_PROJECT_ENDPOINT"],
    credential=DefaultAzureCredential(),
)

# An OpenAI-compatible client that already points at your project
openai = project.get_openai_client()

response = openai.responses.create(
    model="gpt-4.1-mini",  # the DEPLOYMENT name, not the catalog name
    instructions="You are a friendly travel assistant. Keep answers short.",
    input="What's a good time of year to visit Munnar?",
)
print(response.output_text)
```

`instructions` is the system prompt. You can also pass `input` as a list of messages with `system` and `user` roles if you prefer.

### Making it multi-turn

On its own, each call forgets the last one. Create a **conversation** once and pass its id on every turn so the service keeps the history for you:

```python
conversation = openai.conversations.create()

while True:
    question = input("You: ")
    if question.lower() in ("quit", "exit"):
        break
    response = openai.responses.create(
        model="gpt-4.1-mini",
        conversation=conversation.id,  # earlier turns are included automatically
        instructions="You are a friendly travel assistant. Keep answers short.",
        input=question,
    )
    print("Assistant:", response.output_text)
```

The other option is to chain responses: store `response.id` and pass it as `previous_response_id=` on the next call.

<Callout type="exam">
Know the pieces by name: **azure-ai-projects** (package), **AIProjectClient** (connects to the project), **DefaultAzureCredential** (Entra ID sign-in, the only auth the project client supports), **get_openai_client()**, **responses.create** with `model` set to the **deployment name**, and **output_text** for the reply. For memory across turns, the answer is a **conversation** or **previous_response_id**.
</Callout>

<DeepDive title="Why Entra ID instead of keys">

Keys are shared secrets: anyone who copies one has full access until it's rotated. With `DefaultAzureCredential`, the same code signs in as you on your laptop (Azure CLI), as a managed identity in Azure App Service or Container Apps, or as a workload identity in a pipeline, and access is controlled by the Foundry User role. Tokens expire on their own, and removing a role assignment cuts access instantly.

</DeepDive>
