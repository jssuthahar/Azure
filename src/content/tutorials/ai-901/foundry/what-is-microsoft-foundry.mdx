## Start with a question

<Story question="Where do you actually go in Azure to build an AI app?">

Say you're building a chatbot for a hospital in Kochi. You need a model, a place to try prompts, a way to add safety filters, maybe speech so patients can talk to it, and a URL your app can call. Clicking around ten different Azure services would be painful.

**Microsoft Foundry** puts all of that in one place. You open **ai.azure.com**, pick a project, and everything you need for that app lives there.

</Story>

## Explain it like I'm 10

<Eli10>

Think of a big school building. The building has the electricity, the security guard and the fee office. That's the **Foundry resource**.

Inside are classrooms. Each class has its own desks, books and projects on the wall. Those are **Foundry projects**.

The library and the science lab are shared by every class. Those are the **Foundry Tools** and models.

</Eli10>

## The technical explanation

Foundry has two levels. Get these straight and half the exam questions on this topic get easy.

### What you'll find in the portal

| Area | What it's for |
| --- | --- |
| **Model catalog** | Browse thousands of models (Microsoft Phi, OpenAI GPT-4.1 and GPT-5 family, Meta Llama, Mistral, DeepSeek, Cohere), read model cards and compare benchmarks for quality, cost and speed. |
| **Deployments** | Turn a model into an endpoint you can call, with a deployment name you choose. |
| **Playgrounds** | Chat with a deployed model, change parameters, then use **View code** to copy working code. |
| **Agents** | Build agents from a model, instructions and tools (file search, web search, code interpreter and more). |
| **Foundry Tools** | Azure Speech, Azure Language, Azure Vision, Azure Content Understanding, Azure Translator and others, all in Foundry. |
| **Guardrails** | Content filters for hate, sexual, violence and self-harm, Prompt Shields for jailbreaks, and more. |
| **Evaluations** | Score answers for quality and safety before you ship. |

### Endpoints, keys and roles

Your app calls the **project endpoint**: `https://<resource-name>.services.ai.azure.com/api/projects/<project-name>`. The Foundry SDK signs in with **Microsoft Entra ID** (for example `DefaultAzureCredential`), so you don't paste keys into code. The resource also shows **keys and endpoints** for Foundry Tools that accept key-based auth.

Access is controlled with Azure RBAC. The Foundry roles were renamed recently:

| Role | What it's for |
| --- | --- |
| **Foundry User** (was Azure AI User) | Build and use deployments and agents in a project. The usual role for developers. |
| **Foundry Project Manager** | Manage a project and give others the Foundry User role on it. |
| **Foundry Account Owner** | Manage the Foundry resource, create projects and deploy models. It can't build in a project on its own (no data actions). |
| **Foundry Owner** | Manage the resource and build in projects: control plane and data plane together. |

<Callout type="exam">
Expect "which should you create?" questions. Shared billing, networking or Foundry Tools access points to the **Foundry resource**. A separate workspace for one team's deployments and agents points to a **project**. The minimum role for a developer to build there is **Foundry User**. Old names (Azure AI Foundry, Azure AI services, Azure AI User) may show up in study material, so know both.
</Callout>

<DeepDive title="Why the two-level design matters">

Putting projects under one resource means security, network isolation and billing are set once and every team inherits them. Teams still can't see each other's agents or files unless you give them access. In Azure, the resource type is `Microsoft.CognitiveServices/accounts` with kind `AIServices`, the same family the older Azure AI services used, which is why Foundry Tools sit naturally on the same resource.

</DeepDive>
