## The technical explanation

**Azure Content Understanding in Foundry Tools** uses generative AI to turn unstructured content into structured output you define. For documents it returns two things: the content as **Markdown** (text, tables, layout) and the **fields** you asked for as JSON. Everything runs through an **analyzer**.

### Prebuilt analyzers for documents

| Analyzer | What you get |
| --- | --- |
| `prebuilt-read` | Text (OCR) only |
| `prebuilt-layout` | Text plus tables, selection marks and structure |
| `prebuilt-documentSearch` | Markdown and a summary, ready for search and RAG |
| `prebuilt-invoice` | Vendor, customer, invoice number, dates, line items, totals |
| `prebuilt-receipt` | Merchant, date, items, tax, total |
| Others | ID documents, tax forms, contracts and more |

Before any analyzer works, the Foundry resource needs its **default model deployments** set (a completion model such as GPT-4.1 and an embedding model). Content Understanding calls those models for you, and you pay for their tokens as well as for content extraction.

### Custom fields

When the prebuilt fields aren't enough, you create a **custom analyzer**. You set `baseAnalyzerId` to `prebuilt-document` (or start from a prebuilt like `prebuilt-invoice`) and add a **field schema**. Each field has a name, a type, a plain-English description and a **method**:

| Method | Use it when | Example field |
| --- | --- | --- |
| **Extract** | The value is printed in the document (documents only) | `PONumber` |
| **Classify** | The answer is one of a fixed list | `SpendCategory`: Utilities, Travel, Raw materials |
| **Generate** | The value has to be written from the content | `PaymentTermsSummary` in one sentence |

```json
{
  "baseAnalyzerId": "prebuilt-document",
  "fieldSchema": {
    "fields": {
      "PONumber":      { "type": "string", "method": "extract",  "description": "Purchase order number printed on the invoice" },
      "SpendCategory": { "type": "string", "method": "classify", "enum": ["Utilities", "Travel", "Raw materials"] },
      "TermsSummary":  { "type": "string", "method": "generate", "description": "One-sentence summary of the payment terms" }
    }
  }
}
```

The JSON above is simplified to show the idea. In the Foundry portal you do the same thing in a form: add a field, pick its type and method, write a description, then test on a sample file.

### Confidence and grounding

Every extracted value carries a **confidence score** between 0 and 1 and **grounding**: the page and region it came from. Your app compares the score to a threshold you choose. High scores flow straight through; low ones go to a person, who can see the highlighted spot on the page instead of hunting for it.

<Callout type="exam">
Expect scenario questions that name the field type. A value **printed on the form** is **extract**. Picking **one of a list** is **classify**. Writing **a summary or a new value** is **generate**. "Which values should a person check?" points to **confidence scores**, and "show where the value came from" points to **grounding**.
</Callout>

<DeepDive title="Content Understanding and Document Intelligence">

Azure Document Intelligence (formerly Form Recognizer) is the older service for forms and invoices, built on task-specific models. Content Understanding covers documents, images, audio and video with one analyzer model, and uses generative AI so you can describe fields instead of labelling training data. Existing Document Intelligence apps keep working, but new AI-901 scenarios point to Content Understanding. The GA API version is 2025-11-01.

</DeepDive>
