## Start with a question

<Story question="Your water pressure is low. Is it your tap, your pipes or the street?">

A plumber doesn't guess. First they look at the meter by the door (that's the overview). Then they test water at the tap every few minutes for a day to catch the drop when it happens. When it drops, they walk the pipe and find the valve someone half closed.

**Azure Monitor Insights** are the meters: ready-made views of your VMs, storage accounts and networks. **Network Watcher** is the plumber's kit. Its **Connection monitor** keeps testing the path from your app to its database, and its diagnostic tools find the exact valve, usually an NSG rule or a route, that closed.

</Story>

## The technical explanation

### Azure Monitor Insights

Insights are curated monitoring experiences under **Monitor > Insights** (and on each resource's **Monitoring > Insights** blade).

| Insight | What you see | What it needs |
| --- | --- | --- |
| **VM insights** | **Performance**: CPU, available memory, logical disk space, network, compared across VMs. **Map** (optional): processes and their connections to other servers | **Azure Monitor Agent** + a VM insights **data collection rule** sending to a Log Analytics workspace (data in **InsightsMetrics**, and VMProcess/VMConnection for Map) |
| **Storage insights** | Capacity, transactions, latency, availability and failures across all storage accounts | Nothing: built on platform metrics |
| **Network insights** | Health and metrics of virtual networks, load balancers, gateways, Application Gateways, a topology view, and links to Network Watcher tools | Nothing: built on platform metrics and resource health |
| Container insights, Application Insights | AKS clusters, apps | Agents or SDKs (covered elsewhere) |

**Enable VM insights:** VM > **Monitoring > Insights > Enable**, or **Monitor > Insights > Virtual Machines > Not monitored > Enable**. Choose the data collection rule (or create one), whether to collect **processes and dependencies (Map)**, and the workspace. The portal installs the Azure Monitor Agent for you.

```bash
# The CLI path: a VMInsights data collection rule plus an association per VM
az monitor data-collection rule create -g rg-ops -n MSVMI-law-contoso-ops \
  --location eastus --rule-file vminsights-dcr.json
az monitor data-collection rule association create --name vmi-vm-app01 \
  --rule-id <dcr id> --resource <vm id>
az vm extension set -g rg-ops --vm-name vm-app01 \
  --name AzureMonitorLinuxAgent --publisher Microsoft.Azure.Monitor --enable-auto-upgrade true
```

Interpreting VM insights: look at the **P95** line, not just the average, to see the busy moments; sort the **Top N** lists to find the VM that's short of memory; and use **Map** to see which servers a VM talks to before you change a firewall rule.

### Network Watcher

Network Watcher is a regional service. Azure turns it on automatically in a region when you create or update a virtual network there, and puts it in the **NetworkWatcherRG** resource group. Its tools:

| Group | Tool | Answers |
| --- | --- | --- |
| Monitoring | **Topology** | What's connected to what in this VNet? |
| | **Connection monitor** | Is the path from A to B healthy right now, and when did it last fail? |
| Diagnostics | **IP flow verify** | Is this 5-tuple allowed or denied on this VM, and by which NSG rule? |
| | **NSG diagnostics** | Same idea, for any source and destination, across NIC and subnet NSGs |
| | **Next hop** | Where does a packet from this VM go next (Internet, VirtualAppliance, VNet peering, None) and which route table decided? |
| | **Effective security rules** | The merged NSG rules that apply to a NIC |
| | **Connection troubleshoot** | A one-off connectivity test between a VM and an endpoint, with hops |
| | **Packet capture** | A capture file of traffic on a VM |
| | **VPN troubleshoot** | Why a VPN gateway or connection is unhealthy |
| Logs | **Flow logs** (VNet flow logs) and **Traffic analytics** | Who talked to whom, how much, allowed or denied |

New NSG flow logs can no longer be created and NSG flow logs retire in September 2027, so use **VNet flow logs**.

### Connection monitor

A connection monitor contains one or more **test groups**. Each test group has:

- **Sources**: Azure VMs or scale sets with the **Network Watcher Agent** extension (the portal installs it), or on-premises and other-cloud machines through Azure Arc with the Azure Monitor Agent.
- **Destinations**: Azure VMs, or external addresses (FQDN, URL or IP), including Microsoft 365 endpoints.
- **Test configurations**: protocol **TCP**, **HTTP** or **ICMP**, port, **test frequency** (for example every 30 seconds), and **success thresholds**: **checks failed (%)** and **round-trip time (ms)**.

Results go to a Log Analytics workspace (tables **NWConnectionMonitorTestResult** and **NWConnectionMonitorPathResult**). You can **create an alert** in the wizard, which uses a metric alert on *Checks failed percent* or *Round-trip time* and calls an action group. The **topology** view in the results shows each hop and flags the one with issues.

**Portal path:** **Network Watcher > Monitoring > Connection monitor > + Create**. Tabs: *Basics, Test groups, Create alert, Review + create*.

```bash
az network watcher connection-monitor create --name cm-app-to-sql --location eastus \
  --endpoint-source-name vm-app01 --endpoint-source-resource-id <vm-app01 id> \
  --endpoint-dest-name vm-sql01 --endpoint-dest-resource-id <vm-sql01 id> \
  --test-config-name tcp-1433 --protocol Tcp --tcp-port 1433 --frequency 30 \
  --workspace-ids <workspace id>
```

<Callout type="exam">
Match the tool to the question. "**Continuously** monitor reachability or latency between a VM and an endpoint, and alert" is **Connection monitor**. "**Is traffic allowed** to this VM on port X, and which rule decides?" is **IP flow verify** (or NSG diagnostics). "**Which route** sends traffic to the firewall?" is **Next hop**. "Capture traffic for Wireshark" is **Packet capture**. "See memory and disk inside VMs and their dependencies" is **VM insights**, which needs the **Azure Monitor Agent**. "Capacity and transactions across storage accounts with no setup" is **Storage insights**.
</Callout>

<DeepDive title="Connection monitor versus the one-off tools">

Connection troubleshoot and IP flow verify answer a question once, from the state at that moment. Connection monitor runs the same kind of check every few seconds and keeps history, which is what you need for problems that come and go. A common workflow: Connection monitor alerts you, its topology points at a hop, and IP flow verify or Next hop names the rule or route.

Cost is per test: the first 10 tests a month are free, then roughly $0.30 per test a month (illustrative), plus Log Analytics ingestion for the results. A "test" is one source, destination and configuration combination, so a mesh of 10 sources and 10 destinations is 100 tests.

</DeepDive>
