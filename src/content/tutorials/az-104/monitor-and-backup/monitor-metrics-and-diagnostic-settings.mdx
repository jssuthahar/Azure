## Start with a question

<Story question="Your car's dashboard shows speed and fuel all the time. So why doesn't it remember who borrowed it last Tuesday?">

The dashboard gives you numbers the moment you start the engine: speed, fuel, temperature. Nobody had to switch that on. But if you want a record of every trip, who drove and where they went, you have to fit a trip recorder and decide where its data goes.

Azure works the same way. **Platform metrics** are the dashboard: CPU, transactions and availability arrive on their own. **Resource logs** are the trip recorder: they're only kept once you add a **diagnostic setting** and choose where they go. And the **activity log** is the car's service book: who changed the car itself.

</Story>

## Explain it like I'm 10

<Eli10>

Your school counts how many kids come in each morning. It does that every day, without anyone asking. That's a **metric**.

If the head teacher wants to know exactly who came in late and through which door, someone has to write it down in a notebook and decide where the notebook lives. That's a **log** and its **diagnostic setting**.

And the office keeps a list of who changed the school rules. That's the **activity log**.

</Eli10>

## The technical explanation

Azure Monitor collects three kinds of data from Azure resources without you installing anything, but only one of them is kept by default.

| Data | What it is | Collected by default? | Kept | Where you see it |
| --- | --- | --- | --- | --- |
| **Platform metrics** | Numbers sampled about once a minute (Percentage CPU, Transactions, Availability) | Yes | **93 days** | Metrics explorer, metric alerts |
| **Resource logs** | Data-plane records from inside the resource (StorageRead, AuditEvent, NetworkSecurityGroupEvent) | **No** | Wherever you send them | Log Analytics, storage, Event Hubs |
| **Activity log** | Control-plane operations for the subscription: create, update, delete, role assignments, Service Health | Yes | **90 days** | Monitor > Activity log, every resource's Activity log blade |

### Interpret metrics in Metrics explorer

Open any resource, then **Monitoring > Metrics** (or **Monitor > Metrics** and pick a scope). Each chart has:

- a **metric namespace** and **metric**, such as *Account / Transactions* on a storage account,
- an **aggregation**: Average, Min, Max, Sum or Count. Average CPU and Max CPU can tell very different stories,
- **Add filter** to keep one dimension value (only *ResponseType = AuthorizationError*),
- **Apply splitting** to draw one line per dimension value (one line per response type, per API name, per VM instance),
- a **time range** and **time granularity**. One chart can show up to 30 days, and you can pan back through the 93 days kept.

From the same chart you can **Save to dashboard** or select **New alert rule**. The CLI equivalent reads the same data:

```bash
az monitor metrics list \
  --resource /subscriptions/<sub>/resourceGroups/rg-ops-mon/providers/Microsoft.Compute/virtualMachines/vm-web01 \
  --metric "Percentage CPU" --interval PT1M --aggregation Average -o table

az monitor metrics list-definitions --resource <resource id> -o table   # what metrics exist
```

<Callout type="tip">
VM platform metrics come from the host, so they show CPU, disk and network but not guest memory usage or free disk space inside the OS. For those you need the Azure Monitor Agent (VM insights turns it on for you).
</Callout>

### Configure log settings with diagnostic settings

A **diagnostic setting** is a rule on one resource. It has a name, the **log categories** or **category groups** to send (`allLogs` or `audit`, which also pick up categories Microsoft adds later), optionally **AllMetrics**, and one or more **destinations**:

| Destination | Pick it when | Notes |
| --- | --- | --- |
| **Log Analytics workspace** | You want to query with KQL, build workbooks or create log search alerts | Choose **Azure diagnostics** (one shared table) or **Resource specific** (one table per category, recommended where offered) |
| **Storage account** | You need a cheap archive for audits | Must be in the **same region** as the resource. Use lifecycle rules for retention |
| **Event Hubs** | You stream to a SIEM or a third-party tool | Needs a namespace and an authorization rule |
| **Partner solution** | You use an Azure Native ISV service such as Datadog or Elastic | Configured from the partner resource |

One setting can use several destinations at once, and a resource can have **up to five** diagnostic settings. Logs flow from the moment you save; nothing is backfilled.

**Portal path:** resource > **Monitoring > Diagnostic settings** > **+ Add diagnostic setting**. For a storage account you first pick the **blob**, **file**, **queue** or **table** service, because that's where StorageRead, StorageWrite and StorageDelete live. The account level only offers the Transaction metrics.

```bash
az monitor diagnostic-settings categories list \
  --resource <storage id>/blobServices/default -o table

az monitor diagnostic-settings create --name diag-blob \
  --resource <storage id>/blobServices/default \
  --workspace law-contoso-ops \
  --logs '[{"categoryGroup":"allLogs","enabled":true}]' \
  --metrics '[{"category":"Transaction","enabled":true}]'
```

```powershell
$log = New-AzDiagnosticSettingLogSettingsObject -CategoryGroup allLogs -Enabled $true
New-AzDiagnosticSetting -Name diag-blob -ResourceId "$storageId/blobServices/default" `
  -WorkspaceId $workspaceId -Log $log
```

### Virtual machines are different

A VM has **no resource log categories**. A diagnostic setting on a VM can only send platform metrics. Windows event logs, Syslog and guest performance counters come from the **Azure Monitor Agent (AMA)**, and a **data collection rule (DCR)** says what to collect and which workspace to send it to. The old Log Analytics agent (MMA) and the Windows Azure Diagnostics extension are retired, so don't pick them in a new design.

### The activity log

The activity log is one per subscription and records **control-plane** events: someone created a VM, changed an NSG rule, assigned a role, listed storage keys, or Azure posted a Service Health event. It doesn't record data-plane actions like reading a blob. Filter it by resource group, resource, operation, caller and time span in **Monitor > Activity log**, or from the CLI:

```bash
az monitor activity-log list -g rg-ops-mon --offset 1h -o table
az monitor activity-log list --caller ben@contoso.com --offset 7d
```

To keep it longer than 90 days or join it with other logs, select **Export Activity Logs**, which creates a **subscription diagnostic setting** (`az monitor diagnostic-settings subscription create`). In a workspace it lands in the **AzureActivity** table.

<Callout type="exam">
Watch for the verb. "Chart CPU for the last two weeks" is **Metrics explorer**, no setup. "Find who **deleted** or **changed** a resource" is the **activity log**. "Find who **read** a blob or got a secret" needs **resource logs**, so the answer includes a **diagnostic setting**. If the question asks for "the least administrative effort to query with KQL", the destination is a **Log Analytics workspace**; "lowest cost retention for years" is a **storage account**; "send to a third-party SIEM" is **Event Hubs**. And if they try to collect guest event logs with a diagnostic setting on a VM, that's the wrong tool: it's the **Azure Monitor Agent** with a **data collection rule**.
</Callout>

<DeepDive title="Resource-specific tables, costs and retention">

When you send logs to a workspace, **resource-specific** mode writes each category to its own table (StorageBlobLogs, AzureBackup tables, AppServiceHTTPLogs). Queries are faster, columns are typed and you can set retention per table. The older **Azure diagnostics** mode puts everything into the wide AzureDiagnostics table. Some services only support one mode; Azure Backup reports need resource-specific.

Workspaces charge per GB ingested (around $2.30 per GB on pay-as-you-go for Analytics logs, illustrative) and include 31 days of retention. Interactive retention goes up to two years, and long-term retention up to 12 years at a lower price. For noisy, rarely queried data, look at the **Basic** or **Auxiliary** table plans, or archive to storage instead.

</DeepDive>
