## Start with a question

<Story question="Where do you keep copies of the house keys, and how often do you check they're still there?">

You don't keep the spare keys inside the house; a fire would take both. You leave them with a neighbour on the same street so you can get them quickly, or with family in another town in case the whole street floods. And you agree a routine: check every Sunday, replace them when the locks change.

Azure Backup is that arrangement. The **vault** is the neighbour holding the copies, in the **same region** as your VM, with **redundancy** deciding whether a copy also sits in another region. The **backup policy** is the routine: when to copy and how long to keep each copy.

</Story>

## Explain it like I'm 10

<Eli10>

Every night at bedtime you take a photo of your Lego castle and put it in a safe box. That's a **backup** on a **schedule**.

You keep the last 30 photos, plus one from the end of each month for a year. That's **retention**.

There are two safe boxes: a big one for whole castles (**Recovery Services vault**) and a newer one for loose bricks and baseplates (**Backup vault**).

If your little brother throws photos in the bin, the box keeps them in a drawer for two weeks. That's **soft delete**.

</Eli10>

## The technical explanation

### Two vault types

| | Recovery Services vault | Backup vault |
| --- | --- | --- |
| Protects | **Azure VMs**, SQL Server in Azure VMs, SAP HANA in Azure VMs, **Azure Files**, on-premises files and folders (**MARS agent**), MABS and DPM | **Azure Blobs** (operational and vaulted backup), **managed disks**, **Azure Database for PostgreSQL flexible server**, **AKS** |
| Also does | **Azure Site Recovery** replication | — |
| Resource type | Microsoft.RecoveryServices/vaults | Microsoft.DataProtection/backupVaults |
| CLI | `az backup …` | `az dataprotection …` |
| Access to the data | Azure Backup service handles VM snapshots | The vault's **system-assigned managed identity** needs roles on each data source |

Both appear in **Business Continuity Center** (which brings together the older Backup center views), so you can manage all of them from one place.

### Create a Recovery Services vault

**Portal path:** search **Recovery Services vaults > + Create**. Tabs: *Basics, Redundancy, Vault properties, Networking, Tags, Review + create*.

- **Region**: for Azure VM backup, the vault must be in the **same region as the VMs**. You need one vault per region you protect.
- **Backup Storage Redundancy**: **Geo-redundant** (default), **Locally-redundant** or **Zone-redundant**. You can change it only **before** any item is protected.
- **Cross Region Restore**: needs GRS. Lets you restore into the paired region at any time, not only during a Microsoft-declared outage.
- **Soft delete** is on by default (14 days, configurable to 180). You can make it **always on**, which can't be undone. **Immutability** and **multi-user authorization** (a Resource Guard in another tenant or subscription) protect the vault from someone with admin rights.

```bash
az backup vault create -g rg-ops-bk -n rsv-contoso-eus -l eastus
az backup vault backup-properties set -g rg-ops-bk -n rsv-contoso-eus \
  --backup-storage-redundancy LocallyRedundant
```

```powershell
New-AzRecoveryServicesVault -ResourceGroupName rg-ops-bk -Name rsv-contoso-eus -Location eastus
$v = Get-AzRecoveryServicesVault -Name rsv-contoso-eus
Set-AzRecoveryServicesBackupProperty -Vault $v -BackupStorageRedundancy LocallyRedundant
```

### Create a Backup vault

**Portal path:** search **Backup vaults > + Create**. Tabs: *Basics* (name, region, **Backup Storage Redundancy**), *Vault Properties* (soft delete, immutability), *Tags, Review + create*. A system-assigned managed identity is created with it.

```bash
az dataprotection backup-vault create -g rg-ops-blob --vault-name bv-contoso-eus -l eastus \
  --type SystemAssigned \
  --storage-setting "[{type:LocallyRedundant,datastore-type:VaultStore}]"
```

Before a Backup vault can protect a data source, its identity needs a role there: **Storage Account Backup Contributor** on a storage account for blobs; **Disk Backup Reader** on a disk and **Disk Snapshot Contributor** on the resource group where snapshots go. The portal offers to grant these; from the CLI, `az dataprotection backup-instance update-msi-permissions` does it.

### Backup policies for VMs

**Portal path:** vault > **Manage > Backup policies > + Add > Azure Virtual Machine**.

| Setting | Standard | Enhanced |
| --- | --- | --- |
| Frequency | Daily (or weekly) | Every 4, 6, 8 or 12 hours, or daily |
| Instant restore snapshots | 1 to 5 days (default 2) | 1 to 30 days (default 7) |
| Needed for | Most VMs | **Trusted Launch** VMs, Premium SSD v2 and Ultra disks, more frequent backups |

**Retention range**: daily points 7 to 9999 days; weekly points on chosen days; monthly and yearly points on a chosen day or week. A vault starts with a **DefaultPolicy** (daily, 30 days, 2 days of instant restore) and an **EnhancedPolicy**. Each protected item follows exactly **one** policy, and changing a policy changes every item that uses it.

```bash
az backup policy show -g rg-ops-bk --vault-name rsv-contoso-eus -n DefaultPolicy > policy.json
# edit name, scheduleRunTimes, retention counts, instantRpRetentionRangeInDays
az backup policy create -g rg-ops-bk --vault-name rsv-contoso-eus -n DailyAt23-Keep60 \
  --backup-management-type AzureIaasVM --policy policy.json
az backup protection enable-for-vm -g rg-ops-bk --vault-name rsv-contoso-eus \
  --vm vm-prod01 --policy-name DailyAt23-Keep60
```

### Backup policies in a Backup vault

Backup vault policies are per data source type. **Blobs**: **operational backup** keeps continuous, local point-in-time restore (up to 360 days) inside the storage account; **vaulted backup** copies data to the vault on a daily or weekly schedule. **Disks**: incremental snapshots every few hours or daily, kept in a snapshot resource group. Start from the default template:

```bash
az dataprotection backup-policy get-default-policy-template --datasource-type AzureBlob > blob-policy.json
az dataprotection backup-policy create -g rg-ops-blob --vault-name bv-contoso-eus \
  -n blob-policy --policy blob-policy.json
```

<Callout type="exam">
First pick the vault from the data source: **VMs, Azure Files, SQL in a VM, MARS, Site Recovery** go to a **Recovery Services vault**; **blobs, managed disks, PostgreSQL flexible server, AKS** go to a **Backup vault**. Then the region: the vault is in the **same region** as the VM, so three regions means three vaults. Redundancy is chosen **before** protecting items; "restore in the secondary region on demand" needs **GRS + Cross Region Restore**. A backup every few hours, or a **Trusted Launch** VM, means an **Enhanced** policy. If a Backup vault can't protect a storage account, the missing piece is the **Storage Account Backup Contributor** role for the vault's identity.
</Callout>

<DeepDive title="Protecting the backups themselves">

Ransomware crews go after backups first. Layer the defences: **soft delete** (14 to 180 days, set it to **always on** so nobody can switch it off), **immutable vaults** (recovery points can't be deleted before they expire; lock immutability to make it permanent), and **multi-user authorization**, which puts critical operations such as disabling soft delete or reducing retention behind a **Resource Guard** owned by a different team. Add a **CanNotDelete lock** on the vault's resource group and alerts on security events.

Cost has two parts: a **protected instance** fee per VM (about $10 a month for a VM up to 50 GB, illustrative) and **backup storage** per GB, which is higher for GRS than LRS. Instant restore snapshots are billed as managed disk snapshots, so long snapshot retention adds up.

</DeepDive>
