## Start with a question

<Story question="If your office building flooded tonight, where would everyone work tomorrow?">

A sensible company has a second office in another city with desks ready and copies of every file synced overnight, or better, every few minutes. Twice a year they send a small team there for a day to prove the laptops log in, without closing the main office.

**Azure Site Recovery** is that second office for your VMs. It keeps copying every change to **another region**. A **test failover** is the practice day. A real **failover** is moving everyone when the main office floods, and **re-protect** is setting up the sync in the other direction so you can move back later.

</Story>

## Explain it like I'm 10

<Eli10>

You're writing a story in your notebook. Every few minutes your friend copies what you wrote into her notebook at her house.

If your notebook falls in a puddle, you carry on in her notebook. That's **failover**.

Before that ever happens, you practise once by writing a page in a spare notebook, then throwing the spare away. That's a **test failover** and **cleanup**.

When your notebook dries, she starts copying back to yours. That's **re-protect**.

</Eli10>

## The technical explanation

### How Azure-to-Azure replication works

    { title: 'Replicate', text: 'Changes are sent to replica managed disks in West US 2. No VM runs there yet.' },
    { title: 'Recover', text: 'Crash-consistent points every 5 minutes, app-consistent on the policy schedule, kept up to 15 days.' },
  ]}

What lives where:

| Component | Region | Notes |
| --- | --- | --- |
| Source VM, cache storage account | **Source** (East US) | The cache buffers changes before they're sent |
| **Recovery Services vault** | **Target** (West US 2) | Must be in a different region from the VM |
| Replica disks, target resource group, target VNet | **Target** | Created at enable time or chosen by you. The target VM itself is created only at failover |

You can replicate to any region in the same geographic cluster (often the paired region), and into an availability zone. You pay a Site Recovery fee per protected VM (about $25 a month, illustrative, first 31 days free) plus storage, and compute in the target region only while a failed-over or test VM runs.

### Enable replication

**Portal path:** VM > **Backup + disaster recovery > Disaster recovery**. Tabs: *Basics* (target region, replicate to availability zones), *Advanced settings* (target subscription, VM resource group, virtual network, availability, capacity reservation, cache storage, **replication policy**, Recovery Services vault), *Review + Start replication*. You can also start from the vault: **Site Recovery > Azure virtual machines > Enable replication**.

The default **replication policy** keeps recovery points for 24 hours and takes app-consistent snapshots every 4 hours; you can keep points up to **15 days**. **Multi-VM consistency** groups VMs that must share consistent recovery points, such as an app tier and its database.

Most admins enable replication in the portal. From the command line it's PowerShell (`New-AzRecoveryServicesAsrReplicationProtectedItem` with fabrics, containers and mappings) or the `az site-recovery` extension, which needs fabric, protection container and provider JSON. The practice lab below uses a simplified version of those commands.

### Test failover: rehearse without risk

Vault > **Protected items > Replicated items** > the VM > **Test failover**. Pick a **recovery point** and an **Azure virtual network** that's **isolated** from production (a separate test VNet in the target region, so IP addresses don't clash). Site Recovery creates a VM from the recovery point; production keeps running and replicating. Check the app, then run **Cleanup test failover** with notes, which deletes the test VM.

```powershell
$item = Get-AzRecoveryServicesAsrReplicationProtectedItem -ProtectionContainer $container -FriendlyName vm-erp01
$job = Start-AzRecoveryServicesAsrTestFailoverJob -ReplicationProtectedItem $item -Direction PrimaryToRecovery -AzureVMNetworkId $testVnetId
Start-AzRecoveryServicesAsrTestFailoverCleanupJob -ReplicationProtectedItem $item -Comment "Drill passed"
```

### Real failover, commit, re-protect, fail back

| Step | What it does |
| --- | --- |
| **Failover** | Choose a recovery point and create the VM in the target region. Tick **Shut down machine before beginning failover** if the source is still reachable, to avoid data loss |
| **Commit** | Makes the chosen recovery point final and removes the others. Until you commit, you can **change recovery point** |
| **Re-protect** | Starts replication from the target region back to the original region (uses the original disks where possible) |
| **Fail back** | A planned failover back to the original region when it's healthy, then commit and re-protect again |

Recovery point choices: **Latest** (lowest RPO, processes all pending data first, slower), **Latest processed** (lowest RTO, default), **Latest app-consistent**, **Latest multi-VM processed** or **app-consistent** for multi-VM groups, and **Custom**.

```powershell
Start-AzRecoveryServicesAsrUnplannedFailoverJob -ReplicationProtectedItem $item -Direction PrimaryToRecovery
Start-AzRecoveryServicesAsrCommitFailoverJob -ReplicationProtectedItem $item
Update-AzRecoveryServicesAsrProtectionDirection -ReplicationProtectedItem $item -AzureToAzure `
  -ProtectionContainerMapping $reverseMapping -LogStorageAccountId $cacheId -RecoveryResourceGroupId $rgId
```

### Recovery plans

A **recovery plan** groups replicated VMs into ordered **groups** (database first, then app, then web), with **pre and post actions**: Azure Automation runbooks (for example to update DNS or a load balancer) and manual steps. You run test failover, failover and failback on the plan as a whole, which turns a 40-step runbook into one button.

<Callout type="exam">
Three things come up again and again. **Vault location**: in the **target** region, never next to the source VM. **Drills**: "test DR without affecting production or replication" is a **test failover** into an **isolated** VNet, followed by **cleanup test failover**. **Order**: after a real outage it's **failover**, **commit**, **re-protect**; failing back is another failover plus commit and re-protect. Recovery point wording: "**minimise downtime**" = **Latest processed**; "**minimise data loss**" = **Latest**; "**application-consistent**" = **Latest app-consistent**. If several VMs must fail over together in order, the answer is a **recovery plan**.
</Callout>

<DeepDive title="Things that break a real failover">

Capacity: in a big regional outage, many customers fail over to the same region. **Capacity reservation** in the target region guarantees the VM sizes you need. Networking: map the target VNet, subnets, NSGs and public IPs in advance, and plan DNS changes (Traffic Manager or a runbook in the recovery plan). Identity: make sure domain controllers or Microsoft Entra Domain Services are reachable from the target region. And remember that replication copies everything, including ransomware encryption, within minutes. That's why Site Recovery sits next to Azure Backup, not instead of it.

</DeepDive>
