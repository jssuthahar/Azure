## Start with a question

<Story question="Your phone backs up every night. You lost one photo. Do you wipe the phone and restore everything?">

Of course not. You open the backup, find the photo and save it back. You'd only restore the whole phone if it was broken or stolen, and if you were setting up a new phone you'd restore onto that one instead.

Azure Backup gives you the same choices for a VM: copy back **one file**, build a **new VM** next to the old one, restore **just the disks**, or **replace** the broken VM's disks. And because a backup you never check isn't worth much, **Backup reports** and **alerts** tell you when a night's backup didn't happen.

</Story>

## Explain it like I'm 10

<Eli10>

You built a sandcastle and took a photo of it every evening.

If one tower falls, you look at yesterday's photo and rebuild just that tower. That's **File Recovery**.

If the whole castle is washed away, you build a new one from the photo. That's **Create new VM**.

Your teacher keeps a chart of which evenings you remembered the photo. That's **Backup reports**. If you forget, she sends a note home. That's an **alert**.

</Eli10>

## The technical explanation

### Back up now and watch the jobs

The policy runs backups on schedule, but you can start one any time: vault > **Protected items > Backup items > Azure Virtual Machine** > the VM > **Backup now**, and set **Retain Backup Till**. A VM backup has two phases: a **snapshot** (ready for instant restore in minutes) and the **transfer to vault**. Track both in **Monitoring > Backup Jobs**.

```bash
az backup protection backup-now -g rg-ops-bk --vault-name rsv-contoso-eus \
  -c vm-prod01 -i vm-prod01 --backup-management-type AzureIaasVM --retain-until 31-12-2026
az backup job list -g rg-ops-bk --vault-name rsv-contoso-eus -o table
```

```powershell
$item = Get-AzRecoveryServicesBackupItem -VaultId $v.ID -BackupManagementType AzureVM -WorkloadType AzureVM -Name vm-prod01
Backup-AzRecoveryServicesBackupItem -Item $item -VaultId $v.ID -ExpiryDateTimeUTC (Get-Date).AddDays(30)
```

### Restore options for a VM

Select **Restore VM**, choose a **restore point** (crash-consistent, app-consistent or file-system consistent; snapshot tier, vault tier or both), then a configuration:

| Option | What happens | Pick it when |
| --- | --- | --- |
| **Create new > Create new virtual machine** | A new VM with the name, resource group, VNet and subnet you choose | Fast side-by-side recovery, or a test copy |
| **Create new > Restore disks** | Managed disks plus a template land in a resource group | You need to change size, availability or network first, or attach disks to another VM |
| **Replace existing** | The existing VM's disks are replaced; name, NIC and IP stay. Azure snapshots the current disks first | The VM is corrupted but its identity and network should stay the same |
| **Cross Region Restore** | Any of the above in the paired region | GRS vault with CRR enabled, and the primary region is unavailable or you want a copy there |

Restores need a **staging storage account** in the **same region as the vault**. Restores from the snapshot tier are much faster than from the vault tier.

```bash
az backup recoverypoint list -g rg-ops-bk --vault-name rsv-contoso-eus \
  -c vm-prod01 -i vm-prod01 --backup-management-type AzureIaasVM -o table
az backup restore restore-disks -g rg-ops-bk --vault-name rsv-contoso-eus \
  -c vm-prod01 -i vm-prod01 --rp-name <rp> --storage-account stopsrestore01 \
  --target-resource-group rg-ops-bk --target-vm-name vm-prod01-restored \
  --target-vnet-name vnet-prod --target-subnet-name app
# --restore-mode OriginalLocation replaces the existing VM's disks
```

### File Recovery

**File Recovery** > pick a recovery point > **Download Executable** (Windows) or script (Linux), with a password shown once. Run it on the VM or any machine with a compatible OS. It mounts the recovery point's volumes as local drives over iSCSI. Copy what you need, then **Unmount Disks**; the connection closes by itself after 12 hours. CLI: `az backup restore files mount-rp` and `unmount-rp`.

For **Azure Files**, restore the whole share or individual files and folders to the original or an alternate location. For **blobs** in a Backup vault, operational backup restores containers to a point in time; vaulted backup restores from vault copies.

### Stop protection and soft delete

**Stop backup** either **retains backup data** (points stay, nothing new is taken) or **deletes backup data**. With soft delete on, deleted data stays in a **soft-deleted** state for 14 days by default at no charge. **Undelete** brings it back with all recovery points; then **resume backup**.

```bash
az backup protection disable -g rg-ops-bk --vault-name rsv-contoso-eus -c vm-prod01 -i vm-prod01 \
  --backup-management-type AzureIaasVM --delete-backup-data true --yes
az backup protection undelete -g rg-ops-bk --vault-name rsv-contoso-eus -c vm-prod01 -i vm-prod01 \
  --backup-management-type AzureIaasVM --workload-type VM
```

A vault can't be deleted while it holds protected **or soft-deleted** items.

### Backup reports

Backup reports are workbooks that read vault logs from Log Analytics, across vaults, subscriptions and tenants.

1. Create (or reuse) a **Log Analytics workspace**.
2. On each vault, add a **diagnostic setting** with **CoreAzureBackup** and the **AddonAzureBackup*** categories (Jobs, Alerts, Policy, Storage, ProtectedInstance), destination table **Resource specific**. Azure Policy has built-in definitions to deploy this to every vault.
3. Open **Business Continuity Center** (or a vault's **Backup Reports** blade), choose the workspaces, and read the tabs: **Summary, Backup Items, Usage, Jobs, Policies, Optimize, Policy adherence**.

Data can take up to 24 hours to appear the first time. You can also query the tables yourself, for example `AddonAzureBackupJobs | where JobStatus == "Failed"`.

### Backup alerts

- **Built-in Azure Monitor alerts**: Azure Backup raises alerts for **security events** (such as stopping backup with delete data, or soft delete being disabled) and **job failures** (backup and restore). They appear in **Monitor > Alerts** and Business Continuity Center. To get emails or SMS, create an **alert processing rule** that applies your **action group** to them.
- **Metric alerts** on the vault's **Backup Health Events** and **Restore Health Events** metrics for custom conditions.
- **Log search alerts** on AddonAzureBackupJobs for anything else.
- The old classic backup alerts are being retired, so build on Azure Monitor alerts.

<Callout type="exam">
Map each restore need to the option. **One file** = **File Recovery**. **New VM side by side** = **Create new virtual machine**. **Customise before creating** or **attach to another VM** = **Restore disks**. **Keep the same VM name and IP** = **Replace existing**. **Restore in the paired region** = **Cross Region Restore** (GRS). For reports, the answer is always a **diagnostic setting** from the vault to a **Log Analytics workspace** in **resource-specific** mode. For notifications, built-in alerts plus an **alert processing rule** that adds an **action group**. Deleted backups inside the soft delete period are recovered with **undelete**.
</Callout>

<DeepDive title="Test your restores">

A backup that has never been restored is a guess. Schedule a quarterly restore test: restore a VM to an isolated VNet with **Create new**, check the app starts and the data is current, then delete the test VM. Track restore time against your recovery time objective. Restores from the **snapshot tier** take minutes; from the **vault tier**, longer, depending on disk size. If your RTO is tight, keep more days of instant restore snapshots or look at Site Recovery for that workload.

</DeepDive>
