## Start with a question

<Story question="How do you find three late deliveries in a warehouse logbook with 40,000 lines?">

You don't read every line. You say: only this week, only deliveries marked late, then count them per driver. In a spreadsheet you'd filter one column, then make a pivot table.

**KQL** is that habit written down. You name the logbook (a **table**), then add one step per line: keep the late ones (**where**), count them per driver (**summarize**), sort, and draw a chart (**render**). Log Analytics runs it over millions of rows in seconds.

</Story>

## Explain it like I'm 10

<Eli10>

Imagine a big box of Lego bricks of every colour.

First you tip out the box: that's the **table**.

Then you keep only the red bricks: **where**.

Then you sort the red bricks into piles by size and count each pile: **summarize count() by size**.

Then you draw a bar chart of the piles for your teacher: **render**.

</Eli10>

## The technical explanation

You run queries in **Logs**: from a Log Analytics workspace, from **Monitor > Logs**, or from any resource's **Monitoring > Logs** blade (which scopes the query to that resource). Switch the editor to **KQL mode** for full queries. The **time range** picker applies unless the query has its own TimeGenerated filter.

### The shape of a query

```kusto
StorageBlobLogs                                   // 1. start with a table
| where TimeGenerated > ago(24h)                  // 2. filter early (time first)
| where StatusCode >= 400
| summarize Failures = count() by OperationName, CallerIpAddress
| order by Failures desc
| take 10
```

Each line takes the rows from the line above. Read it out loud and you'll know what it does.

### Operators you'll use every week

| Operator | Does | Example |
| --- | --- | --- |
| `where` | Keeps matching rows | `where ResultType != "Success"` |
| `summarize` | Groups and aggregates | `summarize count(), avg(DurationMs) by bin(TimeGenerated, 5m)` |
| `project` | Picks or renames columns | `project TimeGenerated, Caller, ResourceGroup` |
| `extend` | Adds a calculated column | `extend SizeMB = Size / 1048576` |
| `order by` / `sort by` | Sorts | `order by TimeGenerated desc` |
| `take` / `limit`, `top` | Limits rows | `top 10 by Failures` |
| `distinct` | Unique values | `distinct Computer` |
| `join` | Combines two tables on a key | `join kind=inner (Heartbeat) on Computer` |
| `render` | Draws a chart | `render timechart` |

Useful comparisons: `==` (case-sensitive), `=~` (case-insensitive), `!=`, `has` (whole-word match, fast), `contains` (any substring, slower), `in ("a","b")`, `between (a .. b)`. Time helpers: `ago(1h)`, `now()`, `bin(TimeGenerated, 1h)`. Aggregates: `count()`, `dcount()`, `avg()`, `max()`, `min()`, `sum()`, `percentile(x, 95)`, `arg_max(TimeGenerated, *)`.

### Admin tables worth knowing

| Table | Comes from | Typical question |
| --- | --- | --- |
| **AzureActivity** | Activity log exported with a subscription diagnostic setting | Who deleted resources last week? |
| **AzureDiagnostics** | Resource logs in Azure diagnostics mode (Key Vault, many PaaS services) | Who got secrets from the vault? |
| **StorageBlobLogs** | Blob service diagnostic setting (resource-specific) | Which IP keeps getting 403? |
| **Heartbeat** | Azure Monitor Agent | Which VMs went silent? |
| **Perf**, **InsightsMetrics** | AMA data collection rules, VM insights | Which VM is short of memory? |
| **Event**, **Syslog** | AMA data collection rules | Which Windows service crashed? |
| **AzureMetrics** | Metrics sent through a diagnostic setting | Long-term metric history |

If a table is empty, it's usually not a query problem: nothing is sending data there yet.

### Queries an admin actually writes

```kusto
// Who deleted things in the last 7 days?
AzureActivity
| where TimeGenerated > ago(7d)
| where OperationNameValue endswith "DELETE" and ActivityStatusValue == "Success"
| project TimeGenerated, Caller, ResourceGroup, _ResourceId

// VMs that stopped reporting
Heartbeat
| summarize LastSeen = max(TimeGenerated) by Computer
| where LastSeen < ago(15m)

// Failed blob requests per 15 minutes, as a chart
StorageBlobLogs
| where StatusCode >= 400
| summarize count() by bin(TimeGenerated, 15m)
| render timechart
```

From the CLI, `az monitor log-analytics query` runs the same text (PowerShell: `Invoke-AzOperationalInsightsQuery`):

```bash
az monitor log-analytics query -w <workspace GUID> \
  --analytics-query "StorageBlobLogs | where StatusCode >= 400 | summarize count() by OperationName" \
  -t P1D
```

### From query to action

In the Logs toolbar you can **Save** a query (to a query pack), **Share** a link, **Export** to CSV or Power BI, **Pin to** a dashboard or workbook, or select **New alert rule**. A **log search alert** runs the query on a schedule (for example every 5 minutes over the last 15) and fires when the number of rows or an aggregated value crosses a threshold, then calls an action group.

<Callout type="exam">
Expect to read a query and say what it returns, or pick the missing operator. Filtering rows is **where**; choosing columns is **project**; counting per group is **summarize count() by**; time buckets are **bin(TimeGenerated, …)**; charts are **render**. `ago(1h)` is a time value, not a bucket. A query that starts with a pipe or names the table later is wrong. If a scenario says a table has no data, look for the missing **diagnostic setting** or **agent**, not a KQL fix.
</Callout>

<DeepDive title="Query scope, cost and speed">

A query run from a resource's Logs blade is **resource-context**: it only sees rows for that resource, even in a shared workspace. That's how people with access to one VM can query only its data, depending on the workspace access mode. From the workspace, you see everything you have rights to.

Queries on Analytics tables don't cost extra; you pay for ingestion and retention. **Basic** and **Auxiliary** table plans are cheaper to ingest but charge per GB scanned and support a limited set of operators. Keep queries fast by filtering on TimeGenerated first, using `has` over `contains`, and projecting only the columns you need before a `join`.

</DeepDive>
