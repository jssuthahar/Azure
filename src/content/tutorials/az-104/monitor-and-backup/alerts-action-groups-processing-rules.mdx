## Start with a question

<Story question="Your house has a smoke alarm. Who should it ring, and should it ring while you're making toast?">

The smoke detector decides there's a problem. That's the **alert rule**. What happens next is a separate choice: beep in the hall, text your phone, call the neighbour. That list is the **action group**, and every detector in the house can share it.

And when you know you're about to burn the toast, you press the hush button for ten minutes. The detector still notices the smoke, it just doesn't call anyone. That's an **alert processing rule**.

</Story>

## Explain it like I'm 10

<Eli10>

A teacher watches the class. If it gets too noisy for five minutes, that's the rule, and it **fires**.

The teacher has a list: tell the head teacher, ring the bell, write it on the board. That list is the **action group**.

On sports day everyone is noisy on purpose, so the head says "don't tell me about noise today". That's the **processing rule**. The teacher still notices, but nobody gets called.

</Eli10>

## The technical explanation

Azure Monitor alerts have three building blocks. Keeping them separate is the whole trick.

### Alert rule types

| Type | Signal | Evaluated | Use it for |
| --- | --- | --- | --- |
| **Metric** | Platform or custom metric | Every 1 to 15 minutes over a lookback (window) | CPU, memory, disk, availability, queue length. **Static** or **dynamic** thresholds. One rule can watch many VMs in a resource group |
| **Log search** | A KQL query on a workspace | On a schedule (1 minute to 24 hours) | Event IDs, failed sign-ins, patterns across tables |
| **Activity log** | Activity log events | When the event arrives | "Someone deleted a VM", policy events, **Service Health** (Azure incident in your region) and **Resource Health** (your VM became unavailable) |
| Smart detection, Prometheus | Application Insights, managed Prometheus | Varies | App anomalies, Kubernetes metrics |

Every rule has a **scope** (a resource, resource group or subscription), a **condition**, **action groups**, and **details**: name, **severity** (Sev0 critical to Sev4 verbose), and whether it **automatically resolves**. Metric alerts are **stateful** by default: they fire once, then resolve when the condition clears.

**Portal path:** **Monitor > Alerts > + Create > Alert rule**, or **New alert rule** from Metrics explorer or Logs. Tabs: *Scope, Condition, Actions, Details, Tags, Review + create*.

```bash
az monitor metrics alert create -g rg-ops-alerts -n alert-cpu-high \
  --scopes <vm id> --condition "avg Percentage CPU > 80" \
  --window-size 5m --evaluation-frequency 1m --severity 2 --action ag-ops
```

### Action groups

An **action group** is a global resource with a **display name** of at most **12 characters** (it shows up in SMS and emails). It holds:

- **Notifications**: email, SMS, Azure mobile app push, voice call, and **email Azure Resource Manager role** (for example every Owner of the subscription).
- **Actions**: **webhook** and **secure webhook**, **Logic App**, **Azure Function**, **Automation runbook**, **Event Hubs**, **ITSM** connector.

Azure rate-limits some notifications, for example no more than one SMS or voice call every 5 minutes per number and about 100 emails an hour per address, so an alert storm doesn't flood a phone. Many alert rules can share one action group; change the on-call number once and every rule follows.

```bash
az monitor action-group create -g rg-ops-alerts -n ag-ops --short-name opsteam \
  --action email ops ops@contoso.com \
  --action sms oncall 1 5555550100 \
  --action webhook itsm https://itsm.contoso.com/hooks/azure
```

```powershell
$email = New-AzActionGroupEmailReceiverObject -Name ops -EmailAddress ops@contoso.com
New-AzActionGroup -ResourceGroupName rg-ops-alerts -Name ag-ops -ShortName opsteam `
  -Location Global -EmailReceiver $email
```

### Alert processing rules

An **alert processing rule** doesn't create alerts. It changes what happens to alerts that fire within its **scope**:

| Setting | Options |
| --- | --- |
| **Rule type** | **Suppress notifications** (removes all action groups) or **Apply action group** (adds one or more) |
| **Filters** | Alert rule name, severity, monitor service, resource type, alert context and more |
| **Scheduling** | **Always**, **At a specific time** (one window), or **Recurring** (daily, weekly or monthly with start and end times and a time zone) |

Suppressed alerts still appear in **Monitor > Alerts** with their history, so you keep a record. If a suppression rule and an apply rule both match, suppression wins.

```bash
az monitor alert-processing-rule create -g rg-ops-alerts -n apr-patch-window \
  --scopes /subscriptions/<sub>/resourceGroups/rg-ops-alerts \
  --rule-type RemoveAllActionGroups \
  --schedule-recurrence-type Weekly --schedule-recurrence Saturday \
  --schedule-recurrence-start-time 21:00:00 --schedule-recurrence-end-time 23:59:00
```

### Working with fired alerts

In **Monitor > Alerts** each alert has a **condition state** set by Azure (*Fired*, *Resolved*) and a **user response** you set (*New*, *Acknowledged*, *Closed*). Acknowledging tells your team someone is on it; it doesn't stop the condition.

<Callout type="exam">
Separate the three jobs. Questions that ask "**when** should we be told" are about the **alert rule** (and its type: metric for numbers, log search for KQL, activity log for deletes and Service Health). "**Who** gets told and **what** runs" is the **action group**. "**Don't** notify during maintenance" or "also send **all** Sev0 alerts in the subscription to security" is an **alert processing rule**, which is less work than editing every rule. A short name over 12 characters is invalid. Suppression doesn't stop alerts from firing.
</Callout>

<DeepDive title="Costs, scale and noise">

Metric alerts are charged per monitored time series (about $0.10 a month each, illustrative), so one rule over 50 VMs costs more than one over a single VM. Log search alerts are charged by frequency: a 1-minute query costs more than a 15-minute one. SMS and voice notifications cost per message after a free allowance; email and push are free.

To cut noise, use **dynamic thresholds** for metrics with daily patterns, set a sensible lookback so a 30-second blip doesn't page anyone, and enable **automatically resolve**. Use **Azure Policy** built-in initiatives (Azure Monitor baseline alerts) to create the same alert rules across many subscriptions.

</DeepDive>
