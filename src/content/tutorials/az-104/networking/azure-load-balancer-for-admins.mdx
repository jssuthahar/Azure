A **public** load balancer uses a Standard public IP; an **internal** one uses a private IP in a subnet. A **load-balancing rule** maps a frontend port to a backend port and uses a **health probe** (TCP, HTTP or HTTPS) to send new flows only to healthy instances. keyTerms:
  - term: Frontend IP configuration
    definition: The IP address clients connect to. A Standard public IP for a public load balancer, or a private IP in a subnet for an internal one.
  - term: Backend pool
    definition: The VMs or scale set instances, by NIC or by IP address in one VNet, that receive the traffic.
  - term: Health probe
    definition: A regular TCP, HTTP or HTTPS check of each backend. HTTP and HTTPS need a 200 response to count as healthy.
  - term: Load-balancing rule
    definition: Maps a frontend IP and port to a backend pool and port, with a probe, distribution mode and options such as floating IP.
  - term: Session persistence

  - term: Inbound NAT rule
    definition: Forwards one frontend port to one backend instance, for example port 50001 to VM1 port 22.

<Story question="How does a busy café keep the queue moving when one barista goes on break?">

The manager points each new customer to a free barista. Every few minutes she glances along the counter, and if someone has stepped away, she stops sending customers to that spot until they're back.

## The technical explanation

### The parts

| Part | What you set |
| --- | --- |
| **Frontend IP** | Public (a Standard public IP, zone-redundant) or internal (a private IP in a subnet) |
| **Backend pool** | VMs or scale set instances by **NIC** or by **IP address**, all in **one VNet** |
| **Health probe** | Protocol TCP, HTTP or HTTPS, port, path (HTTP/S), interval (default 5 seconds) |
| **Load-balancing rule** | Frontend IP + port → backend pool + port, probe, session persistence, idle timeout, floating IP, TCP reset |
| **Inbound NAT rule** | One frontend port → one VM (for example 50001 → VM1:22) |
| **Outbound rule** | SNAT for outbound internet from the pool (public load balancer) |

Distribution: **None** (5-tuple hash of source IP, source port, destination IP, destination port, protocol), **Client IP** (2-tuple) or **Client IP and protocol** (3-tuple). **HA ports** (all ports, all protocols) exist on internal Standard load balancers for NVAs.

### Standard SKU behaviour

- **Secure by default**: backends get no inbound traffic unless an NSG on the subnet or NIC allows it.
- **Zone-redundant** frontends, 99.99% SLA, HTTPS probes, up to 1,000 backend instances.
- Backends must be in **one virtual network**.
- **Basic was retired** on 30 September 2025, so new deployments are Standard (or Gateway for chaining NVAs).

Price feel: about $0.025 an hour for the first 5 rules plus a small charge per GB processed (illustrative).

### Troubleshooting

| Symptom | Likely cause | Check |
| --- | --- | --- |
| One backend never gets traffic | Probe fails on that VM | Probe port/path, app listening, NSG blocking **AzureLoadBalancer** / 168.63.129.16, guest firewall |
| All backends Down | Probe misconfigured | Wrong port, HTTP path returns 404 or 301 |
| Probes healthy, clients time out | NSG doesn't allow client traffic | Effective security rules on the backend NIC (Standard is secure by default) |
| Backend VM can't reach the internal frontend | Flow hashed back to itself | Not supported; call the other tier directly |
| Uneven distribution | Few clients behind one NAT | Expected with hashing; review session persistence |

Use **Load balancer → Insights** and the metrics **Health Probe Status** (DipAvailability) and **Data Path Availability** (VipAvailability), plus Network Watcher on the backend VMs.

### Portal and CLI

Portal: **Load balancers → + Create**: **Basics** (SKU Standard, Type Public or Internal, Tier Regional) → **Frontend IP configuration** → **Backend pools** → **Inbound rules** (rule + new health probe) → **Review + create**.

```bash
az network public-ip create -g rg-net-lb -n pip-lb --sku Standard --allocation-method Static
az network lb create -g rg-net-lb -n lb-web --sku Standard --public-ip-address pip-lb \
  --frontend-ip-name fe-web --backend-pool-name bepool-web
az network lb probe create -g rg-net-lb --lb-name lb-web -n probe-http --protocol Http --port 80 --path /health
az network lb rule create -g rg-net-lb --lb-name lb-web -n rule-http --protocol Tcp \
  --frontend-port 80 --backend-port 80 --frontend-ip-name fe-web --backend-pool-name bepool-web --probe-name probe-http
az network nic ip-config address-pool add -g rg-net-lb --nic-name nic-web01 --ip-config-name ipconfig1 \
  --lb-name lb-web --address-pool bepool-web
# Internal instead: az network lb create ... --vnet-name vnet-web --subnet snet-app --private-ip-address 10.40.2.10
```

PowerShell: `New-AzLoadBalancerFrontendIpConfig`, `New-AzLoadBalancerBackendAddressPoolConfig`, `New-AzLoadBalancerProbeConfig`, `New-AzLoadBalancerRuleConfig`, `New-AzLoadBalancer -Sku Standard`.

<Callout type="exam">
Read for the layer: TCP/UDP across VMs is **Load Balancer**; URL paths, TLS offload or a WAF is **Application Gateway**. "Only reachable from inside the VNet" is an **internal** frontend. When a backend is unhealthy, the answers are the **probe** (port, path, a 200 response) or an **NSG blocking AzureLoadBalancer / 168.63.129.16**. A Standard load balancer with **no NSG** on its backends lets nothing in. "Users must stay on the same VM" is **Client IP** session persistence.
</Callout>

<DeepDive title="Floating IP and HA ports">

**Floating IP** (direct server return) keeps the frontend IP as the destination when the packet reaches the VM, which SQL Server Always On listeners need. **HA ports** on an internal Standard load balancer balance every port and protocol with one rule, which is how you put a pair of firewall NVAs behind one internal frontend and point UDRs at it.

</DeepDive>
