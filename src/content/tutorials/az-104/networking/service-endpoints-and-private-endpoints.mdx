## Start with a question

<Story question="Is a staff-only lane at the airport the same as having your own gate inside the building?">

A staff lane still leads to the public terminal, but only people with a staff badge get through it. Your own gate is a door inside your office that opens straight onto the plane.

A **service endpoint** is the staff lane: your subnet reaches the storage account's **public** address, and the account's firewall lets in only your subnet. A **private endpoint** is your own gate: the account gets a **private address inside your network**, so you can close the public terminal completely.

</Story>

## The technical explanation

### Service endpoints

Enable a service endpoint on a **subnet** for a service such as **Microsoft.Storage**, **Microsoft.Sql**, **Microsoft.KeyVault** or **Microsoft.Web**. Then:

- Traffic from the subnet to that service takes the **Microsoft backbone**, and Azure adds a route with next hop **VirtualNetworkServiceEndpoint**.
- The service sees the traffic coming from your **subnet** (private source IP), so you add a **virtual network rule** in its firewall and set the default action to deny.
- The service's endpoint is still **public**, and **on-premises traffic can't use** the endpoint.
- It's **free**. A **service endpoint policy** can limit Microsoft.Storage to named storage accounts.

```bash
az network vnet subnet update -g rg-net-paas --vnet-name vnet-paas -n snet-app --service-endpoints Microsoft.Storage
az storage account network-rule add -g rg-net-paas --account-name stfabrikampaas01 --vnet-name vnet-paas --subnet snet-app
az storage account update -g rg-net-paas -n stfabrikampaas01 --default-action Deny
```

Portal: storage account → **Networking → Firewalls and virtual networks → Enabled from selected virtual networks and IP addresses → + Add existing virtual network**. The portal enables the endpoint on the subnet for you.

### Private endpoints

A private endpoint is a **NIC** in your subnet with a private IP (for example 10.30.2.4) that connects through **Azure Private Link** to **one resource and one target sub-resource** (blob, file, queue, table, dfs, web for storage; sqlServer for SQL; vault for Key Vault). Then:

- Clients in the VNet, **peered VNets** and **on-premises** (over VPN or ExpressRoute) reach the resource on that private IP.
- You can set the resource's **public network access** to **Disabled**.
- Cost is about $0.01 an hour per endpoint plus per GB processed (illustrative).

### DNS makes or breaks it

When a private endpoint exists, public DNS answers `stfabrikampaas01.blob.core.windows.net` with a CNAME to `stfabrikampaas01.privatelink.blob.core.windows.net`. If your VNet has a **private DNS zone** `privatelink.blob.core.windows.net` **linked** to it, with an A record for the account, the name resolves to the private IP. Without that zone or link, it resolves to the **public IP**, and if public access is off, connections fail.

The portal's **Integrate with private DNS zone: Yes** creates the zone, the VNet link and a **DNS zone group** that keeps the A record updated.

```bash
az network private-endpoint create -g rg-net-paas -n pe-stfabrikam-blob --vnet-name vnet-paas --subnet snet-pe \
  --private-connection-resource-id <storage-account-id> --group-id blob --connection-name stfabrikam-blob
az network private-dns zone create -g rg-net-paas -n privatelink.blob.core.windows.net
az network private-dns link vnet create -g rg-net-paas -n link-vnet-paas \
  --zone-name privatelink.blob.core.windows.net --virtual-network vnet-paas --registration-enabled false
az network private-endpoint dns-zone-group create -g rg-net-paas --endpoint-name pe-stfabrikam-blob \
  -n default --private-dns-zone privatelink.blob.core.windows.net --zone-name blob
nslookup stfabrikampaas01.blob.core.windows.net
```

### Side by side

| | Service endpoint | Private endpoint |
| --- | --- | --- |
| Service address | Public | Private IP in your subnet |
| Works from on-premises | No | Yes |
| Scope | Whole service (policy can narrow storage) | One resource and sub-resource |
| DNS change | None | privatelink zone |
| Disable public access | No | Yes |
| Cost | Free | Per hour + per GB |

<Callout type="exam">
Pick on three clues. **On-premises** or **peered VNet** access, or "no public endpoint at all" means **private endpoint**. "Restrict the storage account to Subnet1" with nothing about on-premises usually means **service endpoint plus a virtual network rule**. And if a private endpoint exists but clients still hit the public IP, the answer is the **private DNS zone or its virtual network link**, not another endpoint. Remember a **blob** endpoint doesn't cover **file**.
</Callout>

<DeepDive title="Network policies for private endpoints">

By default, NSGs and UDRs on a subnet don't apply to private endpoints in it. You can turn on **private endpoint network policies** on the subnet (`--private-endpoint-network-policies Enabled`), after which NSG rules and route tables affect traffic to the endpoints. That's how you force private endpoint traffic through a firewall.

</DeepDive>
