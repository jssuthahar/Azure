## Start with a question

<Story question="If you're friends with Priya and Priya is friends with Sam, are you friends with Sam?">

Not automatically. You might meet Sam at Priya's party, but you don't have Sam's number. You'd have to swap numbers yourself, or ask Priya to pass messages along.

**VNet peering** works the same way. Peer spoke 1 with the hub and spoke 2 with the hub, and each spoke can talk to the hub. The spokes still can't talk to each other, because **peering isn't transitive**. They need their own peering, or the hub has to pass the messages on.

</Story>

## The technical explanation

### What a peering is

A peering connects two VNets so they route to each other directly. Traffic stays **private** and on **Microsoft's backbone**, latency is like being in one network, and there's no gateway in the path. It works:

- In the same region (**regional peering**) or across regions (**global peering**).
- Across subscriptions and across Microsoft Entra tenants (you need permissions on both VNets, such as Network Contributor).

Each side has its own link. One side alone shows **Initiated**; when both exist, both show **Connected**. If one side is deleted, the other shows **Disconnected** and you recreate it.

Rules to remember:

- Address spaces **can't overlap**.
- Peering is **not transitive**.
- NSGs still apply. The default rule AllowVnetInBound covers peered VNets, because the VirtualNetwork tag includes peered address spaces.
- You pay per GB in and out of each side; global peering costs more (around $0.01 to $0.035 per GB, illustrative).

### Peering settings

| Setting (portal wording, simplified) | What it does |
| --- | --- |
| Allow *A* to access *B* | Lets traffic flow at all. On by default. |
| Allow *A* to receive forwarded traffic from *B* | Accepts packets that didn't start in *B*, for example forwarded by an NVA in the hub. |
| Allow gateway or route server in *A* to forward traffic to *B* | **Allow gateway transit** on the side that has the gateway (the hub). |
| Enable *A* to use *B*'s remote gateway or route server | **Use remote gateways** on the side without a gateway (the spoke). |

For **gateway transit**, the hub needs a VPN or ExpressRoute gateway, the spoke can't have its own, and the hub link must allow transit before the spoke link can use remote gateways.

### Hub and spoke

Shared services (firewall, VPN gateway, Bastion, DNS) live in the **hub**. Each workload gets a **spoke** peered to the hub. Spoke-to-spoke traffic goes through the hub firewall using **user-defined routes**, or you peer specific spokes directly. **Azure Virtual Network Manager** can create these topologies for many VNets at once.

### Portal and CLI

Portal: **vnet-hub → Settings → Peerings → + Add**. One form creates both links.

```bash
az network vnet peering create -g rg-net-hub -n hub-to-spoke1 \
  --vnet-name vnet-hub --remote-vnet vnet-spoke1 --allow-vnet-access --allow-gateway-transit
az network vnet peering create -g rg-net-hub -n spoke1-to-hub \
  --vnet-name vnet-spoke1 --remote-vnet vnet-hub --allow-vnet-access \
  --allow-forwarded-traffic --use-remote-gateways
az network vnet peering list -g rg-net-hub --vnet-name vnet-hub -o table
```

For a remote VNet in another resource group or subscription, pass its full resource ID to `--remote-vnet`. In PowerShell it's `Add-AzVirtualNetworkPeering` (once per side), with `-AllowGatewayTransit` and `-UseRemoteGateways`.

<Callout type="exam">
Expect a chain question: VNet1 to VNet2 to VNet3, can VNet1 reach VNet3? **No**, peering isn't transitive. "Spokes must use the hub's VPN gateway" needs settings on **both** links: **allow gateway transit** on the hub side and **use remote gateways** on the spoke side. A peering that won't create almost always has **overlapping address spaces**. Peering one way only leaves it **Initiated**.
</Callout>

<DeepDive title="Changing address space on a peered VNet">

You can add or resize address ranges on a VNet that's already peered. After the change the peering shows it's out of sync, and you run **Sync** on the remote side (portal button or `az network vnet peering sync`) so the other VNet learns the new range. You no longer need to delete and recreate the peering.

</DeepDive>
