keyTerms:
  - term: Network security group (NSG)
    definition: A set of stateful allow and deny rules for inbound and outbound traffic, attached to subnets and/or network interfaces.
  - term: Priority
    definition: A number from 100 to 4096. Lower numbers are processed first, and processing stops at the first match.
  - term: Default security rules
    definition: AllowVnetInBound (65000), AllowAzureLoadBalancerInBound (65001), DenyAllInBound (65500), and the outbound equivalents including AllowInternetOutBound. They can't be deleted, only overridden.
  - term: Service tag
    definition: A Microsoft-maintained name for a group of IP ranges, such as Internet, VirtualNetwork, AzureLoadBalancer or Storage.
  - term: Application security group (ASG)
    definition: A label you attach to NICs so NSG rules can use it as a source or destination instead of IP addresses.
  - term: Effective security rules
    definition: The combined rules from every NSG that applies to a NIC, shown on the NIC in the portal or with az network nic list-effective-nsg.

    a: >-

  - level: intermediate
    q: You allowed port 443 in the subnet NSG, but traffic is still blocked. Why?
    a: >-

    followUps: []
  - level: experienced
    q: Why use application security groups instead of IP addresses in rules?
    a: >-
      Rules then describe roles. "Internet to asg-web on 443, asg-web to asg-db on 1433" stays the same when servers are added, removed or re-addressed; you just put the new NIC in the ASG. ## Start with a question

<Story question="Why does a visitor get past reception but still can't open the lab door?">

Reception checks the visitor list for the whole building. The lab has its own card reader with its own list. Being on reception's list doesn't put you on the lab's.

A **subnet NSG** is reception and a **NIC NSG** is the lab door. Traffic coming in has to pass both. And instead of writing every visitor's name, you can write "anyone with a contractor badge". That badge is an **application security group**.

## The technical explanation

### Rules

Each rule has a **name**, **priority** (100 to 4096), **source** and **destination** (IP, CIDR, **service tag** or **ASG**), **source and destination ports**, **protocol** (TCP, UDP, ICMP or Any), **direction** and **action** (Allow or Deny). Azure checks rules from the **lowest number up** and **stops at the first match**.

Default rules you can't delete:

| Direction | Name | Priority | Effect |
| --- | --- | --- | --- |
| Inbound | AllowVnetInBound | 65000 | Allow from the VirtualNetwork tag (your VNet, peered VNets, on-premises via gateway) |
| Inbound | AllowAzureLoadBalancerInBound | 65001 | Allow health probes from 168.63.129.16 |
| Inbound | DenyAllInBound | 65500 | Deny everything else |
| Outbound | AllowVnetOutBound | 65000 | Allow to VirtualNetwork |
| Outbound | AllowInternetOutBound | 65001 | Allow to Internet |
| Outbound | DenyAllOutBound | 65500 | Deny everything else |

NSGs are **stateful**: when inbound traffic is allowed, its replies go out without an outbound rule. An NSG must be in the **same region** as what it's attached to, and one NSG can be attached to many subnets and NICs.

### Subnet NSG plus NIC NSG

Most designs put NSGs on **subnets** and avoid NIC NSGs unless one VM really needs different rules. Two layers make troubleshooting harder.

### Application security groups

Create an ASG (for example `asg-web`), add NICs to it, and use it as the source or destination in NSG rules: *Internet → asg-web : 443 allow*, *asg-web → asg-db : 1433 allow*. New web servers just join the ASG. Limits: all NICs in an ASG are in the **same VNet**, and if a rule uses ASGs for both source and destination, they must be in the same VNet.

### Effective security rules

On a running VM's NIC, **Help → Effective security rules** shows each NSG that applies (subnet and NIC) with its merged rules. **Network Watcher → IP flow verify** tests one flow and names the rule that allowed or denied it. **NSG diagnostics** does the same for a broader range of sources.

### Portal and CLI

Portal: **Network security groups → + Create**, then **Inbound security rules → + Add**, then **Subnets → Associate** (or NIC → **Network security group**). **Application security groups → + Create**, then on the NIC **Application security groups → Add**.

```bash
az network asg create -g rg-net-sec -n asg-web
az network nic create -g rg-net-sec -n nic-web01 --vnet-name vnet-app --subnet snet-web --application-security-groups asg-web
az vm create -g rg-net-sec -n web01 --image Ubuntu2204 --nics nic-web01
az network nsg create -g rg-net-sec -n nsg-snet-web
az network nsg rule create -g rg-net-sec --nsg-name nsg-snet-web -n Allow-HTTPS-to-web \
  --priority 200 --direction Inbound --access Allow --protocol Tcp \
  --source-address-prefixes Internet --destination-asgs asg-web --destination-port-ranges 443
az network vnet subnet update -g rg-net-sec --vnet-name vnet-app -n snet-web --network-security-group nsg-snet-web
az network nic list-effective-nsg -g rg-net-sec -n nic-web01
az network watcher test-ip-flow -g rg-net-sec --vm web01 --direction Inbound --protocol TCP \
  --local 10.20.1.4:443 --remote 203.0.113.10:50000
```

PowerShell: `New-AzNetworkSecurityRuleConfig`, `New-AzNetworkSecurityGroup`, `New-AzApplicationSecurityGroup`, `Get-AzEffectiveNetworkSecurityGroup`.

<Callout type="exam">
The exam loves a table of rules with priorities and asks what happens to one packet. Sort by **priority number**, find the **first match**, and remember the **DenyAllInBound** at 65500 catches anything unmatched. If there are NSGs on both the subnet and the NIC, the packet needs an allow in **both**. "Rules shouldn't need updating when VMs are added" points to **ASGs**. A rule blocking **AzureLoadBalancer** breaks load balancer health probes.
</Callout>

<DeepDive title="Augmented rules and service tags">

A single rule can list several IP ranges, ports and service tags (augmented security rules), so you rarely need dozens of near-identical rules. Service tags such as `Storage.EastUS`, `Sql`, `AzureMonitor` or `GatewayManager` are kept up to date by Microsoft, which is why they beat hard-coded IP lists for outbound rules to Azure services.

</DeepDive>
