  - term: Azure Network Watcher
    definition: A regional service with network diagnostic and monitoring tools, enabled automatically when you create a VNet in a region.
  - term: IP flow verify
    definition: Tests whether a single flow (protocol, local IP:port, remote IP:port, direction) to or from a VM is allowed, and names the NSG rule that decides.
  - term: Next hop
    definition: Shows the next hop type, next hop IP and route table for a packet from a VM to a destination IP.
  - term: Connection troubleshoot
    definition: Tests connectivity from a VM to another VM, IP or FQDN on a port and reports reachability, latency and the hop where it fails.
  - term: Effective routes
    definition: The combined system, BGP and user-defined routes applied to a NIC, with each route's state.
  - term: NSG diagnostics
    definition: A Network Watcher tool that evaluates NSG rules for a traffic pattern across the NSGs on its path.

  - level: beginner
    q: A VM can't reach another VM. What's the first tool you'd use?
    a: >-
      Connection troubleshoot in Network Watcher. It tests the real path on the port I care about and tells me whether it's reachable, and if not, which hop failed, which points me at routes or NSGs.
    followUps: []
  - level: intermediate
    q: What's the difference between IP flow verify and next hop?
    a: >-
      IP flow verify answers "is this flow allowed?" by checking NSG rules and naming the rule. Next hop answers "where does this packet go?" by checking routes and returning the next hop type, like VirtualAppliance, Internet or None. One is security, the other is routing.
    followUps: []
  - level: experienced
    q: Next hop returns None between two spokes. What does that tell you?
    a: >-
      There's no route to the destination, so Azure drops the packet. Between spokes that are only peered to a hub, that's non-transitive peering. I'd either peer them directly or add UDRs on both spokes to a hub NVA, turn on IP forwarding on the NVA and allow forwarded traffic on the peerings.
    followUps: []
  - level: scenario
    q: After adding a firewall in the hub, spoke VMs lost access to each other. Routes point at the firewall. Walk through your checks.
    a: >-
      Next hop from a spoke VM should say VirtualAppliance with the firewall IP. Then I check IP forwarding on the firewall's NIC if it's an NVA, the return route in the other spoke so traffic is symmetric, allow forwarded traffic on the spoke peerings, and the firewall's own rules. Connection troubleshoot then confirms which hop still fails.
    followUps: []

## The technical explanation

### Work through the layers

| Question | Tool | What a bad answer looks like |
| --- | --- | --- |
| Can A reach B on port X at all? | **Connection troubleshoot** (`az network watcher test-connectivity`) | Unreachable, with the hop that failed |
| Where does the packet go? | **Next hop** (`show-next-hop`), **Effective routes** on the NIC | None, Internet when you expected VirtualAppliance, a wrong appliance IP |
| Which NSG rule decides? | **IP flow verify** (`test-ip-flow`), **Effective security rules**, **NSG diagnostics** | Deny with the rule name, such as DenyAllInBound on the NIC NSG |
| Does the name resolve right? | `nslookup` from a VM in the VNet | Public IP for a private endpoint, NXDOMAIN for a private zone |
| Is it the app? | Packet capture, the VM's own firewall and logs | Port not listening |

**Network Watcher** is enabled automatically in each region where you have a VNet (resources live in **NetworkWatcherRG**). Most tools need the VM running and the **Network Watcher agent** extension for packet capture and connection troubleshoot. Monitoring tools such as **Connection monitor** and **VNet flow logs** belong to the monitoring domain; here we troubleshoot one problem at a time.

### Classic causes

| Symptom | Cause | Fix |
| --- | --- | --- |
| Spoke 1 can't reach spoke 2, next hop None | Peering isn't transitive | Peer them, or UDRs to a hub NVA on both sides |
| Peering shows Initiated | Only one side created | Create the other link |
| Peering won't create | Overlapping address spaces | Re-address one VNet |
| Packets die at the NVA | IP forwarding off, or no return route | Enable IP forwarding (NIC and OS), add the mirror route |
| NVA forwards into a spoke but it's dropped | Peering doesn't allow forwarded traffic | Allow forwarded traffic on the spoke's peering |
| Allowed on the subnet, still blocked | NIC-level NSG | Fix or remove the NIC NSG |
| Load balancer backend Down | Probe blocked or wrong port/path | Allow AzureLoadBalancer, fix the probe |
| Private endpoint ignored | No privatelink DNS zone or VNet link | Link the zone, add a DNS zone group |

### Portal and CLI

Portal: **Network Watcher → Network diagnostic tools → Connection troubleshoot / IP flow verify / Next hop / Effective security rules**. On a NIC: **Help → Effective routes** and **Effective security rules**. From a VM: **Help → Connection troubleshoot**.

```bash
az network watcher test-connectivity -g rg-net-hub --source-resource vm-app1 --dest-address 10.2.1.4 --dest-port 443
az network watcher show-next-hop -g rg-net-hub --vm vm-app1 --source-ip 10.1.1.4 --dest-ip 10.2.1.4
az network watcher test-ip-flow -g rg-net-hub --vm vm-app2 --direction Inbound --protocol TCP \
  --local 10.2.1.4:443 --remote 10.1.1.4:50000
az network nic show-effective-route-table -g rg-net-hub -n nic-app1 -o table
az network nic list-effective-nsg -g rg-net-hub -n nic-app2
```

PowerShell: `Test-AzNetworkWatcherConnectivity`, `Get-AzNetworkWatcherNextHop`, `Test-AzNetworkWatcherIPFlow`, `Get-AzEffectiveRouteTable`.

<Callout type="exam">
Match the question to the tool. "Which security rule blocks it?" is **IP flow verify** (or effective security rules). "Does traffic go to the virtual appliance?" is **Next hop**. "Test from VM1 to an FQDN on a port and see where it fails" is **Connection troubleshoot**. "Capture traffic for analysis" is **Packet capture**. If the scenario involves three VNets in a chain, the answer is usually **non-transitive peering**.
</Callout>

<DeepDive title="Why Cloud Shell can't test your VNet">

Cloud Shell runs in a Microsoft-managed container outside your VNet (unless you deploy it into a VNet), so `nslookup` or `curl` from it tests the public internet path, not what your VMs see. Network Watcher tools run from the VM's NIC, which is why they give the real answer for private endpoints, private zones and UDRs.

</DeepDive>
