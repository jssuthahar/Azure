## Start with a question

<Story question="If someone steals the key to your house, how do you still keep them out?">

You put a guard at the gate of your housing society. The guard has a list: residents of Block A, the office van, the milk delivery. A stranger walks up holding a perfectly good copy of your house key. The guard doesn't care about the key. The stranger isn't on the list, so the stranger doesn't get through the gate.

That's the **storage firewall**. Keys and SAS tokens decide *what* someone can do. The firewall decides *where* they're allowed to come from, and it checks first.

</Story>

## The technical explanation

Every storage account has a public endpoint, such as `https://stcontoso.blob.core.windows.net`. Out of the box it accepts requests from **all networks**. The storage firewall (Microsoft calls it *network security* for the account) lets you narrow that down.

### The settings on the Networking blade

In the portal go to the storage account, then **Security + networking > Networking > Firewalls and virtual networks**. Under **Public network access** you'll see three choices:

| Choice | What it means |
| --- | --- |
| Enabled from all networks | Default action **Allow**. Anyone on any network can try. |
| Enabled from selected virtual networks and IP addresses | Default action **Deny**. Only the rules and exceptions below get in. |
| Disabled | No public access at all. Only **private endpoints** work. |

Once you pick *selected networks*, four kinds of exceptions open up:

- **Virtual networks**: add a subnet. The subnet needs the **Microsoft.Storage** service endpoint, and the portal offers to turn it on for you. Traffic then reaches storage over the Azure backbone and storage knows which subnet it came from.
- **Firewall (IP rules)**: public IPv4 addresses or CIDR ranges, such as `198.51.100.0/24` for an office. Private ranges (10.x, 172.16-31.x, 192.168.x) are refused, and `/31` or `/32` ranges aren't supported, so add a single address without a prefix. There's also a tick box to add your own client IP so the portal can still show data.
- **Resource instances**: allow one specific resource, like a single Azure AI Search service, based on its managed identity.
- **Exceptions**: *Allow Azure services on the trusted services list to access this storage account* (Azure Backup, Event Grid, Azure Monitor and others), plus read access to storage logging and metrics.

<Callout type="note">
IP rules don't apply to requests that come from the **same Azure region** as the account, because those use private Azure addresses. For an Azure VM or app in the same region, use a **virtual network rule** or a **private endpoint**, not its public IP.
</Callout>

### Data plane, not management plane

The firewall guards **data**: blobs, files, queues and tables. It doesn't stop `az storage account show`, listing keys or changing settings, because those go through Azure Resource Manager and are controlled by Azure RBAC. That's why you can lock yourself out of reading blobs while still being able to fix the firewall.

### The same thing in the CLI and PowerShell

```bash
# Block by default, but keep trusted Azure services working
az storage account update -g rg-storage-prod -n stcontosoprod \
  --default-action Deny --bypass AzureServices

# Allow one subnet (it needs the Microsoft.Storage service endpoint)
az network vnet subnet update -g rg-storage-prod --vnet-name vnet-app -n snet-app \
  --service-endpoints Microsoft.Storage
az storage account network-rule add -g rg-storage-prod --account-name stcontosoprod \
  --vnet-name vnet-app --subnet snet-app

# Allow the office's public range
az storage account network-rule add -g rg-storage-prod --account-name stcontosoprod \
  --ip-address 198.51.100.0/24
```

```powershell
Update-AzStorageAccountNetworkRuleSet -ResourceGroupName rg-storage-prod -Name stcontosoprod `
  -DefaultAction Deny -Bypass AzureServices
Add-AzStorageAccountNetworkRule -ResourceGroupName rg-storage-prod -Name stcontosoprod `
  -IPAddressOrRange "198.51.100.0/24"
```

<Callout type="exam">
Watch for the order of checks: a question that says "the user has a valid SAS but gets 403" often means the **firewall**. "Allow only the app subnet" is a **virtual network rule** with the **Microsoft.Storage service endpoint**. "Allow the office" is an **IP rule** with a **public** range. "Backups stopped after locking the account" is the **trusted Microsoft services** exception. "No public access at all" is **Disabled** plus a **private endpoint**.
</Callout>

<DeepDive title="Service endpoints or private endpoints?">

A service endpoint keeps the storage account's public IP but lets you say "only this subnet". It's free and quick. A **private endpoint** gives the account a private IP inside your VNet, so traffic never touches the public endpoint, and it works from on-premises over VPN or ExpressRoute. Many companies use a private endpoint and set public network access to **Disabled**. Service endpoints by default only work for accounts in the same region as the VNet (and its pair); `Microsoft.Storage.Global` endpoints extend that to any region.

</DeepDive>
