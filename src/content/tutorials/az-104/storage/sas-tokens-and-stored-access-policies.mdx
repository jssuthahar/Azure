## The technical explanation

A SAS is a query string you append to a storage URL. It carries the permissions (`sp`), expiry (`se`), optional start (`st`), allowed IPs (`sip`), protocol (`spr=https`), the resource type and a **signature** (`sig`). Storage recomputes the signature with the same key; if anything was changed, the request fails.

### Three kinds of SAS

| | User delegation SAS | Service SAS | Account SAS |
| --- | --- | --- | --- |
| Signed with | User delegation key from **Microsoft Entra ID** | Account key | Account key |
| Covers | Blob Storage (containers and blobs) | One service (blob, file, queue or table) | One or more services, service-level operations too |
| Max lifetime | **7 days** | Whatever you set | Whatever you set |
| Stored access policy | No | **Yes** | No |
| Works with key access disabled | **Yes** | No | No |
| Revoke early | Revoke delegation keys or the signer's role | Delete the policy, or regenerate the key | Regenerate the key |

Microsoft recommends the **user delegation SAS** wherever it fits. The signer needs permission to get a user delegation key, and at use time the SAS can't do more than the signer's own data role allows.

### Stored access policies

A stored access policy lives on a **container**, **file share**, **queue** or **table**, and each can hold up to **five**. It holds any of: permissions, start time, expiry time. A service SAS names it with `si=<policy>` and takes the missing fields from the policy. Don't set the same field in both places; storage rejects that.

To revoke every SAS tied to a policy, **delete the policy**, rename it, or set its expiry in the past. Changes can take up to 30 seconds to apply. An **ad hoc** SAS (no policy) can only be revoked by **regenerating the key** that signed it.

### Portal steps

1. Open the container, then **Settings > Access policy > + Add policy**. Enter the identifier, tick the permissions, set start and expiry, then **Save**.
2. Open **Settings > Shared access tokens**. Choose **Signing method** (*Account key* or *User delegation key*), the signing key, the **Stored access policy**, allowed IPs and **HTTPS only**.
3. Select **Generate SAS token and URL** and copy it straight away. Azure doesn't keep a copy.

The account-wide **Shared access signature** blade (under Security + networking) creates **account SAS** tokens.

### CLI and PowerShell

```bash
EXP=$(date -u -d "+30 days" '+%Y-%m-%dT%H:%MZ')

# Stored access policy + service SAS that uses it
az storage container policy create --account-name stcontosoprod -c invoices \
  -n auditors-read --permissions rl --expiry $EXP
az storage container generate-sas --account-name stcontosoprod -n invoices \
  --policy-name auditors-read --https-only -o tsv

# Revoke every SAS tied to the policy
az storage container policy delete --account-name stcontosoprod -c invoices -n auditors-read

# User delegation SAS for one blob (max 7 days, no account key)
az storage blob generate-sas --account-name stcontosoprod -c invoices -n invoice-1001.pdf \
  --permissions r --expiry 2026-11-30T18:00Z --auth-mode login --as-user --https-only --full-uri
```

```powershell
$ctx = (Get-AzStorageAccount -ResourceGroupName rg-storage-prod -Name stcontosoprod).Context
New-AzStorageContainerStoredAccessPolicy -Container invoices -Policy auditors-read `
  -Permission rl -ExpiryTime (Get-Date).AddDays(30) -Context $ctx
New-AzStorageContainerSASToken -Name invoices -Policy auditors-read -Protocol HttpsOnly -Context $ctx
```

<Callout type="exam">
Key phrases. "Revoke without regenerating keys" means a **stored access policy** with a **service SAS**. "Secured with Microsoft Entra credentials" or "doesn't use the account key" means a **user delegation SAS**. "Grant access to blobs and queues with one token" means an **account SAS**. If a question has six policies on one container, something is wrong: the limit is **five**. And remember that disabling **Allow storage account key access** stops service and account SAS tokens but not user delegation SAS.
</Callout>

<DeepDive title="SAS expiration policies and good hygiene">

You can set a **SAS expiration policy** on the account (for example, one day). Azure then logs any SAS signed with an account key whose validity is longer, so you can find bad habits. Other habits that pay off: keep expiry short, use HTTPS only, restrict `sip` to known ranges, give only the letters you need (`r` and `l`, not `racwdl`), and prefer user delegation SAS so a leaked account key isn't part of the story at all.

</DeepDive>
