## Start with a question

<Story question="Who should hold the key to your bank locker: you or the bank?">

Every locker in the bank vault is locked, whatever you do. The question is who keeps the key. For most people, letting the bank manage it is fine. Some customers want their own key so that, if they choose, nobody can open the locker, not even the bank.

Azure Storage works the same way. Your data is **always encrypted**. You decide whether Microsoft manages the key or you bring a **customer-managed key**.

</Story>

## The technical explanation

### Create the account: the decisions that matter

Portal: **Storage accounts > + Create**. The wizard tabs are **Basics, Advanced, Networking, Data protection, Encryption, Tags, Review + create**.

| Tab | Setting | Notes |
| --- | --- | --- |
| Basics | Storage account name | Globally unique, 3 to 24 lowercase letters and numbers. Becomes `https://<name>.blob.core.windows.net`. |
| Basics | Performance | **Standard** (general-purpose v2, HDD-backed) or **Premium** (SSD) with an account type of block blobs, file shares or page blobs. Can't be changed later. |
| Basics | Redundancy | LRS, ZRS, GRS, GZRS (and read-access versions). Can be changed later. |
| Advanced | Require secure transfer | HTTPS only for REST calls. Keep it on. |
| Advanced | Allow enabling anonymous access on individual containers | Off by default. Leave it off unless you publish public content. |
| Advanced | Enable storage account key access | Turn off once everything uses Microsoft Entra ID. |
| Advanced | Minimum TLS version | 1.2. |
| Advanced | Hierarchical namespace | Turns the account into Data Lake Storage Gen2. Some features, such as blob versioning, don't support it. |
| Advanced | Access tier | Default tier for blobs: Hot, Cool or Cold. |
| Networking | Public network access | All networks, selected networks or disabled with private endpoints. |
| Data protection | Soft delete and versioning | The portal turns soft delete on by default; the CLI doesn't. |
| Encryption | Key type, CMK support, infrastructure encryption | Covered below. |

### Encryption at rest

All data in Azure Storage (blobs, files, queues, tables, disks) is encrypted with **256-bit AES** before it's stored. There's nothing to enable and no extra cost.

- **Microsoft-managed keys (MMK)**: the default. Microsoft rotates and protects the keys.
- **Customer-managed keys (CMK)**: you keep an RSA key in **Azure Key Vault** or **Managed HSM**. Storage uses it to wrap the account's data encryption key. Requirements: the vault has **soft delete and purge protection**, and the account has a **system-assigned or user-assigned managed identity** with **Key Vault Crypto Service Encryption User** on the key. Leave the key version empty and storage picks up new versions automatically.
- **Infrastructure encryption**: a second AES-256 layer with a different key. **Create time only.**
- **Encryption scopes**: named key settings that can apply a different key to a container or even a single blob.
- **Customer-provided keys**: a client sends its own key with each Blob Storage request. Rare, but it exists.

At create time you also choose whether CMK support covers **blobs and files only** or **all service types** (tables and queues too); that can't change later.

If you **disable** the CMK or remove the identity's access, storage can't decrypt, so requests fail until you restore access. That's the control customers want, and also the reason purge protection is mandatory.

### CLI and PowerShell

```bash
# A secure general-purpose v2 account with double encryption
az storage account create -g rg-storage-prod -n stcontosoprod -l eastus \
  --sku Standard_GZRS --kind StorageV2 --min-tls-version TLS1_2 \
  --allow-blob-public-access false --https-only true --require-infrastructure-encryption

# Switch to a customer-managed key
az keyvault create -g rg-storage-prod -n kv-contoso-cmk --enable-purge-protection true
az storage account update -g rg-storage-prod -n stcontosoprod --assign-identity
# (give the identity "Key Vault Crypto Service Encryption User" on the key, then:)
az storage account update -g rg-storage-prod -n stcontosoprod \
  --encryption-key-source Microsoft.Keyvault \
  --encryption-key-vault https://kv-contoso-cmk.vault.azure.net \
  --encryption-key-name cmk-storage
```

```powershell
New-AzStorageAccount -ResourceGroupName rg-storage-prod -Name stcontosoprod -Location eastus `
  -SkuName Standard_GZRS -Kind StorageV2 -MinimumTlsVersion TLS1_2 `
  -AllowBlobPublicAccess $false -RequireInfrastructureEncryption
Set-AzStorageAccount -ResourceGroupName rg-storage-prod -Name stcontosoprod `
  -KeyvaultEncryption -KeyVaultUri https://kv-contoso-cmk.vault.azure.net -KeyName cmk-storage
```

<Callout type="exam">
"Encrypt with a key the company controls and can revoke" is a **customer-managed key**. "Add a second layer of encryption" is **infrastructure encryption**, and if the account already exists the answer involves **creating a new account**. "The CMK setup fails" usually means the vault lacks **purge protection** or the account has no **managed identity** with access. "Low latency for an SMB share" means a **Premium file shares** account. Performance can't be changed after creation.
</Callout>

<DeepDive title="Upgrading old accounts">

Older general-purpose v1 and BlobStorage accounts can be upgraded to general-purpose v2 in place (Configuration > Upgrade), which is a one-way change and can change your bill because of tier pricing. Premium accounts can't become Standard and the reverse is also true: you create a new account and copy the data with AzCopy or object replication.

</DeepDive>
