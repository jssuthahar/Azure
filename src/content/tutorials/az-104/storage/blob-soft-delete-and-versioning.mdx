## Start with a question

<Story question="Why does your phone's photo app keep deleted photos for 30 days?">

Because people delete the wrong photo all the time. The "Recently deleted" album gives you a month to change your mind. And your document editor keeps a version history, so a bad edit isn't the end of the world either.

Azure Blob Storage has both. **Soft delete** is the recently deleted album. **Versioning** is the version history.

</Story>

## The technical explanation

All three settings live in **Data management > Data protection** on the storage account (and on the **Data protection** tab when you create one). The portal turns soft delete on by default for new accounts (7 days); accounts created with the CLI or templates don't get it unless you ask.

### Blob soft delete

When a blob, a snapshot or a version is deleted, it's kept in a soft-deleted state for the retention period (**1 to 365 days**). You can list it (`--include d`, or **Show deleted blobs** in the portal) and **undelete** it. When versioning is off, overwriting a blob also keeps the old data as a soft-deleted snapshot. Soft-deleted data is billed until it's purged.

### Container soft delete

Deleted containers and everything in them are kept for **1 to 365 days**. Restore from **Containers > Show deleted containers > Undelete**, or with `az storage container restore`. You can't restore over a container that has since been recreated with the same name.

### Blob versioning

With versioning on, every write creates a new **current version** and keeps the old one as a **previous version** with a timestamp **version ID**. Deleting a blob turns its current version into a previous version. To recover, **copy** a previous version over the base blob (portal: blob **> Versions > Make current version**). Versions are billed, so pair versioning with a lifecycle rule that deletes old versions. Versioning isn't supported on hierarchical namespace accounts.

### How they fit together

| Accident | With soft delete only | With versioning (and soft delete) |
| --- | --- | --- |
| Blob deleted | Undelete it | Make a previous version current |
| Blob overwritten | Restore the soft-deleted snapshot | Make a previous version current |
| Version deleted | Undelete the version | Undelete the version |
| Container deleted | Needs container soft delete | Needs container soft delete |
| Account deleted | Not covered (use a lock) | Not covered (use a lock) |

**Point-in-time restore** builds on these: it restores block blobs in chosen containers to a moment in the past, and needs **versioning**, the **change feed** and **blob soft delete**, with a restore window shorter than the soft delete retention. **Object replication** also needs versioning.

### CLI and PowerShell

```bash
az storage account blob-service-properties update -g rg-storage-prod -n stcontosoprod \
  --enable-delete-retention true --delete-retention-days 14 \
  --enable-container-delete-retention true --container-delete-retention-days 7 \
  --enable-versioning true

# Deleted blob (soft delete): list and undelete
az storage blob list --account-name stcontosoprod -c contracts --include d -o table
az storage blob undelete --account-name stcontosoprod -c contracts -n contract-88.docx

# Overwritten blob (versioning): copy a previous version back
az storage blob list --account-name stcontosoprod -c contracts --include v -o table
az storage blob copy start --account-name stcontosoprod \
  --destination-container contracts --destination-blob contract-12.docx \
  --source-uri "https://stcontosoprod.blob.core.windows.net/contracts/contract-12.docx?versionid=<version-id>"
```

```powershell
Enable-AzStorageBlobDeleteRetentionPolicy -ResourceGroupName rg-storage-prod -StorageAccountName stcontosoprod -RetentionDays 14
Enable-AzStorageContainerDeleteRetentionPolicy -ResourceGroupName rg-storage-prod -StorageAccountName stcontosoprod -RetentionDays 7
Update-AzStorageBlobServiceProperty -ResourceGroupName rg-storage-prod -StorageAccountName stcontosoprod -IsVersioningEnabled $true
```

<Callout type="exam">
"Recover a deleted blob" is **blob soft delete** (undelete). "Recover from an overwrite automatically" is **versioning**. "Recover a deleted container" is **container soft delete**. "Prevent the storage account from being deleted" is a **CanNotDelete lock**. Retention for blob and container soft delete is **1 to 365 days**. If a question mentions object replication or point-in-time restore, versioning must be on.
</Callout>

<DeepDive title="Immutability is a different tool">

Soft delete and versioning help with mistakes, but an admin can still turn them off and purge data. If regulations say data must not be changed or deleted for a period, use **immutable storage**: time-based retention policies or legal holds on a container or on versions. Locked policies can't be shortened, even by the account owner.

</DeepDive>
