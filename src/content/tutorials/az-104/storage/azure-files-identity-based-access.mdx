## Start with a question

<Story question="Why should everyone in the office open the HR folder with the same password?">

They shouldn't. On the old file server, Priya opened `\\fileserver\hr` as Priya, and Windows checked her group membership. Nobody shared a master password.

When the HR folder moves to **Azure Files**, you want the same thing. **Identity-based access** lets Priya map the drive with her normal sign-in, and Azure checks who she is before letting her in.

</Story>

## Explain it like I'm 10

<Eli10>

The file share is the school library.

With the storage key, anyone holding the master key can walk in and change any book.

With identity-based access, you show your school ID card. The librarian checks you're allowed in the library at all (share-level permission).

Then each shelf has its own sign: "Year 6 only" (Windows ACLs).

</Eli10>

## The technical explanation

SMB clients authenticate with **Kerberos**. Azure Files needs to know which directory issues those tickets, and then which permissions to check.

### Step 1: choose one identity source

| Identity source | Who signs in | Good for |
| --- | --- | --- |
| **On-premises AD DS** | Domain users, synced to Microsoft Entra ID with Entra Connect | Domain-joined PCs on the corporate network or VPN |
| **Microsoft Entra Domain Services** | Users of the managed domain | Apps and VMs joined to an Entra DS domain in Azure |
| **Microsoft Entra Kerberos** | Hybrid users on Entra-joined or hybrid-joined devices | Remote workers and Azure Virtual Desktop, no domain controller line of sight |

A storage account uses **one** source at a time. For AD DS you register the account as a computer object in the domain, usually with the **AzFilesHybrid** PowerShell module (`Join-AzStorageAccount`). Entra Kerberos and Entra DS are switched on from the portal: **File shares > Identity-based access > Set up**.

### Step 2: share-level permissions (Azure RBAC)

| Role | Allows |
| --- | --- |
| Storage File Data SMB Share Reader | Read files and directories |
| Storage File Data SMB Share Contributor | Read, write, delete |
| Storage File Data SMB Share Elevated Contributor | Contributor plus changing Windows ACLs |

Assign them on the **share** (or the account) through **Access control (IAM)**. Identities must exist in Microsoft Entra ID, so AD DS users need to be synced. If you'd rather manage everything with NTFS permissions, set a **default share-level permission** that applies one of these roles to every authenticated identity.

Owner, Contributor and Storage Account Contributor are management roles. They don't let anyone open files over SMB.

### Step 3: Windows ACLs

Inside the share, normal NTFS permissions apply per folder and file. Admins usually set them once by mounting with the storage account key (a superuser mount) or with a role that allows ACL changes, then using File Explorer or `icacls`. Share-level permission and ACLs both have to allow the action.

### Mount it

```powershell
# Check the network path first: SMB needs TCP 445 outbound
Test-NetConnection -ComputerName stcontosoprod.file.core.windows.net -Port 445
net use Z: \\stcontosoprod.file.core.windows.net\hr-share
```

```bash
# Turn on Microsoft Entra Kerberos and a default share-level permission
az storage account update -g rg-storage-prod -n stcontosoprod --enable-files-aadkerb true
az storage account update -g rg-storage-prod -n stcontosoprod \
  --default-share-permission StorageFileDataSmbShareReader

# Or a share-level role for one group
az role assignment create --role "Storage File Data SMB Share Contributor" \
  --assignee hr-staff@contoso.com \
  --scope "/subscriptions/<sub>/resourceGroups/rg-storage-prod/providers/Microsoft.Storage/storageAccounts/stcontosoprod/fileServices/default/fileshares/hr-share"
```

<Callout type="exam">
Read for the layer the question is about. "Users can't reach the share at all" is usually **share-level permission** (an SMB Share role or default permission). "Users can open the share but not one folder" is **Windows ACLs**. "Users need to change NTFS permissions" is **Elevated Contributor**. "Clients have no line of sight to a domain controller" is **Microsoft Entra Kerberos**. And only **one** identity source per account.
</Callout>

<DeepDive title="Cloud-only identities and other details">

Microsoft Entra Kerberos was built for hybrid identities, and Microsoft has been extending it to cloud-only users, so check the current docs before you plan around it. For AD DS, the storage account's computer account password should be rotated like any other. NFS shares don't use any of this: they rely on network controls (VNet and private endpoints) and Unix permissions instead.

</DeepDive>
