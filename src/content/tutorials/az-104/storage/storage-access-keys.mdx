## Start with a question

<Story question="How do you change the locks on a shop without closing it for a day?">

A shop with one front door has a problem: changing the lock means the door is out of use for a while. A shop with two doors doesn't. You send everyone through the side door, change the front lock, hand out the new key, and next month you do it the other way round.

A storage account has **two access keys** for the same reason. Your apps use one while you **regenerate** the other.

</Story>

## The technical explanation

Each account gets two 512-bit keys when it's created. A request signed with either key (**Shared Key** authorization) can read, write and delete anything in the account. Connection strings contain a key. **Account SAS** and **service SAS** tokens are signed with a key too, so they live and die with it.

### Who can see the keys

Listing keys uses the `Microsoft.Storage/storageAccounts/listkeys/action` permission. **Owner**, **Contributor**, **Storage Account Contributor** and **Storage Account Key Operator Service Role** have it. **Reader** doesn't. Anyone who can list keys can read all the data, so treat that permission as a data permission.

### Rotate without downtime

1. Update every app to use **key2** (ideally by changing one secret in Azure Key Vault).
2. Regenerate **key1**: portal **Access keys > Rotate key** on key1, or `az storage account keys renew --key primary`.
3. Next rotation, move apps back to key1 and regenerate key2.

If you regenerate the key an app is still using, that app gets 403 errors until you fix it, and every SAS signed with that key is dead.

### Rotation reminders

**Set rotation reminder** on the Access keys blade creates a **key expiration policy**: keys older than, say, 90 days are flagged in the portal, and Azure Policy can report non-compliant accounts. It's a reminder, not automation.

### Turn keys off

Once apps use Microsoft Entra ID, go to **Settings > Configuration** and set **Allow storage account key access** to **Disabled**. Then any request signed with a key, and any account or service SAS, is refused. User delegation SAS and Entra ID keep working. Check first: old tools that only know keys will break.

```bash
az storage account keys list -g rg-storage-prod -n stcontosoprod -o table
az storage account keys renew -g rg-storage-prod -n stcontosoprod --key primary
az storage account update -g rg-storage-prod -n stcontosoprod --key-exp-days 90
az storage account update -g rg-storage-prod -n stcontosoprod --allow-shared-key-access false
```

```powershell
Get-AzStorageAccountKey -ResourceGroupName rg-storage-prod -Name stcontosoprod
New-AzStorageAccountKey -ResourceGroupName rg-storage-prod -Name stcontosoprod -KeyName key1
Set-AzStorageAccount -ResourceGroupName rg-storage-prod -Name stcontosoprod -AllowSharedKeyAccess $false
```

<Callout type="exam">
"Rotate keys with no downtime" is always **move clients to the other key, then regenerate**. Ordering questions love this sequence. "Stop all use of account keys and key-signed SAS" is **Allow storage account key access: Disabled**. "Remind admins to rotate" is the **key expiration policy**. "A user can regenerate keys but nothing else" points to **Storage Account Key Operator Service Role**. And Reader can't list keys.
</Callout>

<DeepDive title="Keys in Key Vault, and rotating automatically">

Put the connection string in Key Vault and have apps read it at start-up through a managed identity. Rotation then means updating one secret. To automate it, a common pattern is an Azure Function triggered on a schedule (or by Key Vault's near-expiry event) that regenerates the inactive key, writes it to Key Vault as a new secret version, then flips which key is active. Even better is dropping keys for Microsoft Entra ID altogether.

</DeepDive>
