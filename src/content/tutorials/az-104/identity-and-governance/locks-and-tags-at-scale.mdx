## Start with a question

<Story question="How do museums stop anyone, even staff, from moving the most valuable painting?">

A museum puts the famous painting behind glass with a lock. Curators can still dim the lights and adjust the label, but nobody lifts it off the wall without first getting the key from security. During a stocktake they lock the whole room, so nothing gets touched at all. And every item has a little card saying who donated it and which gallery pays for its care.

The glass case is a **CanNotDelete** lock, the locked room is a **ReadOnly** lock, and the little card is a set of **tags**.

</Story>

## Explain it like I'm 10

<Eli10>

A **Delete lock** is like gluing your Lego model to the table. You can still add bricks, but nobody can throw it away.

A **ReadOnly lock** is a glass box over it. You can look, but you can't touch.

**Tags** are sticky notes on each model: "Built by Mia, Class 5B". They help you find things and know whose they are.

</Eli10>

## The technical explanation

### Resource locks

| | CanNotDelete (portal: **Delete**) | ReadOnly (portal: **Read-only**) |
| --- | --- | --- |
| Read | Yes | Yes |
| Update, tag, scale, start | Yes | **No** |
| Delete | **No** | **No** |
| Side effects | Few | Blocks POST actions like listing storage keys; can stop App Service, VMs and backups working normally |
| Typical use | Production, always on | Short freezes, audits |

- Scopes: **subscription**, **resource group** or **resource**. A lock on a parent applies to everything under it, including resources created later. The most restrictive lock wins.
- Locks affect the **control plane** only. A CanNotDelete lock on a storage account doesn't stop someone deleting a blob inside it.
- Locks apply to **everyone**. To remove one you need `Microsoft.Authorization/locks/delete`, which **Owner** and **User Access Administrator** have and **Contributor** doesn't.

Portal: resource or group → **Settings → Locks → + Add** → Lock name, Lock type (**Read-only** or **Delete**), Notes.

```bash
az lock create --name no-delete --lock-type CanNotDelete --resource-group rg-finance --notes "Finance production"
az lock create --name freeze --lock-type ReadOnly --resource-group rg-finance \
  --resource-name stfin0424 --resource-type Microsoft.Storage/storageAccounts
az lock list --resource-group rg-finance -o table
az lock delete --name freeze --resource-group rg-finance --resource-name stfin0424 --resource-type Microsoft.Storage/storageAccounts
```

```powershell
New-AzResourceLock -LockName no-delete -LockLevel CanNotDelete -ResourceGroupName rg-finance
```

### Tags

A tag is `name: value`, such as `costcenter: FIN-042`, `env: prod`, `owner: finance-ops@contoso.com`. Each resource, resource group or subscription can have up to **50** tags. Names are case-insensitive, values case-sensitive, and some resource types don't support tags.

```bash
az group update -n rg-finance --tags costcenter=FIN-042 env=prod     # replaces the group's tags
az tag update --resource-id <id> --operation Merge --tags owner=finance-ops   # adds without wiping
az resource tag -g rg-finance -n stfin0424 --resource-type Microsoft.Storage/storageAccounts --tags costcenter=FIN-042
```

Use `--operation Merge` to add tags and keep the existing ones; `Replace` swaps the whole set and `Delete` removes the ones you list. You need write access to the resource or the **Tag Contributor** role to change tags. A ReadOnly lock blocks tag changes too.

### Tags at scale

Resource group tags **aren't inherited**. To make them stick everywhere:

- **Inherit a tag from the resource group if missing** (Modify) copies the group's tag to resources, with a remediation task for existing ones.
- **Require a tag on resources** or **on resource groups** (Deny) forces people to supply one.
- **All resources → select → Assign tags** tags many resources in the portal at once.
- Cost Management's **tag inheritance** setting applies group and subscription tags to **cost records** only, without changing the resources.

<Callout type="exam">
"Allow changes but prevent deletion" = **CanNotDelete**. "Prevent all modifications" = **ReadOnly**. A user with **Owner** still can't delete a locked resource. **Contributor can't remove** a lock. Watch for ReadOnly side effects: a question about failing to list storage keys or scale an app often hides a ReadOnly lock. For tags, remember they **don't inherit**, and the fix is **policy**.
</Callout>

<DeepDive title="Locks, deployments and automation">

ARM template and Bicep deployments in **Complete** mode try to delete resources that aren't in the template, and a CanNotDelete lock will make that fail. Backup and Site Recovery need write access to restore points, so a ReadOnly lock on a VM's resource group can break backups. Some services create their own locks; for example, a Recovery Services vault may add one. If automation must remove and re-add a lock, give its managed identity a narrow custom role with only the lock actions rather than Owner.

</DeepDive>
