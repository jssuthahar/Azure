## Start with a question

<Story question="If you have a library card and a museum pass, what are you allowed to do?">

Both. A library card lets you borrow books, a museum pass gets you into the galleries, and having both doesn't cancel either one. The only thing that stops you is a sign on a door that says "closed to everyone today", whatever pass you hold.

Azure access works the same way. Every role a user has, directly or through groups, at this level or above, **adds up**. The "closed to everyone" sign is a **deny assignment**.

</Story>

## Explain it like I'm 10

<Eli10>

You have a sticker that says "can use the art room" and another that says "can use the music room".

You can use both rooms. Stickers add up.

If the head teacher hangs a "closed" sign on the art room, nobody goes in, not even teachers. That sign is a **deny assignment**.

</Eli10>

## The technical explanation

### Four sources of access

To answer "what can User1 do on RG1?", collect assignments from:

1. **Directly on RG1** to User1.
2. **Through groups** User1 belongs to (including nested groups).
3. **Inherited** from the subscription and every management group above it.
4. Anything on a **specific resource** inside RG1 applies to that resource only.

Add all the roles together. That union is the effective access. Then check two things that can only take away: **deny assignments** and **resource locks**.

### Reading a role definition

```json
{
  "roleName": "Contributor",
  "actions": [ "*" ],
  "notActions": [
    "Microsoft.Authorization/*/Delete",
    "Microsoft.Authorization/*/Write",
    "Microsoft.Authorization/elevateAccess/Action",
    "Microsoft.Blueprint/blueprintAssignments/write",
    "Microsoft.Blueprint/blueprintAssignments/delete",
    "Microsoft.Compute/galleries/share/action"
  ],
  "dataActions": [],
  "notDataActions": []
}
```

- **Actions** `*` = every management operation.
- **NotActions** removes role assignment and lock writes. That's why Contributor can't grant access or delete locks.
- **DataActions** is empty, so Contributor doesn't get blob or queue **data** access through Entra ID. For that you need roles like **Storage Blob Data Contributor**.

NotActions only subtracts from **this role**. If the same person is also User Access Administrator, they can write role assignments.

### Tools

| Tool | Shows |
| --- | --- |
| IAM → **Check access** → select a user | Current role assignments (direct and via groups, with scope), deny assignments, eligible PIM assignments |
| IAM → **Role assignments** | Every assignment at this scope; the **Scope** column says *This resource* or *(Inherited)* |
| IAM → **Roles** → View | The role's JSON permissions |
| IAM → **Deny assignments** | Deny assignments that apply here |
| `az role assignment list --assignee <upn> --all --include-inherited -o table` | All of a user's assignments across scopes |
| `Get-AzRoleAssignment -SignInName <upn> -ExpandPrincipalGroups` | Includes assignments through groups |

An inherited assignment can't be removed at the child scope. Go to the scope where it was made.

### Deny assignments

A **deny assignment** lists actions that are blocked for some principals at a scope, with optional **excluded principals**. They beat role assignments, Owner included. You can't create them in IAM; Azure adds them for **deployment stacks** (deny settings) and **Azure managed applications**.

<Callout type="exam">
These questions give you a table of assignments and ask Yes/No for several actions. Work it like this: list every role from **direct**, **group** and **inherited** assignments, combine them, then check for **locks** (ReadOnly blocks writes, CanNotDelete blocks deletes) and **deny assignments**. Remember **NotActions isn't a deny**, Contributor **can't** assign roles, and management roles don't include **data** access to blobs.
</Callout>

<DeepDive title="Why a role change didn't take effect">

Azure Resource Manager caches some permission data, and tokens hold group claims, so a new assignment can take a few minutes to apply. Signing out and back in (or `az logout` / `az login`) refreshes the token. Very large group memberships can overflow token claims, in which case Azure looks them up instead, which is slower. If a removed role still seems to work, wait, refresh the token, and check for a second path through a group.

</DeepDive>
