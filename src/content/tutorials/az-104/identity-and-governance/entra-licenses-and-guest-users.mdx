## Start with a question

<Story question="How does a gym give members the right pass, and let a visiting friend in for a day?">

A gym hands each member a pass for the classes they've paid for. Some companies buy passes for a whole team, so anyone who joins the team gets one and anyone who leaves hands it back. And when you bring a friend, the gym doesn't make them a new ID card. They show their own driving licence and sign in as a guest.

In Microsoft Entra ID the pass is a **license**, the team deal is **group-based licensing**, and the visiting friend is a **B2B guest** who signs in with their own company account.

</Story>

## Explain it like I'm 10

<Eli10>

A **license** is a ticket that lets you use the paid rides.

You can hand tickets to kids one by one. Or you give tickets to the whole football team, and anyone who joins the team gets one too. That's **group licensing**.

A kid from another school can visit. They bring their own school card. You just write "visitor" next to their name. That's a **guest**.

</Eli10>

## The technical explanation

### Licenses

Products such as **Microsoft 365 E3**, **Microsoft Entra ID P1** and **P2** are bought as a number of seats. Each license contains **service plans** (Exchange Online, Teams, Entra ID P1 and so on) that you can switch off when you assign it.

| | Direct assignment | Group-based licensing |
| --- | --- | --- |
| Where | User → **Licenses** → + Assignments | Group → **Licenses** → + Assignments |
| Needs | **Usage location** on the user | **Entra ID P1** (or a plan that includes it) |
| Leavers | You remove it by hand | Removed when they leave the group |
| Missing usage location | Assignment fails | The directory's location is used |
| Not enough seats | Assignment fails | Members show an **error state**; add seats, then **Reprocess** |

Pair group licensing with a **dynamic group** and licenses follow HR data with no clicks at all. If a user gets the same product directly and from a group, they use one seat, and you can remove the direct one safely.

```powershell
# Microsoft Graph PowerShell
Update-MgUser -UserId sam@contoso.com -UsageLocation "IN"
$e3 = Get-MgSubscribedSku | Where-Object SkuPartNumber -eq "SPE_E3"
Set-MgUserLicense -UserId sam@contoso.com -AddLicenses @{SkuId = $e3.SkuId} -RemoveLicenses @()
```

### External users (B2B collaboration)

**Users → + New user → Invite external user** sends an invitation. The guest redeems it and signs in with their own Microsoft Entra account, a Microsoft account, Google or a one-time email passcode. In your tenant they appear with **User type: Guest**, and a UPN like `priya_fabrikam.com#EXT#@contoso.onmicrosoft.com`. You give them access the same way as anyone else: groups, app assignments, Azure roles.

**External Identities → External collaboration settings** controls:

- **Guest user access**: same as members, **limited** (the default), or restricted to their own objects.
- **Guest invite settings**: from "anyone, including guests" down to "no one".
- **Collaboration restrictions**: allow any domain, deny listed domains, or allow **only** listed domains.

**Cross-tenant access settings** go further per organisation: block or allow inbound and outbound B2B, and **trust the partner's MFA** so guests aren't asked twice. For customer-facing sign-up apps, Microsoft points you to **External ID in an external tenant** instead of B2B guests.

<Callout type="exam">
"The license can't be assigned to a newly created user" points to **usage location**. "Licenses must be removed automatically when users change department" is **group-based licensing**, usually on a **dynamic group**. "Users from a partner must use their existing credentials" is **B2B collaboration** (guest). "Only users from fabrikam.com can be invited" is **Collaboration restrictions** with an allow list. If a question asks which license enables group-based licensing, answer **Microsoft Entra ID P1**.
</Callout>

<DeepDive title="Guests and Azure resources">

Guests can hold **Azure roles** too. Invite the partner, then assign them, or better a group they're in, a role at a resource group. By default guests can't browse your directory freely, which is why the "limited access" setting exists. If a guest needs to see other users in a picker, you either raise their access level or give them a directory role like Directory Readers. Remove guests (or let **access reviews** remove them) when the work ends; stale guests are a common audit finding.

</DeepDive>
