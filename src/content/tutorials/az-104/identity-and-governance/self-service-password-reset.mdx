## Start with a question

<Story question="What if you could reset your own bank PIN without visiting the branch?">

Most banks let you reset a forgotten PIN in the app. You prove it's you with a code sent to your phone and maybe your date of birth, and you're done in two minutes. Nobody at the branch has to check your passport.

**Self-service password reset (SSPR)** is that for your work account. Users register a couple of methods in advance, like the Authenticator app and a personal email. When they forget their password, they go to **aka.ms/sspr**, prove it's them, and pick a new one. The helpdesk never hears about it.

</Story>

## Explain it like I'm 10

<Eli10>

You forgot the code for your locker.

Instead of finding the caretaker, you answer two secret checks you set up at the start of term: a word only your mum's phone gets, and a code sent to your email.

Pass both, and the locker lets you choose a new code. Set up the checks first, or it can't help you.

</Eli10>

## The technical explanation

Everything lives in **Microsoft Entra ID → Password reset** (also in the Entra admin center under **Protection → Password reset**). The blades you'll use:

| Blade | Setting | Options |
| --- | --- | --- |
| **Properties** | Self service password reset enabled | **None**, **Selected** (pick **one** group), **All** |
| **Authentication methods** | Number of methods required to reset | **1** or **2** |
| | Methods available to users | Mobile app notification, Mobile app code, Email, Mobile phone, Office phone, Security questions |
| **Registration** | Require users to register when signing in? | Yes / No |
| | Days before users are asked to re-confirm | 0 to 730, default **180** |
| **Notifications** | Notify users on password resets? / Notify all admins when other admins reset | Yes / No |
| **On-premises integration** | Write back passwords to your on-premises directory? | Needs Entra Connect or Cloud Sync |

Microsoft now manages methods centrally in the **Authentication methods policy** (**Security → Authentication methods**), and the legacy SSPR method settings are being folded into it. The Password reset blade still turns SSPR on, sets the scope and the number of methods. On the exam, expect the blade names above.

### Rules that catch people out

- **Selected** takes exactly **one** group. Nest other groups in it, or move to **All**.
- Users must **register** before they can reset. "Require users to register when signing in" prompts them on their next sign-in.
- **Administrators** are always enabled for SSPR, whatever you choose, and always need **two** methods. They can't use security questions.
- A **method you've disabled** doesn't count, even if the user registered it.
- **Guests** reset their password in their home tenant, not in yours.
- Licensing: cloud users need **Entra ID P1** (or Microsoft 365 Business Premium) for reset; **writeback** for synced users also needs P1.

There's no Azure CLI command for SSPR settings. You configure it in the portal, or through the Microsoft Graph authentication methods policy APIs.

<Callout type="exam">
"Only members of Group1 can use SSPR" = **Selected** with Group1. "Two groups need SSPR" with Selected means **nest** one group in the other or choose **All**. "Users must verify with two methods" = **number of methods required: 2**. "New passwords must be usable on-premises" = **password writeback**. If a user "can't reset" while others can, check group membership and registration before anything else.
</Callout>

<DeepDive title="SSPR and MFA registration together">

Users register for SSPR and MFA in one place: **aka.ms/mysecurityinfo** (combined registration). Strong methods like the Authenticator app count for both. A **Registration campaign** in the Authentication methods policy can nudge users towards Authenticator at sign-in. For a first sign-in or a lost phone, a **Temporary Access Pass** lets a user sign in once to register new methods, which is safer than a helpdesk-set password.

</DeepDive>
