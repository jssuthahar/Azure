## Start with a question

<Story question="How does a hotel make sure cleaners can open every room on their floor, but not the safe?">

A hotel doesn't give everyone a master key. Cleaners get a card that opens every room on floor 3. The manager's card opens every floor. The night auditor's card opens the office but no guest rooms. Each card is a **role**, and the floor or building it works on is the **scope**.

**Azure RBAC** works the same way. You give a person or group a **role** (what they can do) at a **scope** (where), and it works there and everywhere underneath.

</Story>

## Explain it like I'm 10

<Eli10>

Your school gives out badges.

A **Reader** badge lets you look into any classroom. A **Contributor** badge lets you move the desks. An **Owner** badge lets you move desks and hand badges to other people.

If your badge works for the whole building, it works in every classroom too. That's the **scope**.

</Eli10>

## The technical explanation

### Who, what, where

A **role assignment** has three parts:

1. **Security principal**: a **user**, **group**, **service principal** (an app) or **managed identity**.
2. **Role definition**: a list of permissions written as **Actions** (control plane, like `Microsoft.Compute/virtualMachines/start/action`), **NotActions** (taken out), **DataActions** and **NotDataActions** (data plane, like reading blobs).
3. **Scope**: one of four levels, each inheriting from the one above.

```text
Management group   /providers/Microsoft.Management/managementGroups/mg-contoso
  Subscription     /subscriptions/<id>
    Resource group /subscriptions/<id>/resourceGroups/rg-app
      Resource     /subscriptions/<id>/resourceGroups/rg-app/providers/Microsoft.Compute/virtualMachines/vm-app01
```

### Built-in roles you must know

| Role | Can do | Can't do | Portal tab |
| --- | --- | --- | --- |
| **Owner** | Everything, including role assignments | Bypass locks or deny assignments | Privileged administrator roles |
| **Contributor** | Create, change and delete any resource | Assign roles, delete locks, manage Blueprints assignments | Privileged administrator roles |
| **Reader** | View everything | Change anything | Job function roles |
| **User Access Administrator** | Manage role assignments | Create or change resources | Privileged administrator roles |
| **Role Based Access Control Administrator** | Assign roles (optionally limited by a condition) | Manage access through other routes like Azure Policy | Privileged administrator roles |
| **Virtual Machine Contributor** | Manage VMs, disks, NICs | Manage the VNet or storage, sign in to the VM | Job function roles |
| **Network Contributor** | Manage networks | Manage VMs | Job function roles |
| **Storage Blob Data Reader** | Read blob data (DataActions) | Manage the storage account | Job function roles |

Use the smallest role at the smallest scope, and assign it to a **group**. When nothing fits, write a **custom role** in JSON with your own Actions and **AssignableScopes**.

### Assigning roles

Portal: open the scope → **Access control (IAM)** → **+ Add → Add role assignment** → **Role** tab (Job function roles or Privileged administrator roles) → **Members** tab (user, group, or service principal / managed identity) → **Conditions** (privileged roles only) → **Review + assign**.

```bash
# Resource group scope
az role assignment create --assignee app-ops@contoso.com --role "Virtual Machine Contributor" --resource-group rg-app

# Management group scope: every subscription below inherits it
az role assignment create --assignee ben@contoso.com --role Reader \
  --scope /providers/Microsoft.Management/managementGroups/mg-contoso

az role definition list --name "Virtual Machine Contributor"   # read the permissions
```

```powershell
New-AzRoleAssignment -SignInName ben@contoso.com -RoleDefinitionName Reader -Scope "/providers/Microsoft.Management/managementGroups/mg-contoso"
```

Changes usually apply within minutes, though they can take longer to reach every service. A subscription can hold up to **4,000** role assignments.

### Azure roles vs Microsoft Entra roles

**Azure roles** control Azure resources. **Microsoft Entra roles** (Global Administrator, User Administrator, License Administrator) control the directory. A Global Administrator has no Azure resource access by default; they can **elevate access** (Entra ID → Properties → Access management for Azure resources) to get User Access Administrator at root scope `/`, and should turn it off afterwards.

<Callout type="exam">
Map the verbs. "Manage resources but not access" = **Contributor**. "Manage access but not resources" = **User Access Administrator**. "Do everything" = **Owner**. "View only" = **Reader**. "Start and stop VMs only" points to **Virtual Machine Contributor** or a **custom role**. "Apply to all current and future subscriptions" = assign at a **management group**. If the requirement says "least privilege", the widest role is almost never the answer.
</Callout>

<DeepDive title="PIM and conditions">

**Privileged Identity Management (PIM)**, part of Entra ID P2, makes Azure and Entra roles **eligible** instead of permanent: people activate them for a few hours with a justification and MFA. **Role assignment conditions** (ABAC) narrow an assignment further, for example Storage Blob Data Reader only on blobs tagged `project=alpine`, or RBAC Administrator only for specific roles. Both show up on the **Assignment type** and **Conditions** tabs of Add role assignment.

</DeepDive>
