## Start with a question

<Story question="How does a company with 3,000 staff keep track of who belongs to which team?">

Think of a school office. Every pupil has a record card with their name, class and house. The office doesn't write "Year 7 football team" on each card by hand every term. It keeps one list per club, and some lists are just "everyone in Year 7", which updates itself when a new pupil arrives.

**Microsoft Entra ID** is that office for a company. Each person has a **user** account with properties like department and job title. **Groups** are the lists. Some you keep by hand (**assigned**), and some fill themselves from a rule on those properties (**dynamic**).

</Story>

## Explain it like I'm 10

<Eli10>

Everyone at your school has a name badge. That's a **user**.

Clubs are **groups**. The chess club teacher writes names on the list herself. That's an **assigned** group.

The "all Year 5 kids" list never needs anyone to write on it. If you're in Year 5, you're on it. Move up a year, you're off. That's a **dynamic** group.

</Eli10>

## The technical explanation

### Users

A user lives in your **tenant** and signs in with a **user principal name (UPN)**, such as `sam@contoso.onmicrosoft.com` or `sam@contoso.com` once you've added a custom domain. Users are either **Members** (your staff) or **Guests** (people from other organisations, covered in the next lesson). They're created in one of three ways:

- **Cloud-only**: you create them in the Azure portal (**Microsoft Entra ID → Users → + New user → Create new user**) or the Microsoft Entra admin center.
- **Synced**: Microsoft Entra Connect or Cloud Sync copies them from on-premises Active Directory. You edit those in AD, not in the cloud.
- **Bulk**: **Bulk operations → Bulk create** takes a CSV template, which suits a big intake.

The **Create new user** wizard has four tabs: **Basics** (UPN, mail nickname, display name, password, account enabled), **Properties** (first and last name, user type, job title, department, company, manager, **usage location**), **Assignments** (groups, roles, administrative units) and **Review + create**.

```bash
# Azure CLI
az ad user create --display-name "Sam Rivera" \
  --user-principal-name sam@contoso.onmicrosoft.com \
  --password "<temporary-password>" --force-change-password-next-sign-in true

az ad user update --id sam@contoso.onmicrosoft.com --account-enabled false   # block sign-in
az ad user list --query "[].{name:displayName, upn:userPrincipalName}" -o table
```

```powershell
# Microsoft Graph PowerShell: properties the CLI doesn't expose
Update-MgUser -UserId sam@contoso.onmicrosoft.com -Department "Sales" -JobTitle "Account Executive" -UsageLocation "IN"
```

Deleted users go to **Deleted users** for **30 days**, and you can restore them in that window with their group memberships.

### Groups

When you select **+ New group** you choose:

| Setting | Options | Why it matters |
| --- | --- | --- |
| Group type | **Security** or **Microsoft 365** | Security for access; Microsoft 365 adds a mailbox, calendar and SharePoint site |
| Microsoft Entra roles can be assigned to the group | Yes / No | Must be set at creation if the group will hold Entra roles. It can't be changed later |
| Membership type | **Assigned**, **Dynamic User**, **Dynamic Device** | Who manages the member list: you or a rule |
| Owners | Users | Owners can manage the group without being admins |

```bash
az ad group create --display-name App-Ops --mail-nickname app-ops
az ad group member add --group App-Ops --member-id <user-object-id>
az ad group member list --group App-Ops -o table
```

### Dynamic membership rules

A dynamic group uses a rule built from **property, operator, value**. The rule builder writes the syntax for you, or you type it:

```text
(user.department -eq "Sales")
(user.department -eq "Sales") -and (user.usageLocation -eq "IN")
(user.jobTitle -startsWith "Engineer")
(device.deviceOSType -eq "Windows")
```

A group is **Dynamic User** or **Dynamic Device**, never both. Rules are evaluated in the background, so changes can take a while to show. You **can't** add or remove members by hand; you change the property instead. Dynamic groups need a **Microsoft Entra ID P1** license for each user in scope.

<Callout type="exam">
Watch for "membership must change automatically when a user's department or job title changes": that's a **Dynamic User** group, and it needs **Entra ID P1**. "Add a device group for all Windows laptops" is **Dynamic Device**. If a question says an admin can't add a user to a group, check whether the group is dynamic. And a group that must hold **Entra roles** needs that option set when it's **created**.
</Callout>

<DeepDive title="Who can manage users and groups?">

You don't need Global Administrator for daily work. **User Administrator** creates and edits users and groups and resets passwords for non-admins. **Groups Administrator** manages groups only. **Helpdesk Administrator** resets passwords for non-admins. Group **owners** manage their own group's members. Use **administrative units** to limit an admin to one region or department's users. These are **Microsoft Entra roles**, separate from the Azure roles you'll meet in the RBAC lessons.

</DeepDive>
