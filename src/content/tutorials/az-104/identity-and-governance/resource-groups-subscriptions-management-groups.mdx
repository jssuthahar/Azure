## Start with a question

<Story question="How does a supermarket chain run the same rules in 300 stores?">

Head office doesn't phone every store when a rule changes. It sets rules for regions, regions pass them to stores, and stores apply them to each aisle. Each store has its own budget and books. Inside a store, things that belong together sit in one aisle, and you can move a product from aisle 4 to aisle 9 without moving it to another town.

In Azure, head office and regions are **management groups**, each store is a **subscription** with its own bill, the aisles are **resource groups**, and the products are **resources**.

</Story>

## Explain it like I'm 10

<Eli10>

Think of folders on a computer.

The big folder is a **management group**. Inside it are **subscription** folders, each with its own pocket money. Inside those are **resource group** folders. Inside those are your files, the **resources**.

If you set a rule on the big folder, every folder inside follows it.

</Eli10>

## The technical explanation

### The ladder

```text
Tenant Root Group
└── mg-contoso
    ├── mg-prod
    │   └── Contoso Production (subscription)
    │       ├── rg-app   → vm-app01, stapp0424
    │       └── rg-data  → sql-contoso
    └── mg-nonprod
        └── Contoso Dev/Test (subscription)
```

| Level | Limits and rules |
| --- | --- |
| Management group | Up to **10,000** per tenant, **six levels** deep below the root, one parent each |
| Subscription | One parent management group; trusts **one** Entra tenant; its own billing, quotas and RBAC boundary |
| Resource group | Each resource in exactly **one** group; the group's region holds metadata only; deleting it deletes everything inside |
| Resource | Can be in a different region from its resource group |

Policy, role assignments and budgets set at any level apply below it.

### Resource groups

```bash
az group create -n rg-app -l westeurope --tags env=prod costcenter=APP-11
az group list -o table
az resource list -g rg-app -o table
az group delete -n rg-old --yes        # deletes everything inside (locks permitting)
```

Group things by lifecycle: what you create, update and delete together. An app's VMs, disks and NICs in one group; a shared hub network in another.

### Moving resources

Portal: resource group → **Move** → *Move to another resource group*, *Move to another subscription* or *Move to another region*. The first two run validation, then move.

```bash
az resource move --destination-group rg-archive \
  --ids /subscriptions/<sub-id>/resourceGroups/rg-app/providers/Microsoft.Storage/storageAccounts/stapp0424
# another subscription: add --destination-subscription-id <id>
```

What to remember:

- The **resource ID changes**; the **region doesn't**. Update scripts, alerts and role assignments that point at the old ID. Role assignments on the resource itself don't move with it.
- Source and target groups are **locked for writes** during the move (reads still work).
- Not every resource type can move, and some have rules (for example, dependent resources moving together). Check the move support list.
- You need write and move rights on the source group and write on the target.
- To change **region**, use **Azure Resource Mover** or redeploy.

### Subscriptions

A subscription is how Azure bills and limits you. Common reasons to have several: separate production from dev/test, separate billing for departments, hit quota limits, or isolate access. A subscription trusts one Entra tenant; you can **change the directory** (transfer it to another tenant), but RBAC assignments in it are removed when you do. **Rename**, **cancel** and **transfer billing ownership** are on the subscription's blade.

```bash
az account list -o table
az account set --subscription "Contoso Production"
```

### Management groups

Portal: search **Management groups** → **+ Create** (Management group ID, display name). Then move subscriptions or groups under it with **… → Move**.

```bash
az account management-group create --name mg-nonprod --display-name "Non-production" --parent mg-contoso
az account management-group subscription add --name mg-nonprod --subscription "Contoso Dev/Test"
az account management-group list -o table
```

The **ID** can't change; the display name can. New subscriptions land under the root (or a default management group you set in **Settings**). Moving a subscription needs write access on the subscription and on the source and target management groups. By default, the root's access is controlled by elevated Global Administrators.

<Callout type="exam">
"All current and future subscriptions" = **management group**. "Resources that are deployed, updated and deleted together" = one **resource group**. "Move a resource to another group" changes the **resource ID**, not the region; "to another region" needs **Azure Resource Mover**. A **resource group's location** doesn't restrict its resources. Expect questions on the **six-level** limit and **one parent** rule.
</Callout>

<DeepDive title="Landing zones">

Microsoft's Cloud Adoption Framework suggests a management group layout: **Platform** (identity, management, connectivity subscriptions), **Landing zones** (split into **Corp** for internal apps and **Online** for internet-facing ones), **Sandbox** and **Decommissioned**. Policies get stricter as you go down, and workloads get their own subscriptions. Even if you don't build the full design, separating production and non-production management groups early saves painful moves later.

</DeepDive>
