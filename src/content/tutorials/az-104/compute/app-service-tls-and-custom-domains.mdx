keyTerms:
  - term: Custom domain verification ID
    definition: A value unique to the app (and subscription) that you put in an asuid TXT record to prove you control the domain.
  - term: asuid TXT record
    definition: The DNS TXT record App Service checks for domain ownership, named asuid.<subdomain>, or asuid for the root domain.
  - term: CNAME record
    definition: A DNS alias from one name to another, such as www to app-contoso.azurewebsites.net. Used for subdomains, not the root.
  - term: App Service managed certificate
    definition: A free TLS certificate App Service issues and renews for a custom domain. No wildcards and it can't be exported.
  - term: SNI SSL
    definition: A TLS binding that uses Server Name Indication, so many certificates share one IP address. The usual choice.
  - term: HTTPS Only
    definition: A setting that redirects every HTTP request to HTTPS with a 301.
  - term: Minimum inbound TLS version
    definition: The oldest TLS version clients may use to connect. Default 1.2; 1.0, 1.1 and 1.3 are the other options.

## Start with a question

<Story question="How does a post office know it's really your new address?">

When you move house, you can't just tell the post office "send Ravi's letters to me". They want proof: a bill or a letter with your name at the new address. Then they forward the mail, and you put a lock on the letterbox so nobody reads it on the way.

A custom domain works the same way. A **TXT record** in DNS is your proof of address. A **CNAME** (or A record) forwards visitors to the app. The **TLS certificate** is the lock, and **HTTPS Only** makes sure nothing arrives in an open envelope.

</Story>

## Explain it like I'm 10

<Eli10>

Your app has a long, boring name like app-contoso-www01.azurewebsites.net.

You want people to type `www.contoso-learn.com` instead.

First you write a secret code in your domain's settings so Azure believes it's yours. That's the **TXT record**.

Then you add a sign saying "www goes over there". That's the **CNAME**.

Then you add a padlock so nobody can peek. That's the **certificate**.

</Eli10>

## The technical explanation

### Map an existing custom DNS name

You need three things: a plan on **Basic** or higher (Free doesn't support custom domains, and Shared can't bind certificates), access to the domain's DNS, and the app's **custom domain verification ID**.

**Portal:** web app → **Settings → Custom domains** → **+ Add custom domain**. Choose **All other domain services** (or **App Service Domain** if you bought it in Azure), the certificate option and **SNI SSL**, type the domain, and the pane lists the records to create:

| Domain | Records to create at your DNS host |
| --- | --- |
| **Subdomain** (`www.contoso-learn.com`) | **TXT** `asuid.www` = verification ID, **CNAME** `www` → `app-contoso-www01.azurewebsites.net` |
| **Root** (contoso-learn.com) | **TXT** `asuid` = verification ID, **A** `@` → the app's inbound IP address |
| **Wildcard** (*.contoso-learn.com) | **TXT** `asuid` = verification ID, **CNAME** `*` → the app's default domain |

Select **Validate**, then **Add**. If the domain already serves live traffic elsewhere, add the TXT record first and switch the CNAME last, so the move has no downtime.

```bash
az webapp show -g rg-admin-dns -n app-contoso-www01 --query customDomainVerificationId -o tsv
az network dns record-set txt add-record -g rg-admin-dns -z contoso-learn.com -n asuid.www -v <verification-id>
az network dns record-set cname set-record -g rg-admin-dns -z contoso-learn.com -n www -c app-contoso-www01.azurewebsites.net
az webapp config hostname add -g rg-admin-dns --webapp-name app-contoso-www01 --hostname www.contoso-learn.com
```

```powershell
Set-AzWebApp -ResourceGroupName rg-admin-dns -Name app-contoso-www01 -HostNames @('www.contoso-learn.com', 'app-contoso-www01.azurewebsites.net')
```

### Certificates: four ways to get one

| Option | Cost | Wildcard | Export | Notes |
| --- | --- | --- | --- | --- |
| **App Service managed certificate** | Free | No | No | Basic and up; renews itself; the app must be publicly reachable |
| **App Service certificate** | Paid yearly | Yes | Yes | Bought in Azure, stored in Key Vault |
| **Import from Key Vault** | Your certificate | Yes | Yes | The app needs access to the vault; renewals sync |
| **Upload a .pfx** | Your certificate | Yes | You hold it | Password-protected, private key exportable |

You'll find them in **Settings → Certificates**: **Managed certificates**, **Bring your own certificates (.pfx)** and **Public key certificates (.cer)**, the last one for outbound calls, not for your domain.

**Binding** connects a certificate to a hostname. **SNI SSL** is the normal choice; **IP SSL** gives the hostname its own IP address and is for old clients that don't send SNI.

```bash
az webapp config ssl create -g rg-admin-dns -n app-contoso-www01 --hostname www.contoso-learn.com
az webapp config ssl bind -g rg-admin-dns -n app-contoso-www01 \
  --certificate-thumbprint <thumbprint> --ssl-type SNI
```

PowerShell uses `New-AzWebAppCertificate` for a managed certificate and `New-AzWebAppSSLBinding` to bind one.

### Configure TLS

In **Settings → Configuration → General settings** (the platform settings):

- **HTTPS Only**: On sends a 301 from `http://` to `https://`.
- **Minimum Inbound TLS Version**: 1.2 by default. Choose 1.3 for the strictest setting; 1.0 and 1.1 are only for very old clients.
- **FTP state**: FTPS only or Disabled, so nothing uploads in clear text.

```bash
az webapp update -g rg-admin-dns -n app-contoso-www01 --https-only true
az webapp config set -g rg-admin-dns -n app-contoso-www01 --min-tls-version 1.2
```

<Callout type="exam">
"Verify ownership" is always the **asuid TXT** record. A **CNAME** can't sit at the root, so the apex needs an **A** record. "Free certificate, renews automatically" is the **managed certificate**, but it fails for a **wildcard** or when the certificate must be **exported**. "Redirect all HTTP traffic" is **HTTPS Only**, and "reject TLS 1.0 clients" is the **minimum TLS version**. If the plan is **Free**, the first step is to **scale up**.
</Callout>

<DeepDive title="What a swap does to domains and certificates">

Custom domain names, non-public certificates and TLS settings stay with their deployment slot when you swap. That's on purpose: production keeps `www.contoso-learn.com` and its certificate, and only the code and swappable settings move. If you want staging on its own domain, add a separate hostname (such as `staging.contoso-learn.com`) to the staging slot.

</DeepDive>
