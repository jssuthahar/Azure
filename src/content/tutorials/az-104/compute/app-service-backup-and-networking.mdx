keyTerms:
  - term: Automatic backup
    definition: An hourly backup App Service takes for you and keeps for 30 days. You can restore it but not download or schedule it.
  - term: Custom backup
    definition: A backup you configure to your own storage container, on demand or on a schedule, with retention and optional linked databases.
  - term: SAS URL
    definition: A container URL with a shared access signature that lets App Service write backups into your storage account.
  - term: VNet integration
    definition: Outbound connectivity from an app into a virtual network through a delegated subnet. It doesn't give the app a private inbound address.
  - term: Subnet delegation
    definition: Marking a subnet for one service, here Microsoft.Web/serverFarms, so App Service can place its integration there.
  - term: Access restrictions
    definition: An inbound allow and deny list for the app, evaluated by priority, matching IP ranges, service tags or subnets.
  - term: Private endpoint
    definition: A network interface with a private IP from your VNet that receives inbound traffic for the app.

## Start with a question

<Story question="Can a shop have a back door to the warehouse and a guard at the front door?">

A shop has two doors. The back door goes to the company's private warehouse, so staff can fetch stock. The front door has a guard who checks a list before letting customers in. And every night the manager photocopies the day's ledger and locks it in a safe across the road.

App Service has the same three things. **VNet integration** is the back door: the app goes **out** to private resources. **Access restrictions** (or a **private endpoint**) are the front door: who can come **in**. **Backups** are the photocopies, kept in a storage account you own.

</Story>

## Explain it like I'm 10

<Eli10>

**VNet integration** is a secret tunnel from the treehouse to your house, so the treehouse can get snacks from the kitchen. It only goes one way: out.

**Access restrictions** are a list at the ladder: "only friends from my street can climb up".

## The technical explanation

### Configure backup

| | Automatic backups | Custom backups |
| --- | --- | --- |
| Setup | None | Storage account + container in the same subscription |
| Frequency | Every hour, fixed | On demand, or a schedule you set (for example every 1 day) |
| Retention | 30 days, fixed | Days you choose, with "keep at least one backup" |
| Size | Up to 30 GB | Up to 10 GB, of which up to 4 GB can be databases |
| Linked databases | No | Yes (Azure SQL, MySQL, PostgreSQL via connection strings) |
| Download | No | Yes, it's a file in your container |

Backup and restore need **Basic** or higher. Restores can overwrite the app, go to a **different app**, or go to a **deployment slot** so you can check the result before users see it.

**Portal:** web app → **Settings → Backups** → **Configure custom backups**. Pick the **Storage account** and **Container**, turn **Scheduled backup** On, set **Backup every** (days or hours), **Start backup schedule from**, **Retention (Days)** and **Keep at least one backup**, tick any databases, then **Configure**. **Backup Now** takes one on demand, **Restore** brings one back.

```bash
SAS_URL="https://stcontosobak01.blob.core.windows.net/webbackups?<sas-token>"
az webapp config backup create -g rg-admin-fin --webapp-name app-contoso-fin01 \
  --backup-name fin-before-release --container-url "$SAS_URL"
az webapp config backup update -g rg-admin-fin --webapp-name app-contoso-fin01 \
  --container-url "$SAS_URL" --frequency 1d --retention 30 --retain-one true
az webapp config backup restore -g rg-admin-fin --webapp-name app-contoso-fin01 \
  --backup-name fin-before-release --container-url "$SAS_URL" --overwrite
```

```powershell
New-AzWebAppBackup -ResourceGroupName rg-admin-fin -Name app-contoso-fin01 -StorageAccountUrl $sasUrl -BackupName fin-before-release
Edit-AzWebAppBackupConfiguration -ResourceGroupName rg-admin-fin -Name app-contoso-fin01 -StorageAccountUrl $sasUrl -FrequencyInterval 1 -FrequencyUnit Day -RetentionPeriodInDays 30 -KeepAtLeastOneBackup
```

To leave files out of a custom backup (logs, caches), add a `_backup.filter` file listing the paths in the app's `D:\home\site\wwwroot` folder (or `/home/site/wwwroot` on Linux).

### Configure networking

**Settings → Networking** splits the two directions.

**Outbound traffic configuration**

- **Virtual network integration**: the app's calls to private IPs (and, with **route all** on, which is the default, all its outbound traffic) leave through a subnet of your VNet. Requirements: **Basic** or higher, an **empty subnet** used only for this, **/28 or larger** (/26 recommended so the plan can scale out), **delegated to Microsoft.Web/serverFarms**. NSGs and route tables on that subnet apply to the app's outbound traffic.
- **Hybrid connections**: reach a single host and port on-premises through a relay, without a VPN.
- **Outbound addresses**: the public IPs the app uses when it calls the internet, useful for partner firewalls.

**Inbound traffic configuration**

- **Public network access**: Enabled from all networks, enabled from select virtual networks and IP addresses (access restrictions), or Disabled.
- **Access restrictions**: rules with a name, **Allow** or **Deny**, **priority** (lowest first, first match wins), and a source: IPv4/IPv6 range, **service tag** (for example `AzureFrontDoor.Backend`), or a **subnet** through a service endpoint. Once any Allow rule exists, unmatched traffic gets **403**. The **advanced tool site** (SCM/Kudu) can reuse the main rules or have its own.
- **Private endpoints**: a private IP for the app in your VNet, for clients on the VNet, peered VNets or on-premises over VPN or ExpressRoute. Pair it with a private DNS zone (`privatelink.azurewebsites.net`) and, if you want, public access Disabled.

```bash
az network vnet subnet create -g rg-admin-fin --vnet-name vnet-fin -n snet-app-outbound --address-prefixes 10.20.1.0/26
az webapp vnet-integration add -g rg-admin-fin -n app-contoso-fin01 --vnet vnet-fin --subnet snet-app-outbound
az webapp config access-restriction add -g rg-admin-fin -n app-contoso-fin01 \
  --rule-name office --action Allow --ip-address 203.0.113.0/24 --priority 100
```

```powershell
Add-AzWebAppAccessRestrictionRule -ResourceGroupName rg-admin-fin -WebAppName app-contoso-fin01 -Name office -Priority 100 -Action Allow -IpAddress 203.0.113.0/24
```

<Callout type="exam">
Sort the question by direction first. The app **calling** something private (a database, a storage account with a firewall, an on-premises server) is **outbound**: **VNet integration** or a hybrid connection. People **reaching** the app is **inbound**: **access restrictions** to filter, a **private endpoint** to make it private. For backups, "keep 30 days, daily, include the database, downloadable" is a **custom backup** to a **storage container**; "nothing configured, hourly" is the **automatic** kind. Both need at least **Basic**.
</Callout>

<DeepDive title="Why the integration subnet needs room">

Each instance of the plan takes an address in the integration subnet, and scaling or platform upgrades briefly need extra ones. Azure also reserves five addresses in every subnet. A /28 has 16 addresses, so 11 are usable, which a busy plan can run out of. A /26 gives 59 usable addresses and lets several plans share the subnet. You can't resize a subnet that's in use, so start bigger than you think.

</DeepDive>
