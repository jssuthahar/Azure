## Start with a question

<Story question="How many tills should a shop open?">

A supermarket on a quiet Tuesday morning opens one till. On Saturday afternoon it opens ten, and at 11 PM it closes them all. Nobody plans the exact number in advance: the manager watches the queue.

**Azure Container Apps** is that manager for your containers. Each open till is a **replica**. A **scale rule** watches the queue (HTTP requests, connections or messages) and opens or closes tills between a **minimum** and **maximum** you set. If the minimum is zero, the shop can close completely when nobody's there.

</Story>

## Explain it like I'm 10

<Eli10>

Imagine a lemonade stand where helpers appear when the line gets long.

You decide how big each helper's table is: that's **CPU and memory**.

You decide the rule: "one helper for every 50 people waiting". That's the **scale rule**.

You decide the most helpers you can afford, like 10. That's **max replicas**.

When nobody's around, all the helpers go home. That's **scale to zero**.

</Eli10>

## The technical explanation

### Provision a container app in the portal

1. Search **Container Apps**, select **+ Create → Container App**.
2. **Basics**: subscription, resource group, **Container app name**, region and a **Container Apps environment** (create one if needed; it brings a Log Analytics workspace for logs).
3. **Container**: image source (Azure Container Registry, Docker Hub or another registry), image and tag, **Workload profile** (Consumption) and **CPU and Memory**.
4. **Ingress**: turn it on for an HTTP app. **Accepting traffic from anywhere** gives a public URL; **Limited to Container Apps Environment** keeps it internal. Set the **target port** your container listens on.
5. **Review + create**. Then open **Application → Scale** to set replicas and rules.

```bash
az containerapp env create -g rg-admin-apps -n cae-contoso-adm -l eastus
az containerapp create -g rg-admin-apps -n ca-orders-api --environment cae-contoso-adm \
  --image mcr.microsoft.com/k8se/quickstart:latest --ingress external --target-port 80 \
  --cpu 0.5 --memory 1.0Gi --min-replicas 0 --max-replicas 5
```

In PowerShell the Az.App module does the same with `New-AzContainerAppManagedEnv` and `New-AzContainerApp`, with scale rules built by `New-AzContainerAppScaleRuleObject`.

### Sizing: CPU and memory per replica

On the **Consumption** profile, CPU goes from 0.25 to 4 vCPU in steps of 0.25, and memory must be **2 Gi per vCPU**:

| CPU | Memory |
| --- | --- |
| 0.25 | 0.5Gi |
| 0.5 | 1.0Gi |
| 1 | 2.0Gi |
| 2 | 4.0Gi |
| 4 | 8.0Gi |

Need an odd shape, more memory or GPUs? Add a **dedicated workload profile** to the environment and run the app there. You pay for those machines whether they're busy or not.

### Scaling: replicas and rules

| Setting | Default | Notes |
| --- | --- | --- |
| **Min replicas** | 0 | 0 means the app can scale to zero |
| **Max replicas** | 10 | Raise it (the platform allows up to 1,000) or lower it to cap cost |
| **HTTP rule** | 10 concurrent requests per replica when ingress is on and you add no rule | Set your own value, such as 50 |
| **TCP rule** | | Concurrent TCP connections |
| **Custom (KEDA)** | | Event sources such as Azure Service Bus, Storage queues or Event Hubs |
| **CPU / memory** | | Utilisation-based; **can't** scale to zero |

Container Apps checks the rules about every 30 seconds and waits a **cool-down** of 300 seconds with no load before it scales all the way back to zero.

```bash
az containerapp update -g rg-admin-apps -n ca-orders-api \
  --scale-rule-name http-scale --scale-rule-type http \
  --scale-rule-http-concurrency 50 --min-replicas 0 --max-replicas 10
```

With that rule, 400 concurrent requests give `400 ÷ 50 = 8` replicas. 1,000 requests would want 20 but stop at 10, so requests start to queue. That's the trade-off max replicas gives you: a predictable bill.

<Callout type="exam">
"The app must cost nothing when nobody uses it" points to **min replicas 0**, and the rule has to be HTTP, TCP or an event scaler, never CPU or memory. "Handle at most N replicas" is **max replicas**. If an option pairs 0.5 vCPU with 2 Gi on Consumption, it's invalid. And compared with Container Instances, Container Apps is the one that **scales automatically**.
</Callout>

<DeepDive title="Revisions are how changes roll out">

The scale section is part of the app's **template**, so saving new scale settings creates a new **revision**. In single revision mode the new one takes all the traffic and the old one is deactivated. In multiple revision mode you can split traffic between revisions, for example 90% and 10%, and roll back by moving the traffic. Ingress, secrets and the registry settings are app-level and don't create a revision.

</DeepDive>
