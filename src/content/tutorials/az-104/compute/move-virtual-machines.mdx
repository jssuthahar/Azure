## Start with a question

<Story question="Is moving to another department the same as moving to another city?">

If you switch department, you keep your desk, your building and your commute. Only your badge and your manager change.

If you move to another city, you pack everything, set up a new desk, check it all works, then hand back the old keys.

A VM moving to another **resource group** or **subscription** is the department change: same region, still running, new ID badge. A move to another **region** is the city move, and **Azure Resource Mover** is the removal company.

</Story>

## Explain it like I'm 10

<Eli10>

Your toys live in labelled boxes.

Moving a toy car to another box is easy. But the car has wheels and a remote. If you move the car and leave the remote behind, it won't work. Those are **dependent resources**.

The car also gets a new label because it's in a new box. That's the **resource ID** changing.

Sending the car to grandma's house in another city means packing a copy, checking it arrived, and then clearing the old shelf. That's a **region move**.

</Eli10>

## The technical explanation

### Resource group and subscription moves

Portal: select the VM and its related resources in the resource group, then **Move › Move to another resource group** (or **subscription**). The wizard has **Source + target**, **Resources to move** (validation) and **Review**, where you confirm that scripts using the old IDs will need updating.

```bash
az resource move --destination-group rg-finance \
  --ids $(az resource list -g rg-contoso-prod --query "[?contains(name,'vm-rpt-01')].id" -o tsv)
# to another subscription:
az resource move --destination-group rg-finance --destination-subscription-id <sub-id> --ids <ids>
```

```powershell
$ids = (Get-AzResource -ResourceGroupName rg-contoso-prod | Where-Object Name -like 'vm-rpt-01*').ResourceId
Move-AzResource -DestinationResourceGroupName rg-finance -ResourceId $ids
```

What you need to know:

| Topic | Rule |
| --- | --- |
| Region | Doesn't change |
| VM state | Keeps running; source and target groups are locked for writes during the move |
| Resource IDs | Change (they contain the resource group and subscription) |
| Dependencies | VM + OS and data disks + NIC; public IP and NSG with them. Across subscriptions, the VNet and everything on it too |
| Subscriptions | Same Microsoft Entra tenant; resource provider registered in the target; enough quota |
| Permissions | `moveResources/action` on the source group and write on the target (Contributor on both works) |
| Role assignments | Ones made directly on the moved resource don't come along |
| Limits | Some VMs can't move, for example ones with Marketplace plans across subscriptions or with certain backup setups. Check the move guidance for VMs |

Moving a VM doesn't move its resource group's locks, tags or policies. Policies at the target apply from then on.

### Region moves with Azure Resource Mover

From the VM: **Move › Move to another region**, or open **Azure Resource Mover › Across regions**. The flow:

The CLI has the same steps under `az resource-mover move-collection` (`create`, `resolve-dependency`, `prepare`, `initiate-move`, `commit`, `discard`) and `az resource-mover move-resource add`. A region move is really a copy: until you delete the source, you're paying for both.

<Callout type="exam">
"Move VM1 to another **region**" is **Azure Resource Mover** (not az resource move). "Move to another resource group or subscription" is **Move** / **az resource move** / **Move-AzResource**. After a move the **resource ID changes** but the **location doesn't**. A move fails if the VM leaves behind its **disks or NIC**, if the subscriptions are in **different tenants**, or if the target subscription hasn't registered the **resource provider**.
</Callout>

<DeepDive title="Zones, not regions">

Moving a VM into an **availability zone** in the same region is a separate job. Resource Mover has an **Across zones** option, and Azure Site Recovery can also do a zone-to-zone move. You can't simply edit the zone of an existing VM, just as you can't add an existing VM to an availability set. When a question says "with minimal downtime" and "another region", think about Site Recovery replication under Resource Mover and testing before commit.

</DeepDive>
