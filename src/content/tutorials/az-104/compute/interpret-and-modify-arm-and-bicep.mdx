  - term: ARM template

  - term: Symbolic name

## Start with a question

<Story question="How do you build the same thing twice and get exactly the same result?">

Think of flat-pack furniture. The instructions list the parts, the measurements you can choose ("shelf height: 30, 40 or 50 cm") and the finished piece. Follow them twice and you get two identical bookcases.

A **template** is that instruction sheet for Azure. It lists the resources, the choices you're allowed to make (**parameters**) and what you get back at the end (**outputs**). AZ-104 expects you to read one, in **ARM JSON** or **Bicep**, and change it without breaking it.

</Story>

## Explain it like I'm 10

<Eli10>

Imagine ordering a pizza with a form.

The boxes you fill in, like size and toppings, are **parameters**. The shop's rule "only small, medium or large" is the **allowed values** list.

The kitchen reads the form and makes the pizza. That's **Azure Resource Manager** building your **resources**.

The receipt with your order number is the **output**.

</Eli10>

## The technical explanation

Both formats are **declarative**: you describe what should exist, not the clicks to make it. Resource Manager compares that with what's already there and does the rest.

### The same storage account in both formats

```bicep
@minLength(3)
@maxLength(24)
param storageName string

param location string = resourceGroup().location

@allowed([
  'Standard_LRS'
  'Standard_ZRS'
  'Standard_GRS'
])
param skuName string = 'Standard_LRS'

var tags = {
  env: 'prod'
  owner: 'platform-team'
}

resource st 'Microsoft.Storage/storageAccounts@2023-05-01' = {
  name: storageName
  location: location
  sku: { name: skuName }
  kind: 'StorageV2'
  tags: tags
}

output blobEndpoint string = st.properties.primaryEndpoints.blob
```

```json
{
  "$schema": "https://schema.management.azure.com/schemas/2019-04-01/deploymentTemplate.json#",
  "contentVersion": "1.0.0.0",
  "parameters": {
    "storageName": { "type": "string", "minLength": 3, "maxLength": 24 },
    "location": { "type": "string", "defaultValue": "[resourceGroup().location]" },
    "skuName": {
      "type": "string",
      "defaultValue": "Standard_LRS",
      "allowedValues": [ "Standard_LRS", "Standard_ZRS", "Standard_GRS" ]
    }
  },
  "variables": { "tags": { "env": "prod", "owner": "platform-team" } },
  "resources": [{
    "type": "Microsoft.Storage/storageAccounts",
    "apiVersion": "2023-05-01",
    "name": "[parameters('storageName')]",
    "location": "[parameters('location')]",
    "sku": { "name": "[parameters('skuName')]" },
    "kind": "StorageV2",
    "tags": "[variables('tags')]"
  }],
  "outputs": {
    "blobEndpoint": { "type": "string", "value": "[reference(parameters('storageName')).primaryEndpoints.blob]" }
  }
}
```

### Reading it part by part

| Part | ARM JSON | Bicep | What to look for |
| --- | --- | --- | --- |
| Inputs | `"parameters": {}` | `param name type = default` | Type, default value, allowed values, min/max length |
| Worked-out values | `"variables": {}` | `var name = …` | Values built from parameters, such as names and tags |
| Resources | `"resources": []` | `resource sym 'type@api' = {}` | Type, API version, name, location, SKU, properties |
| Results | `"outputs": {}` | `output name type = …` | What the deployment hands back |
| Expressions | `"[parameters('x')]"` | `x` | Square brackets mean "evaluate this" in JSON |
| Dependencies | `dependsOn` | inferred from references | In Bicep, `plan.id` inside another resource creates the dependency |

A few functions turn up everywhere: `resourceGroup().location`, `uniqueString(resourceGroup().id)` for unique names, `concat()` or Bicep string interpolation `'st${prefix}'`, and `resourceId()` in JSON.

**Which value wins?** A value passed at deployment time (on the command line or in a parameters file) beats the default. No default and no value means validation fails.

### Modifying a template safely

The exam shows you a template and asks what to change. The usual edits:

- **Allow a new SKU**: add it to `allowedValues` (JSON) or `@allowed` (Bicep). Change `defaultValue` or `= 'value'` if it should become the default.
- **Make a hard-coded value configurable**: add a parameter and replace the literal with `[parameters('x')]` or `x`.
- **Add a resource**: a new entry in `resources` (or a new `resource` block) with type, API version, name and location. If it needs another resource, reference it (Bicep) or add `dependsOn` (JSON).
- **Protect secrets**: `"type": "securestring"` in JSON, `@secure()` in Bicep. The value isn't logged in deployment history.
- **Pass values in a file**: a JSON parameters file, or a `.bicepparam` file that starts with `using 'main.bicep'`.

Watch out for one trap: changing a resource's `name` doesn't rename anything. Resource Manager creates a second resource with the new name and, in the default mode, leaves the old one where it is.

In the portal, **Deploy a custom template › Build your own template in the editor** lets you paste or load JSON, edit it and see a parameter form built from it. For Bicep, edit the file in VS Code with the Bicep extension or in Cloud Shell's editor.

<Callout type="exam">
Expect a template on screen and a question like "which SKU will be used?" or "what must you change so admins can pick Standard_ZRS?". Read the **parameters** first: a passed value beats `defaultValue`, and anything outside **allowedValues** fails validation before deployment. `[resourceGroup().location]` puts the resource in the group's region. In Bicep, look for `@allowed`, `@secure()` and string interpolation with `${}`.
</Callout>

<DeepDive title="Why Bicep is usually the better file to edit">

Bicep removes most of the punctuation and the `[ ]` expression strings, infers `dependsOn` from references, and gives you type checking in VS Code before you deploy. Modules (`module net 'network.bicep' = { … }`) split big deployments into reusable files. Because it compiles to the same JSON, nothing changes for Resource Manager: day-one support for new resource types and API versions applies to both. Keep JSON when another tool generates it or a vendor ships it that way, and use `az bicep decompile` when you want to take one over.

</DeepDive>
