## Start with a question

<Story question="Is it the shop that's busy, or the building it's in?">

Picture a food court. Several stalls share one building, one electricity bill and one set of kitchens. If the whole food court gets crowded, you can move to a bigger building (more power per kitchen) or open more identical kitchens next door.

An **App Service plan** is the building. The **web apps** are the stalls inside it. Moving to a bigger building is **scale up**. Opening more kitchens is **scale out**. And because the stalls share the building, everything you do to it happens to all of them.

</Story>

## Explain it like I'm 10

<Eli10>

The **plan** is a set of computers. Your **apps** live on them.

If one computer is too slow, swap it for a faster one. That's **scale up**.

If there are too many visitors, add more computers that run the same apps. That's **scale out**.

**Autoscale** is a grown-up who watches how busy the computers are and adds or removes them for you, but only if you're on a good enough plan.

</Eli10>

## The technical explanation

### Provision an App Service plan

**Portal:** search **App Service plans** → **+ Create**. On **Basics**: subscription, resource group, **Name**, **Operating System** (Linux or Windows), **Region** and **Pricing plan** (select **Explore pricing plans** to compare). Zone redundancy needs Premium v2 or v3. **Review + create**.

```bash
az appservice plan create -g rg-admin-web -n asp-contoso-shop --sku B1 --is-linux --number-of-workers 1
```

```powershell
New-AzAppServicePlan -ResourceGroupName rg-admin-web -Name asp-contoso-shop -Location eastus -Tier Basic -WorkerSize Small -NumberofWorkers 1 -Linux
```

### What each tier gives you

| Tier | Max instances | Autoscale | Deployment slots | Custom domain + TLS | Notes |
| --- | --- | --- | --- | --- | --- |
| **Free (F1)** | 1 (shared) | No | No | No | 60 CPU minutes a day, for tests |
| **Shared (D1)** | 1 (shared) | No | No | Domain only, no TLS binding | Windows only |
| **Basic (B1–B3)** | 3 | No (manual) | No | Yes | Backups, VNet integration |
| **Standard (S1–S3)** | 10 | Yes | 5 | Yes | Daily backups |
| **Premium v3 (P0v3–P5mv3)** | 30 | Yes, plus automatic scaling | 20 | Yes | Zone redundancy, bigger sizes |
| **Isolated v2 (I1v2–I6v2)** | 100 | Yes | 20 | Yes | Runs in an App Service Environment |

As a feel for cost, Basic B1 is about $13 a month per instance, Standard S1 about $73 and Premium v3 P1v3 about $124 (illustrative Linux prices).

### Create an App Service (web app)

**Portal:** search **App Services** → **+ Create → Web App**. **Basics**: **Name** (becomes `<name>.azurewebsites.net`), **Publish** (Code or Container), **Runtime stack**, **Operating System**, **Region**, then the **Linux/Windows Plan** and **Pricing plan**. The plan list only shows plans in the same region and OS. The other tabs cover **Database**, **Deployment** (GitHub Actions), **Networking**, **Monitor + secure** (Application Insights) and **Tags**.

```bash
az webapp create -g rg-admin-web -p asp-contoso-shop -n app-contoso-shop01 --runtime PYTHON:3.12
```

```powershell
New-AzWebApp -ResourceGroupName rg-admin-web -Name app-contoso-shop01 -Location eastus -AppServicePlan asp-contoso-shop
```

### Scale up and scale out

Both live on the **plan**, and you can reach them from the plan or from any app on it: **Scale up (App Service plan)** and **Scale out (App Service plan)**.

```bash
# scale out by hand (Basic allows up to 3)
az appservice plan update -g rg-admin-web -n asp-contoso-shop --number-of-workers 3
# scale up to Standard to unlock autoscale and slots
az appservice plan update -g rg-admin-web -n asp-contoso-shop --sku S1
```

```powershell
Set-AzAppServicePlan -ResourceGroupName rg-admin-web -Name asp-contoso-shop -Tier Standard -NumberofWorkers 2
```

Scaling up moves the apps onto new instances, so they restart. Scaling out adds instances behind the built-in load balancer and leaves the running ones alone.

### Autoscale rules

In **Scale out (App Service plan)** the **Scale out method** has three choices: **Manual**, **Automatic** (platform-managed HTTP scaling on Premium v2/v3) and **Rules Based** (an Azure Monitor autoscale setting). For rules you set:

- **Instance limits**: minimum, maximum and default (used if metrics are missing).
- **Scale-out rule**: for example **CPU Percentage > 70** averaged over **10 minutes** → **increase count by 1**, **cool down 5 minutes**.
- **Scale-in rule**: for example **CPU Percentage below 30** → **decrease count by 1**. Always pair them.

```bash
az monitor autoscale create -g rg-admin-web --resource asp-contoso-shop \
  --resource-type Microsoft.Web/serverfarms --name asp-contoso-shop-autoscale \
  --min-count 2 --max-count 6 --count 2
az monitor autoscale rule create -g rg-admin-web --autoscale-name asp-contoso-shop-autoscale \
  --condition "CpuPercentage > 70 avg 10m" --scale out 1
az monitor autoscale rule create -g rg-admin-web --autoscale-name asp-contoso-shop-autoscale \
  --condition "CpuPercentage < 30 avg 10m" --scale in 1
```

Other useful plan metrics are **Memory Percentage** and **Http Queue Length**. You can also add a **schedule** profile, such as 4 instances every weekday from 08:00 to 18:00.

<Callout type="exam">
Questions often hide the tier. "Configure autoscale" or "add a staging slot" on a **Basic** plan means you must **scale up to Standard** first. "More memory per instance" is **scale up**, "more instances" is **scale out**. If several apps share a plan, scaling affects all of them, so "scale only the busy app" means **move it to its own plan**. And autoscale targets the **plan** (`Microsoft.Web/serverfarms`), not the web app.
</Callout>

<DeepDive title="How many apps per plan?">

There's no fixed number. Put apps on the same plan when they're small, owned by the same team and scale together; it saves money. Split them when one app's load would starve the others, when they need different tiers or regions, or when you want separate bills. Remember a deployment slot is also an app on the plan and uses the same instances.

</DeepDive>
