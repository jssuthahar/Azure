## Start with a question

<Story question="How do you rebuild a room exactly as it was, without throwing out what someone else put there?">

You've got the floor plan for an office. Put the furniture back where the plan says and leave everything else alone: that's one way. Make the room match the plan exactly, so anything not on the plan goes in the skip: that's another.

Template deployments work the same. **Incremental** mode adds and fixes what's on the plan. **Complete** mode also throws out what isn't. And when you only have the room and no plan, **Export template** draws one for you.

</Story>

## Explain it like I'm 10

<Eli10>

You and your sister share a toy shelf, and you have a list of your toys.

"Put my toys back on the shelf" is **Incremental**. Her toys stay.

"Make the shelf match my list" is **Complete**. Her toys get taken off, because they aren't on your list.

Reading the list out loud first, so everyone hears what will happen, is **what-if**.

</Eli10>

## The technical explanation

### Deploy

| Tool | Command or path |
| --- | --- |
| Azure CLI | `az deployment group create -g rg-contoso-prod --template-file main.bicep --parameters storageName=stcontosologs` |
| PowerShell | `New-AzResourceGroupDeployment -ResourceGroupName rg-contoso-prod -TemplateFile main.bicep -storageName stcontosologs` |
| Portal | Search **Deploy a custom template** › Build your own template in the editor (ARM JSON) |
| Other scopes | `az deployment sub create`, `az deployment mg create`, `az deployment tenant create` (they need `--location`) |

The CLI compiles Bicep for you. PowerShell needs the Bicep CLI installed. Parameters can come from the command line (`key=value`), a JSON parameters file (`--parameters @main.parameters.json`) or a `.bicepparam` file. The deployment name defaults to the template file name, and each one is kept in the resource group's **Deployments** history (up to 800 per group; older entries are removed automatically).

### Preview with what-if

```bash
az deployment group what-if -g rg-contoso-prod --template-file main.bicep --parameters storageName=stcontosologs
#  ~ Microsoft.Storage/storageAccounts/stcontosologs
#    ~ sku.name: "Standard_LRS" => "Standard_ZRS"
# Resource changes: 1 to modify.
```

The symbols are `+` create, `~` modify, `-` delete, `=` no change, `*` ignore. PowerShell uses `-WhatIf` on the same cmdlet. `az deployment group create --confirm-with-what-if` shows the preview and asks before deploying.

### Incremental vs Complete

| | Incremental (default) | Complete |
| --- | --- | --- |
| Resources in the template | Created or updated | Created or updated |
| Resources in the group but not in the template | Left alone | **Deleted** |
| How to choose | Nothing to add | `--mode Complete` / `-Mode Complete` |
| Use it for | Almost everything | A group that only this template owns |

Two details catch people out. In both modes a resource that **is** in the template gets the template's properties, so a setting someone changed in the portal is reverted. And the portal's custom deployment always runs Incremental. A **CanNotDelete** lock on a resource stops Complete mode from removing it.

### Export what already exists

- **Resource group or resource › Automation › Export template**: generates a template from the current state, with **ARM Template** and **Bicep** tabs and an **Include parameters** option. Download it or select **Deploy**.
- **Deployments history**: open a past deployment and view or download the exact template and inputs it used.
- **CLI / PowerShell**: `az group export -n rg-contoso-prod > exported.json`, `az deployment group export -g rg-contoso-prod -n storage` (one deployment's template), `Export-AzResourceGroup`, `Save-AzResourceGroupDeploymentTemplate`.

Exported templates hard-code names and values, can't include every resource type or property, and are limited to a few hundred resources per export. Treat them as a draft.

### Convert to Bicep

```bash
az bicep decompile --file exported.json   # creates exported.bicep (best effort, read the warnings)
az bicep build --file main.bicep          # creates main.json (what Resource Manager deploys)
```

<Callout type="exam">
"Delete resources in the group that aren't in the template" is **Complete** mode; the default is **Incremental**. "See what will change before deploying" is **what-if**. "Get a template for resources that were created in the portal" is **Export template** (or the **Deployments** history if they came from a deployment). "Convert an ARM template to Bicep" is **az bicep decompile**, not `az bicep build`. Know both `az deployment group create` and `New-AzResourceGroupDeployment`.
</Callout>

<DeepDive title="Deployment stacks and the end of Complete mode">

Microsoft recommends **deployment stacks** over Complete mode for managing a set of resources as a unit. A stack (`az stack group create`) remembers which resources it created. When you remove one from the template, the stack can delete or detach it (`--action-on-unmanage`), and **deny settings** can stop people changing managed resources outside the stack. That gives you Complete mode's clean-up without deleting things the template never owned. The exam still asks about Incremental and Complete, so learn those first.

</DeepDive>
