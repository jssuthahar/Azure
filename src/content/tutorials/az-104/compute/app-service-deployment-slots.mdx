keyTerms:
  - term: Deployment slot
    definition: A separate live app with its own hostname that belongs to a web app and runs on the same App Service plan.
  - term: Swap
    definition: Exchanging the content and swappable settings of two slots after warming up the source, so the switch has no downtime.
  - term: Slot setting
    definition: An app setting or connection string marked Deployment slot setting, which stays with its slot during a swap.
  - term: Swap with preview
    definition: A two-phase swap that applies the target's settings to the source and stops, so you can check before completing or cancelling.
  - term: Auto swap
    definition: A slot option that swaps the slot into a target automatically after each deployment. Not supported on Linux apps or Web App for Containers.
  - term: Traffic routing
    definition: Sending a percentage of production traffic to another slot for testing in production. A cookie keeps each user on one slot.

## Start with a question

<Story question="How does a theatre change the set without closing the curtain?">

Big theatres have a second stage behind the main one. While the audience watches act one, the crew builds act two back there, lights it, and checks every prop. Then the stages swap, and the audience sees the new scene with no wait. If something's wrong, they can roll the old set straight back.

A **deployment slot** is that second stage. You deploy the new version to **staging**, check it on its own URL, then **swap** it with production. App Service warms it up first, so users never see a half-built set.

</Story>

## Explain it like I'm 10

<Eli10>

You have a toy shop window that people walk past.

Behind it is a second window where you set up the new toys.

When it looks perfect, you **swap** the windows. People see the new toys straight away, with no empty window in between.

Some things stay with each window, like its name card. Those are **slot settings**.

Don't like the new toys? Swap back.

</Eli10>

## The technical explanation

### Create a slot

Slots need a **Standard** plan (5 slots per app) or **Premium v3** (20). Each slot is a real app with its own hostname, settings and deployments, running on the **same plan's instances**.

**Portal:** web app → **Deployment → Deployment slots** → **+ Add slot**, enter a **Name** and choose **Clone settings from** (production, another slot or none).

```bash
az webapp deployment slot create -g rg-admin-web -n app-contoso-shop01 --slot staging --configuration-source app-contoso-shop01
az webapp deploy -g rg-admin-web -n app-contoso-shop01 --slot staging --src-path shop-v2.zip --type zip
```

```powershell
New-AzWebAppSlot -ResourceGroupName rg-admin-web -Name app-contoso-shop01 -Slot staging
```

### Slot settings: what stays and what moves

In **Settings → Environment variables**, tick **Deployment slot setting** on values that describe the environment rather than the code: the production database, the payment gateway, `ENVIRONMENT=Production`.

| Swapped (moves with the code) | Not swapped (stays with the slot) |
| --- | --- |
| App settings and connection strings **not** marked as slot settings | App settings and connection strings marked **Deployment slot setting** |
| General settings such as framework version, 32/64-bit, web sockets | Custom domain names, non-public certificates and TLS settings |
| Handler mappings, path mappings | Scale settings, Always On |
| Public certificates, WebJobs content | IP restrictions (access restrictions), CORS |
| | VNet integration, managed identities, diagnostic settings |
| | Publishing endpoints and settings ending in `_EXTENSION_VERSION` |

```bash
az webapp config appsettings set -g rg-admin-web -n app-contoso-shop01 --slot-settings ENVIRONMENT=Production
az webapp config appsettings set -g rg-admin-web -n app-contoso-shop01 --slot staging --slot-settings ENVIRONMENT=Staging
```

### Swap

What happens, in order:

1. App Service applies the **target's** slot settings, connection strings and related config to the **source** instances, which restart.
2. It waits for every instance to start and **warm up** (it calls the site root, or the paths in `applicationInitialization`).
3. If everything's healthy, it **switches the routing**, so the source's warm instances now serve production. If not, the swap stops and production is untouched.

**Portal:** **Deployment slots** → **Swap**, pick **Source** and **Target**, look at **Config changes**, optionally tick **Perform swap with preview**, then **Start Swap**.

```bash
az webapp deployment slot swap -g rg-admin-web -n app-contoso-shop01 --slot staging --target-slot production
# two-phase: preview, check, then complete (or reset)
az webapp deployment slot swap -g rg-admin-web -n app-contoso-shop01 --slot staging --action preview
az webapp deployment slot swap -g rg-admin-web -n app-contoso-shop01 --slot staging --action swap
```

```powershell
Switch-AzWebAppSlot -ResourceGroupName rg-admin-web -Name app-contoso-shop01 -SourceSlotName staging -DestinationSlotName production
```

**Roll back** by swapping again: the previous version is still warm in staging.

### Auto swap and traffic routing

- **Auto swap** (in the slot's **Configuration → General settings**) swaps a slot into production after every deployment to it. It isn't supported on Linux apps or Web App for Containers.
- **Traffic routing** (the **Traffic %** column) sends a share of production users to another slot. A cookie (`x-ms-routing-name`) keeps each user on one slot. `az webapp traffic-routing set --distribution staging=10`.

<Callout type="exam">
"Release with no downtime" and "roll back quickly" both point to **slots and swap**. "A connection string must stay with production" means **Deployment slot setting**. "Check the app with production settings before it goes live" is **swap with preview**. "Send 10% of users to the new version" is **traffic routing**. If the plan is **Basic**, the answer starts with **scale up to Standard**. And remember custom domains and TLS bindings **don't** swap.
</Callout>

<DeepDive title="Slots share the plan, so watch the load">

Every slot runs on the plan's instances. A staging slot under a heavy load test competes with production for CPU and memory. Keep load tests short, scale the plan out while you test, or run heavy tests against a copy on a separate plan. Also stop slots you aren't using; a stopped slot doesn't serve traffic but still exists on the plan.

</DeepDive>
