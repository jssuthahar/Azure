## Start with a question

<Story question="You ask Copilot to 'fix the discount bug' and it rewrites the wrong function. Whose fault is that?">

Think of an auto-rickshaw driver. "Take me somewhere nice" gets you a ride, just not to where you wanted. "MG Road metro station, the gate near the bank, and please avoid the flyover, it's jammed" gets you there.

Copilot works the same way. It can only act on what's in the **prompt**: your words plus the **context** it can see. Give it a clear goal, point it at the right code and tell it the rules, and you spend less time cleaning up.

</Story>

## Explain it like I'm 10

<Eli10>

You ask your older brother, "Can you help me draw something?"

He draws a cat. You wanted a red racing car for your science poster, and it had to fit on half a page.

Next time you say: "Draw a red racing car for my science poster, half a page, no people." And you show him the poster.

That's a good prompt. What you want, what it's for, the rules, and something to look at.

## The technical explanation

### Goal, context, constraints

| Part | Ask yourself | In the contoso-shop example |
| --- | --- | --- |
| **Goal** | What do I want, and why? | Unknown discount codes should leave the total unchanged instead of returning NaN |
| **Context** | Which code, framework or data? | `applyDiscount(total, code)` in `src/discount.js`, Node.js 22, ES modules |
| **Constraints** | What rules must the answer follow? | Never return a negative total, don't change the function signature, add a test in `tests/` |

Here's the difference in chat:

```text
Vague:    fix the discount bug

Specific: In #file:src/discount.js, applyDiscount returns NaN for unknown
          codes. Return the total unchanged when the code isn't in CODES,
          never return a negative number, and keep the signature.
          Then suggest a test for tests/discount.test.js.
```

Short is fine. Vague isn't. When the output format matters, add an example (that's few-shot prompting, covered in the next lesson), and break big jobs into small steps you check one at a time.

### Prompting in the editor

Inline suggestions don't have a chat box, so your prompt is the code itself:

```javascript
// Return the total after the discount for `code`.
// Unknown codes: return total unchanged. Never return less than 0.
export function applyDiscount(total, code) {
```

A clear **function name**, a **comment** with inputs, outputs and rules, and **meaningful variable names** all go into the prompt. Copilot also reads related **open tabs**, so open a similar file you'd like it to imitate and close ones that have nothing to do with the task.

### How context is determined

| Surface | Context Copilot uses |
| --- | --- |
| Inline suggestions | Code before and after the cursor, file name and language, related open tabs |
| Chat in the editor | Your question, the active file or selection, plus what you add |
| What you can add in chat | `#file`, `#selection`, `#codebase`, `#changes`, `#terminalSelection`, `#terminalLastCommand`, dragged-in files and images |
| Participants | `@workspace`, `@terminal`, `@vscode`, `@github` |
| Always added when present | Repository instructions (`.github/copilot-instructions.md`) and matching `.github/instructions/*.instructions.md` files |
| The conversation | Earlier turns in the same chat |
| Never | Files covered by a content exclusion (in supported IDEs) |

After an answer, expand **Used n references** to check what was sent. The **VS Code & GitHub** tab shows an old tab pulling suggestions off course, a `#file` chip in chat, and the references list.

### Put house rules in instructions, not every prompt

If you keep typing "use ES modules, tests use `node --test`, never log secrets", move it into `.github/copilot-instructions.md`. Those rules are added to chat, agent and code review requests in the repo automatically. Path-specific rules go in `.github/instructions/tests.instructions.md` with `applyTo: "tests/**"`.

<Callout type="exam">
Prompt questions usually show a weak prompt and ask what would improve it. The best answer adds a **specific goal**, the **relevant context** (the file or function) and **constraints**, not just "more words". For context questions: inline suggestions use **nearby code and open tabs**; chat uses the **selection or active file**, **# variables**, **@ participants**, **instructions** and **history**. Rules for every request in a repo belong in **.github/copilot-instructions.md**.
</Callout>

<DeepDive title="Why specific beats polite or long">

The model predicts text that fits the prompt. Vague prompts fit thousands of possible answers, so you get the most average one. Each specific detail (a file name, a version, an edge case, an example) removes possibilities and moves the answer towards yours. Background that doesn't change the answer just uses up the context window. So a good prompt reads like a clear ticket: one goal, the code it applies to, the acceptance criteria. If the first answer is close, keep the conversation going and refine rather than starting over with a longer prompt.

</DeepDive>
