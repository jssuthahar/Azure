## Start with a question

<Story question="If you asked a new colleague to 'write a log line', would you get the format your team uses?">

Probably not. They'd write what they wrote at their last job. Now imagine you show them two lines from your logs first: `[INFO] 2026-11-19 10:02 | cart | Cart created`. They'd get it right straight away.

Copilot works the same way. Asked with no examples (**zero-shot**), it writes `console.error("Payment failed")`, the most common answer on the internet. Shown two examples first (**few-shot**), it writes `[ERROR] 2026-11-19 10:04 | payments | Payment failed for order 1004`. Same model, same request. The examples did the work.

</Story>

## The technical explanation

### Zero-shot: the instruction alone

A zero-shot prompt is just the task: "Write a function that validates an Indian PIN code." There are no examples of the answer. Copilot relies on patterns from its training data and the context it can see (your file, your selection, open tabs).

Zero-shot is fine, and fastest, when the task is common and has a standard answer:

- "Write a function that reverses a string."
- "Explain what this regex does." (with the regex selected)
- "/tests for applyDiscount" when your test style is already obvious from `tests/`.

It goes wrong when the answer depends on **your** conventions: a log format, an error envelope, a naming scheme, a test layout nobody else uses. Copilot can't guess those, so it picks the popular option.

### Few-shot: show, then ask

A few-shot prompt puts one or more **examples** of the output (and often the input) before the real request. The model spots the pattern and continues it. With exactly one example it's sometimes called **one-shot**.

```text
Examples:
[INFO] 2026-11-19 10:02 | cart | Cart created
[WARN] 2026-11-19 10:03 | discount | Unknown code NOPE
Now: a failed payment for order 1004.
```

Copilot answers `[ERROR] 2026-11-19 10:04 | payments | Payment failed for order 1004`. It inferred the level, the date layout, the pipe separators and the module name from just two lines.

Tips for good examples:

| Do | Why |
| --- | --- |
| Use 2 or 3 short examples | Enough to show what varies and what stays fixed |
| Make them agree with each other | Mixed formats give a mixed answer |
| Show the variation you need | One INFO and one WARN teaches that the level changes |
| Use real-looking but fake data | Never paste real customer data into a prompt |

### Few-shot in the editor

You don't need chat for this. Inline suggestions read the code above and below the cursor, so examples in the file act as few-shot context:

```js
// Format: [LEVEL] yyyy-mm-dd hh:mm | module | message
logLine('INFO', 'cart', 'Cart created');
logLine('WARN', 'discount', 'Unknown code NOPE');
// cursor here: Copilot suggests the next logLine(...) in the same shape
```

The same trick works for test cases, enum maps, SQL inserts and translation files. Write two by hand, then let Tab do the rest, and still read every line you accept.

<Callout type="exam">
"Copilot keeps producing a generic format instead of ours" points to **few-shot**: add examples to the prompt. "A prompt that gives only the instruction" is **zero-shot**. If the question says the format must apply to **every** chat in the repository without people pasting examples, the answer moves to **custom instructions** (`.github/copilot-instructions.md`), and a reusable few-shot prompt belongs in a **prompt file** (`.github/prompts/*.prompt.md`).
</Callout>

### Best practices for crafting prompts

The exam lists "apply best practices for prompt crafting" next to few-shot. These are the ones that matter most with Copilot:

1. **Be specific.** Name the language, framework, inputs, outputs and rules. "Return 0 for unknown codes" beats "handle errors".
2. **Give examples** when the format matters (that's few-shot).
3. **One task per prompt.** Ask for the function, then the tests, then the docs. Big combined requests give shallow answers.
4. **Keep it short and relevant.** Extra noise competes for space in a limited context window.
5. **Point at the right code.** Select it, or add `#file:src/discount.js`, or `@workspace` for repo-wide questions.
6. **Iterate.** Treat the first answer as a draft. Say what to keep and what to change.

<DeepDive title="Why examples work so well on a language model">

A large language model predicts the most likely next tokens given everything in the prompt. With no examples, "most likely" means most common across its training data. Examples change the odds: once two lines in the prompt share a pattern, the most likely continuation is a third line in that pattern. That's also why conflicting examples hurt, and why output can still vary between runs. The model isn't learning permanently; the examples only affect this request.

</DeepDive>
