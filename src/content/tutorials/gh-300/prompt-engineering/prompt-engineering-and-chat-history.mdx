## Start with a question

<Story question="If you told a colleague at 9 am to use the v1 pricing API, then at 11 am said 'actually we moved to v2', which one would they use at 4 pm?">

A person would probably remember the correction. Copilot Chat sees the whole conversation every time you send a message, both the 9 am instruction and the 11 am correction, and it has to weigh them. In a long thread, the old one can win.

That's what happened to Asha on the contoso-shop team. She asked for a discount endpoint late in the day, and Copilot called `/v1/prices`. Nothing was wrong with the model. The history was. She opened a new chat, wrote "Using pricing API v2 (`/v2/prices`), add a discount endpoint, follow #file:src/orders.js", and got the right answer first time.

</Story>

## Explain it like I'm 10

<Eli10>

Imagine passing a notebook to a friend. Every time you write a new question, they read the **whole notebook** before answering.

That's handy when your question is "and what about the next one?", because they can see what "the next one" means.

But if the first pages are about maths and you've switched to a story about dragons, the maths pages still get read. Your friend gets muddled.

So when you change subject, you start a fresh notebook.

## The technical explanation

### Principles of prompt engineering

Prompt engineering is just giving the model what it needs to do the job. Microsoft Learn's GitHub Copilot training uses the **4 S's**:

| Principle | What it means | Example |
| --- | --- | --- |
| **Single** | One well-defined task per prompt | "Add input validation to applyDiscount" (not validation, tests and docs at once) |
| **Specific** | Clear inputs, outputs, rules | "Unknown codes return the total unchanged" |
| **Short** | Concise; no padding | Two sentences, not a page |
| **Surround** | Useful context around the prompt | Related files open, clear file and function names, `#file:` references |

Add to that the ideas from the few-shot lesson: give **examples** when the format matters, **break big work into steps**, and **iterate** instead of expecting perfection first time.

### The prompt process flow

When you press Enter in Copilot Chat, more than your sentence goes to the model.

1. **Context gathering.** The extension collects your message, the active file and any selection, references you added (`#file`, `#selection`, `#codebase`, `@workspace`), repository **custom instructions**, and the **chat history** of this conversation. Everything has to fit in a limited **context window**, so the extension picks what matters most.
2. **Secure transmission.** The prompt goes over **HTTPS** to the GitHub Copilot **proxy**.
3. **Filtering.** The proxy authenticates the request and runs pre-filters, for example for harmful or offensive content and prompt-injection attempts.
4. **Generation.** The large language model produces a reply.
5. **Post-processing.** The response is checked again (for example quality, insecure patterns, offensive content, and public code matching where that policy applies) before it reaches you.
6. **You review and continue.** Your next message repeats the loop, now with this answer in the history.

Expand **Used n references** under a reply to see exactly which files went in.

### How chat history helps

History is what makes a conversation possible:

```text
You:     Explain applyDiscount in #file:src/discount.js
Copilot: It looks up the code in CODES and subtracts that percentage...
You:     What happens for an unknown code?
Copilot: CODES[code] is undefined, so the result is NaN...
You:     Fix it and write a test for that case.
```

"It", "that case" and "fix it" only make sense because the earlier turns are part of the prompt.

### How chat history hurts

The same mechanism causes trouble when the thread drifts:

- **Stale facts.** A correction doesn't delete the original instruction. Both are still in the history.
- **Topic bleed.** Answers about the payment module leak into a question about the report module.
- **Crowding.** A long thread takes space in the context window that your actual code could use.

The fixes are simple. Start a **new chat** (the **+** button) or type **`/clear`** when the topic changes. Put the facts that matter **in the new prompt** rather than relying on something said an hour ago. Copilot doesn't remember other conversations, so anything that should apply every time belongs in `.github/copilot-instructions.md`. In Copilot CLI, `/clear` does the same, `/context` shows how full the context is, and `/compact` summarises a long session to free space.

<Callout type="exam">
Expect stories. "Copilot's answer refers to code you discussed three questions ago" means **chat history** is part of the prompt. "After switching to an unrelated task the answers became inaccurate" means start a **new chat** or run **/clear**. "Every developer's chats must follow the team's conventions" means **custom instructions**, because history doesn't carry between conversations. And if a question lists the 4 S's, remember **single, specific, short, surround**.
</Callout>

<DeepDive title="Why the model doesn't just 'know' the latest instruction wins">

A model doesn't keep a list of facts that get overwritten. Each request is a fresh pass over the whole prompt, and the model predicts the most likely reply given all of it. Recent turns usually carry more weight, but an earlier detailed instruction can still pull the answer its way, especially if the correction was brief. Restating the current facts in one clear prompt, in a clean conversation, removes the conflict instead of hoping the model resolves it.

</DeepDive>
