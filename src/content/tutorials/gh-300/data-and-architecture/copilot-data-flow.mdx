## Start with a question

<Story question="When you press a key and Copilot finishes your line, where did your code just go, and who kept a copy?">

Think of sending a parcel through a courier. You don't ship your whole house. You pack the few things that matter, the courier checks the label and scans the box, the parcel arrives, and the courier keeps a delivery record (sent, delivered, signed for), not the contents.

**GitHub Copilot** works much the same way. The extension in your editor packs a small **prompt** from the code around your cursor, sends it **encrypted** to GitHub's **Copilot proxy**, and gets a suggestion back. What's kept afterwards depends on your plan and the feature, and companies care a lot about that answer.

</Story>

## Explain it like I'm 10

<Eli10>

## The technical explanation

### The round trip

Every Copilot request makes the same journey. Here it is for an inline suggestion in `src/discount.js` of the `contoso-shop` repo.

Two things to notice. First, for a completion the extension sends **context it picked**, not your whole repository. Second, the proxy sits on GitHub's side, so filtering happens before the model sees your prompt and again before you see the answer. The next two lessons zoom into each half.

### What's kept, and what isn't

| Data | What it is | What happens to it (Business and Enterprise) |
| --- | --- | --- |
| **Prompts and suggestions** (IDE code completions) | Your code context and the completion | Per the GitHub Copilot Trust Center at the time of writing, not retained once the response is returned |
| **Prompts and suggestions** (other features, such as chat and the CLI) | Your question, attached context, the answer | May be retained for up to 28 days, per the Trust Center at the time of writing |
| **Engagement data** | Events: shown, accepted, dismissed, errors, latency, editor and language | Kept to operate the service and to build usage metrics |
| **Model training** | Using your data to improve models | Your code isn't used to train GitHub's models |

Everything travels **encrypted in transit**. Retention numbers can change, so treat the Trust Center as the source of truth and quote it with a date.

On individual plans (**Copilot Free, Pro and Pro+**), you'll find a personal setting on github.com under your Copilot settings that controls whether GitHub may use your data for product improvements. The walkthrough in the **VS Code & GitHub** tab shows that setting next to the request flow.

### Who sees what inside a company

Admins don't get a feed of everyone's code. They get **metrics** built from engagement data: active users, acceptance rate, chat turns. The seats API shows each person's `last_activity_at` and `last_activity_editor`. Settings changes, seat changes and content exclusion changes appear in the **audit log** as `copilot.` events. That's enough to manage adoption and licences without reading anybody's prompts.

<Callout type="exam">
Expect a security-officer story. "Will our code train the model?" On **Copilot Business or Enterprise**, **no**. "What does GitHub keep to show usage dashboards?" **Engagement data**, not code. "What sits between the IDE and the LLM and filters requests?" The **Copilot proxy**. If a question mentions retention, remember completions and chat are treated differently, and the numbers come from the Trust Center.
</Callout>

<DeepDive title="Why sending less context is a privacy feature too">

The context window limit is usually explained as a quality problem: the model can only read so much. It also helps privacy. Because the extension sends nearby code and short snippets from related tabs instead of the whole project, less of your code travels for each completion. Chat is different: when you use `#codebase` or `@workspace`, Copilot searches your workspace and may attach more files to the request. If some paths should never leave the machine as context, the right tool is a **content exclusion**, set by a repository, organization or enterprise admin on Business or Enterprise.

</DeepDive>
