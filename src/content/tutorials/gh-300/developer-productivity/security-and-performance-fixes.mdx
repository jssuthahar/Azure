## Start with a question

<Story question='Your orders page is slow and a reviewer wrote "this looks injectable". Can Copilot help with both?'>

Yes, if you ask it the right way. Here's the function in `contoso-shop`:

```js
export async function findOrders(db, customer) {
  return db.query(`SELECT * FROM orders WHERE customer = '${customer}'`);
}
```

The customer name goes straight into the SQL. Type `' OR '1'='1` as a name and you get every order in the table. And the page calls this once per customer in a loop, so 200 customers means 200 queries.

Select it, ask Copilot "Is this safe, and can it be faster?", and it'll name both problems and suggest a fix. Your job is to prove the fix works.

</Story>

## The technical explanation

Copilot doesn't scan your code on its own. You get security and performance help by **asking**, and the more you say about the risk and how the code is used, the better the answer.

### Asking for a security review

Select the code, open Chat, and be specific:

- "Review this for security issues, especially injection and input validation."
- "Is there anything here that would leak a secret?"
- `/fix` when you already know what's wrong, for example after a test fails.

Here's what Copilot usually suggests for the function above:

```js
export async function findOrders(db, customer) {
  return db.query('SELECT id, total FROM orders WHERE customer = $1', [customer]);
}
```

The value goes in as a parameter, so it can't change the SQL. It also selects only the columns the page needs.

| Problem Copilot often spots | Typical fix it proposes |
| --- | --- |
| SQL built by joining strings | Parameterised query |
| API key written in the code | Read it from an environment variable or a secrets manager |
| No checks on user input | Validate type, length and range at the edge |
| Weak hashing for passwords | A slow password hash such as bcrypt or Argon2 |
| Unescaped HTML from user input | Escape the output, or use the framework's safe rendering |

### Asking for a performance fix

"Make this faster" on its own gets you a guess. Tell Copilot how the code runs: "This is called once per customer in a loop of a few hundred."

| Problem | What it looks like | Fix |
| --- | --- | --- |
| **N+1 queries** | One query per item in a loop | One query: `WHERE customer = ANY($1)` |
| Repeated work | Same calculation on every pass | Compute once, outside the loop |
| Too much data | `SELECT *` for two fields | Select only what you use |
| No caching | Same expensive call every request | Cache the result with a sensible expiry |

### What Copilot's filters do and don't do

Before a suggestion reaches your editor, Copilot's **post-processing** checks it for some common insecure patterns, such as hard-coded credentials. That helps. It doesn't make suggestions secure. The model predicts likely code, and plenty of public code is insecure or out of date. It can also invent package names or use an API that's been deprecated.

So every Copilot fix gets the same checks as human code:

<Callout type="exam">
Questions here test judgement. If Copilot suggested a security fix, the next step is **validate it** with tests, code scanning and review, never "accept because Copilot filters insecure code". If the scenario says performance advice was vague, the fix is **more context** (how often the code runs, data size), not a different model. And don't paste secrets or real customer data into a prompt to get help.
</Callout>

<DeepDive title="Make good habits the default with custom instructions">

You can put your security rules in `.github/copilot-instructions.md`, for example "Always use parameterised queries with the pg driver" and "Read secrets from process.env, never literals". Chat, the coding agent and Copilot code review all read that file, so suggestions follow your standards more often. It nudges the output. It doesn't replace code scanning.

</DeepDive>
