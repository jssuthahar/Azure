## The technical explanation

### Generate sample data

Copilot is quick at producing data shaped like your real data:

```text
Generate 5 sample orders as JSON matching #file:src/types/order.js.
Fake data only: "Test Customer N" names, customerN@example.com emails,
totals between 50 and 5000, one order with an empty items array.
```

What makes a good sample data prompt:

| Ask for | Why |
| --- | --- |
| The exact format (JSON, CSV, SQL `INSERT`) | So you can drop it straight into a test or seed script |
| The schema, via `#file` or a type | Field names and types match your code |
| Clearly fake values | example.com emails, "Test Customer" names, made-up IDs |
| Edge cases on purpose | Empty lists, zero, very large numbers, unusual characters |
| A generator for big volumes | For thousands of rows, ask for a script using a fake-data library instead of pasting rows |

The rule that matters most: **never paste real customer or employee data into a prompt** to "show the shape". Give the schema or one invented example. Using fake data is one of the responsible-AI mitigations the exam expects you to know.

### Modernize legacy code

Here's the before:

```js
// 2014 code, still in production
var report = function (rows, cb) {
  var out = '';
  for (var i = 0; i < rows.length; i++) {
    out = out + rows[i].name + ',' + rows[i].total + '\n';
  }
  cb(null, out);
};
module.exports = report;
```

And a safe path to the after:

1. **Understand it.** Select the file and run **`/explain`**. Ask follow-ups: who calls it, what happens with an empty array, any hidden side effects.
2. **Pin the behaviour.** Ask for **characterization tests** that capture the current output, including odd cases. Run them against the old code; they must pass.
3. **Modernize in small steps.** "Convert to an ES module with the same CSV output." Then, separately, "update the two callers".
4. **Let agent mode do the legwork.** It can find callers, edit them and run `npm test` after you approve the command, then fix failures it sees.
5. **Review every diff** and keep the tests in the repo.

```js
// Modernized with Copilot: same CSV output as before
export function report(rows) {
  return rows.map((r) => `${r.name},${r.total}`).join('\n') + '\n';
}
```

Notice the `+ '\n'` at the end. The old code added a newline after every row, including the last. Without the characterization test, a "cleaner" version would drop it and the finance import could break.

### Translating between languages

Copilot can translate code, for example COBOL to Java or VB6 to C#, and explain old idioms along the way. Treat that output with extra care. Models see far less code in older or rarer languages, so suggestions are less reliable, and details such as rounding, integer division, date handling and character encoding can change silently. Tests built from the old system's outputs are your safety net.

<Callout type="exam">
"Generate test data without exposing customer information" points to asking Copilot for **synthetic, clearly fake** data, never pasting production rows. "A developer must understand a legacy module before changing it" is **/explain**. "Ensure the modernized code produces the same results" means **write tests first**, change in **small steps**, and **review the diffs**. Options that skip testing because "Copilot understands the code" are wrong: it predicts code, it doesn't run it.
</Callout>

<DeepDive title="Why small steps beat one big rewrite">

Each Copilot request works within a limited context window. A 3,000-line file asked to "modernize everything" means the model can't see all of it at once in detail, and you get a huge diff that nobody reviews properly. Small steps keep each request focused, keep each diff readable, and let the tests catch a mistake right where it was introduced. In agent mode, a long task also fills the session's context; splitting the work, or letting a sub-agent do research in its own context, keeps answers sharp.

</DeepDive>
