## The technical explanation

### Generate code

Copilot generates code in two main ways:

- **Inline suggestions.** Write a comment or a function signature, pause, and ghost text appears. **Tab** accepts, **Esc** dismisses, **Alt+]** / **Alt+[** (Option on macOS) cycle alternatives, **Ctrl+→** accepts one word at a time.
- **Chat.** Ask in the Chat view (**Ctrl+Alt+I**) or inline chat (**Ctrl+I**) and insert the code block you want. Agent mode can create whole files and wire them up.

```js
// Return the cart total in paise, rounded, after applying the discount code
export function cartTotalPaise(items, code) {
  // Copilot suggests the body here as ghost text
}
```

A precise comment is a prompt. "Return the total in paise, rounded" gets better code than "calculate total".

### Refactor without changing behaviour

A refactor changes structure, not behaviour. The safe loop:

1. **Have tests** for the code you're about to change. If there aren't any, ask Copilot for some first.
2. **Select** the code and open chat in **Edit** mode (or inline chat for a single spot).
3. **Say what must not change**: "Refactor cartTotal to use reduce and keep the behaviour the same."
4. **Read the diff**. Removed lines show in red, added in green.
5. **Run the tests**, then **Keep** or **Undo**.

```js
// before
let total = 0;
for (const i of items) total += i.price * i.qty;

// after (Copilot Edits)
const total = items.reduce((sum, i) => sum + i.price * i.qty, 0);
```

Good refactor prompts are specific: extract a function, rename a variable everywhere, replace callbacks with async/await, split a long file. After you make one change, **next edit suggestions (NES)** can predict the related edit further down the file, which suits repetitive renames.

<TryIt labs="gh-tests" text="Write tests first, let Copilot propose a fix, and only commit once the whole suite is green." />

### Document code

- **`/doc`** on a selection writes doc comments (JSDoc, docstrings, XML comments depending on the language).
- Chat can draft a **README** section, a usage example, or a changelog entry from a diff.
- On github.com, the Copilot button in a pull request description drafts a **PR summary**.

Read generated docs as carefully as code. Copilot describes what the code looks like it does, and if the code has a bug, the docs will cheerfully describe the bug as intended.

### Learn faster, switch less

The exam groups "accelerate learning and reduce context switching" with this topic. Inside the IDE you can:

| Ask | Use |
| --- | --- |
| What does this code do? | Select it, `/explain` |
| Where is X handled in this repo? | `@workspace` or `#codebase` |
| How do I do Y in this framework? | Ask chat with the relevant file attached |
| What does this error mean? | `#terminalLastCommand` or `@terminal` |
| What's open in this repo's issues? | `@github` |

Each answer saves a trip to a search engine or a wiki, and keeps your focus on the code. Confirm the answers that matter by reading the code yourself; Copilot can be confidently wrong.

<Callout type="exam">
"Change the structure of code without changing its behaviour" is a **refactor**: review the **diff** and run **tests** before keeping it. "Generate documentation comments for a function" is **/doc**. "A new developer must understand an unfamiliar module without leaving Visual Studio Code" is **/explain** or **@workspace**. If an option says Copilot's output can be merged without review, it's wrong.
</Callout>

<DeepDive title="Ask, Edit or Agent for a refactor?">

**Ask** suggests code you copy in yourself, fine for learning or a tiny change. **Edit** applies changes to the files you pick and shows each diff, the usual choice for a refactor you want to control. **Agent** decides which files to touch, edits them, can run the tests after you approve the command, and iterates on failures. Use agent mode for wider changes such as "rename this field across the API, the UI and the tests", and keep the request small enough that you can still review every diff.

</DeepDive>
