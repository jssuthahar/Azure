<Story question="Who's better at thinking of the weird inputs that break your code: you, at the end of a long day, or a tool that has seen millions of test files?">

Honestly, neither on its own. You know what the code is for. Copilot is good at listing the cases people forget.

## Explain it like I'm 10

<Eli10>

You built a vending machine out of cardboard. A test is a friend who tries it out.

A **unit test** checks one part: does the coin slot take a coin?

An **integration test** checks the whole thing together: put a coin in, press a button, does a sweet come out?

**Edge cases** are the tricky tries: a bent coin, no coin, a button pressed twice.

If the machine gets stuck, that's not your friend's fault. They just found the problem before a real customer did.

## The technical explanation

### Generate unit tests

Select the function and ask:

```text
/tests applyDiscount: cover unknown codes, no code, 0 and very large totals
```

Copilot writes tests in the framework your project already uses (it reads `package.json` and existing files in `tests/`). You can also ask agent mode: "Write unit tests for src/discount.js, run them, and tell me what fails." It writes the file, asks before running `npm test`, and reports back. If you keep test rules in `.github/instructions/tests.instructions.md` with `applyTo: "tests/**"`, Copilot follows them.

```js
import { test } from 'node:test';
import assert from 'node:assert/strict';
import { applyDiscount } from '../src/discount.js';

test('SAVE10 takes 10% off', () => assert.equal(applyDiscount(100, 'SAVE10'), 90));
test('unknown code leaves the total unchanged', () => assert.equal(applyDiscount(100, 'NOPE'), 100));
test('no code leaves the total unchanged', () => assert.equal(applyDiscount(100), 100));
test('empty cart stays at 0', () => assert.equal(applyDiscount(0, 'HALF'), 0));
```

### Find the edge cases

Edge cases are where bugs live. Name the ones you know and ask Copilot for more: "What edge cases am I missing for applyDiscount?"

| Category | For `applyDiscount(total, code)` |
| --- | --- |
| Unknown or invalid input | `'NOPE'`, lowercase `'save10'` |
| Missing input | no code, `null`, empty string |
| Zero and boundaries | total `0`, a 100% code |
| Very large or small | `1e12`, negative totals |
| Wrong type | `'100'` as a string |

Copilot is good at producing this list. You decide which behaviours are correct, because only you know the business rule: should a lowercase code work? Should a negative total throw?

### Write assertions that can fail

An assertion compares the actual result with an exact expected value. Check every generated test for this:

| Weak | Strong |
| --- | --- |
| `assert.ok(applyDiscount(100, 'SAVE10'))` | `assert.equal(applyDiscount(100, 'SAVE10'), 90)` |
| "doesn't throw" | "throws a RangeError for a negative total" |
| one test checking five things | five tests, each named after one behaviour |

A weak test passes even when the code is wrong, which is worse than no test because it looks like coverage. Use **arrange, act, assert**: set up inputs, call the code, check one result.

### Integration tests

Unit tests isolate one function. **Integration tests** check that parts work together: the HTTP route, the cart and discount modules, and the JSON response.

```js
import request from 'supertest';
import { app } from '../src/app.js';

test('POST /cart/total applies SAVE10', async () => {
  const res = await request(app)
    .post('/cart/total')
    .send({ items: [{ price: 50, qty: 2 }], code: 'SAVE10' });
  assert.equal(res.status, 200);
  assert.equal(res.body.total, 90);
});
```

Ask Copilot for the **setup and teardown** too: starting the app, seeding a test database with fake data, cleaning up afterwards. Mocks and stubs keep unit tests isolated; integration tests use the real pieces (or realistic test doubles for external services).

### Read the failures

```text
$ npm test
✔ SAVE10 takes 10% off
✖ unknown code leaves the total unchanged   expected 100, got NaN
✖ no code leaves the total unchanged        expected 100, got NaN
ℹ pass 4  fail 2
```

A failing generated test means one of two things: **the code has a bug** or **the test expects the wrong behaviour**. Here the code is wrong, so ask for the smallest fix (`const pct = CODES[code] ?? 0;`), read the diff and rerun. Never delete a failing test just to get green.

<Callout type="exam">
"Generate tests for the selected function" is **/tests**. "Ensure the tests cover unusual and boundary inputs" means asking Copilot to **identify edge cases**. "Verify the API route, discount logic and response work together" is an **integration test**, while "test one function in isolation" is a **unit test**. If a generated test fails, the right answer is to **investigate** whether the code or the test is wrong, never to delete the test or accept the output without review.
</Callout>

<DeepDive title="Coverage numbers can lie">

Copilot can push line coverage up quickly, and that's tempting to celebrate. But coverage only says which lines ran, not whether anything was checked. A test that calls every function and asserts nothing gives high coverage and zero protection. Look at the assertions, try breaking the code on purpose to see if a test fails (the idea behind mutation testing), and keep tests readable so the next person knows what behaviour each one protects.

</DeepDive>
