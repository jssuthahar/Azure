## Start with a question

<Story question="Copilot wrote a neat line of code that calls Money.roundBankers(). Your project has never had a Money library. Where did it come from?">

It came from patterns. Plenty of codebases have a money helper with a rounding function, so the model guessed that yours might too. It didn't check, because it can't.

That's the heart of this lesson. **Generative AI** predicts what code usually looks like. Most of the time that's very useful. Some of the time it's wrong in a way that looks completely right, and you're the one who has to notice.

</Story>

## Explain it like I'm 10

<Eli10>

Think of a friend who has read a million recipes but has never cooked.

Ask for a cake recipe and you'll get a great one, fast. Ask about a brand-new oven and they might invent a button it doesn't have.

They aren't lying. They're just guessing from what recipes usually say.

So you still taste the cake before you serve it.

</Eli10>

## The technical explanation

Copilot runs on **large language models (LLMs)**. An LLM takes your prompt (the code around your cursor, open files, your chat message) and predicts the next tokens, one after another. It's very good at "what usually comes next". It isn't checking facts, running code or reading your whole repository.

Every risk below comes from that one idea.

### The limits you need to know

| Limit | What it looks like in contoso-shop | Why it happens |
| --- | --- | --- |
| **Hallucination** | `Money.roundBankers(total)`, or `npm install` for a package name that doesn't exist | The model produces plausible names from patterns, not from your code or a registry |
| **Knowledge cut-off** | An old Node.js API, a library version with a known vulnerability | Training data ends at a date; newer releases and fixes aren't in it |
| **Insecure code** | String-built SQL, a hard-coded secret, no input validation | Insecure patterns exist in public code the model learned from |
| **Bias** | Sample data that assumes every customer has a first and last name | Training data reflects human bias |
| **Non-deterministic output** | Ask twice, get two different versions of `applyDiscount` | Generation involves sampling, so answers vary |
| **Limited context window** | Copilot ignores a rule in a file it never saw | Only so much fits into one prompt |
| **Weaker on rare languages** | Thin suggestions for an old in-house scripting language | Less training data for that language |
| **No real understanding** | Code that compiles but breaks the business rule | It predicts text; it doesn't know your intent |

### Confident isn't the same as correct

The tricky part is tone. A wrong answer is formatted just as nicely as a right one. There's no warning label on a hallucination. Here's a suggestion that reads fine:

```js
export function applyDiscount(total, code) {
  const pct = CODES[code];
  return total - (total * pct) / 100;
}
```

It works for `SAVE10`. For an unknown code, `pct` is `undefined` and the function returns `NaN`. Nothing about the suggestion hinted at that. A one-line test would have caught it.

### What the context window means for you

Copilot only knows what's in the prompt. In the editor that's mostly the current file, the code near your cursor and related snippets from open tabs. In chat it's what you add with `#file`, `#codebase` or a selection, plus earlier messages. If a validation rule lives in a file Copilot never saw, it can't respect it. Long chats also push older details out.

<Callout type="exam">
The exam describes a symptom and asks for the limit behind it. "Suggests a function or package that doesn't exist" is a **hallucination**. "Doesn't know a recent library version" is the **knowledge cut-off**. "Gives different code for the same prompt" is **non-deterministic output**. "Ignores code in other parts of a large project" is the **limited context window**. The answer to "how do you reduce the risk" is almost always **human review plus testing**, not "write a longer prompt" on its own.
</Callout>

<DeepDive title="Package hallucinations are a supply-chain risk">

If a model keeps inventing the same plausible package name, someone can publish a malicious package under that name and wait. A developer who runs `npm install` on the suggestion without checking pulls it in. So check that a package is real, maintained and the one you meant before you add it, and let dependency review and `npm audit` look at every new dependency in the pull request.

</DeepDive>
