## Start with a question

<Story question="If Copilot writes a bug that leaks customer data, who gets the phone call at 2 a.m.?">

You do. Or your team lead. Not Copilot.

That one answer explains most of responsible AI. The tool can draft code faster than any of us, but it can't be held responsible, so people have to be. **Responsible AI** is the set of principles and habits that keep a person in charge: checking for bias, protecting data, being open about AI use, and owning the result.

</Story>

## Explain it like I'm 10

<Eli10>

Imagine a robot that helps you with homework.

It's fast, but sometimes it's wrong, and sometimes it only thinks about kids like the ones in its books.

So there are rules. Check its answers. Don't tell it secrets. Make sure its answer works for every kid in class. Tell the teacher when the robot helped.

And if the homework is wrong, it's still your name on it.

</Eli10>

## The technical explanation

Microsoft describes six **responsible AI principles**. GitHub builds Copilot with them in mind, and the GH-300 exam expects you to know them and apply them to everyday coding.

### The six principles, in Copilot terms

| Principle | What it means | What it looks like with Copilot |
| --- | --- | --- |
| **Fairness** | No unfair treatment of groups of people | Check generated validation, sample data and messages for assumptions about names, genders, regions or languages |
| **Reliability and safety** | Works as intended and fails safely | Test suggestions, cover edge cases, don't ship code you don't understand |
| **Privacy and security** | Protects data and resists attack | No secrets or real personal data in prompts, content exclusions, code scanning |
| **Inclusiveness** | Works for people of all abilities and backgrounds | Ask for accessible UI (labels, contrast, keyboard use) and test it |
| **Transparency** | People understand the system and know when AI was used | Say in the pull request when Copilot drafted code; know its limits |
| **Accountability** | People stay responsible | A person reviews, approves and owns every change |

The last two are the ones people forget. Transparency isn't about blame. It helps reviewers know where to look harder. Accountability means "Copilot wrote it" is never a reason a bug shipped.

### Harms and the mitigation for each

The exam likes to pair a harm with the right fix. Learn these as pairs.

| Harm | Example | Mitigation |
| --- | --- | --- |
| **Hallucination / wrong code** | An API that doesn't exist, a function that returns `NaN` | Human review, tests, checking the docs |
| **Insecure code** | String-built SQL, missing input checks | Code scanning (for example CodeQL), secure review, dependency review |
| **Bias** | A form that rejects one-word names | Diverse test data, review for assumptions |
| **IP and licensing** | A suggestion that matches public code | Public code filter (Block, or Allow with code references), licence check |
| **Privacy leaks** | Real customer data pasted into chat | Fake sample data, content exclusions, team guidance |
| **Over-reliance** | Accepting everything with Tab, skills fading | Review every suggestion, understand before you accept |

Here's a small fairness example in contoso-shop:

```js
// Copilot's first suggestion
const valid = /^[A-Za-z]+ [A-Za-z]+$/.test(fullName);
// Rejects "Siddharth", "O'Brien", "José García" and many real names
```

The fix is less clever code: accept any non-empty display name, and test with names from different cultures.

<Callout type="exam">
When a question asks who's responsible for code that Copilot suggested, the answer is the **developer** (and the team that reviews it), never GitHub or the model. "Tell reviewers AI helped" maps to **transparency**. A question about "users with disabilities" maps to **inclusiveness**, and "biased results for a group" maps to **fairness**. For mitigations, pick the one that matches the harm: content exclusions for sensitive files, the public code filter for matching public code, code scanning for vulnerabilities.
</Callout>

<DeepDive title="Policies help, people still decide">

An organization can set Copilot policies (which features are on, whether suggestions matching public code are blocked, which models and MCP servers are allowed) and content exclusions. Those reduce risk across hundreds of developers. They don't make a suggestion correct or fair. Responsible use is the mix of both: guardrails from admins, and a person who reviews, tests and owns each change.

</DeepDive>
