## The technical explanation

Copilot predicts code. It doesn't run it, test it or know your business rules. So the output needs the same checks as code from a new colleague, plus a bit more care because it sounds so sure of itself.

### Why validation isn't optional

- **It can be wrong and look right.** No warning appears on a bad suggestion.
- **It can be insecure.** Insecure patterns exist in the code models learned from.
- **It can be outdated.** The knowledge cut-off means old APIs and versions.
- **It can miss your rules.** If a rule wasn't in the context, Copilot didn't see it.
- **You own it.** Once you accept it, it's your code.

### A validation routine that works

In contoso-shop, the test that catches the bug is short:

```js
// tests/discount.test.js
test('unknown code leaves the total unchanged', () => {
  expect(applyDiscount(100, 'NOPE')).toBe(100);   // fails: NaN
});
```

The fix is one line, `const pct = CODES[code] ?? 0;`, and then `npm test` passes. Ask Copilot for tests with `/tests`, but add the edge cases you care about yourself. If the same model wrote the code and the tests, both can share one wrong assumption.

### Operating Copilot responsibly every day

| Habit | Why |
| --- | --- |
| Give clear context (open the right files, use `#file`, write a specific prompt) | Better input means fewer wrong guesses |
| Keep secrets and real personal data out of prompts | Prompts leave your machine; use fake sample data |
| Never accept code you don't understand | You can't review or maintain what you can't explain |
| Keep pull request review, CI and branch protection | Copilot speeds up writing, it doesn't replace the gates |
| Give feedback with thumbs up or down | It helps GitHub improve responses |
| Say when Copilot helped | Reviewers know where to look harder |

**Copilot code review** is useful here, but know its limits: it leaves comments and suggested changes, it never approves, and it doesn't count toward required approvals. A person still signs off.

<Callout type="exam">
If a question asks the best way to confirm that Copilot's code works, the answer is to **test it** (and review it), not to ask Copilot whether it's correct or to rewrite the prompt. For security problems the answer is **code scanning** or security review. And when two answers both sound reasonable, prefer the one that keeps a **human** reviewing before merge.
</Callout>

<DeepDive title="Why tests written by the same model aren't enough">

If you ask Copilot to write `applyDiscount` and then its tests, both come from the same prompt and the same patterns. If the model assumed every code is valid, the tests may only use valid codes and pass happily. Write at least the edge-case tests yourself, or ask for them explicitly ("include an unknown code, a zero total and a negative total"), and review the expected values with the business rule in hand.

</DeepDive>
