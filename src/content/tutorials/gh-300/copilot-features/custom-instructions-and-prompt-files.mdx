## The technical explanation

Copilot only knows what's in the prompt. Custom instructions and prompt files are two ways to put the same good context into the prompt every time, without typing it.

### The instruction files

| File | Where | When it applies | Who reads it |
| --- | --- | --- | --- |
| `copilot-instructions.md` | `.github/` | Every request in the repository | Copilot Chat, Copilot coding agent, Copilot code review |
| `*.instructions.md` | `.github/instructions/` | Only when the files involved match its `applyTo` glob | Chat and agents in supported editors, coding agent, code review |
| `AGENTS.md` | Repo root (or a folder) | Agent work in that part of the repo | Agents, including the coding agent |
| Personal and organization instructions | Your GitHub settings, or set by the org | Your requests, or the org's | Copilot Chat on github.com and supported clients |

A repository file for contoso-shop might look like this:

```markdown
# Copilot instructions for contoso-shop
- Node.js 22, ES modules, no CommonJS.
- Tests use the Node test runner: node --test.
- Never log secrets; read config from environment variables.
```

Keep it short and true for the whole repo. Rules that only matter for some files go in a path-specific file:

```markdown
---
applyTo: "tests/**/*.js"
---
Arrange, act, assert. One behaviour per test.
Name each test after the behaviour it checks.
```

Save that as `.github/instructions/tests.instructions.md`. When you ask Copilot to change `tests/cart.test.js`, both files go into the prompt. When you change `src/discount.js`, only the repo-wide file does.

### Did it work?

In Copilot Chat, the answer's **references** list shows the instruction files that were used. If yours isn't there, check the folder and file name, check that instruction files are turned on in your editor's Copilot settings, and check that the `applyTo` glob really matches.

### Prompt files: reusable prompts

A prompt file is a saved task. It lives in `.github/prompts/` and ends in `.prompt.md`. The front matter is optional and can set:

| Field | What it does |
| --- | --- |
| `mode` (or `agent`) | Which chat mode or custom agent runs it, for example `agent` |
| `description` | The text you see when you pick the command |
| `tools` | Which tools the prompt may use |
| `model` | A model to use, if your organization allows it |

```markdown
---
mode: agent
description: Add a REST endpoint with validation and tests
---
Create a new endpoint for ${input:resource}.
Validate input, return 400 on bad data, and add tests.
```

Save it as `.github/prompts/new-endpoint.prompt.md` and type `/new-endpoint resource=orders` in Chat. `${input:resource}` becomes `orders`. Because the file is in the repo, the prompt gets reviewed in pull requests and improves over time, and every developer gets a **consistent response** shape.

### Custom agents, briefly

If you keep asking Copilot to play the same role, make a **custom agent**: `.github/agents/test-writer.agent.md` with a name, a description, a short list of tools and its own instructions. In the CLI you can keep personal agents in `~/.copilot/agents/` and run one with `--agent=test-writer` or pick it with `/agent`.

<Callout type="exam">
Read the verbs. "Every request in the repository" or "review standards for Copilot code review" points to **`.github/copilot-instructions.md`**. "Only for files in a folder" or "only test files" points to an **`.instructions.md`** file with **`applyTo`**. "Reuse a prompt so the team gets consistent responses" points to a **prompt file** in **`.github/prompts/`** run with **`/name`**. A distractor often swaps the folder (`.vscode/` instead of `.github/`) or the ending (`.md` instead of `.prompt.md`).
</Callout>

<DeepDive title="Instructions steer; they don't enforce">

Instructions are text added to the prompt. The model weighs them with everything else, so a long, contradictory file works worse than ten clear lines. Write rules as short statements, avoid "always try to" phrasing, and don't paste whole style guides. If a rule must never break (no `console.log` of tokens, no new dependencies without approval), back it with a linter rule, a test or a branch protection check. Copilot code review reading your instructions is useful, but it leaves comments only, and a person still decides.

</DeepDive>
