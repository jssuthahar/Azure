## Start with a question

<Story question="My pull request waits two days for a reviewer, and then they only spot a typo and a missing null check. Can something catch that sooner?">

You open pull request #52 on contoso-shop: a new `FREE` discount code. The senior developer is busy. When she finally looks, her first three comments are things any careful reader would have caught: `free` and `FREE` behave differently, an unknown code returns `NaN`, there's no test for the new branch.

**Copilot code review** reads the same diff in a few minutes and leaves those comments, often with a fix you can commit. The senior developer still reviews, but now she's looking at the design, not the typos. And she's still the one who approves.

</Story>

<Eli10>

## The technical explanation

### Three ways to get a Copilot review

| Where | How | Good for |
| --- | --- | --- |
| On a pull request | Open the PR, go to **Reviewers**, pick **Copilot** | A review on demand. Request it again after you push fixes. |
| Automatically | A repository or organization **ruleset** with the rule that requests a Copilot review | Every new pull request gets reviewed, nobody has to remember |
| In the IDE | Ask Copilot to review your selection or your changes in VS Code (and other supported editors) | Catching problems before you even push |

### What the review looks like

Copilot reads the changed files and posts a review such as "Copilot reviewed 2 files and left 1 comment". Each comment points to a line and usually explains the problem in a sentence. Many include a **suggested change**:

```js
// suggested change on src/discount.js, line 4
const pct = CODES[String(code).toUpperCase()] ?? 0;
```

The author can **Commit suggestion** from the comment, or reply and **Resolve conversation** if it doesn't fit.

### What it doesn't do

This is the part the exam loves:

- It always submits a **Comment** review. It never **Approves** and never **Requests changes**.
- Its review **doesn't count toward required approvals**. A branch that needs one approval still needs one human approval.
- It doesn't merge. A person does, and branch protections and status checks still apply.
- It can miss problems and can be wrong. Treat each comment like a colleague's suggestion: read it, then decide.

### Review standards from your instructions

Copilot code review reads the same instruction files as Chat. Put your team's review rules in `.github/copilot-instructions.md`:

```markdown
## Code review
- Flag any discount logic without a unit test.
- Prefer early returns over nested ifs.
- Comment in English, be brief.
```

Rules for one part of the codebase go in a path-specific `.instructions.md` file with `applyTo`, and Copilot code review uses those for matching files too.

### Turning it on

Copilot code review is part of the paid plans. In an organization, an admin controls it under **Organization settings › Copilot › Policies**, and can add a **ruleset** so it runs on new pull requests. If an enterprise enforces the policy, the organization can't change it.

<Callout type="exam">
Watch for answers that give Copilot more power than it has. "Copilot approves the pull request" or "Copilot's review satisfies the required reviewer rule" is wrong: it leaves **Comment** reviews only. "Review every new pull request without manual requests" is a **ruleset**. "Make Copilot's review comments follow the team's coding standards" is **custom instructions** in `.github/copilot-instructions.md`, not a setting in the PR.
</Callout>

<DeepDive title="Copilot reviewing Copilot">

When Copilot coding agent opens a draft pull request, you can ask Copilot code review to look at it too. That's fine as a first pass, but it's the same family of models checking its own kind of output, so it shares blind spots. Keep at least one human approval required, keep tests and code scanning as status checks, and make sure whoever assigned the issue to the agent isn't the only one approving its pull request.

</DeepDive>
