## Start with a question

<Story question="Our company bought Copilot for 300 developers. Who decides whether they can use the CLI, the coding agent or a particular model?">

A school buys tablets for every class. The head office decides some rules for every school ("no social media apps"). For everything else, each school's principal decides ("tablets allowed in the library, not at lunch").

GitHub works the same way. Contoso buys **Copilot Business** for the `contoso` organization. The organization owner decides **who gets a seat** and **which features** those people can use: chat on github.com, the Copilot CLI, Copilot code review, the coding agent, MCP servers, which models. If Contoso has an **enterprise** account above several organizations, the enterprise can lock a rule for all of them.

</Story>

## Explain it like I'm 10

<Eli10>

Head office makes a rule: "No phones in exams." Every school must follow it. That's an **enforced** policy.

For other things head office says: "You decide." That's **No policy**.

Then each principal decides: "Our class can use the art room, not the science lab." Those are the **organization's** policies.

And the principal decides which kids get a tablet at all. That's **access**.

</Eli10>

## The technical explanation

### Three pages under Organization settings › Copilot

| Page | Question it answers | Options |
| --- | --- | --- |
| **Access** | Who gets a Copilot seat? | All members, selected members and teams, or nobody (disabled) |
| **Policies** | Which features can seat holders use? | Each feature Enabled or Disabled |
| **Models** | Which models show in the model picker? | Each model on or off |

The same Copilot menu also holds **Content exclusion** (paths Copilot shouldn't use), **MCP** and **Metrics**, which have their own lessons.

### The feature policies you'll see on the exam

| Policy | What it controls |
| --- | --- |
| Copilot in the IDE / Copilot Chat in the IDE | Chat and agent features in supported editors |
| Copilot Chat in github.com | Asking Copilot on the GitHub website |
| Copilot CLI | Whether members can use the `copilot` command in the terminal |
| Copilot code review | Whether Copilot can review pull requests (add a **ruleset** for automatic reviews) |
| Copilot coding agent | Whether issues can be assigned to Copilot to open pull requests |
| MCP servers in Copilot | Whether agents can use Model Context Protocol servers |
| Suggestions matching public code | **Block** them, or **Allow** them with code references |

These policies apply to people who get Copilot through the organization. Turning a feature off removes it for them across IDEs and github.com, so you don't need to touch anyone's editor settings.

### Enterprise versus organization

<Flow
  caption="How a Copilot policy reaches a developer"
  steps={[
    { title: 'Enterprise', text: 'Enforce Enabled, enforce Disabled, or No policy.' },
    { title: 'Organization', text: 'If No policy, the org owner picks Enabled or Disabled.' },
    { title: 'Seat', text: 'Access decides if the member has Copilot at all.' },
    { title: 'Developer', text: 'Gets the features the policies allow, in every supported client.' },
  ]}
/>

An enterprise owner (GitHub Enterprise Cloud) sets each Copilot policy to an enforced value or to **No policy**. Enforced means every organization in the enterprise gets that value, and the organization's settings page shows it locked. No policy hands the decision to each organization.

<Callout type="exam">
Two traps. First, **Access** and **Policies** are different questions: Access is *who* has Copilot, Policies is *what* they can use. Second, if a question says an organization owner "can't change" a Copilot setting, the answer is that the **enterprise enforces** it. "Let each organization choose" is **No policy**. And "enable Copilot code review on every new pull request" needs the **code review policy** plus a **ruleset**.
</Callout>

<TryIt labs="gh-seats-audit" text="Act as the Contoso org admin: check the subscription, manage seats with the REST API and find the changes in the audit log." />

<DeepDive title="Roll out in stages">

Big rollouts go better in steps. Give seats to one or two teams first. Start with inline suggestions, chat and code review, block suggestions matching public code if your legal team prefers it, and leave the coding agent and MCP off until you've written guidance (which servers are approved, who reviews agent pull requests). Watch the Copilot metrics and the audit log, then widen access. Because policies are central, turning something off later is one click, not a message to 300 developers.

</DeepDive>
