## Start with a question

<Story question="We pay for 120 Copilot seats. Finance asks how many people actually use them, and security asks who switched off the public code filter. Where do I look?">

Think of an office building. The front desk keeps a **visitor book**: who came in, when, which floor. And the facilities team has a **badge list**: who has a badge, and when each badge last opened a door.

GitHub gives a Copilot admin both. The **audit log** is the visitor book: every Copilot settings change, seat change and content exclusion change, with who did it and when. The **Copilot user management REST API** is the badge list: every seat, when it was last used, and calls to hand out or take back seats in bulk.

## The technical explanation

### Audit log events for Copilot

Organization owners open the **Audit log** page in the organization settings. Copilot events have names that start with **`copilot.`**, so the search **`action:copilot`** filters to them. You'll see things like:

- a seat added or cancelled for a user or team
- a Copilot policy changed (for example, a feature enabled or disabled)
- content exclusion settings changed

Each entry has the **actor**, the **action**, the **time** and details. You can export the results. Event names change over time, so check the docs' list of audit log events rather than memorising each one. For the exam, remember the prefix and the search.

### The Copilot user management REST API

All the endpoints sit under `/orgs/{org}/copilot/billing`. With the GitHub CLI, `gh api` makes the calls for you:

| Method and path | What it does |
| --- | --- |
| `GET /orgs/{org}/copilot/billing` | Subscription settings and a seat breakdown for the org |
| `GET /orgs/{org}/copilot/billing/seats` | Every seat with `assignee`, `last_activity_at` and `last_activity_editor` |
| `POST /orgs/{org}/copilot/billing/selected_users` | Add seats for `selected_usernames` |
| `DELETE /orgs/{org}/copilot/billing/selected_users` | Cancel seats for `selected_usernames` |
| `POST` / `DELETE /orgs/{org}/copilot/billing/selected_teams` | The same, for `selected_teams` |
| `GET /orgs/{org}/copilot/metrics` | Usage metrics for the org |

Finding an unused seat:

```bash
gh api /orgs/contoso/copilot/billing/seats
# { "total_seats": 3, "seats": [
#   { "assignee": { "login": "chen-qa" },
#     "last_activity_at": "2026-09-02T09:12:00Z",
#     "last_activity_editor": "jetbrains/2026.2" }, ... ] }
```

Giving one person a seat and taking one away:

```bash
gh api -X POST /orgs/contoso/copilot/billing/selected_users -f "selected_usernames[]=dina-new"
# { "seats_created": 1 }
gh api -X DELETE /orgs/contoso/copilot/billing/selected_users -f "selected_usernames[]=chen-qa"
# { "seats_cancelled": 1 }
```

Three rules to remember:

1. The token needs the **`manage_billing:copilot`** scope.
2. Adding and cancelling by user or team applies when the org gives Copilot to **selected** members and teams, not "all members".
3. A cancelled seat goes into **pending cancellation** and keeps working until the **end of the billing cycle**.

<Callout type="exam">
Match the question to the tool. "Who changed a Copilot setting" or "when was a seat removed" is the **audit log** with **`action:copilot`**. "Which seats are inactive" is **GET `/copilot/billing/seats`** and **`last_activity_at`**. "Assign seats to a team in a script" is **POST `/copilot/billing/selected_teams`**. Distractors use PUT or PATCH, a `/copilot/seats` path without `billing`, or claim a cancelled seat stops at once.
</Callout>

<DeepDive title="Automate the review, keep a human in it">

You can run the seat review on a schedule, for example a GitHub Actions workflow that calls the seats endpoint once a month and opens an issue listing seats with no activity in 60 days. Don't let the script cancel seats on its own: someone on leave or using an editor that reports activity late would lose access. Let a manager confirm, then cancel with one API call. Keep the token in an Actions secret, scoped to just what the job needs, and the audit log will show the cancellations with the token's owner as the actor.

</DeepDive>
