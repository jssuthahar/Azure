## Start with a question

<Story question="My pull request description just says 'fixes stuff'. Reviewers hate it, new joiners keep asking the same questions, and the product team wants a tiny app nobody has time to build. Is there one fix for all three?">

Not one fix, but three small tools that live on github.com.

When you open pull request #53 on contoso-shop, Copilot can **write the description** from the diff. When new joiners keep asking how discounts work, a **Copilot Space** holds the files, issues and notes that answer it, so they ask the space instead of you. And when the product manager wants a quick page that tracks which discount codes get used, **GitHub Spark** can build it from a sentence.

The trick for the exam is knowing which tool matches which problem.

</Story>

## The technical explanation

### Pull request summaries

When you create or edit a pull request, the description box has a **Copilot** button. Select it and Copilot reads the changes and writes a summary, for example:

```text
What changed: adds page and pageSize query params to GET /orders (max 100).
Files: src/orders.js, tests/orders.test.js
```

It's a draft. A diff tells Copilot **what** changed, not **why**, so add the reason, the risk and how to test it. Then check the summary is accurate: it can describe a change too broadly or miss one. Copilot can also summarise in other places on github.com, but for the exam the PR description is the one to know.

### Copilot Spaces

A **Copilot Space** is curated context for a topic. You add:

| Source | Example for contoso-shop |
| --- | --- |
| Files from repositories | `README.md`, `docs/`, `src/discount.js` |
| Issues and pull requests | #41 HALF applies twice, #44 NaN for unknown codes |
| Notes | "Discounts never stack. Totals never go below 0." |
| Instructions | "Answer for someone new to the codebase. Cite the file." |

Then you ask questions in the space, and Copilot answers from those sources. You can keep a space personal or **share** it with your team or organization, so everyone's questions are grounded in the same material. Compared with custom instructions: instructions are **rules** added to requests in a repository; a space is **knowledge** for a topic, and it can pull from more than one repository.

### GitHub Spark

**GitHub Spark** builds **micro apps** from natural language. You describe what you want, Spark builds a working full-stack app and hosts it, and you **iterate** by chatting or by editing the code. When you're happy, you publish it, or open the code in a repository to keep working on it like any other project. Spark is available on **Copilot Pro+** and **Copilot Enterprise**.

It's for small tools and prototypes. Anything that handles customer data or money needs the same review, tests and security checks as hand-written code.

| You want to… | Use |
| --- | --- |
| Describe a pull request's changes quickly | PR summary |
| Give the team one place to ask about a topic, grounded in your sources | Copilot Spaces |
| Build a small app from a description | GitHub Spark |
| Set rules Copilot follows in a repo, including review standards | Custom instructions |

<Callout type="exam">
The exam groups these features in one objective and swaps them in the answers. "Curated context shared with a team" or "ground answers in selected files and issues" is **Copilot Spaces**. "Natural-language micro app" is **GitHub Spark**, and only Pro+ and Enterprise include it. "Generate a description of the changes in a pull request" is a **PR summary**. "Customizable review standards" means **instructions files**, not Spaces.
</Callout>

<DeepDive title="What a summary can and can't know">

A PR summary is generated from the diff and the pull request's own content. It doesn't know the conversation you had in a meeting, the customer complaint behind the change, or which parts you're unsure about. That's exactly what reviewers need most. A good habit: let Copilot write the "what changed" part, then write two lines yourself, "why" and "how to test". It takes a minute, and it makes the summary honest about where the human judgement went.

</DeepDive>

## When to use it and when not to

<UseWhen
  use={[
    'PR summaries for a quick, accurate first draft of what changed.',
    'Copilot Spaces when a team keeps asking about the same topic and the answers live in known files and issues.',

  ]}
  avoid={[
    'An unedited summary as the whole PR description. Add the why and how to test.',
