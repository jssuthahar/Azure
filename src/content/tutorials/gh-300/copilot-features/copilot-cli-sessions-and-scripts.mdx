## Start with a question

<Story question="Would you give a new assistant your house keys and say 'do whatever you think is needed' while you're away?">

Probably not. You'd say "you can water the plants and take in the post, but don't touch the car". And if you're at home, you'd rather they ask before each new job.

Copilot CLI works exactly like that. In an **interactive session** you're at home: it asks before each new tool, like writing a file or running `mv`. In a **non-interactive** run (`copilot -p`) you're away, so you hand over a written list: `--allow-tool 'write'`, `--deny-tool 'shell(rm)'`. Anything not on the list, it doesn't do.

</Story>

## Explain it like I'm 10

<Eli10>

You can talk with Copilot in the terminal for a long time, like a phone call. It asks "may I?" before it does something new.

Or you can leave it one note with one job, and walk away.

When you leave a note, you also write what it's allowed to do and what it must never do.

"Never" always beats "allowed".

And whatever it makes, you check before you use it.

</Eli10>

## The technical explanation

### Interactive sessions

```text
$ copilot                                         # open a session
$ copilot -i "organize the old log files into logs/archive"   # open one with a first prompt
```

In a session, Copilot asks before it uses a tool it hasn't been allowed:

```text
? Allow Copilot to use shell(mv)? (y/n) y
✔ Moved 2 files to logs/archive/
```

The real prompt lets you approve that tool once or for the rest of the session, or say no and tell Copilot what to do instead (the exact wording changes between versions). Useful session commands:

- `/exit` leaves and **saves** the session. `copilot --continue` resumes the most recent one; `copilot --resume` lets you pick. Inside a session, `/resume` switches and `/session` shows details.
- `/context` shows what's filling the context window, `/compact` summarises history to free space, and `/clear` starts over.
- `/usage` shows what the session used, including premium requests.
- `!git status` runs a shell command yourself without leaving.

### Non-interactive runs with -p

`copilot -p "…"` (or `--prompt`) runs one prompt and exits. That's what you want in shell scripts, cron jobs and CI. It **can't stop to ask**, so any tool you haven't pre-approved is refused:

```text
$ copilot -p "write a bash script that backs up logs/ and keeps 7 archives"
✖ Create scripts/backup-logs.sh: needs permission for "write".
```

Give it exactly what it needs:

```bash
copilot -p "write a bash script that backs up logs/ and keeps 7 archives" \
  --allow-tool 'write' \
  --deny-tool 'shell(rm)'
```

### Tool patterns and the deny rule

| Pattern | Means |
| --- | --- |
| `'write'` | Create or change files |
| `'shell'` | Any shell command |
| `'shell(git)'` | Only `git` commands |
| `'github(list_issues)'` | One tool from an MCP server (server name, then tool) |

Two rules matter. **`--deny-tool` always wins** over an allow, so `--allow-tool 'shell' --deny-tool 'shell(rm)'` runs anything except `rm`. And **`--allow-all-tools`** approves everything: fine in a throwaway container you trust, risky on your laptop or in a CI job that holds secrets.

### Scripts and files: review the draft

Here's the kind of script you might get:

```bash
#!/usr/bin/env bash
set -euo pipefail
mkdir -p backups
tar -czf "backups/logs-$(date +%F).tar.gz" logs/
ls -1t backups/logs-*.tar.gz | tail -n +8 | xargs -r rm --
```

It looks fine, but the last line deletes files. Read it, check it keeps seven archives as you asked, run it once against a test folder, then commit it so someone reviews it. The same goes for file moves and renames: check `git status` afterwards and make sure nothing went missing.

<TryIt labs="gh-cli-scripts" text="Run a -p prompt with no permissions, then allow write and deny a command, review the script and resume your session." />

<Callout type="exam">
Look for the word "non-interactive", "script" or "pipeline": that's **copilot -p** with **--allow-tool**. "Block one command no matter what" is **--deny-tool**, because **deny wins**. "Approve everything" is **--allow-all-tools**, usually the wrong answer when the question mentions safety. "Continue where you left off" is **--continue** (latest) or **--resume** (choose). "The session is getting long" points to **/compact** or **/context**.
</Callout>

<DeepDive title="Configuration, custom agents and MCP in scripted runs">

Copilot CLI keeps its settings in `~/.copilot/`: `settings.json`, `mcp-config.json` for MCP servers, and `agents/` for personal custom agents. A repository can add its own agents in `.github/agents/*.agent.md` and instructions in `.github/copilot-instructions.md` or `AGENTS.md`, which the CLI reads. In a script you can combine them: `copilot --agent=test-writer -p "write tests for src/discount.js" --allow-tool 'write' --model <model>`. MCP tools follow the same permission rules, so allow them by name, for example `--allow-tool 'github(list_issues)'`, rather than opening everything.

</DeepDive>
