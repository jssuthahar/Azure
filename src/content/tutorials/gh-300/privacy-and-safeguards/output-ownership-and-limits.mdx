## Start with a question

<Story question="Copilot wrote half of src/discount.js. A customer finds a bug that gives everyone 100% off. Whose bug is it?">

Yours. Not Copilot's, not GitHub's.

That sounds harsh, but it's how every other tool works. If you paste a snippet from a forum and it's wrong, you don't get to blame the forum. You read it, you pressed Tab, you committed it.

The flip side is good news: GitHub doesn't claim ownership of what Copilot suggests. The code you accept is yours to use, under the same rules as code you typed. Owning it and being responsible for it come together.

</Story>

## The technical explanation

### Ownership

GitHub's terms for Copilot say GitHub **doesn't claim ownership** of suggestions. Once accepted, the code sits in your repository like anything else. Whether it belongs to you or your employer is decided by your normal employment and contract rules, the same as code you wrote by hand.

### Responsibility

You're responsible for what you accept. That covers three things:

| Check | Question to ask | Tool that helps |
| --- | --- | --- |
| **Correctness** | Does it do what I need, for every input? | Tests, review |
| **Security** | Could it be abused or leak data? | Code scanning, secret scanning, review |
| **Licensing** | Does it match code under a licence I must follow? | Code references, the public code policy |

The **public code** policy decides what happens when a suggestion matches public code of about 150 characters or more. **Block** hides it. **Allow** shows it with a **code reference** listing the repository and licence, so you can decide whether you can use it and how to attribute it.

On the legal side, Copilot Business and Copilot Enterprise terms include **IP indemnity**. The details and conditions live in the terms, so know what your plan says rather than assuming.

### Limits of the output

Copilot is a large language model. It predicts likely code from patterns in its training data and the context you give it. That leads to predictable limits:

- **Wrong with confidence.** It doesn't run your code, so it can't tell when it's wrong.
- **Hallucinated APIs and packages.** It can call `cart.applyCoupon()` when no such method exists, or suggest a package that was never published.
- **Outdated.** The model has a **knowledge cut-off**. A library version released after it may be missing or misused.
- **Insecure.** Public code includes insecure patterns, and filters catch only some.
- **Limited context.** It sees a slice of your project, not all of it, so it can miss rules defined elsewhere.
- **Uneven quality.** Results are weaker for rare languages and frameworks with less public code.
- **Not repeatable.** Ask twice and you may get two different answers.
- **Bias.** Generated names, comments or logic can carry assumptions from training data.

None of these mean "don't use it". They mean "check it the way you'd check a new teammate's first pull request".

<Callout type="exam">
Two answers come up again and again. **Who is responsible for accepted code?** The developer and their organization. **Does GitHub own Copilot's suggestions?** No. For limits, map the symptom: "used a method that doesn't exist" is a **hallucination**; "didn't know a new library version" is the **knowledge cut-off**; "matched a licensed repository" calls for **code references** or the **Block** policy. The fix for every limit is human review, tests and scanning.
</Callout>

<DeepDive title="Why a made-up package is a security problem">

If a model often suggests a package name that doesn't exist, an attacker can publish a malicious package under that name and wait. Developers who trust the suggestion install it. Before adding any dependency Copilot proposes, check it exists, who publishes it, how many people use it and what licence it has. Dependency review on pull requests catches some of this; your own check catches the rest.

</DeepDive>
