## Start with a question

<Story question="Half of Contoso's policies are scanned PDFs. How do you make them searchable for an AI agent without retyping anything?">

Think of a library that receives boxes of paper. Someone has to open each box, read what's inside, split a long report into chapters, write a card for every chapter and put the cards in the catalogue. If a page is a photograph of text, somebody has to read the photo first.

In Azure AI Search that person is the **indexer**. The reading glasses are the **OCR skill**. The chapter splitting is **Text Split**. The catalogue is the **index**, and every chapter gets its own card, a **chunk**.

</Story>

## The technical explanation

RAG (retrieval-augmented generation) only works as well as the index behind it. Azure AI Search (Microsoft calls it **Foundry IQ** when agents use it) builds that index with a pipeline of four objects.

### The four objects

| Object | What it holds |
| --- | --- |
| **Data source** | Where the files are (a Blob Storage container, for example) and the identity used to read them. |
| **Index** | The fields: a key, a title, the `chunk` text, a `text_vector` field, and optional semantic settings. |
| **Skillset** | The enrichment steps: OCR, Text Split, an embedding skill, and any others you add. |
| **Indexer** | Runs the pipeline: crack the file, run the skills, map the output, write documents. |

You can create them in the portal with the **Import data (new)** wizard, with the Python SDK (`azure-search-documents`), or with the REST API.

### From file to chunks

1. **Document cracking.** The indexer opens PDFs, Office files and images and pulls out text, metadata and (if you ask) images.
2. **OCR.** If `imageAction` is `generateNormalizedImages`, the extracted images go to the **OCR skill**. A scanned page is only an image, so without this step it has no text at all.
3. **Text Split.** The text is cut into chunks (for example 2,000 characters with a 500 character overlap) so each passage stays focused.
4. **Embedding.** The **Azure OpenAI embedding skill** calls your embedding deployment, such as `text-embedding-3-small`, and returns a vector for each chunk.
5. **Index projections.** One search document per chunk, with a `parent_id` that points back to the file.

```python
indexers.create_or_update_indexer(SearchIndexer(
    name="ixr-policies", data_source_name="ds-policies",
    target_index_name="policies-idx", skillset_name="ss-policies",
    parameters=IndexingParameters(configuration={
        "dataToExtract": "contentAndMetadata",
        "imageAction": "generateNormalizedImages"})))   # without this, OCR sees nothing
```

This is **integrated vectorization**: chunking and embedding happen inside the pipeline, and a **vectorizer** on the index embeds the user's question at query time with the same model. If you embed documents with one model and queries with another, the vectors don't line up and results turn to noise.

### Access without keys

Give the search service a **system-assigned managed identity**, then assign it **Storage Blob Data Reader** on the storage account. The data source then uses the identity instead of a connection string. If you forget the role, the indexer fails with a 403.

### Keeping the index current

For blobs, **change detection is built in**: a scheduled run reads only new and changed files. Two cases need care:

- **Deleted files.** Turn on a deletion policy (such as soft delete) so removed blobs leave the index.
- **Pipeline changes.** If you change the skillset, chunk size or `imageAction`, unchanged files are still skipped. **Reset** the indexer so every document is processed again. **Enrichment caching** stops you paying twice for skills whose input didn't change.

### What about images, audio and video?

| Content | How it gets in |
| --- | --- |
| PDFs and Office files | Document cracking, then Text Split and embeddings |
| Scanned pages and images | OCR skill with `imageAction`; optionally image description with a model or multimodal embeddings |
| Audio and video | Analyse first with **Content Understanding** (transcripts, segments, summaries) or **Azure Speech**, then index the text |

<DeepDive title="Push or pull?">

An indexer is the **pull** model: the service reads from a supported source on a schedule. The **push** model means your own code calls the index API to upload JSON documents, which is the only option for sources an indexer doesn't support, and it gives you full control of timing.

Push has no skillset. If you need chunking or embeddings, you do them yourself before you upload, or you land the files in Blob Storage and use an indexer. Many teams do exactly that: a small job analyses audio or video, writes the Markdown transcript to Blob Storage, and the normal indexer picks it up.

Also check the limits of your tier: the number of indexes, indexers and skillsets, and the maximum time one indexer run can take, before you plan a very large first load.

</DeepDive>
