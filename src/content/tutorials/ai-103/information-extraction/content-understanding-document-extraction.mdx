## Start with a question

<Story question="Claim forms arrive as PDFs with photos and handwriting. How do you turn them into data a claims system and an agent can trust?">

Picture a clerk who reads every claim. A scanner only gives her a photocopy of the words. A good clerk does more: she copies the claim number into the right box, ticks "water damage" from a list, writes a two-line summary for the adjuster, and puts a small question mark next to the number she couldn't read.

**Content Understanding** is that clerk. The photocopy is OCR. The boxes are **fields**. The ticks are **classify**, the summary is **generate**, and the question mark is a low **confidence score**.

</Story>

## The technical explanation

Content Understanding is a **Foundry Tool**, part of your Microsoft Foundry resource. It reads **documents, images, audio and video** and returns output in a shape you choose: Markdown for reasoning and search, and fields for automation. This lesson focuses on documents.

### Prebuilt analyzers

| Analyzer | Use it for |
| --- | --- |
| **prebuilt-read** / **prebuilt-layout** | OCR, paragraphs, tables and structure, no fields |
| **prebuilt-documentSearch** | RAG: Markdown, table structure, figure descriptions, handwritten annotations and a summary |
| Industry analyzers (invoice, contract and others) | Common documents with fields already defined |
| **prebuilt-document** | The base you extend for a custom analyzer |

Start here. If a prebuilt analyzer returns what you need, don't build a custom one.

### Custom analyzers and the field schema

When you need your own fields, you create an analyzer with a base, the models it should use, a config, and a `fieldSchema`:

```json
{
  "analyzerId": "insurance-claim",
  "baseAnalyzerId": "prebuilt-document",
  "models": { "completion": "gpt-4.1-mini", "embedding": "text-embedding-3-small" },
  "config": { "returnDetails": true, "estimateFieldSourceAndConfidence": true, "tableFormat": "markdown" },
  "fieldSchema": { "fields": {
    "ClaimNumber":  { "type": "string", "method": "extract",  "description": "Claim reference, starts with CLM-" },
    "TotalClaimed": { "type": "number", "method": "extract",  "description": "Total amount claimed" },
    "IncidentType": { "type": "string", "method": "classify", "enum": ["water damage", "fire", "theft", "collision", "other"] },
    "Summary":      { "type": "string", "method": "generate", "description": "Two-sentence summary for the adjuster" }
  } }
}
```

| Method | Returns | Example |
| --- | --- | --- |
| **extract** | A value written in the content | Claim number, total |
| **classify** | One value from a list you give | Type of incident |
| **generate** | A value the model writes | Summary, a yes or no judgement |

Good descriptions matter: they act as the instruction for each field. Use the least creative method that works, because **extract** can be checked against the page and **generate** can't.

### Setting up on your Foundry resource

1. Deploy a **chat** model and an **embedding** model on the resource, for example `gpt-4.1-mini` and `text-embedding-3-small`.
2. Map them once as the resource's **default model deployments**.
3. Create the analyzer (`PUT .../contentunderstanding/analyzers/{id}`).
4. Analyze a file (`POST ...:analyze`). It's a long-running operation, so you poll or use the SDK's poller.

```python
client = ContentUnderstandingClient(endpoint=endpoint, credential=DefaultAzureCredential())
result = client.begin_analyze(analyzer_id="insurance-claim",
                              inputs=[AnalysisInput(url=blob_url)]).result()
content = result.contents[0]
print(content.markdown)                       # clean text for RAG and agents
for name, f in content.fields.items():
    print(name, f.value, f.confidence, f.source)
```

The GA API version is **2025-11-01** (checked 25 November 2026). A **2026-06-01-preview** version adds newer features such as an agentic mode for complex documents, so confirm which one your SDK targets.

### Confidence and grounding

With `estimateFieldSourceAndConfidence` on, each field comes with a **confidence** and a **source** (where it was found). That lets you build **straight-through processing**: values above your threshold flow straight into the claims system, and anything below goes to a person who sees the exact spot on the page. A handwritten policy number at 0.61 is exactly the value you don't want to trust blindly.

### Feeding agents and RAG

- **Markdown** is the clean representation for a model: headings, tables and figure descriptions stay intact. Index it in Azure AI Search, or use the **Content Understanding skill** inside the indexer's skillset.
- **Fields** feed workflows and tools, such as an agent that opens a claim only when the fields are confident.
- One analyzer can produce both in the same call.

<DeepDive title="Classification, segmentation and limits">

Analyzers can **classify whole files** or **split a multi-document PDF** into segments by category (for example invoice, contract, other) and send each segment to a category-specific analyzer. Always include an "other" category so unmatched content doesn't get forced into a wrong one.

Plan for limits: file size, page counts and language support differ by modality and version, so check the service limits page for the type you process. Cost has two parts: the content processed (pages or minutes) and the model tokens used for field extraction on your deployments. Test on a sample set and measure accuracy per field before you switch off human review.

</DeepDive>
