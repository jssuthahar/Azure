keyTerms:
  - term: BM25
    definition: The relevance scoring used for keyword (full-text) queries. It rewards rare words that appear often in a document.
  - term: Embedding
    definition: A list of numbers that represents the meaning of a text, so similar meanings sit close together.
  - term: Vector query
    definition: A query that compares a query vector with the vector field and returns the k nearest neighbours.
  - term: Vectorizer
    definition: An index setting that calls an embedding model so a text query can be embedded for you at query time (query kind text).
  - term: Hybrid search
    definition: One request that contains a keyword query and one or more vector queries. The lists are merged with RRF.
  - term: Reciprocal Rank Fusion
    definition: A merge method that scores each document by the sum of 1 divided by (a constant plus its rank) in every list.
  - term: Semantic ranker
    definition: A second-stage reranker that uses a language model on the top 50 results to reorder them and add captions and answers.
  - term: Semantic configuration
    definition: An index setting that names the title, content and keyword fields the semantic ranker should read.

## Start with a question

<Story question="An employee asks, “Can I get my cab money back?” The policy says “taxi fares are reimbursed”. Which search finds it?">

Picture two librarians. The first one only looks at the exact words on the book spines. You ask for "cab" and she shrugs: no book has that word.

The second one has read every book and knows what each is about. You say "cab money" and she says: "You mean taxi refunds. Shelf three."

That's **keyword** versus **vector** search. A good library uses both, and then asks a third person, the **semantic ranker**, to read the top few books and tell you which one really answers the question.

</Story>

## Explain it like I'm 10

<Eli10>

Imagine a game of "find the matching card". Keyword search only matches cards with the same word. If one card says "taxi" and yours says "cab", no match.

Vector search gives every card a spot on a big map, and cards that mean the same thing live close together. "Taxi" and "cab" are neighbours.

Hybrid asks both helpers and combines their answers. The semantic ranker is a teacher who reads the best few cards and puts the best one first.

</Eli10>

## The technical explanation

All four options work on the same index. What changes is the query you send.

### Keyword (full-text) search

The `search` parameter runs a BM25 query over searchable text fields. It's fast, precise for **exact words, names and codes**, and supports filters, facets and analyzers. Its weakness is vocabulary: it can't know that "cab" and "taxi" mean the same.

### Vector search

A **vector query** compares an embedding of the question with the vector field and returns the `k` nearest neighbours. You can send a ready-made vector (`kind: "vector"`) or, if the index has a **vectorizer**, send the text and let the service embed it (`kind: "text"`).

```json
{
  "select": "title, chunk",
  "vectorQueries": [
    { "kind": "text", "text": "Can I get my cab money back?",
      "fields": "text_vector", "k": 5 }
  ]
}
```

Vector search finds meaning, so it works across paraphrases and even languages. Its weakness is **exact identifiers**: an error code like `E-1074` has no meaning to blur into, so the nearest neighbours may be unrelated. The documents and the query must use **the same embedding model**.

Behind the scenes the vector field uses an **HNSW** graph for fast approximate search, or **exhaustive KNN** when you need exact results on a small set. You can also add **filters** to the same query. A `preFilter` narrows the candidates first, and a `postFilter` trims the nearest neighbours after.

### Hybrid search

Put `search` and `vectorQueries` in the same request. The service runs the keyword and vector queries in parallel and merges their ranked lists with **Reciprocal Rank Fusion**:

`RRF score = sum over lists of 1 / (60 + rank in that list)`

A document that ranks well in both lists beats a document that is first in only one. You get one list back, with small RRF scores. You can weight individual vector queries if one field matters more.

```json
{
  "search": "Can I get my cab money back?",
  "vectorQueries": [ { "kind": "text", "text": "Can I get my cab money back?", "fields": "text_vector", "k": 50 } ],
  "top": 5
}
```

### The semantic ranker

Add `queryType: "semantic"` and a `semanticConfiguration`, and a second stage runs. It rereads the **top 50** results from the first stage with a language model, reorders them by a **reranker score (0 to 4)**, and can return extractive **captions** (highlighted passages) and **answers**.

```json
{
  "search": "Can I get my cab money back?",
  "queryType": "semantic",
  "semanticConfiguration": "default",
  "captions": "extractive",
  "answers": "extractive",
  "vectorQueries": [ { "kind": "text", "text": "Can I get my cab money back?", "fields": "text_vector", "k": 50 } ]
}
```

Two things to remember. First, the **semantic configuration** has to exist on the index (it names a title field, content fields and optional keyword fields), and the feature has to be turned on for the service. Second, the ranker only **reorders**: if the right passage isn't in the first stage's results, it can't appear.

### Which one when?

| Need | Use |
| --- | --- |
| Users type exact part numbers, names or codes | Keyword (or hybrid) |
| Users ask in their own words | Vector (or hybrid) |
| You can't predict the style | Hybrid |
| The right answer is in the top 50 but not first, or you need captions | Hybrid plus the semantic ranker |

For an agent, you often don't pick at all. A **knowledge base** with agentic retrieval plans the subqueries and sends hybrid queries with semantic reranking for you (next but one lesson).

| Query | Finds "taxi" for "cab"? | Finds "E-1074"? |
| --- | --- | --- |
| Keyword | No | Yes |
| Vector | Yes | Often not |
| Hybrid | Yes | Yes |
| Hybrid + semantic ranker | Yes, ranked best first | Yes |

<Callout type="exam">
Match the symptom to the feature. "No shared words but the meaning is the same" is **vector**. "Exact product codes must match" is **keyword**. "One request, both kinds of match, one list" is **hybrid** (RRF). "Reorder the top results and show captions" is the **semantic ranker**, which needs a **semantic configuration** and only sees the **top 50**.
</Callout>

<DeepDive title="Tuning and cost">

Start with `k` of 50 on the vector query so the semantic ranker has enough candidates. Increase it only if tests show good documents falling outside the top 50.

Vector fields use memory. **Vector compression** (scalar or binary quantization) and **truncated dimensions** on supported embedding models shrink the index with a small recall cost, and **oversampling** with rescoring wins some of that back. Measure recall on your own questions before you compress.

The semantic ranker is a billed feature: a free allowance each month, then a charge per thousand queries. Agentic retrieval adds model token charges for query planning at low and medium effort. Look at the current pricing page before you size a production system, and keep an eye on **search latency** and **throttled queries** in the metrics.

</DeepDive>
