## Start with a question

<Story question="Can a transcript tell you the caller was angry?">

Contoso Telecom takes calls in Hindi. The agents read English and Tamil. A supervisor also wants to know how upset a caller sounded at the start of a call and whether they calmed down by the end.

These are two different jobs. One is **translating speech**. The other is **understanding sound**. A transcript handles the first and loses the second.

</Story>

## Explain it like I'm 10

<Eli10>

**Speech translation** is a friend who listens to your Hindi and writes it down in English and Tamil at the same time. If you ask, they can say it out loud too.

An **audio model** is a friend who listens to the whole recording and tells you how it felt: "She started angry and fast, then relaxed". A written note can't tell you that. And if you give the recording to a friend who can only read, they say "I can't listen to that".

</Eli10>

## The technical explanation

### Speech translation

Azure Speech recognises speech in a **spoken language** and returns text in one or more **target languages** from the same pass. Set a voice name and it also produces **synthesized speech** of the translation (speech to speech).

```python
cfg = speechsdk.translation.SpeechTranslationConfig(subscription=KEY, endpoint=ENDPOINT)
cfg.speech_recognition_language = "hi-IN"
cfg.add_target_language("en")
cfg.add_target_language("ta")
cfg.voice_name = "en-IN-NeerjaNeural"     # also speak the English translation

rec = speechsdk.translation.TranslationRecognizer(translation_config=cfg, audio_config=audio)
result = rec.recognize_once_async().get()
print(result.text)                 # what was heard, in Hindi
print(result.translations["en"])   # the English translation
```

If the caller's language isn't known, enable **language identification** for the candidate languages. Results are keyed by language code.

### Reasoning over audio

A transcript keeps the words and loses everything else. Questions about **tone, emotion, pace, hesitation or background sounds** need a model that takes audio. **gpt-4o-audio-preview** is one such deployment. The audio goes in as an **input_audio** content part, base64 encoded:

```python
completion = client.chat.completions.create(
    model="gpt-4o-audio-preview",
    modalities=["text"],
    messages=[{"role": "user", "content": [
        {"type": "text", "text": "How did the customer feel at the start and at the end?"},
        {"type": "input_audio", "input_audio": {"data": audio_b64, "format": "wav"}},
    ]}],
)
```

A **text-only deployment** such as gpt-4.1-mini returns an error for this request. Deploy an audio-capable model, or transcribe first.

### Which pattern?

| Need | Use | Why |
| --- | --- | --- |
| Transcripts and fixed languages, high volume | Speech translation | Cheaper and predictable |
| Transcript, then text analysis | Speech to text, then Azure Language or a model | Reuse text tools |
| Tone, emotion, pace, sounds | Audio-capable model | It hears the audio |
| Live conversation across languages | Voice Live or speech translation with a voice | Low latency |

<Callout type="exam">
"Return **text in several languages** from **spoken** input" is **speech translation**. "Tell me how the **caller felt**" is an **audio-capable model**. A **400 error** on **input_audio** means the deployment doesn't accept audio. **Fixed languages and low cost** points back to **Speech**, not an audio model.
</Callout>

<DeepDive title="Preview model names change">

Audio-capable models such as gpt-4o-audio-preview are listed in the Foundry model catalog with their own regions and quotas, and preview names and versions get replaced over time (checked 25 November 2026). In an exam answer, remember the idea: audio in needs an audio-capable deployment. In a project, check the catalog for the current model and region.

</DeepDive>
