## The technical explanation

### Azure Language: entities, PII and summaries

Azure Language in Foundry Tools (the service formerly called Azure AI Language) runs on your Foundry resource. The calls are the same across features: send documents, get a result per document.

| Feature | Returns | Good for |
| --- | --- | --- |
| Named entity recognition | Entities with a category (Person, Organization, Location, DateTime, Quantity and more) and a confidence score | Standard facts in tickets, emails, contracts |
| PII detection | Entities plus **redacted text** | Masking personal data before storage or before an agent reads it |
| Abstractive summarization | A short summary written in new sentences | Long documents and conversations |
| Custom NER | Your own entity types | Repeated extraction of business fields |

Prebuilt categories are fixed. An order number often comes back as a **Quantity**, because the service doesn't know your business.

```python
from azure.identity import DefaultAzureCredential
from azure.ai.textanalytics import TextAnalyticsClient

client = TextAnalyticsClient(endpoint=ENDPOINT, credential=DefaultAzureCredential())
result = client.recognize_entities([ticket_text])[0]
for e in result.entities:
    print(e.text, e.category, round(e.confidence_score, 2))

pii = client.recognize_pii_entities([ticket_text], categories_filter=["PhoneNumber", "Email"])[0]
print(pii.redacted_text)
```

### Strict JSON from a model

A model can return your own fields. Three levels of control:

1. **Plain text prompt**: "Return JSON." It usually works until it doesn't. Don't parse this in production.
2. **JSON mode** (`response_format={"type": "json_object"}`): the reply is valid JSON. The keys are still the model's idea.
3. **Structured outputs** (`response_format` of type `json_schema` with `strict: true`): the reply matches your schema.

```python
schema = {
  "name": "ticket",
  "strict": True,
  "schema": {
    "type": "object",
    "properties": {
      "customer": {"type": "string"},
      "order_id": {"type": "string"},
      "priority": {"type": "string", "enum": ["low", "normal", "high"]},
      "churn_risk": {"type": "boolean"}
    },
    "required": ["customer", "order_id", "priority", "churn_risk"],
    "additionalProperties": False
  }
}
resp = openai_client.chat.completions.create(
    model="gpt-4.1-mini",
    messages=[{"role": "user", "content": ticket_text}],
    response_format={"type": "json_schema", "json_schema": schema},
)
```

For strict mode, list every property in `required` and set `additionalProperties` to `false`. An **enum** keeps a field to values your code understands.

### Domain tasks: compliance summaries and domain extraction

A plain request such as "summarise this policy update" gives a nice paragraph that an auditor can't use. Fix the prompt before you think about training.

- **Role**: "You are a compliance analyst writing for the audit team."
- **Checklist**: WHAT changed, WHO is responsible, DEADLINE, CONTROL ID, RISK.
- **Glossary**: what "PCI-07" or "four-eyes check" mean in your company.
- **Example**: one policy update and the summary you'd accept, including "Not stated" for something missing.
- **Temperature 0**, so the layout doesn't wander.

If prompting still can't hold the format, consider **fine-tuning**. If the job is pulling the same fields from huge volumes, **custom NER** in Azure Language is usually cheaper and steadier than prompting a large model every time.
