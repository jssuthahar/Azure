## Start with a question

<Story question="Who answers when a customer says, charged twice and still no parcel?">

At a good service desk nobody handles everything. A receptionist listens, a billing clerk checks the charge, a delivery clerk checks the parcel, and someone writes one clear reply. Which clerk speaks first, and whether they work together or one after another, is a decision about the **process**.

**Multi-agent orchestration** is that process for AI agents. Each agent has a narrow job, and the pattern says who goes next.

</Story>

## Explain it like I'm 10

<Eli10>

Imagine a group project where each friend has one job.

Sometimes you pass the work down a line: draft, then check, then finish. That's **sequential**.

Sometimes two friends work at the same time and then combine notes. That's **concurrent**.

Sometimes the first friend says "this is a maths question, ask Sam" and hands over. That's **handoff**.

And sometimes a team captain makes a plan and gives out tasks. That's **Magentic**.

</Eli10>

## The technical explanation

### Pick the pattern by who decides the next step

| Pattern | Who decides | Good for | Watch out |
| --- | --- | --- | --- |
| **Sequential** | You, in advance | Draft, then review | Time adds up |
| **Concurrent** | You, in advance | Independent checks, speed | Results must be merged |
| **Handoff** | The current agent | Triage to a specialist | The route depends on the conversation |
| **Group chat** | A manager picks the speaker | Debate and refinement | Set a maximum number of rounds |
| **Magentic** | A manager plans and delegates | Open-ended tasks | Most calls, least predictable |

### Build it with Microsoft Agent Framework

```python
# pip install agent-framework-foundry azure-identity
from azure.identity import AzureCliCredential
from agent_framework.foundry import FoundryChatClient
from agent_framework.orchestrations import SequentialBuilder, ConcurrentBuilder

client = FoundryChatClient(project_endpoint=os.environ["FOUNDRY_PROJECT_ENDPOINT"],
                           model="support-chat", credential=AzureCliCredential())
triage   = client.as_agent(name="triage",   instructions="Work out what the customer needs. Don't answer it yourself.")
billing  = client.as_agent(name="billing",  instructions="Answer billing and refund questions from the policy.")
delivery = client.as_agent(name="delivery", instructions="Answer delivery questions. Use get_order_status.")
writer   = client.as_agent(name="writer",   instructions="Write one friendly reply from the specialists' notes.")
reviewer = client.as_agent(name="reviewer", instructions="Check the reply against policy. Say APPROVED or list fixes.")

line     = SequentialBuilder(participants=[triage, writer, reviewer]).build()
parallel = ConcurrentBuilder(participants=[billing, delivery]).build()      # fan out, then aggregate
# handoff, group chat and Magentic use HandoffBuilder, GroupChatBuilder and MagenticBuilder
```

Each agent keeps its own short instructions and only the tools it needs. That's the main reason to split: the billing agent never sees the delivery tool, so it can't call it by mistake.

### Design rules that save you

1. **Start with one agent.** Split when instructions get long or tools collide.
2. **Narrow jobs.** "Billing" beats "customer helper".
3. **Limit rounds** in group chat and Magentic, and set timeouts.
4. **Trace every turn.** When the answer is wrong you need to see which agent said what.
5. **Evaluate the whole flow**, not just each agent.

Foundry's portal also lets you wire agents into a **workflow** visually (preview as of 25 November 2026). The orchestration patterns above are the same ideas in code.

Translate the wording. "Fixed order, each agent uses the previous output" is **sequential**. "At the same time" and "combine" is **concurrent**. "Transfer the conversation to a specialist" is **handoff**. "A manager builds a plan and tracks tasks" is **Magentic**. The SDK that provides these builders is **Microsoft Agent Framework**.
</Callout>

<DeepDive title="Cost and latency add up">

Every extra agent turn is another model call. A five-agent sequential pipeline pays five latencies in a row, and a group chat of six rounds may call the model dozens of times. Concurrent runs cut waiting but not tokens. Measure with traces, use small models for narrow agents such as triage, and keep the large model for the agent that needs it.

</DeepDive>
