## Start with a question

<Story question="How does a good shop assistant know your order, the policy and you?">

Three different things are at work. She looks at the **computer** for where your parcel is right now. She flips the **policy folder** for the return rules. And she remembers **you**: "You like WhatsApp messages, don't you?"

An agent has the same three. A **function** reads the live order system. **File search** or **Azure AI Search** reads the policy documents. **Memory** remembers you the next time you come in.

</Story>

## The technical explanation

### Which tool for which need

| The agent needs | Tool | Notes |
| --- | --- | --- |
| Live data or an action | **Function** | The model asks, **your code runs it**, you send the result back |
| Answers from documents users or apps provide | **File search** | Vector store over uploaded files |
| Answers from a curated company index | **Azure AI Search** (or a Foundry IQ knowledge base) | Hybrid search, citations |
| A REST API with a spec | **OpenAPI tool** | Describe it once, the agent calls it |
| A remote tool server | **MCP tool** | Choose allowed tools and approval |
| Fields from a document or image | A **Content Understanding** analyzer, called from a function or tool | Predictable extraction |
| Facts about a user over time | **Memory** | Scoped per user |

### The function-calling loop

```python
conversation = openai.conversations.create()
r = openai.responses.create(conversation=conversation.id, input="Where is order ORD-1042?")
for item in r.output:
    if item.type == "function_call":                      # the model ASKS
        result = lookup_order(**json.loads(item.arguments))   # your code RUNS it
        r = openai.responses.create(conversation=conversation.id,
              input=[{"type": "function_call_output", "call_id": item.call_id,
                      "output": json.dumps(result)}])    # send the result back
print(r.output_text)
```

The model never runs your code. That's why a function is the safest way to reach private systems: you decide what it can do and you can add checks inside it.

### Memory across conversations

A **conversation** holds one chat. **Memory** (preview as of 25 November 2026) extracts durable facts, such as "prefers WhatsApp updates", stores them in a **memory store**, and retrieves them in a later chat. It stores **user profile** facts and **chat summaries**.

```python
tools.append(MemorySearchPreviewTool(memory_store_name="customer-memory",
                                     scope="{{$userId}}",       # one memory per customer
                                     update_delay=300))
```

Set the **scope** so each user sees only their own memory, and set a **retention** period. A memory store needs a chat deployment and an embedding deployment, because recall uses search over the stored items.

<Callout type="exam">
Read the verbs. "Check the **live** status" is a **function**. "**Search** the documents the user **uploads**" is **file search**. "**Remember** preferences **across sessions**" is **memory**. "**Call** the partner's **REST API**" with a spec is an **OpenAPI tool**. And the code that executes a function is always **your application**.
</Callout>

<DeepDive title="Why a function beats pasting data into the prompt">

Order data changes every minute and belongs to one customer. Putting it in the prompt up front wastes tokens and risks showing the wrong customer's data. A function fetches only what the question needs, for the signed-in customer, at the moment of the question. It can also enforce rules, such as only returning orders for the current user ID, because your code decides what it returns.

</DeepDive>
