## Start with a question

<Story question="Why does a bakery use a checklist for a wedding cake?">

One person doing everything in one go makes mistakes. A good bakery splits the job: measure, mix, bake, cool, decorate, check. Each stage has one purpose, and someone checks the result before the cake leaves.

An **AI workflow** is that checklist. Instead of asking a model to read a claim email, look up the warranty and write a reply in one prompt, you run **steps**. Each step does one job, and a **check** at the end stops a wrong cake from leaving the shop.

</Story>

## Explain it like I'm 10

<Eli10>

Runner one sorts the letters. Runner two reads the important parts. Runner three asks the warranty office a question. Runner four writes the answer. Runner five checks it.

If runner three can't reach the office, the team doesn't make up a number. It hands the baton to a grown-up.

</Eli10>

## The technical explanation

### The five steps of a claims flow

| Step | What it does | Setting that matters |
| --- | --- | --- |
| **1 Classify** | Warranty, refund or other | Temperature 0, short answer |
| **2 Extract** | Pull product, serial number and date | **Structured output** with a strict JSON schema |
| **3 Tool** | Call `check_warranty(serial)` | Timeout, **bounded retries**, fallback value |
| **4 Draft** | Write the reply from the facts | Only the verified facts go in the prompt |
| **5 Verify** | Compare the draft with the facts | Rules or a second model, refuse to send on mismatch |

```python
kind = openai.responses.create(model=model, temperature=0,
        input=f"Classify as warranty, refund or other: {email}").output_text

fields = json.loads(openai.responses.create(model=model, input=email,
        text={"format": {"type": "json_schema", "name": "claim", "strict": True,
                         "schema": CLAIM_SCHEMA}}).output_text)

status = with_retry(lambda: check_warranty(fields["serial_number"]), attempts=3) or "needs_human_review"

draft = openai.responses.create(model=model, input=f"Write a reply. Facts: {fields} {status}").output_text
print(draft if verify(draft, fields, status) else "Held for a person to check")
```

### Structured outputs, not hopeful prompts

Asking for JSON in words isn't enough. **JSON mode** (`json_object`) only promises something that parses. **Structured outputs** (`json_schema` with `strict: true`) make the reply match your schema: every required field present, no extras when `additionalProperties` is false. That's what lets step 3 trust the serial number from step 2.

### Tools and multistep reasoning

A **tool-augmented** flow lets a model ask for a tool when it needs data or an action. Your code runs the tool and returns the result. For one step that needs real planning, such as comparing contract clauses, use a **reasoning model** for that step and keep cheap models for the rest. Foundry also has a workflow builder in preview as of 25 November 2026, where you wire steps, agents and conditions together without writing the control flow by hand.

<Callout type="exam">
When code must read the model's reply, the answer is **structured outputs with a strict JSON schema**, not "ask for JSON in the prompt". When a tool can fail, look for **retries with a limit and a safe fallback**, never "let the model guess". A single prompt that does everything and is hard to debug should be **split into steps**.
</Callout>

<DeepDive title="Where to put the checks">

Put a check wherever a mistake becomes expensive. After extraction, validate the schema and the serial number format. After the tool, treat an empty or error result as a failure, not as data. Before sending, compare every fact in the draft with its source. Cheap rule checks catch most errors; a second model can review tone and completeness. Log each step so a held claim shows exactly where it stopped.

</DeepDive>
