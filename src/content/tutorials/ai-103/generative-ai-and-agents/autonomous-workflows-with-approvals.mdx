## Start with a question

<Story question="Would you let a new hire send refunds without asking anyone?">

Not on day one. They can look up orders freely. For a refund they check with a manager, and there's a company rule that no one can refund more than a set amount without finance, however polite the customer is.

That's how to run an **autonomous agent**. Reads are free, risky writes need a **person's approval**, and some limits are **rules in code** that nobody can talk their way around.

</Story>

## Explain it like I'm 10

<Eli10>

Imagine a robot helper at a shop till.

It can look at the price list as much as it likes. No one needs to say yes.

But before it hands out money from the till, it stops and calls the manager. The manager says yes or no.

And there's a lock on the till: the robot can never give out more than a certain amount, even if the manager is in a hurry.

</Eli10>

## The technical explanation

### Levels of autonomy

| Tool kind | Example | Control |
| --- | --- | --- |
| **Read-only** | `lookup_order` | Runs freely, logged |
| **Low-impact write** | Add a note to a ticket | Allowed with limits and logging |
| **High-impact write** | `issue_refund` | **Approval required** |
| **Beyond policy** | Refund over ₹20,000 | **Blocked in code** |

### Approval in code

In Microsoft Agent Framework a tool opts in to approval with `approval_mode`:

```python
@tool
def lookup_order(order_id: Annotated[str, "Order number"]) -> str:
    '''Read-only: order total, items and delivery status.'''

@tool(approval_mode="always_require")           # pauses the run until a person decides
def issue_refund(order_id: Annotated[str, "Order number"], amount_inr: Annotated[int, "Amount in rupees"]) -> str:
    '''Write action: send money back to the customer.'''
    if amount_inr > 20000:                      # hard limit in code, whatever the model says
        raise ValueError("Refunds over ₹20,000 go to the finance team")
```

When the agent decides to call `issue_refund`, the run **pauses** and returns a pending **approval request** with the exact arguments. Your app shows it to a reviewer and sends back an **approval response**, either approve or reject, and the run continues. A rejected call never runs. Foundry Agent Service has the same idea for remote MCP tools through a `require_approval` setting, so the model's request waits for your decision.

### Safeguards around the approval

1. **Least privilege.** Give the agent only the tools the job needs, and limit what each tool can do.
2. **Hard limits in code.** Maximum amounts, allowed recipients and allowed fields are checked inside the tool.
3. **Run limits.** Cap the number of steps, the time and the tokens per run so a loop can't run away.
4. **Guardrails.** A guardrail can check what the agent sends to a tool and what comes back.
5. **Traces.** Log the tool call, arguments, approver and decision. That's the audit trail.

An approval is a judgement call by a person. It isn't a substitute for a limit, because a tired reviewer can click yes.

<Callout type="exam">
"Pause until a person decides" is **approval required** on the tool. "Must never exceed the legal limit" is **enforced in code**, not in the prompt. "Show who approved and when" is the **trace**. Read-only tools normally **don't** need the same approval as write tools.
</Callout>

<DeepDive title="Autonomous is a spectrum">

Human in the loop means a person approves before each risky action. Human on the loop means the agent acts and a person monitors and can step in. Full autonomy means neither. Move along the spectrum only as far as your evaluation results and risk tolerance allow: start with approval on every write, measure how often reviewers change the outcome, and relax the rule for tools that prove safe, never for tools whose mistakes can't be undone.

</DeepDive>
