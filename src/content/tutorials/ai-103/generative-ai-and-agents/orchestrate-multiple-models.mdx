## Start with a question

<Story question="Who answers the phone at a good hospital?">

The receptionist answers "what are the visiting hours?" from a card on the desk. A nurse handles common questions. Only the hard cases go to a consultant, whose time is the most expensive.

A good AI system works the same way. **Rules** answer what a table can answer. A **small model** handles easy language work. The **large model** is the consultant, called only when needed.

</Story>

## Explain it like I'm 10

<Eli10>

Imagine three helpers at school.

The first just reads from a list on the wall: "The library opens at nine." No thinking needed.

The second is a quick helper who can sort and label things.

The third is the clever professor who solves the hard puzzles but is slow and busy.

You ask the list first, then the quick helper, and only go to the professor when you really must.

</Eli10>

## The technical explanation

### Choose the cheapest thing that works

| Request | Handled by | Why |
| --- | --- | --- |
| "What are your store hours?" | **Rules** (lookup table) | Exact, free, no model |
| "Refund ₹1,200 for ORD-1042" | **Rules** (policy limit in code) | The limit is a policy, so code decides |
| "Classify this review" | **Small model** (Phi-4-mini-instruct) | Simple, high volume |
| "Compare three warranty plans for a café" | **Large or reasoning model** (gpt-4.1, o4-mini) | Multi-part reasoning |

### A cascade in code

```python
def route(request: str) -> str:
    if re.search(r"store hours|opening time", request, re.I):  return "rules"     # deterministic answer, no LLM
    if re.search(r"refund", request, re.I):                    return "rules"     # policy limit decided by code
    if len(request) < 120:                                     return os.environ.get("SMALL_DEPLOYMENT", "Phi-4-mini-instruct")
    return os.environ.get("LARGE_DEPLOYMENT", "gpt-4.1")                          # long, multi-part reasoning

for req in REQUESTS:
    target = route(req)
    answer = RULES[req] if target == "rules" else openai.responses.create(model=target, input=req).output_text
```

Real systems often decide with more than length. They use a **classifier**, the small model's own **confidence**, or the result of a first attempt, and **escalate** when the cheaper component isn't sure.

### Let a router choose

A **model router** is a Foundry deployment (preview as of 25 November 2026) that looks at each prompt and selects one of several underlying models, balancing quality and cost. You call it like any deployment, and the response says which model answered. Use it when you want routing without writing the logic, and check traces to confirm the mix is what you expect.

### Combine models and tools in one flow

Routing also joins different kinds of components in one flow: Content Understanding extracts fields from an invoice, a small model classifies the vendor, a large model drafts a dispute letter, and rules check the totals. Each piece is the right size for its job.

### Measure it

In the lab's four-request example, one large model makes **4** model calls. The cascade makes **2**, because rules answered two requests, so the relative cost falls to roughly a quarter. Compare **quality**, **cost** and **latency** per route with evaluations and traces, and watch the share of requests that reach the large model.

<Callout type="exam">
"Exact policy answer" is a **rules engine**. "Cheapest option for simple, high-volume text labelling" is a **small language model**. "Let the platform pick a model per prompt" is a **model router**. "Order of attempts to reduce cost" is **rules, then small model, then large model**, with **escalation** for low confidence.
</Callout>

<DeepDive title="Guard the router too">

If a user's text decides which model runs, a user can try to steer it. Don't let the request tell the router "use the biggest model". Route on your own signals, cap the large-model calls per user, and trace routing decisions so a spike of expensive calls is easy to spot.

</DeepDive>
