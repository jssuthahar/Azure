keyTerms:
  - term: Reasoning model
    definition: A model that spends extra tokens thinking through a problem before it answers. Better at multistep tasks, slower and more expensive per answer. Reasoning models take a reasoning effort setting instead of temperature.
  - term: Small language model (SLM)
    definition: A compact model, such as Phi-4-mini, that is cheap and fast and good enough for narrow tasks like labelling or short answers.
  - term: Multimodal model
    definition: A model that accepts more than text, such as images or audio, so one call can describe a photo or reason over a recording.
  - term: Foundry Tools
    definition: Prebuilt AI services in Foundry (Content Understanding, Azure Speech, Azure Language, Azure Vision, Translator and more) that do a fixed job through an API.

    definition: The catalog page for a model. It lists supported inputs, context window, capabilities, regions and deployment options, plus benchmark scores.

    definition: The knowledge layer in Foundry. A knowledge base on Azure AI Search that agents query for grounded, cited answers.

## Start with a question

<Story question="Would you send a courier on a motorbike to deliver one envelope across the road, or ask a lorry?">

Priya runs support engineering at Contoso. Last month the team sent every request to the biggest model they could find. Tickets got labelled, contracts got reviewed, invoices got read. It worked, and the bill was alarming.

The fix wasn't a cleverer prompt. It was sending each job to the **cheapest thing that does it well**. Some jobs needed a thinker. Some needed a fast, cheap labeller. Some didn't need a language model at all.

</Story>

## Explain it like I'm 10

<Eli10>

Imagine a school with different helpers.

One teacher is brilliant at hard puzzles, but she's slow and busy. That's a **reasoning model**.

One helper is quick at sorting lost property into boxes. That's a **small language model**.

One helper can look at photos and tell you what's in them. That's a **multimodal model**.

And there's a scanner machine that reads forms and gives you the answers. That's a **Foundry Tool**.

You wouldn't ask the puzzle teacher to sort socks.

</Eli10>

## The technical explanation

### The model families you'll choose between

| Need | Pick | Why |
| --- | --- | --- |
| Hard, multistep reasoning, planning, maths, code | **Reasoning model** (o4-mini and similar) | It thinks before answering. It uses a reasoning effort setting, not temperature. |
| Everyday chat, summaries, tool calling | **gpt-4.1-class LLM** or its **mini** version | Good balance of quality, speed and cost. Large context. |
| Narrow, high-volume, latency-sensitive work | **Small language model** (Phi-4-mini-instruct) | Cheap, fast, and easier to run at the edge. |
| Photos, screenshots, charts | **Multimodal model** (gpt-4.1, gpt-4o, Phi-4-multimodal) | Accepts image input. A text-only model returns an error. |
| Audio reasoning | **Audio-capable model** (gpt-4o-audio-preview) | Hears tone and pace, not just words. |
| Search by meaning | **Embedding model** (text-embedding-3-small) | Turns text into vectors for retrieval. |

Read the **model card** before you design: supported inputs, context window, capabilities (tool calling, structured outputs, reasoning), the regions and the deployment types it can use. Model availability changes often, so check the catalog the week you build.

### When a Foundry Tool beats a model

Foundry Tools give you a fixed job through an API, often with a fixed price and output shape.

| Job | Foundry Tool |
| --- | --- |
| Fields and markdown from documents, images, audio, video | **Content Understanding** |
| Speech to text, text to speech, speech translation | **Azure Speech** |
| Entities, PII, sentiment, summaries | **Azure Language** |
| Text translation with glossaries | **Azure Translator** |
| Image analysis and OCR | **Azure Vision** |
| Harmful content scoring and Prompt Shields | **Azure Content Safety** |

Use a model when you need reasoning, free-form output, or a task the tool can't do. Many solutions use both: Content Understanding reads the invoice, a model decides what to do with it.

### Choosing the Foundry service for the task

- **Generate text, images, code**: **Foundry Models** (a deployment of a model in your Foundry resource).
- **Ground answers on your data and search by meaning**: **Foundry IQ** knowledge bases on **Azure AI Search** (keyword, vector, hybrid, semantic ranking).
- **Run an agent with tools and conversation state**: **Foundry Agent Service**.
- **Process documents, audio, video**: **Content Understanding**.
- **Many agents or steps with approvals**: workflows in Foundry (covered in domain 2).

### Test before you commit

1. Collect 50 to 200 real inputs with the answers you'd accept.
2. Run two or three candidates with the same prompt.
3. Score with evaluators (groundedness, relevance, your own graders), and note cost and latency.
4. Pick the smallest model that clears your bar. Write down why, so the next change is a decision and not a guess.

<Callout type="exam">
Read the verbs. "Plan", "reason through" and "multistep" point to a **reasoning model**. "Classify thousands" and "lowest cost" point to a **small language model**. "Describe an image" needs a **multimodal** model. "Extract fields from invoices" is **Content Understanding**. When a question says answers must come from company documents, the service is **Foundry IQ on Azure AI Search**, and a bigger model isn't the fix.
</Callout>

<DeepDive title="Why 'best model' isn't a thing">

A quality index averages many public tests. Your support tickets, your policies and your languages aren't those tests. A model that's second on the leaderboard can be first on your data. That's why the test set matters more than the ranking, and why you re-run it when a new model version arrives.

</DeepDive>
