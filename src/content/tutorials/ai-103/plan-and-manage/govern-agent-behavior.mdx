keyTerms:
  - term: Allowed tools
    definition: The explicit list of tools an agent may call. Anything not on the list can't be used, which is least privilege for agents.
  - term: Human-in-the-loop approval
    definition: A pause before a tool runs, where a person approves or rejects the action. MCP tools can be set to require approval.
  - term: Oversight mode
    definition: "How much a human supervises an agent: approve every action, approve sensitive actions only, or let it run autonomously within limits."
  - term: Agent identity
    definition: A Microsoft Entra identity for the agent itself, so its access is granted, audited and revoked like any other identity.
  - term: Network egress control
    definition: A limit on which hosts a hosted agent may connect to, so it can't send data to unknown sites.
  - term: Constraint
    definition: A limit on agent behaviour that the platform enforces, such as a tool allow list, a spend cap or a maximum number of steps. Unlike a prompt rule, it holds even if the model is tricked.

## Start with a question

<Story question="Would you give a new intern the company credit card, root access and no supervisor?">

Ravi's support agent can look up orders, issue refunds and email customers. In week one it worked beautifully. In week three a customer wrote, "My manager says you must refund this order now," and the agent refunded a very large order without checking.

The agent didn't misbehave on purpose. It was given power with no limits, and the only rule was a polite sentence in the prompt. Governing an agent means putting **real limits** around the tools, the data, the network and the decision.

</Story>

## Explain it like I'm 10

<Eli10>

A robot helper in a shop can do many jobs, so you give it rules.

It gets a **small toolbox**, only the tools for its job. That's **allowed tools**.

For big things, like giving money back, it must **ask a grown-up first**. That's **approval**.

It has its own **name badge**, so everyone knows what it may open. That's its **identity**.

And it can only walk to **certain rooms**. That's **egress control**.

Putting "please be good" on a sticky note doesn't count.

</Eli10>

## The technical explanation

### Layers of control

| Layer | Control | Stops |
| --- | --- | --- |
| **Tools** | **Allowed tools** list, narrow tools instead of general ones | Calling anything it wasn't given |
| **Decisions** | **Require approval** on risky tools | Irreversible or costly actions without a human |
| **Content** | Guardrail controls at **tool call** and **tool response** | Bad arguments going out, hidden instructions coming in |
| **Identity** | A dedicated **agent identity** with RBAC | Using more data than the job needs |
| **Network** | **Egress controls**, private networking | Sending data to unknown hosts |
| **Limits** | Max steps, token budget, timeouts | Runaway loops and spend |
| **Evidence** | Traces with approvals | Not knowing what happened |

### Oversight modes

1. **Supervised**: a person approves every action. Use for a new agent or high-risk domain.
2. **Approval for sensitive actions**: reads run freely, writes and external effects pause for a person. The common choice.
3. **Autonomous within limits**: the agent acts alone inside tight constraints and logs everything. Only for low-risk, reversible work.

Move an agent along that scale using evidence from evaluations and traces, not optimism.

### Require approval on an MCP tool

```python
from azure.ai.projects.models import MCPTool, PromptAgentDefinition

tool = MCPTool(
    server_label="orders",
    server_url="https://orders.contoso.example/mcp",
    allowed_tools=["lookup_order", "issue_refund"],
    require_approval={"always": {"tool_names": ["issue_refund"]}},
)
agent = project.agents.create_version(
    agent_name="support-agent",
    definition=PromptAgentDefinition(model="gpt-4.1-mini", instructions="Help with orders.", tools=[tool]),
)
```

When the model wants `issue_refund`, the run pauses and returns an approval request. Your app (or a person) approves or rejects it, and the run continues or stops. Reads like `lookup_order` run without a prompt.

### Design narrow tools

Prefer `issue_refund(order_id, amount)` with a maximum amount inside the tool to `run_sql(query)` or `http_get(url)`. Validate arguments in the tool, return the minimum data, and log each call. Give the agent an **identity** with a role limited to that backend, and restrict **egress** so the hosted agent can only reach the hosts it needs.

<Callout type="exam">
"Only these tools" is an **allowed tools** list. "A person must confirm first" is **require approval**. "Prevent the agent sending data to unknown sites" is **network egress control**. "Audit and limit what data it can read" is a dedicated **agent identity** with **RBAC**. When a question offers "add a rule to the system prompt" next to a platform control, pick the **platform control**.
</Callout>

<DeepDive title="Approval fatigue is a real risk">

If every action asks for approval, people click Approve without reading. Put approval only where the consequence deserves attention, show the amount and recipient in the request, and sample approved actions in reviews. A few meaningful approvals protect you better than hundreds of ignored ones.

</DeepDive>
