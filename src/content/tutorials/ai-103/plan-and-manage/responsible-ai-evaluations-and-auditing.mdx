## Start with a question

<Story question="How do you prove the agent is safe, and how do you explain what it did last Tuesday?">

Before launch, the risk team asks Asha for evidence. "It seemed fine in testing" isn't evidence. After launch, a customer disputes a refund and an auditor asks who approved it and why.

Both questions have the same answer: **measure before, record during**. Evaluators and red teaming produce the numbers before launch. Traces and approvals produce the story afterwards.

</Story>

## Explain it like I'm 10

<Eli10>

Think of a driving test.

Before you get your licence, an examiner gives you **marks** for different skills: stopping, signalling, parking. Those are **evaluators**.

Then a tricky examiner tries to **fool** you with surprise situations. That's the **red team**.

After you pass, the car keeps a **diary** of every trip, so if there's a bump, people can see what happened. That's a **trace**.

</Eli10>

## The technical explanation

### Evaluators

| Family | Examples | Question answered |
| --- | --- | --- |
| **Quality** | Groundedness, relevance, coherence, fluency, similarity | Is it correct, on topic and readable? |
| **Safety** | Violence, sexual, self-harm, hate and unfairness, protected material, code vulnerability | Does it contain harmful content? |
| **Agent** | Intent resolution, tool call accuracy, task adherence | Did the agent understand, act and finish correctly? |
| **Custom** | Your code or a prompt-based grader | Anything your policy needs |

Each result has a **score** and a **reason**, which is how you explain a low score to the team. Run evaluators on a dataset in the portal or from code:

```python
from azure.ai.evaluation import evaluate, GroundednessEvaluator, RelevanceEvaluator

result = evaluate(
    data="evals/support-cases.jsonl",
    evaluators={"groundedness": GroundednessEvaluator(model_config), "relevance": RelevanceEvaluator(model_config)},
)
```

Put the same run in the pipeline as a **gate** and use a sampled version for **continuous evaluation** after release.

### Red teaming

The **AI red teaming agent** generates adversarial prompts across risk categories (violence, hate and unfairness, sexual, self-harm), applies **attack strategies** (encoding, character flipping, jailbreak templates, multi-turn), sends them to your target and reports an **attack success rate**. Fix gaps with guardrail controls or prompt changes, then scan again.

### Auditing: trace, provenance, approval

1. **Trace logging**: connect Application Insights and enable tracing (OpenTelemetry). Each run records spans for the model call, tool calls, retrievals, guardrail results and approvals.
2. **Provenance metadata**: store the retrieved source IDs, citations, model and prompt version, and the approver with each important answer or action.
3. **Approval workflows**: risky tools pause for a human decision. The decision, approver and time go into the trace.
4. **Retention and access**: traces contain user text. Set a retention period, limit who can read them, and mask personal data.

<Callout type="exam">
"Check that answers are supported by the retrieved passages" is **groundedness**. "Check that the agent used the right tools" is **tool call accuracy**. "Find weaknesses before launch with automated attacks" is the **AI red teaming agent**. "Show an auditor what happened" is **tracing** with **approval records**. Evaluators and red teaming are **pre-release evidence**, and traces are **post-release evidence**.
</Callout>

<DeepDive title="Why a model grades the model">

Most quality evaluators use a language model as the judge, with a rubric and a reason. It's cheaper than humans and consistent, and it has its own blind spots. Calibrate it by comparing its scores with a few hundred human-labelled examples, keep the judge model pinned, and use humans for high-stakes domains.

</DeepDive>
