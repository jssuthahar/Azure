keyTerms:
  - term: Workload identity federation
    definition: A way for a pipeline to get an Azure token by proving its identity with an OIDC token from GitHub or Azure DevOps, so no client secret is stored.
  - term: Federated credential
    definition: The trust setting on a managed identity or app registration that says which repository, branch or environment may sign in.
  - term: Evaluation gate
    definition: A pipeline step that runs evaluators on a test set and fails the build if scores fall below a threshold.
  - term: Bicep
    definition: Azure's declarative language for infrastructure. It describes Foundry resources, projects, deployments and role assignments as code.
  - term: Environment promotion
    definition: Moving the same tested definition from dev to test to prod, with approvals between stages, instead of rebuilding it each time.
  - term: Infrastructure as code
    definition: Describing cloud resources in files kept in source control, so environments can be recreated and reviewed like software.

## Start with a question

<Story question="Who checks that a prompt tweak didn't make the agent worse?">

On Friday, someone shortened the support agent's instructions to make replies "snappier". It passed a quick look. By Monday, answers were quoting policy that didn't exist. Nobody was careless. There was just no step that measured quality before the change reached customers.

A pipeline is that step. It runs the same checks every time, and nobody has to remember.

</Story>

## Explain it like I'm 10

<Eli10>

Imagine a cake factory with a door guard.

Every new recipe goes through the door. First it's baked in a **practice kitchen** (dev), then tasted by testers (test), then sold in the shop (prod).

The guard doesn't use a key you could lose. He recognises the baker's badge for that day, so there's **no key to steal**.

And before the cake goes to the shop, a taste test gives it marks. If the marks are low, the guard says "not today".

</Eli10>

## The technical explanation

### What goes into Git

```text
repo/
  infra/main.bicep          Foundry resource, projects, deployments, role assignments
  infra/dev.bicepparam      per-environment values (capacity, names)
  agents/support-agent.yaml instructions, model, tools
  evals/support-cases.jsonl test set with expected answers
  .github/workflows/deploy.yml
```

Review changes by pull request. A prompt edit is a code change.

### Sign in without a secret

1. Create a **user-assigned managed identity** (or app registration).
2. Add a **federated credential**: issuer `https://token.actions.githubusercontent.com`, subject such as `repo:contoso/agents:environment:prod`.
3. Give that identity the roles it needs on each environment's scope, for example **Contributor** on the dev resource group and a narrower role in prod.
4. In the workflow, grant `id-token: write` and use `azure/login`.

```yaml
permissions: { id-token: write, contents: read }
jobs:
  release:
    runs-on: ubuntu-latest
    environment: prod
    steps:
      - uses: actions/checkout@v4
      - uses: azure/login@v2
        with: { client-id: ${{ vars.AZURE_CLIENT_ID }}, tenant-id: ${{ vars.AZURE_TENANT_ID }}, subscription-id: ${{ vars.AZURE_SUBSCRIPTION_ID }} }
      - run: az deployment group create -g rg-agents-dev -f infra/main.bicep -p infra/dev.bicepparam
      - run: python run_evals.py --dataset evals/support-cases.jsonl --min-groundedness 4.0
```

### The stages

1. **Pull request**: validate Bicep (`az deployment group what-if`), run unit tests and a small evaluation.
2. **Merge to main**: deploy to **dev**, run the full evaluation, publish an agent version.
3. **Gate**: evaluators score the run. Under the threshold, the pipeline stops and prod is untouched.
4. **Promote** to **test**, then **prod** through protected environments that need an approver.
5. **After release**: continuous evaluation and monitoring keep watching.

Use separate **projects or resources** per environment, each with its own RBAC and networking, and promote the **same definition** with different parameters.

<Callout type="exam">
"No secrets stored in the pipeline" means **workload identity federation** with a **federated credential**. "Stop a release that lowers quality" means an **evaluation gate**. "Recreate the same environment reliably" means **Bicep**. "Promote tested changes" means the **same definition** moves through dev, test and prod, with approvals before prod.
</Callout>

<DeepDive title="Why the subject claim in the federated credential matters">

The subject says which workflow runs may sign in: a repo, a branch, a tag or an environment. A loose subject, such as any branch in the repo, lets a pull request from a fork-like context ask for production access. Tie prod's credential to the protected `prod` environment, so the approval rule applies before Azure issues a token.

</DeepDive>
