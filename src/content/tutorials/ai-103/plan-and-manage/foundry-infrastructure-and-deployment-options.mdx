keyTerms:
  - term: Foundry resource
    definition: The Azure resource (Microsoft.CognitiveServices/accounts, kind AIServices) that holds model deployments, keys, networking and identity for your Foundry projects.
  - term: Foundry project
    definition: A workspace inside a Foundry resource for one team or app. It has its own agents, files, connections, evaluations and access control.
  - term: Standard agent setup
    definition: An agent setup where threads, files and vector data live in your own Cosmos DB, Storage account and Azure AI Search, instead of Microsoft-managed storage.
  - term: Data Zone deployment
    definition: A deployment type that processes data only inside a data zone, such as the EU or the US, while still pooling capacity across regions in that zone.
  - term: Provisioned throughput (PTU)
    definition: Reserved model capacity that gives predictable latency and cost for steady, high-volume workloads. Billed for the capacity, whether you use it or not.
  - term: Global Batch
    definition: A deployment type for large offline jobs. You upload a file of requests and get results within 24 hours at a lower price.

## The technical explanation

### The resources behind a Foundry app

```text
Resource group
  Foundry resource (AIServices)  <- deployments, keys, identity, networking
    Project: support-bot          <- agents, files, evaluations, connections
  Application Insights            <- traces and metrics
  Azure AI Search                 <- knowledge bases and indexes (optional)
  Storage account, Cosmos DB      <- agent data (standard setup)
  Virtual network + private endpoints (when private)
```

Plan one Foundry resource per environment or security boundary, and projects per team or app. Region matters: pick it for **model availability**, **quota**, and **where data must stay**. Not every model exists in every region.

**Portal:** Azure portal → **Create a resource** → **Microsoft Foundry** → **Basics** (subscription, resource group, name, region, default project name) → **Storage**, **Networking**, **Identity** → **Review + create**.

```bash
az cognitiveservices account create -n contoso-ai -g rg-agents -l westeurope --kind AIServices --sku S0 --custom-domain contoso-ai
```

### Basic or standard agent setup

| Setup | Agent data lives in | Choose it when |
| --- | --- | --- |
| **Basic** | Microsoft-managed storage | Prototypes, low-risk data, you want to start fast |
| **Standard** | **Your** Cosmos DB (threads), Storage (files) and Azure AI Search (vectors) | You need data ownership, customer-managed keys, private networking or audit |

### Deployment types

| Type | Billing | Data processing | Use it for |
| --- | --- | --- | --- |
| **Global Standard** | Pay per token | Any Azure region | Most workloads that have no residency limit; newest models first |
| **Data Zone Standard** | Pay per token | Inside the EU or US zone | Residency without a single-region limit |
| **Standard** | Pay per token | One Azure geography | Strict single-region rules |
| **Provisioned** (Global, Data Zone, regional) | Reserved PTUs | As the type says | Steady high volume that needs predictable latency |
| **Global Batch** | Pay per token, lower price | Any region | Offline jobs where 24 hours is fine |

Deployment types differ in **quota**, and a model may support only some of them. Check the model card.

Match the sentence to the control. "Must not leave the EU" is **Data Zone** or **Standard**. "Highest throughput, no residency rule" is **Global**. <DeepDive title="Why a Global deployment isn't a data leak">

A Global deployment may process prompts and responses in any region where the model runs. The data at rest still stays in the geography you chose for the resource. Whether that's acceptable depends on your contract and regulation, not on a rule of thumb. If anyone needs a yes or no on "where is my data processed", the deployment type is the answer, and Microsoft's data residency page is the source.

</DeepDive>
