## The technical explanation

### What a guardrail contains

A guardrail is a list of **controls**. Each control answers three questions:

| Question | Options |
| --- | --- |
| **Which risk?** | Hate, sexual, violence, self-harm (with severity thresholds); user prompt attacks; indirect attacks; protected material (text, code); PII; groundedness checks |
| **Where?** | **User input**, **tool call**, **tool response**, **output** (tool points apply to agents, and some are in preview as of 25 Nov 2026) |
| **What action?** | **Annotate**, or **annotate and block** |

Foundry applies a default guardrail to every deployment. Create your own for a stricter policy, and attach it to a **model deployment** or an **agent**. The deployment's guardrail applies to every call. An agent can add its own.

**Portal:** Foundry portal → **Guardrails** → **Create guardrail** → pick the controls → **Assign to** deployments and agents.

### Prompt attacks

- **Jailbreak** (user prompt attack): the user tries to override rules ("ignore previous instructions", role-play tricks).
- **Indirect attack**: hidden instructions inside a document, email, web page or tool result.

Both are covered by **Prompt Shields**. Use **spotlighting**-style prompt hygiene as well: tell the model that retrieved text is data, not instructions.

### Choose thresholds and actions

1. Start with the default severity (medium) for harm categories, and **block** for prompt attacks.
2. Run in **annotate** mode on a new control, review a sample of flagged items, then switch to block.
3. Keep PII out of answers with a PII control at **output**. Mask earlier with Azure Language PII detection if the data shouldn't reach the model.
4. Re-test after every model change, because behaviour near the threshold shifts.
5. Remember what filters can't do: they reduce risk and don't replace **tool approval** or **least privilege**.

<Callout type="exam">
Read where the danger enters. "Hidden instructions in a document or web page" is an **indirect attack**, caught at the **tool response** or document stage by **Prompt Shields**. "The user tries to bypass rules" is a **jailbreak**, caught at **user input**. "Check the final answer for harmful content or PII" is **output**. "Observe before blocking" is **annotate**.
</Callout>

<DeepDive title="False positives are a design cost, not a bug">

Every threshold trades missed harm for blocked users. A medical education app needs to discuss self-harm clinically, so a strict default would block valid use. That's why guardrails are configurable per deployment. Document why a threshold was changed and who approved it, and let evaluations show the effect.

</DeepDive>
