keyTerms:
  - term: Managed identity
    definition: An identity that Azure creates and manages for a resource, such as a web app or Foundry resource, so it can get Entra tokens without any stored secret.
  - term: Keyless authentication
    definition: Calling a service with a Microsoft Entra ID token instead of an API key. Access is controlled by roles and can be audited per identity.
  - term: Foundry User role
    definition: A built-in role that lets an identity use a Foundry project's agents, models and tools through the data plane without managing the resource. Earlier docs called it Azure AI User.
  - term: Local authentication
    definition: Access with the resource's API keys. The disableLocalAuth setting turns it off so only Entra ID tokens work.
  - term: Private endpoint
    definition: A network interface with a private IP address in your virtual network that connects to one Azure resource over Azure Private Link.
  - term: Private DNS zone
    definition: A DNS zone that makes the resource's normal name resolve to the private endpoint's IP inside your network.

## Start with a question

<Story question="What happens if the API key is pasted into a public repository?">

A developer at Fabrikam commits `.env` by accident. Within minutes, bots find the key and start sending requests to the company's model deployment. The bill climbs, and every call looks like the real app.

Rotating the key fixes today's leak. It doesn't fix the design. As long as a key can call the service, a key can leak. The design fix is to **remove the key**, and to **close the door** the key was using.

</Story>

## Explain it like I'm 10

<Eli10>

A key is like a house key: anyone who finds it can walk in.

A **managed identity** is like a guard who recognises your face. Nothing to lose or copy.

The **role** is the list that says what that person may do: "may use the model, may not delete it".

A **private endpoint** moves the front door inside a fenced garden. Only people in the garden can reach it, and the street door is bricked up.

</Eli10>

## The technical explanation

### Identity: roles, not keys

1. **Give the app an identity.** Turn on **system-assigned** (or create a **user-assigned**) managed identity for the web app, function, container app or VM.
2. **Assign a role** on the Foundry resource or project, at the narrowest scope.
3. **Call with Entra ID** in code.

| Role (scope) | Use it for |
| --- | --- |
| **Foundry User** (Azure AI User in older docs) | An app or developer that calls models and agents. Data-plane only. |
| **Foundry Project Manager** / **Azure AI Project Manager** | Creating projects and managing them, with the right to assign User. |
| **Foundry Account Owner / Owner** | Managing the resource. Not for apps. |
| **Cognitive Services OpenAI User** | Calling OpenAI models only |

```bash
az role assignment create --assignee <managed-identity-principal-id> --role "Foundry User" --scope <foundry-resource-id>
```

```python
from azure.identity import DefaultAzureCredential, get_bearer_token_provider
from openai import OpenAI

token = get_bearer_token_provider(DefaultAzureCredential(), "https://cognitiveservices.azure.com/.default")
client = OpenAI(base_url="https://contoso-ai.services.ai.azure.com/openai/v1/", api_key=token)
```

### Turn keys off

After every caller uses Entra ID, disable local authentication. **Portal:** Foundry resource → **Resource Management → Keys and Endpoint** (or the resource's properties) → disable key access. **CLI:**

```bash
az resource update --ids <foundry-resource-id> --set properties.disableLocalAuth=true
```

A request signed with a key now fails with 403. You can enforce this for every new resource with the built-in Azure Policy for disabling local authentication.

### Close the public door, open a private one

1. **Resource Management → Networking** → **Public network access: Disabled** (or **Selected networks** with a few allowed IPs).
2. Create a **private endpoint** with target sub-resource `account` in a subnet of your VNet.
3. Link the **private DNS zones** (`privatelink.cognitiveservices.azure.com`, `privatelink.openai.azure.com`, `privatelink.services.ai.azure.com`) to the VNet, so the normal name resolves to the private IP.
4. For the standard agent setup, give the dependent resources (Cosmos DB, Storage, AI Search) private endpoints too, and use a delegated subnet for the agent's own traffic.

```bash
az network private-endpoint create -g rg-agents -n pe-foundry --vnet-name vnet-agents --subnet snet-pe \
  --private-connection-resource-id <foundry-resource-id> --group-id account --connection-name pe-foundry-conn
```

Keep the setup from drifting with **Azure Policy** (deny public access, require private endpoints) and **role policies** such as deny assignments and PIM for admin roles.

<Callout type="exam">
"No credentials stored in the app" means **managed identity** with **Entra ID**. "Stop anyone using keys" means **disableLocalAuth**. "Reachable only from the VNet" means **public access disabled** and a **private endpoint**, with **private DNS**. "Least privilege to call models" means **Foundry User**, not Owner or Contributor. If the app resolves a public IP after you added the endpoint, check the **DNS zone link**.
</Callout>

<DeepDive title="Why Contributor doesn't let you call a model">

Azure roles split the control plane (create, delete, configure resources) from the data plane (call models, run agents). Contributor is a control-plane role, so it can change the resource but the data actions need a data role. That's why a developer with Owner can still get 401 from the model until Foundry User is assigned. It also means an app identity should never need Contributor to do its job.

</DeepDive>
